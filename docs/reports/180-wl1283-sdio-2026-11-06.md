# 180 — The WL1283 is on MMC5, its enable and interrupt are GPIO2_22/GPIO2_21, and Linux still gets no SDIO card

**Session 29 (absolute), Linux-era 23.  2026-11-06.**
Status: **bench.**  Region 0 was flashed with four build variants; the media was
restored to the 1917 IFS at the end (`BOOTCTR_FCTRY = 0x32`, TabletOS running,
`/base` mounted).  No RPMB, NVRAM or MCT write.  The unit was power-cycled once
by the operator (session test, not a repair).

The aim was ROADMAP item 9 step 4: **enumerate the TI WL1283 combo on its SDIO
bus** and then load `wl12xx`.  The enumeration does not happen yet, but the bus
and the two board lines are now measured rather than assumed, and six candidate
causes are eliminated with evidence.  Everything here is reusable: the method
(live `pidin mem` + whole-map pad/GPIO diff) and the wiring facts.

---

## 0. Headline

* **The WL1283 is on OMAP MMC5 (`0x480D5000`), not MMC1.**  Reports 176 and the
  session-28 DTS assumed MMC1.  QNX's process map is unambiguous: io-pkt holds
  `/dev/mem 0x480d5000` (8 KiB, the hsmmc register file) and attaches **QNX
  vector `0x5b` = GIC SPI 59**, which is `mmc5` in `omap4-l4.dtsi`.  The sdmmc5
  pads (`0x148`–`0x152`) read `0x0118` (mux 0, pull-up, input enable) on the
  running TabletOS while **every sdmmc1 and sdmmc3 pad reads `0x000f` (safe
  mode)**.  Trap 97.
* **WLAN_EN = gpio_54 = GPIO2_22 (pad `gpmc_nwp`, `0x07c`)**, active high; the
  QNX driver drives it high and waits 120 ms.  Confirmed twice, independently:
  static RE of `devnp-ti1283.so`, and a live GPIO diff — the reference's
  `GPIO2_DATAOUT` is `0x31413200` today against `0x31013200` in report 118
  (session 5), i.e. **bit 22 is the only GPIO output that changes when the
  WLAN driver is up**.
* **WLAN_IRQ = gpio_53 = GPIO2_21 (pad `gpmc_ncs3`, `0x07a`)**, an **input**,
  falling-edge, active low.  The old DTS drove this line low as an output — a
  real defect, now fixed (trap 97).
* **`&mmc5` now probes correctly and drives a 400 kHz init clock, and the card
  still does not answer CMD5.**  Six causes are eliminated (§4).  The two
  remaining, measurable differences from the reference are the MMC5 functional
  clock (Linux 48 MHz, QNX 96 MHz) and `MMCHS_CON` (Linux `0x00000600`, QNX
  writes `0x000E0080`); both are the next experiment (§6).
* **The chip itself is fine.**  After the restore, TabletOS's own
  `wpa_supplicant_ti` logged `CTRL-EVENT-SCAN-RESULTS` and `WPS-AP-AVAILABLE`
  in this boot — the radio scans.  So this is a host-side gap, not a dead part.

## 1. How the bus was found (the method worth keeping)

`pidin mem` prints every `/dev/mem` mapping of every process.  It is read-only,
needs no driver support, and it names the exact physical block a QNX driver
owns.  For a device driver loaded into io-pkt (`mount -T io-pkt`), it is the
fastest correct answer to "which controller is this on":

```
2261040   1 sbin/io-pkt-v6-hc
            devnp-ti1283.so    @ 78a00000            1052K   24K
            /dev/mem           @ 28007000 (480d5000)       8192   <- MMCHS5
            /dev/mem           @ 28001000 (4805b000)       4096   <- GPIO5
            /dev/mem           @ 28003000 (48059000)       4096   <- GPIO4
            /dev/mem           @ 28005000 (4a009000)       4096   <- CM2 (L4PER)
            /dev/mem           @ 280d5000 (4a056000)       4096   <- sDMA
            /dev/mem           @ 280f5000 (4a307000)       4096   <- PRM_CORE
            /dev/mem           @ 2810e000 (4805d000)       4096   <- GPIO6
            /dev/mem           @ 2812e000 (48057000)       4096   <- GPIO3
            /dev/mem           @ 28172000 (48055000)       4096   <- GPIO2
            /dev/mem           @ 2818e000 (4a310000)       4096   <- GPIO1
```

Cross-check, same boot: `pidin irq` for that pid attaches vector `0x5b`
(91 = SPI 59) as a pulse, and `0x41d` (1053 = `1000 + gpio 53`).  GIC SPI 59 is
`mmc5` in `omap4-l4.dtsi`; `1000 + gpio` is the QNX OMAP GPIO interrupt
convention, which independently names gpio 53 as the WLAN interrupt.

The pad half of the same method: dump all 120 `0x4a100000` padconf words on
TabletOS and on our Linux boot and diff them.  For the WLAN the result is that
`0x148`/`0x14c`/`0x150` (`sdmmc5_clk/cmd/dat0..3`) are identical `0x0118` on
both, while `sdmmc1` (`0x0e0`–`0x0ec`) and `sdmmc3` (`0x100`–`0x11c`) are
`0x000f` safe mode in the reference and unused in ours.

## 2. The wiring, from `devnp-ti1283.so` (static RE)

Full notes: the subagent report in the session note; the load-bearing facts:

| fact | value | how |
|---|---|---|
| SDIO controller | MMCHS5 `0x480D5000`, 8 KiB | `mmap_device_io(0x2000, 0x480D5000)` in `sdiodrv_sdio_init` |
| bus width | 4-bit | `MMCHS_HCTL |= 2`; only `sdmmc5_dat0..3` pads muxed |
| card clock | **24 MHz** (log string `"SDIO clock Configuration is now set to %dMhz"`), `SYSCTL.CLKD = 2` | functional clock 96 MHz ⇒ 96/(2·2) |
| enable | **gpio 54** (`WLAN_EN_GPIO` default in `hPlatform_Wlan_Hardware_Init`), EN=1 then `delay(120)`; reset strobe = EN 0 for 500 ms then 1 | `hPlatform_DevicePowerOn`, `hPlatform_hardResetTnetw` |
| interrupt | **gpio 53**, input, `FALLINGDETECT`, active low (firmware writes `0x003009B4`/`0x003009C0` and logs "Hwinit IRQ polarity active low") | `wlanDrvIf_LoadFiles`, `hwInit_WriteIRQPolarity` |
| pad writes | 5 `OMAP_pad_config` words: `0x078` (gpio_53 → mux 3, pull-down), `0x07c` (gpio_54 → mux 3), `0x148`, `0x14c`, `0x150` (sdmmc5, mux 0 + pull-up) | `hPlatform_Wlan_Hardware_Init`; skipped when a `WLAN` hwinfo node exists |
| registers it touches | no PMIC/regulator, no 32 kHz, no clock output — only MMCHS5, CM2, PRM_CORE (read), sDMA and the five pads | whole-binary audit |
| enumeration | custom: `CMD0, CMD5, CMD3, CMD7` (`"sdioAdapt_ConnectBus: Send commands sequence: 0, 5, 3, 7"`), then function enable | `sdioAdapt_ConnectBus` |
| options | `firmdir=<path>`, `nvram`; hwinfo suboptions `WLAN_EN_GPIO=`, `WLAN_INT_GPIO=` | `getsubopt` sites |

The two names are **defaults used only when the BSP supplies no `WLAN` hwinfo
node**; there is no `hwinfo` tool on this image to dump that tree, so the
defaults are what we rely on — and the live GPIO diff (§0) corroborates gpio 54.

Because the driver itself does no rail and no clock work, the WL1283's supplies
and its 32 kHz must be on by default (see §4).

## 3. What was built (region 0)

Four variants, one variable each, all booted:

| # | CRC | change | result |
|---|---|---|---|
| 1 | `0x74FA74A3` | `&mmc5` enabled, `sdmmc5` pinctrl (`0x0118` ×6), `vwl1283` fixed 1.8 V, `ti,non-removable`, 4-bit — **no WL_EN** | controller probes (`PBX: mmc4 probe-pm fck=48000000 … idlest=0`), `attach_sdio no`, `Failed to initialize a non-removable card` |
| 2 | `0xA7D3BC13` | + **WL_EN hog** (`gpio2` line 22 output-high, pad `0x07c` mux 3) + the `gpio2` line-21 output hog removed (it is the IRQ input) | same failure; `GPIO2_DATAOUT = 0x31413200`, OE bit22=1, pad `0x07c = 0x0003` — **identical to the reference** |
| 3 | `0x0005424F` | + `PBD:` register dump in `omap_hsmmc_set_ios` | same failure, `CON=00000600 HCTL=00000b00 SYSCTL=000e1e07 CAPA=04e10080 STAT=00000000 PSTATE=01f40000 SYSSTATUS=00000001` |
| 4 | `0x4949969A` | `vwl1283` 1.8 V → **3.3 V** (OCR window) | same failure → the window is not the cause; reverted |

Variant 3 is the one to build from (`local/images/kernel-0x0005424F-wl1283.img`);
the DTS in the tree is variant 2 plus the dump (3.3 V reverted, so rebuilding
gives `0x0005424F` again).  Region 1 is unchanged (`0a55a170…`).

`HCTL = 0x00000b00` is **exactly** what QNX writes (`|= 0x100` SDBP, `|= 0xa00`,
`|= 2` DTW), so the bus power and width are right by construction.

## 4. What is eliminated, with the evidence

1. **Enable line.**  `GPIO2_DATAOUT` bit 22 is high at boot (variant 2) and
   matches the reference bit for bit.  A runtime EN pulse (0/500 ms/1, and a
   5 s low with the host unbound) plus `unbind`/`bind` of `480d5000.mmc` still
   gives `attach_sdio no`.
2. **Pad muxes.**  Live padconf diff against TabletOS: all six WLAN pads
   identical; `0x07c = 0x0003`, `0x07a = 0x410b`, `0x148..0x152 = 0x0118`.
3. **IRQ pin.**  gpio_53 is no longer an output (OE bit 21 = 0 in both OSes).
4. **PMIC rails and the 32 kHz.**  Register-for-register comparison of the TWL6030
   `0x80`–`0xB0` block on both OSes: every rail's **CFG_STATE is identical**
   (`…=0x05` = ON/APP); only group/transition words differ (`CFG_GRP` `0x07` vs
   `0x01`, `CFG_TRANS` `0x55` vs `0x05`), which cannot switch power.  `VMMC`,
   `VPP`, `VUSIM` are off in both (RIM's own policy).  `CLK32KG` is ON in both.
5. **OCR / I/O voltage window.**  1.8 V and 3.3 V both fail; `CAPA = 0x04e10080`
   (VS18/30/33 capable).
6. **Chip state / warm-reset wedging.**  A full power cycle (operator, power
   button) does not change the result, and **QNX's own driver still scans**
   (`CTRL-EVENT-SCAN-RESULTS`, `WPS-AP-AVAILABLE`) after the restore — the chip
   and its SDIO slave are alive.

A seventh exercise, cheap and negative: a runtime rescan of MMC5 (driver
`unbind`/`bind`) after every GPIO change, which avoids a flash and was used for
(1).

## 5. Notes that cost time

* **`devmem` reads of GPIO3–6 (`0x48057000`…`0x4805d000`) are firewalled from
  Linux user mode** and each one logs `L3 Custom Error: MASTER MPU TARGET
  LPER2 (Read): Data Access in User mode` plus an unhandled external abort and a
  backtrace (taints the kernel `W`).  GPIO1 and GPIO2 are readable; MMC5
  (`0x480d5000`) is not readable from user mode on either OS (QNX: SIGBUS).
  Read-only, harmless, but it looks alarming on the console.
* `pkexec chmod 666 /dev/ttyACM0` needs the operator to answer the prompt; the
  node is recreated by every boot (trap 24).
* The i210/`i2cget` path works on the running Linux image — `i2cget -f -y 0 0x48
  <reg>` reads the TWL through a driver-owned client (`-f` is needed; the TWL
  driver holds it).  Reading PMIC registers is safe; nothing here writes.
* BusyBox has `i2cget`/`i2cset`/`i2cdetect`/`i2cdump` enabled, so the shell can
  read I²C without the bring-up console taking over the tty.

## 6. Corrections and what is left

**CORRECTION (same session, from the disassembly).**  The `0x000E0080` in §5 is
**not** written to `MMCHS_CON` — it goes to **`MMCHS_SYSCTL`** (`CLKD = 2`,
`DTO = 14`), and `CON` is only `CON &= ~OD`, exactly as mainline does
(`omap_hsmmc_set_bus_mode`).  QNX's `sdio_core_pm` in full, from `0xcd04c`:
`SYSCONFIG = (v & ~0x331D) | 0x320D`; `HCTL |= 0xA00`; `[0x240] |= 0x04000000`;
`HCTL |= 0x100` (SDBP) and poll; `ISE = 0`; `IE = 0x317F0137`; `STAT = ~0`;
`CON &= ~0x20`; `HCTL |= 2` (DTW); `SYSCTL = (v & ~4)`, then `0x000E0080`.
Our CON/HCTL come out identical; only the clock divider differs.  Likewise the
"96 MHz" was arithmetic: mainline's OMAP4 table gives MMC5 the **48 MHz**
`func_48m_fclk` parent, so QNX's `CLKD = 2` is a 12–24 MHz card clock, not 96.

**Eliminated after that correction** (all measured, session 29):

| tried | result |
|---|---|
| init clock **12 MHz** instead of 400 kHz (new `omap_hsmmc.init_hz` knob, gated to `480d5000`) | `attach_sdio no`, now after ~100 ms instead of 5 ms — the commands really run, still no response |
| WL_EN driven by a `regulator-fixed` **at MMC power-up** (+120 ms, after the pads are muxed) | no card |
| **`ti,no-reset-on-init`** on `gpio2_target` (new label in `omap4-l4.dtsi`) so WL_EN is never dropped | no card |
| EN high **5 s** before the probe (runtime) | chip's IRQ line stays low, no card |

**New facts about the enable line.**  The **loader leaves WL_EN low**; the QNX
driver owns it.  Turning Wi-Fi off in Settings drives gpio 54 low *and* the
chip's IRQ line (GPIO2_21) goes low; turning it back on restores both.  So EN is
the power control, and on the reference the chip drives its IRQ high as soon as
it is up.  **In every Linux build so far, EN high does not make the chip drive
its IRQ** — the chip appears not to come up, and nothing in the SoC-side state
(pads, controller registers, PMIC — all byte-comparable to the reference)
explains it.  Note the IRQ line has no pull, so "low" means "not driven", not
"asserted".

| **UART2 / HCI probe** (`/bin/pbhci`, new; UART2 `0x4806C000` enabled, pads
per the reference, 115200 8N1, one `HCI_Reset`) | **no bytes back** — the combo's
BT core does not answer either.  Two readings: the chip is not powered, or its
BT core needs a second enable (`BT_EN`) that nothing on our boot drives.  It
does not settle the WLAN question on its own. |
| kernel-side GPIO3–6 read (`PBGPIO:` dump, new) | inconclusive: the bank-2
values do not match a `devmem` read taken later in the same boot, so the print
fires at a moment when the registers are not stable. **Do not trust it**; the
L4PER GPIO banks are unreadable from Linux user mode and this needs a proper
kernel-side read at a fixed point. |

**The last readable difference: GPIO4.**  With the banks read from kernel
context (`PBGPIO:`, after fixing a probe that walked one bank too far and
reset-looped the unit — trap 99), our boot had **GPIO4 at its reset state**
(`OE = 0xffffffff`, `DATAOUT = 0`) while the reference drives
`GPIO4_DATAOUT = 0x90000120` with `OE = 0x6ffffe1c` — bits **5, 8, 28 and 31
high**, exactly the four report 118 §10.1 left as "untested candidates".
Mirroring them in the DTS gets us to `OE = 0x6ffffedf`, `OUT = 0x90000120`;
**the card is still silent and the chip still does not drive its IRQ**.  That
was the last GPIO/PMIC/pad/controller difference the bench can read.

**Full padconf diff (CORE 0x4A100000–0x5FC, WKUP 0x4A31E040–0x9C), reference
vs ours.**  87 of 384 CORE words differ, but they are almost all unclaimed pads
that our pinctrl resets to safe mode and the reference simply leaves at the
loader's value — not functional differences.  The one that *is* functional:

| pad | reference | ours | meaning |
|---|---|---|---|
| `0x4A10019C` pad0 | `0x41000000` → **mux 0 = `fref_clk2_out`** | `0x4118010F` → mux 7 = safe_mode | FREF_CLK2 is a **clock output** on the reference and dark on ours |

`VDDS_DV_BANK4` (`CONTROL_CORE_PADCONF_MODE[28]`, `0x4A1005A8`) is `1.8 V` in
both, so the sdmmc5 pads' I/O level matches.  Muxing `0x4A10019C` pad0 to
`fref_clk2_out` live and rescanning MMC5 still gives `attach_sdio no` — but that
write does not enable the clock's parent in CM, so it is not a complete test
(see below).

**Clock/power-manager diff (full blocks, reference-with-WiFi-up vs ours).**
`CM_PER` `0x4A008000`–`0x81FC`, all of `CM2` `0x4A009000`–`0x4A0095FC` and `PRM`
`0x4A307000`–`0x4A3072FC` were captured on both and diffed.  Result: **Nine
CM_PER words differ and 41 CM2 words, but the difference is the wrong way
round — our boot has *more* enabled, not less.**  The reference sits in
`HW_AUTO` (`CLKSTCTRL` `0x00030000`); we hold dozens of domains in `SW_WKUP`
(`0x00000002`).  So there is no missing clock: `CM_DIV_M5_DPLL_PER` is
`0x00000329` on the reference and `0x00000204` here, but bit 9 (`ST_HSDIVIDER_
CLKOUT2`, read-only status) is **1 in both**, i.e. the output is running either
way, and writing the gate bit back had no effect (it reads back unchanged).
That retires the reference-clock hypothesis properly.

**CORRECTION — why MMCHS5 cannot be read on QNX.**  Report 180 §1/§8 attributed
the QNX `SIGBUS` to an L4 firewall.  `tools/qnx-iotest.c` (new) shows
`ThreadCtl(_NTO_TCTL_IO) = -1 errno 22 (EINVAL)` for an sshd session — but the
*same session* reads `0x4A100000`, `0x4A31E000`, `0x48055000` and `0x4A009000`
happily, so I/O privilege is not the gate.  `procmgr_ability(ALLOW|AID_IO)`
returns 0 and `ThreadCtl` still fails the same way.  The block-specific fault is
therefore real and is not something the session can grant: **the only process
that can read MMCHS5 on QNX is io-pkt itself**, so the reference's live SDIO
controller state is not obtainable from the bench.  Stop trying; the target
state cannot be read, only inferred from the driver's own writes (which are in
§5).

**What is left needs evidence this bench cannot produce by register-diffing:**
the WL1283's power-up requirements (VBAT/VIO sequencing, the 32 kHz and the
reference-clock source, and whether a second enable pin gates the digital core)
— i.e. the chip datasheet or the board schematic, or a logic-analyser capture of
CLK/CMD/DAT5 and the enable at boot.  A cheap next probe that does not need
either: enable UART2 (`0x4806C000`, the combo's BT transport) and send an HCI
Reset — if the BT core answers, the chip is powered and its digital core runs,
which splits "not powered" from "SDIO path broken".
