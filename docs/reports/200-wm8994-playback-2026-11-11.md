# 200 — WM8994 playback: machine driver up, stream configures, FLL blocked chip-side

Date: 2026-11-11 (session 39, Linux-era 33), item 9 step 5's audio half.
Bench: unit on our Linux image `0xF97CD9C7` (region 0) + the audio/OSS rootfs
`968d2f20…` (region 1).  All device access was the console; no RPMB, NVRAM or
MCT write.

## 0. Headline

* **The card and the DAI stream work.**  A new board machine driver
  (`sound/soc/ti/playbook-wm8994.c`) registers
  `0 [WM8994]: PlayBook_WM8994`, and an OSS write (`/dev/dsp`) reaches the PCM:
  `SETFMT`/`CHANNELS`/`SPEED` succeed, 48 kHz S16_LE 2ch, and the write
  completes.
* **The DAPM path is complete in the driver's view.**  With the output mixers
  set, the regmap reports `PM4=0x0300`, `PM5=0x0303`, `AIF1CLK_ENA=1` is read
  **directly from the chip** (`i2ctransfer` of `0x200`), and the DAPM files
  show `DAC1L`, `SPKL`, `HPOUT1L`, `SPKOUTLP` all `On`.  The mixer write
  `0x0601 = 1` was also confirmed on the chip directly; note that the regmap
  cache can diverge from the chip for registers it believes unchanged (§4).
* **The codec clock is the blocker.**  The 1917 design clocks the WM8994 FLL1
  from MCLK1 at 12.8 MHz, but that pin does not clock on this unit: the FLL
  never reports lock.  Relocking FLL1 to the incoming **BCLK** locks at once
  (`0x732 bit5 = 1`), so the FLL and BCLK are good and the MCLK1 path is dead.
* **The driver's FLL configuration does not reach the chip.**  After boot the
  codec stops accepting register writes (reads still answer; writes return
  success and do not change the register).  The MFD's regmap cache holds the
  FLL config (`0x220=0x0001`, `0x224=0x0c83`) while the chip reads the reset
  values (`0x0000`, `0x0c80`), and no later `regmap_update_bits` writes it
  because the cache already matches.  This is the open issue.

## 1. What was built (and is on media)

* **`sound/soc/ti/playbook-wm8994.c`** — the board machine driver.  Static
  DAI link `40124000.mcbsp` ↔ `wm8994-aif1`, I2S, CPU bit/frame provider
  (`CBC_CFC`); `hw_params` tells the McBSP its 12.288 MHz fclk and `CLKGDV`
  (BCLK = 32 fs), then points the codec at MCLK1 (12.8 MHz), configures
  `FLL1` from **BCLK**, and switches `AIF1CLK` to `FLL1` at 256 fs.  Board
  DAPM widgets/routes: `Headphone` ← `HPOUT1L/R`, `Speaker` ←
  `SPKOUT[LP/LN/RP/RN]`.
* **Kconfig/Makefile** — `SND_SOC_PLAYBOOK_WM8994` now builds the machine
  driver (it previously only selected simple-card).
* **Board DTS** — the `simple-audio-card` node is replaced by a
  `blackberry,playbook-wm8994` `sound` node with `pinctrl-0 =
  <&codec_mclk_pins>`; `codec_mclk_pins` muxes CORE pad `0x19c` to
  `fref_clk2_out`; the codec node gains `clocks = <&auxclk1_ck>` /
  `clock-names = "MCLK1"`.
* **Region 1 rootfs** — `snd-mixer-oss`/`snd-pcm-oss` modules, a `pbplay`
  OSS test player, and a new `pbmix` ALSA-control tool (list/on/off/set/enum).
  `rcS` loads the OSS modules and sets the playback path:
  `DAC1L/R Mixer AIF1.1`, `DAC1 Switch`, the two output-mixer DAC switches,
  `SPKL/SPKR DAC1 Switch`, `SPKL/SPKR Output Switch`.
* **MFD quirk** — `drivers/mfd/wm8994-core.c` forbids runtime suspend on this
  board (`pm_runtime_forbid`): the suspend path issues `SOFTWARE_RESET` and
  the part then behaves as below.

## 2. How the evidence was read

```
# console, during a stream
pbplay 10 440 &
i2ctransfer -f -y 3 w2@0x1a 0x02 0x00 r2   # AIF1_CLOCKING_1
i2ctransfer -f -y 3 w2@0x1a 0x02 0x20 r2   # FLL1_CONTROL_1
i2ctransfer -f -y 3 w2@0x1a 0x02 0x24 r2   # FLL1_CONTROL_5
i2ctransfer -f -y 3 w2@0x1a 0x07 0x32 r2   # Interrupt Raw Status 2
grep '^0224:' /sys/kernel/debug/regmap/3-001a/registers   # driver cache
```

* **Playback, first attempt (simple-card):** `SETFMT` → `-EINVAL`,
  `wm8994-codec: AIF1CLK not configured`,
  `ASoC error (-22) at snd_soc_dai_hw_params() on wm8994-aif1`.  The generic
  card never calls `set_sysclk`, and `mclk-fs` passes `clk_id 0`, which the
  WM8994 driver rejects (`WM8994_SYSCLK_MCLK1 = 1`).
* **MCLK1 FLL:** with the 1917 FLL1 sequence
  (`REFCLK_SRC=MCLK1`, `REFCLK_DIV=0`, `FRATIO=0`, `OUTDIV=7`, `N=7`,
  `K=0xAE14` → 12.288 MHz from 12.8 MHz), the FLL **never** reports lock
  (`0x732 = 0x6000`).  AUXCLK1 was verified enabled at 12.8 MHz
  (`0x4A30A314 = 0x00020100`, consumer `3-001a MCLK1`) and CORE pad `0x19c`
  reads `0x0000` (mux 0 = `fref_clk2_out`), so the SoC side is configured.
* **BCLK FLL:** writing `0x224 = 0x0c83` (REFCLK_SRC=BCLK) with `N=8`
  (`0x223 = 0x0100`) while a stream ran set `0x732 = 0x6020` — **locked**.
  That is the basis of the machine driver's clocking.
* **The divergence:** during a stream the driver's cache shows
  `0224: 0c83`, `0220: 0001`, but the chip reads `0x0c80`, `0x0000`.
  `cache_only=N`, `cache_dirty=N`, the codec and MFD are runtime-`active`
  (and `power/control=on`), and `0x0601` (a mixer switch the driver wrote at
  boot) does read back `1`.  Direct I²C writes to `0x0601`/`0x0220`/`0x0224`
  return success and do not change the register, so the chip is ignoring
  writes at this point (reads still work, including the ID `0x8994`).

## 3. Earlier results that still stand

* **AUXCLK1 = `fref_clk2_out` is 12.8 MHz and enabled** when the codec asks
  for MCLK1 (`clk_summary`: `auxclk1_ck 1 1 0 12800000 Y 3-001a MCLK1`).
* **The FLL/BCLK ratio is real:** BCLK = 1.536 MHz at 48 kHz (`CLKGDV = 8`),
  and the driver computes `AIF1CLK = 12.288 MHz`; the `-EBUSY` on a second
  `hw_params` ("FLL1 is currently providing SYSCLK") is avoided by moving
  `AIF1CLK` to MCLK1 before `set_pll`.
* **The codec answers and the card enumerates.**  No unknown-symbol or ASoC
  errors; the four `Mic detect IRQ: -22` lines are the unwired jack IRQs.

## 4. The open issue, stated exactly

The WM8994 register interface stops accepting writes after the codec has been
through its boot sequence.  Reads of the ID and of the register file work;
writes return success (`i2ctransfer` rc 0, `snd_soc_component_write`), the
driver's regmap cache is updated, but the chip retains the reset values.  The
values that were written **before** this point (the `rcS` mixer settings, the
DAPM `AIF1CLK_ENA`) are present, so the interface did work earlier in the boot.
Since the FLL is only ever configured later (at `hw_params`), its configuration
is lost, and the stream runs at the 8 kHz OSS default with `AIF1CLK` sourced
from the (dead) MCLK1 — hence no audible output.

Candidates, in order, for the next session:

1. **Read the same registers on the working QNX stack.**  On live TabletOS,
   stop `io-audio` first (never race the vendor driver — trap 103) and read
   `0x200`, `0x220`–`0x224`, `0x732` and `PM4/PM5` with `pbi2c`.  That answers
   whether the reference's FLL1 really locks from MCLK1 on this board (if it
   does, the pin is wired and our pad/source is wrong; if it does not, QNX is
   using another clock or the FLL is not its AIF source), and what a working
   register file looks like.
2. **Settle what the 1917 driver does with AUXCLK1.**  Decompile the
   `0x1ecf0` map/unmap region of `deva-ctrl-omap4abe-wm8994.so` (Ghidra) and
   read the `startup-playbook` call site that writes `AUXCLK1 = 0x00020100`
   (`0x7980`).  Only a map/unmap would mean the 12.8 MHz source is elsewhere.
3. **Find what puts the part into the write-ignoring state.**  `dmesg` has
   only the known benign lines.  Test a register write immediately at the
   first shell prompt (before any `pbplay`) and again after one playback; if
   the first works and the second does not, bisect the boot between `rcS`
   (module load + `pbmix`) and the first stream.  The DAPM power-down
   (`BIAS_OFF`) is the prime suspect.  Also read
   `WM8994_WRITE_SEQUENCER_CTRL_1/2` (`0x110`/`0x111`): the mainline driver
   does not start the sequencer, but a stuck sequence owns the register map
   and looks exactly like this.
4. **Configure the FLL after power-up.**  The earliest ASoC hook after the
   DAPM stream event is the machine's `.trigger(START)` (or a DAPM event).
   If writes work there, move the `set_pll`/`set_sysclk` there (keeping the
   `hw_params` call so the codec's `aifclk` is valid).
5. **If the chip still ignores writes, measure it.**  DCVDD/DBVDD at the
   part, the `/RESET` pin and the FLL supplies (`AVDD2`/`CPVDD`).
