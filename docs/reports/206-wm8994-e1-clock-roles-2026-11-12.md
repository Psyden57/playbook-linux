# 206 — WM8994 E1: the clock roles inverted; the McBSP transmit path works; MCLK1 is the one blocker (session 42)

Date: 2026-11-12 (session 42, Linux-era 36).
Bench: unit on our Linux image; **region 0 = `0x36597040`** (`0x93A2EC`,
kernel 7.3.3, the E1 DTS) and **region 1 = `b20302dc…`**
(`local/images/rootfs-region1-audio-oss.ext4`, 27 modules, the E1 machine
driver), flashed in one bootrom session.  Only the two regions changed; no
RPMB, NVRAM or MCT write.  `BOOTCTR_FCTRY` was **not** read this boot: the
chroot userland has no `/dev/rpmb` node; the initramfs `/init` top-up ran at
boot as designed.

## 0. Headline

**E1 is implemented, verified, and its mechanism is proven.**  The codec is now
the AIF1 master (`R0x302 = 0x4000`, byte-identical to the reference) and the
McBSP2 is a clock consumer (`PCR0 = 0x000f` — `CLKXM`/`FSXM` clear, the sample
rate generator never started).  With a live AIF1CLK the transmit FIFO drains:
`pbplay` streamed a full 20-second tone and exited cleanly, where every
previous run died with `Input/output error` after five periods (~1 s).

**The one remaining blocker is the MCLK1 clock at the pin.**  FLL1 never locks
from MCLK1 despite a register file byte-identical to the working reference —
and a direct test (AIF1CLK sourced from MCLK1 with the FLL bypassed) shows the
pin itself is not clocking.  The free-running NCO (±10–30 %) proves the
architecture but is not a hi-fi clock, so it is a mechanism probe, not a fix.

## 1. The E1 change (one logical variable: clock roles inverted)

* `sound/soc/ti/playbook-wm8994.c`: `.dai_fmt` is now
  `SND_SOC_DAIFMT_I2S | SND_SOC_DAIFMT_CBP_CFP | NB_NF`.  The link format is
  codec-perspective, and `snd_soc_runtime_set_dai_fmt()` flips it for the CPU
  DAI, so `omap_mcbsp_dai_set_dai_fmt()` takes the `BC_FC` (slave) branch:
  `CLKXM`/`FSXM` stay clear and `omap_mcbsp_start()` never raises
  `GRST`/`FRST` (it only enables the SRG for a master — read from the driver,
  not assumed).  `hw_params` drops the `set_sysclk(FCLK)`/`set_clkdiv` SRG
  maths and locks **FLL1 from MCLK1** (12.8 MHz) instead of BCLK — with the
  codec as master a BCLK-referenced FLL is circular (BCLK would be the codec's
  own output).
* Board DTS: `mcbsp2_pins` `clkx`/`fsx` become `PIN_INPUT` (`0x0100`), which
  are exactly the reference's live pad values from report 205 §5a.  `dr` stays
  input, `dx` stays an output — the McBSP still drives the data.  (The
  reference leaves `dx` in safe_mode while playing, which remains unexplained;
  we did **not** copy it, because our McBSP must drive `dx` into the codec.)

Both sides changed in one boot — the handoff's "clock roles inverted" single
variable.

## 2. Verified on the bench (fresh boot after the two-region flash)

```
PCR0:  0x000f    CLKXM=0 FSXM=0  (was 0x0f0f)  -- McBSP is now a consumer
SPCR2: 0x0235    GRST=0 FRST=0   (was 0x02f5)  -- the SRG is out of the path
R0x302 0x4000    AIF1_MSTR set   -- codec is AIF1 master, = the reference
```

and the FLL1 register file is byte-identical to the reference's live capture:

```
R0x220 0x0005   R0x221 0x0700   R0x222 0xAE14   R0x223 0x00E0   R0x224 0x0C80
```

`0x224` decodes (datasheet Rev 4.6 Table 112/114) as `REFCLK_SRC = 0` (MCLK1),
`REFCLK_DIV = 0` (÷1), `FRC_NCO = 0` with the reset-default `FRC_NCO_VAL`
leftover — same fields, same values, as the working reference.

## 3. FLL1 does not lock from MCLK1 — and the pin does not clock

* `R0x732 = 0x6000`: FLL enabled, `FLL1_LOCK_STS` clear.  Reproduced with the
  reference's own enable timing (disable → 50 ms → enable → 100 ms), with
  2 s and 3 s settles, and across repeated enable cycles — no lock.
* `AUXCLK1 = 0x00020100` and CORE pad `0x19C` low half `0x0000` were re-read
  this boot: the DTS `assigned-clock-rates` fix holds and the pad is right.
* **Discriminator (new this session).**  With the FLL fully bypassed and
  `AIF1CLK` sourced **directly from MCLK1** (`R0x200 = 0x0001`, no FLL in the
  path at all), the stream dies exactly like the FLL case.  If MCLK1 clocked
  at 12.8 MHz, AIF1CLK would be live (2.4 % over the 12.5 MHz AIF1CLK spec —
  fine for a test) and BCLK would appear; it did not.  **The MCLK1 pin does
  not clock under our image.**

This closes report 205 §5h's open question from the software side: the FLL was
never the problem — every readable SoC and codec register matches a working
system, and the clock still is not there.  What remains is below the registers
(pad output driver, ball, board net) and needs the probe/boardview the
operator does not have (trap 165).  **Honest caveat:** session 41 measured
one successful MCLK1 FLL lock (§5h); today's result contradicts a "always
dead" reading, so a marginal or boot-state-dependent clock is still possible —
the two facts stand together, not one erasing the other.

## 4. The mechanism proof: the free-running NCO

The WM8994's free-running FLL (datasheet Rev 4.6 "Free-Running FLL Clock",
p. 206) generates ~12 MHz from the internal oscillator with no reference:
`FLL1_OSC_ENA = 1`, `OUTDIV = ÷8` (already set), `FRC_NCO = 1` with
`FRC_NCO_VAL = 0x19` — and `0x19` is the register's own reset default, so only
one bit needed setting.  Frequency tolerance is ±10 % (reference initially
supplied) / ±30 % (none) per the datasheet's H31 row, so this is **not** a
hi-fi clock; it is a switch that makes AIF1CLK exist.

Driven mid-stream by raw I²C (after `trigger(START)` + the repair, because the
driver's own `set_pll()` clears `FRC_NCO` on the next `hw_params` — see trap
168), with the freeze-safe sequence (thaw → `R0x220 = 0x0007` →
`R0x224 = 0x0CC0` → `R0x200 = 0x0011`):

* **`pbplay 20 440` ran the full 20 seconds and exited cleanly.**  Every
  previous run this session (and all of session 41) died with
  `Input/output error` after five 4096-frame periods — the OSS write only
  keeps succeeding when the ring drains, i.e. when XRDY asserts, i.e. when
  BCLK exists.
* Registers read back exactly as injected (`R0x220 = 0x0007`,
  `R0x224 = 0x0CC0`).

**Conclusion.**  With the codec as AIF1 master and the McBSP as a clock
consumer, the transmit path works end to end: sDMA → FIFO → shifter → codec.
The session-41 `XRDY = 0` stall belonged to the **McBSP-master/SRG path**;
with the SRG out of the path it is gone.  The remaining fault is precisely and
only "AIF1CLK does not exist because MCLK1 does not clock".

## 5. What this means for the four handoff experiments

* **E1 — done and decisive** (this report).  The role inversion is correct;
  it is gated only by the MCLK1 clock.
* **E2 — the capture/loopback is no longer needed for the stall question.**
  `pbplay`'s own survival past its 5-period EIO death is the transmit-path
  proof (trap 169).  It would still be the tool for framing-quality questions
  if audio is heard but wrong.
* **E3 — the reference's mid-stream McBSP registers** are now much less
  decisive: the meaning difference between master and consumer no longer
  matters, since we run consumer mode and it works.  Only worth doing if the
  reference's `SPCR2`/`SRGR2` mid-stream reveal something about its own
  master-mode behaviour that we might want to copy.
* **E4 — static RE of the 1917 sDMA/McBSP setup** is moot for the stall: the
  sDMA was never the problem (it runs at exactly the right rate in both
  configurations).

## 6. Where the work goes next (operator's call)

The blocker is now singular: **a live AIF1CLK**.  The software surface is
exhausted (SCRM `AUXCLK1`, pad `0x19C`, padconf mode, SMART3 drive, DPLL_PER,
all PMIC rails, and the FLL file all byte-identical to the working reference;
÷1…÷8 swept in session 41; direct-MCLK1 dead today).  The honest options:

1. **Hardware-layer MCLK1 investigation** — probe on `fref_clk2_out`/MCLK1,
   or a boardview.  Blocked by trap 165 (no probe, no boardview, no pad
   knowledge).  If the operator ever obtains a scope or a multimeter, this is
   a two-minute measurement: is there 12.8 MHz on the codec's MCLK1?
2. **Accept a non-reference clocking scheme** — e.g. route a different live
   clock to the codec (GPIO-sourced MCLK via the ABE? OPCLK?) or generate
   AIF1CLK some other way.  All of these are new designs with no reference
   precedent.
3. **Revisit the McBSP-master SRG stall** with today's knowledge — the codec
   in slave mode with a BCLK-referenced FLL locks every time, and the FLL
   lock proves BCLK ran.  The stall was between the SRG and the shifter.
   E1's success shows the shifter itself works when externally clocked, so
   the question narrows to the SRG's output distribution in master mode —
   `CLKSM`/`FSGM`/`CLKGDV` interplay on this silicon.  A capture stream (E2)
   plus the steady-state dump could probe individual SRG register
   permutations one boot at a time.
