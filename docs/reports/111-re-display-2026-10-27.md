**The single most important operational finding:** `.script` starts `sh /proc/boot/splash_script`
(record 38) **before** `backlight_win` (record 40, gated on `waitfor /dev/hd3`). `winch_lcdctl`
therefore runs the *whole* DSI/DISPC/panel/backlight sequence at splash time **without**

`/dev/backlight`-equivalent (a backlight class device) will get **a correctly scanned but dark
panel**. See §4.3 and step R2 in §9.

## 2. Control flow: what `winch_lcdctl` does, in order

`main` @ `0x1a664`:

1. `confstr(_CS_SYSTEM_NAME…)` and `strstr` against `"Platform Colt"` (`0x27964`) /
   `"Platform Winchester"` (`0x27974`) → sets the global **`platform`** (@`0x2e548`) = **2** (Colt)
   or **1** (Winchester). Anything else → `"%s Unknown platform"` (`0x27df0`) and abort.
2. `getopt("vbrspR:T:t:f:l:x:y:c:U:")` (`0x27a34`). Useful options:
   `-R fps` (refresh), `-p` *"Force clocks on, clock up DSS, DISPC, DSI"*, `-r` force `power_on`,
   `-b` backlight control on, `-l level` (0x00–0xFF), `-f BMP`, `-t/-T n` DSI loopback test,
   `-s` sleep loop, `-c` set `DxS_CLRSIPOCOUNT`.
3. `platform == 1` (Winchester) → `memcpy(g_DISPC_DSI_Configuration_DSI1 @0x2ee08,
   DSI1_RGB888_VID_MODE_1024_600_60fps` (or the `-R`-selected one), **240**) at `0x1aa18…0x1abc0`.
   `platform == 2` (Colt) → copies one of the four `DSI1_RGB888_VID_MODE_1280_768_Colt*` records
   (`0x26044/0x26134/0x26224/0x26314`) and skips the refresh table entirely (`0x1aa30 → 0x1af10`).
4. `0x1bdd4()` + `0x15e74()` — platform/board and DSS-HAL init (allocates the ~1 088-byte runtime
   configuration block at `0x2e5c0/0x2e5c4` in `.bss`).
5. `0x140c8(1)` **only if** the internal `use_evt`-style flag at `cfg+0x28` is set (i.e. `-p`).
6. `0x162ec(&cfg, arg)` — **translates the 240-byte mode record into the internal display config**
   (this is the golden function for the timings; see §3.3).
7. `0x1c6f8(1)` — **LM3532 "charge-pump/backlight enable" over I²C** (§4.2).
8. `0x1c580()` — **panel-type detect (GPIO176) + SPI panel init** (§3.5).
9. `0x1c4dc(...)`, `0x1c7ac(...)`, `0x1c900(...)`, `0x1b038…0x1b564` — the TI-HAL DSI/DISPC
   sequence: `L1DSS_Reset` → `L1DSS_DSI_Lane_config` → `L1DSS_DSI1_setup_config_QNX`
   (the three step names are the strings at `0x26004/0x26020/0x26038`) → DSI PLL → video-mode
   timing → DISPC enable → GO.
10. Splash BMP decode + blit into the tool's own DMA buffer, then `-s` sleep loop.

The named step strings inside the DSI HAL (`.rodata` `0x27e1c…0x28034`, contiguously packed, in
this order) enumerate the register groups the HAL touches — useful as a checklist for the port:

## 3. Panel, mode records, timings and the SPI init sequence

### 3.1 Which DSS output

* Mode-record names are all `DSI1_…`; `g_DISPC_DSI_Configuration_DSI1` is the single runtime config;
  the DSI HAL calls in §2 step 9 all pass `DSI1_PE_ADDR`/`DSI_PLL`(1) instances.
* DISPC is driven on the **digital** output, not the "LCD" output: the CRED accessor at `0x52dc`
  does an RMW of `DISPC_CONTROL` (`DISPC+0x40`) with mask **`0x42` = bit1 `DIGITALENABLE` +
  bit6 `GODIGITAL`** (`bic r7,r7,#0x42` / `orr` of the two shifted inputs, `0x53ac…0x53c0`).
  Compare `RD_FIELD_32(…DISPC_CONTROL1, …GOLCD)` at `0x270f0`, which is the *LCD* GO bit — used
  only by the poll helper, and reachable only from the non-DSI paths.
  ⇒ **DISPC DIGIT/LCD-manager path → DSI1**. **proven** for "digital enable"; the exact
  DISPC channel number (LCD vs LCD2) is **inferred** from "DSI1 ⇔ digital/`DIGIT`" on OMAP4.
* Nothing enables DSI2 (`0x48045000`), RFBI (`0x48042000`), VENC (`0x48043000`) or HDMI
  (`0x48046000`): no `DSI2_*`/`HDMI_*` mode records exist and the only HDMI strings are the
  instance names in `CRED` and the `-p` help text. **inferred (by absence).**

**Key structural result:** the record stores **two display dimensions in `+0x18`/`+0x1c` and the
RGB888 byte-line-length in `+0x24` = 3 × `+0x1c`**. That fixes the mapping:

* Colt ⇒ `+0x1c = 768` is the **scanned width**, `+0x18 = 1280` the **scanned height**;
* PlayBook ⇒ `+0x1c = 1024` is the **scanned width**, `+0x18 = 600` the **scanned height**.

So the PlayBook LCD is scanned as **1024 wide × 600 tall** (landscape, matching the marketed
"1024×600" and the record name), and the mode-record field *order* is `{height, width}` — the
`idx9 = 3 × width` identity is the proof. This resolves the earlier ambiguity; the
`"+0x88 = v−1 / +0x8a = v−1"` pair is a 32-bit **size register** in
`width−1 | (height−1)<<16` form (DISPC `SIZE_*` layout), not two VACT fields.

```
                     ; RGB666 → code 1, RGB888 → code 3   (matches DSI VC pixel-format encoding)
163ac  if (rec[0x04] == 1) { dst[0x50] = 0 ; dst[0x70] = 0 }
              else        { dst[0x50] = 1 ; dst[0x70] = 300 }   ; 300 = TE/command-mode delay
163e8  dst[0x74] = 0
163f8  ldrh ip,[r2,#0x18] ; sub ip,#1 ; strh [dst,#0x88]      ; height − 1
16404  ldrh ip,[r2,#0x1c] ; sub ip,#1 ; strh [dst,#0x8a]      ; width  − 1
16410  r1 = *(u32*)(arg2 + 0x27c) ; dst[0x84] = r1            ; pixel-format / rotation from ctx
16418  dst[0x5c] = 1 ; dst[0x94] = 0
16424  dst[0x0b] = (u8)rec[0x64] = 1                          ; clock lanes
16430  dst[0x0c] = (u8)rec[0x60] = 2                          ; data lanes
```

So the internal config block starts with **six 16-bit timing/blanking values** taken from record
offsets `0x3c,0x34,0x38,0x30,0x28,0x2c` (three of them decremented), followed by
`+0x48/+0x4c/+0x50/+0x54` = mode/pixel-format codes, `+0x70` = TE delay, `+0x84` = pixel format,
`+0x88/+0x8a` = `height−1 / width−1`, `+0x0b/+0x0c` = clock/data lane counts.

For the PlayBook 60 fps record the six values become:

```
dst+0x00 = 138 − 1 = 137      (from rec+0x3c)
dst+0x02 = 162 − 1 = 161      (from rec+0x34)
dst+0x04 =  20 − 1 =  19      (from rec+0x38, u8)
dst+0x06 =  12                (from rec+0x30)
dst+0x08 =  12                (from rec+0x28)
dst+0x0a =   1 − 1 =   0      (from rec+0x2c, u8)
```
and for Colt:
```
dst+0x00 = 45−1 = 44 ; dst+0x02 = 126−1 = 125 ; dst+0x04 = 1−1 = 0 ;
dst+0x06 = 3         ; dst+0x08 = 9           ; dst+0x0a = 4−1 = 3
```

### 3.4 Timings — what is certain, what is derived

**Certain:** the six numbers above are the panel's blanking set, one group of three per axis, and
the −1 applied to three of them is the classic "register wants `n − 1`". The natural grouping is
`{137, 161, 19}` and `{12, 12, 0}` (the code stores them in that order and the three decremented
ones are exactly the three that come from the larger magnitudes and the two u8 fields).

**Derived (arithmetic, not read back):**

| | PlayBook (1024×600 @60) | Colt (1280×768 @60) |
|---|---|---|
| active | 1024 × 600 | 1280 × 768 |
| axis-1 blanking `{a,b,c}` | 137, 161, 19 | 44, 125, 0 |
| axis-1 total | 1024 + 137 + 161 + 19 = **1341** | 1280 + 44 + 125 + 0 = **1449** |
| axis-2 blanking | 12, 12, 0 | 3, 9, 3 |
| axis-2 total | 600 + 12 + 12 + 0 = **624** | 768 + 3 + 9 + 3 = **783** |
| pixels/frame | 836 784 | 1 134 567 |
| **pixel clock @60 Hz** | **≈ 50.2 MHz** | **≈ 68.1 MHz** |

If instead the two groups are swapped between axes (i.e. the tall/narrow axis takes
`{137,161,19}`), the products are identical and the clocks unchanged — **the pixel clock is
independent of which group is H and which is V**, which is why the numbers below are safe to use
even before the assignment is nailed down.

Sanity cross-checks on 50.2 MHz for 1024×600:
* `12.6 × fps = 756` (record idx 32) and `50.2 MHz` ⇒ `756 × 66.4 kHz`; the same relation holds at
  every other refresh rate, so idx 32 is a *refresh-proportional* quantity, plausibly
  `pixel_clock / 66.667 kHz` or a PLL divider product. **Not asserted.**
* with 2 DSI data lanes and RGB888 the DSI bit rate must be `3/2 × pixel clock` ⇒ **≈ 75 Mbps/lane,
  150 Mbps aggregate**. That is a very low DSI rate but is *consistent* with driving a
  DSI→LVDS bridge (the bridge only needs to reproduce a 50 MHz LVDS pixel stream).
  The `DSI_PllCfg` constants `{60, 90, 300, 5, 5}` (record +0x68…+0x78, **identical in all 14
  records**) are the natural home of `CLOCKN/CLOCKM/CLOCKP/HSDIV` and would pin this exactly —
  **one more pass on `0x1cce0` (the `L1DSS_DSI1_setup_config_QNX` callee) is what remains.**

**Polarities:** `DISPC_POL_FREQ` (`0x6c`) fields `IEO/IPC/IHSP/IVSP` and the DSI
`DSI_VID_CFG`/`DSI_CTRL` blanking-mode bits are set by the HAL from constants I did **not**
resolve; the record has no obvious polarity field, so the boot path most likely uses the TI HAL's
defaults (all syncs **active-low**, i.e. `HSYNC/VSYNC` polarity bits clear) — **inferred, must be
confirmed by readback of `DISPC_POL_FREQ`** (see §9 step R5).

> **What is NOT in the image:** there is no DCS/`0x29`-style panel command stream, because the
> panel is behind a DSI→LVDS bridge and has no DCS channel. Anyone expecting an
> `ili9xxx`-style init sequence will not find one. The *only* ordered byte sequences for the panel
> are (a) the SPI control-port table in §3.5 and (b) the LM3532/TWL writes in §4.

### 3.5 Panel-type strap and the SPI init tables — exact bytes

Panel type (`0x1c580`):

```
1c590  r3 = *(u32*)(CRED + 0x138)      ; ldr r3,[pc] = 0x164 ; ldr r3,[r4,r3] = 0x2b1d4 ; ldr r3,[r3,#312]
       ;   312/4 = 78 -> CRED[78] = 0x4805D000 = GPIO6
1c5e0  r3 = *(u32*)(0x4805D000 + 0x138)
1c5e8  tst r3, #0x10000                ; bit 16 -> GPIO6_16 = GPIO 176
       bit set   -> slogf("LCD is Hitachi") ; spi_send(GOT+0x3578 = 0x2e578,  9)
       bit clear -> slogf("LCD is LG")      ; spi_send(GOT+0x3578+20 = 0x2e58c, 11)
```

`0x4805D138` is `GPIO6 + 0x138` = **`GPIO_DATAIN`** on OMAP4 GPIO (TRM Table 26-x; mainline
`OMAP4_GPIO_DATAIN 0x0138`). So:

> **Panel ID = GPIO 176 (GPIO6_16), sampled once. 1 ⇒ Hitachi, 0 ⇒ LG.**

The SPI writer (`0x1c4dc(u16 *table, int n)`) opens `/dev/spi3`, configures it with
`devctl(fd, 0xA0000000, {0x0000C508, 0x0006DDD0}, 8)` — the two config words are `0x0000C508` =
50 440 and `0x0006DDD0` = **450 000** (i.e. the SPI clock is 450 kHz; the first word is the
mode/word-size field). Then for each word it byte-swaps it (`lsr r2,r3,#8 ; orr r3,r2,r3,lsl#8`)
and sends the 2 bytes with `devctl(fd, 0x80100505, …)` (the QNX SPI "write" DCMD), inserting a
**100 ms** delay (`usleep(0x186A0)` = 100 000 µs) after word 0, after word 2 and after the last word.

**Table at `0x2e578` — Hitachi — 9 × u16:**
```
0029 0025 0840 00AD 0430 385F 3CA4 3409 4041
```
**Table at `0x2e58C` — LG — 11 × u16:**
```
0029 0025 0430 0840 385F 3CA4 3400 0843 2828 4041 00AD
```
On the wire (after the byte swap, MSB-first per the QNX SPI convention) each word becomes
`{low, high}` of the value as stored, i.e. the 18/22 bytes are
`29 00 25 00 40 08 AD 00 30 04 5F 38 A4 3C 09 34 41 40` (Hitachi) and
`29 00 25 00 30 04 40 08 5F 38 A4 3C 00 34 43 08 28 28 41 40 AD 00` (LG).

Timing shape (matters for replay):
```
word[0]            -> 100 ms gap
word[1]            -> (no gap)
word[2]            -> 100 ms gap
word[3..n-2]
word[n-1]          -> 100 ms gap, then SPI close
```

The common prefix `0029 0025` in both tables is the power-up/TCON-unlock pair; the two tables then
differ in ordering of `0430/0840` and in the tail (`3409 4041` vs `3400 0843 2828 4041 00AD`).
**The 16-bit encoding is not decoded** (they are almost certainly `{register, data}` byte pairs for
a vendor TCON — e.g. `0x0840 = 0x00AD` reads as "reg 0x08 ← 0x40, reg 0x00 ← 0xAD" under one
reading) — but **the byte sequence itself is what the hardware needs and it is recovered exactly.**

## 4. Backlight

### 4.1 Identity

`backlight_win` QNX_info: `DESCRIPTION=LM3532 Backlight Resource Manager for TI OMAP430`,
`DATE=2011/11/11`. It is a QNX resource manager (`resmgr_attach("/dev/backlight")`, mode via
`iofunc_attr_init`, `-d -i -v` options, daemonises via `procmgr_daemon`).

> **It is a TI LM3532 LED/backlight driver on I²C.** Not the TWL6030 regulator, not a GPT/PWM, not a
> GPIO. The TWL6030 only appears indirectly (see §4.3), and the panel's own brightness register
> does not exist because the panel is LVDS.

### 4.2 Exact I²C traffic

Write helper `0x1904(dev, reg, val)`: 12-byte device struct `{char *path; int fd; u8 addr;}`;
builds the QNX OMAP-I²C 4-byte header `{addr, len=2, nbufs=2, flags=1}` + `{reg, val}` and calls
`devctlv(fd, 0x80100505, 3, 0, iov, …)`. Same header shape as `omap4430-wdtkick`/`pmic_twl6030_cfg`
(report 108), so the address is a **7-bit** slave address.

| order | slave (7-bit) | reg | value | where | note |
|---|---|---|---|---|---|
| 0 | **0x49** | **0x92** | **0x30** | `0x1cb8` | single write, immediately followed by closing both fds; the tool's own text for the neighbouring path is `"PMIC PWM initialization failed"` (`0x3130`). **Inferred: TWL6030 LED/PWM block** (TWL6030 exposes 0x48/0x49/0x4A as separate I²C addresses — cf. report 108 §3.1, which writes `0x49` regs `0x04/0x06/0x07`). |
| 1 | **0x38** | **0x70** | **0xFF** | `0x1e6c` | LM3532 |
| 2 | **0x38** | **0x17** | **0x19** | `0x1e78` | LM3532 |
| 3 | **0x38** | **0x13** | **0x06** | `0x1e88` | LM3532 |
| run | 0x38 | **0x11** | `v \| (v<<3)` | `0x16c0` | `SET_ENABLED` (`0xC0080501`) |
| run | 0x38 | **0x1D** | `1` = on, `0` = off | `0x1714`/`0x175c` | enable/standby |
| run | 0x38 | **0x12** | `v \| (v<<3)` | `0x1828` | `SET_LEVEL` (`0xC0080502`) |
| run | 0x38 | **0x70** | `level` (0..0xFF) | `0x183c` | "reg12=" log companion |

The `v | (v<<3)` transform expands a 5-bit level (0–31) into the 8-bit dual-slope code — i.e. the
brightness value the driver writes is `level5 * 0x09`. `backlight_level` global @`0x2e550`;
`/dev/backlight` dcmds: `0x00000500` = *get power state* (returns 16 bytes `{dcmd, enabled|level<<8}`),
`0xC0080501` = `SET_ENABLED`, `0xC0080502` = `SET_LEVEL`.

### 4.3 The ordering trap (this is the actionable bug)

`.script` records:

```
37  waitfor /dev/spi3
38  sh /proc/boot/splash_script            <-- winch_lcdctl -s splash runs HERE
39  waitfor /dev/hd3
40  backlight_win -U 99:99                <-- /dev/backlight appears only HERE
```

`winch_lcdctl` opens `/dev/backlight` (`0x27ca4`) and logs `"Could not open %s"` /
`"Could not set backlight brightness, err %d"` / `"Could not turn off LCD charge pump, err %d"`
(`0x27cf8`). At splash time **that device does not exist**, so the brightness never gets set
through it. The only backlight action that actually happens during splash is
`winch_lcdctl`'s own direct I²C to slave **0x38**: `0x70←0xFF`, `0x17←0x19`, `0x13←0x06`
(plus `0x1c6f8(1)` → `0x70←1`, and on power-off `0x1D←0`).

⇒ For mainline this means: **`panel-simple` + a `backlight` node is not enough.** You must either
(a) reproduce the three LM3532 init writes + `0x70` from the kernel, or (b) accept a correctly
scanned but unlit panel until userspace can drive it. See §9 R2.

### 5.2 Power / reset sequence (what the HAL's own strings show it does, in this order)

1. `CM_DSS_CLKCTRL` module enable + `DSS_CM2 CLKTRCTRL` wake — QNX's only explicit PRCM action is
   `setup-core-inactive`: **`0x4A009100[1:0] = 2` (SW_WAKEUP)** (report 106, Phase B row 20), plus
   `CM_DIV_M*_DPLL_PER/CORE` gate-control clears (report 106 Phase A) that keep the PER/CORE DPLL
   outputs available.
2. `DSS_CONTROL.SOFTRESET`-style reset; `DSI_RESET` then poll `DSI_SYSSTATUS.RESET_DONE`
   (`0x273b8`), `DSI_COMPLEXIO_CFG1.RESET_DONE` (`0x27454`).
3. `DSI_CIoLaneConf` / `DSI_CIoLaneUlpsConf` — complex-IO lane enable, ULPS exit for the two data
   lanes + clock lane; `"Could not send inital null packet to start HS clock"` (`0x27384`) shows the
   HAL sends a **null/short packet on VC0 first** to spin up the HS clock before video mode.
4. `DSI_PllCfg` → `DSI_PLL_CONFIGURATION1/2`; `DSI_PllGo` → `PLL_GO`; `DSI_PllStatus` → poll
   `PLL_STATUS` for lock.
5. `DSI_ClkConf` → `DSI_CLK_CTRL` (`lp_clk_div`, `ddr_alwon`) and `DSI_CLK_TIMING`
   (`ddr_clk_pre/post`).
6. `DSI_DdrTiming` / `DSI_HsLpTiming` → `DSIPHY_CFG0/1/2/5/10`, `DSI_TIMING1/2`,
   `DSI_STOPCLK_TIMING` (0x94).
7. `DSI_VideoModeTiming` → `DSI_VM_TIMING1..7`; `DSI_VideoportConf` / `DSI_VcConf` /
   `DSI_ParamsConf` → `DSI_VC_CTRL`, `DSI_GNQ`, `DSI_TX_FIFO_VC_SIZE`/`RX_FIFO_VC_SIZE` (0x70/0x74).
8. `DISPC` timing/size/attributes, `DISPC_CONTROL |= DIGITALENABLE`, then `|= GODIGITAL`
   (the CRED accessor at `0x52dc` sets both bits in one RMW — see §3.1).
9. `DSI_Status` / `DSI_TimingTaFTxStop` polls; then the framebuffer DMA from the tool's own buffer.

### 5.3 Clocks — DSS1/DSS2 aliasing, DPLLs

* The DSS functional clock (`dss_clk`) and the DSS interface clock (`sys_clk`) both come from
  `CM_DSS_CLKCTRL` (`0x4A009100`, a.k.a. DSS_CM2 in the QNX table) bits 8 and 10 in the modern
  clkctrl layout, and from `CM_CLKSEL_DSS`/`CM_CLKSTCTRL` in the older OMAP4 layout.
* On OMAP4 the *pixel/functional* clock for a DSI-attached display is produced by the **DSI PLL**,
  which the DSS driver exposes as **"DSS1"/"DSS2"** (`dss->pll`, aliases of DSI1 PLL / DSI2 PLL).
  There is **no separate OMAP4 DSS DPLL** — `DPLL_PER`/`DPLL_CORE` only feed the DSS *interface*
  clock and the L3/L4 interconnect. `winch_lcdctl`'s `-p` help text (*"clock up DSS, DISPC, DSI,
  HDMI"*) matches that model: PRCM side = module/domain enable, PLL side = DSI PLL.
* QNX's shipped clock state for DSS at the moment `winch_lcdctl` runs:
  `DSS_CM2 CLKCTRL[1:0] = 2 (SW_WAKEUP)` from `setup-core-inactive` (report 106) — i.e. the domain
  is **force-awake**, not `HW_AUTO`. **This is the single PRCM value a Linux port must reproduce
  before touching DISPC/DSI**, and it is the concrete answer to "what QNX does that a bare 6.15
  kernel will not": mainline OMAP clockdomain code puts DSS_CM2 into `HW_AUTO` unless a driver
  holds it, and with no `power-domains`/`ti,sysc` wiring the module can idle under you.
* No DPLL M/N/P programming for the DSS is done by any QNX boot-set binary. The DSI PLL values live
  in the mode records (`+0x68…+0x78`, constant `{60, 90, 300, 5, 5}`) and in the HAL's
  `DSI_PllCfg` step (not decoded, §3.4).

## 6. DTS requirements for mainline 6.15.11

Everything below is against the *current* mainline OMAP4 DSS representation, which is what
`kernel-clean` already contains (`arch/arm/boot/dts/ti/omap/omap4.dtsi`: `dss: dss@0` +

### 6.1 What must be added / forced

```dts
/* ---- board .dtsi (PlayBook / winchester) ---- */
&dss {
        status = "okay";
        /* DSS_CORE_CLKCTRL bit8 = dss_clk (functional), bit10 = sys_clk (interface) */
        /* nothing to override here: the parent omap4.dtsi already lists both.        */
};

&dispc { status = "okay"; };              /* ti,omap4-dispc @ 0x48041000 */

&dsi1 {
        status = "okay";
        /* vdd-supply: DSI PHY/regulator if the board gates it (see note below) */
        #address-cells = <1>;
        #size-cells = <0>;

        port {
                dsi1_out: endpoint@0 {
                        remote-endpoint = <&bridge_in>;
                        /* video mode, 2 data lanes, RGB888 */
                        data-lines = <2>;
                };
        };
};

/* the DSI->LVDS bridge (Toshiba TC358764) and the LVDS panel behind it */
&i2c1 {                                   /* 0x48070000 == QNX /dev/i2c0 */
        bridge: tc358764@38 {
                compatible = "toshiba,tc358764";   /* or a local compatible */
                reg = <0x38>;
                /* needs an explicit reset/power GPIO + the panel's LVDS timings */
                ports {
                        #address-cells = <1>;
                        #size-cells = <0>;
                        port@0 { reg = <0>; bridge_in: endpoint { remote-endpoint = <&dsi1_out>; }; };
                        port@1 { reg = <1>; bridge_out: endpoint { remote-endpoint = <&panel_in>; }; };
                };
        };

        backlight: lm3532@38 { reg = <0x38>; };    /* CONFLICT — see 6.2 */
};
```

### 6.2 Traps specific to this board

1. **Two different chips at 7-bit I²C 0x38 on the same bus.** `backlight_win` drives an **LM3532**
   at `0x38` on `/dev/i2c0` (= I²C1, `0x48070000`) with registers `0x11/0x12/0x13/0x17/0x1D/0x70`;
   the TC358764 is *also* plausibly at `0x38` (Toshiba's default) — but `winch_lcdctl` only ever
   writes 8-bit registers `0x70`/`0x1D` there, which is the LM3532 pattern, **not** the bridge's
   16-bit-address pattern. **Conclusion: `0x38` = LM3532 (proven, both tools agree), and the
   TC358764 is either not reprogrammed by QNX at all (only its two GPIOs 36/171 are exercised by
   the `-t/-T` loopback test) or sits at a different address.** Do not put a `tc358764@38` node in
   the DTS without reading the board's I²C addresses first.
2. **`/dev/backlight` arrives late** (§4.3): the kernel must light the panel itself, so use a
   `backlight` node (LM3532) *and* replicate `0x70←0xFF`, `0x17←0x19`, `0x13←0x06`, `0x1D←1`.
3. **Interconnect / firewall**: `winch_lcdctl` is a QNX process that maps device registers 1:1 with
   `disp_mmap_device_memory`. Nothing in the boot set proves the DSS/DSI registers are reachable
   from the *non-secure* world on this secure device. If `DISPC_REVISION` (`0x48041000`) reads
   `0x00000000` or `0xFFFFFFFF` you have a firewall problem, not a driver problem (see R3).
4. **`ti,sysc` offsets for DSS/DISPC/DSI1** (already correct in `omap4.dtsi` — do *not* override
   them, but know them for debugging):
   * DISPC target-module: `rev` @ `+0x1000`, `sysc` @ `+0x1010`, `syss` @ `+0x1014`,
     `ti,sysc-mask = CLOCKACTIVITY|ENAWAKEUP|SOFTRESET|AUTOIDLE`, `ti,syss-mask = 1`,
     clocks `dss_clk` + `sys_clk`.
   * DSI1 target-module: `rev` @ `+0x4000`, `sysc` @ `+0x4010`, `syss` @ `+0x4014`, same masks,
     **no `clocks` property of its own** (inherits), and the `ti,omap4-dsi` child declares
     `reg-names = "proto","phy","pll"` = `<0 0x200>, <0x200 0x40>, <0x300 0x20>` relative to `0x4000`
     → `0x48044000`, `0x48044200`, `0x48044300` — **exactly the QNX instance table's three DSI1
     entries.** That is a strong independent confirmation of the instance map.
5. **`power-domains` / clock-domain policy**: with no PM policy yet, prefer
   `clk_ignore_unused`/`clk_ignore_unused=1` on the command line **and/or** keep
   `DSS_CM2 CLKTRCTRL = SW_WAKEUP` (`0x4A009100[1:0] = 2`) exactly as `setup-core-inactive` does.
   Also worth forcing during bring-up: `CM_DSS_CLKCTRL.MODULEMODE = 2 (SW_WAKEUP/ENABLED)` and
   `CM_CLKSEL_DSS` left at whatever the bootloader left (QNX never changes it).
6. **The panel is portrait-agnostic**: the scan is 1024×600 (proven by
   `idx9 == 3 × idx7 == 3072`), so a `panel-simple` `display-timings` node is straightforward —
   but **you must first settle the H/V assignment of the six blanking fields** (§3.4/§8).

## 8. Residual unknowns (ranked by how much they block bring-up)

1. **H/V assignment of the two blanking triples** `{137,161,19}` / `{12,12,0}`. Blocks a correct
   `display-timings` node. Cheap to close: the consumer chain is `0x162ec → 0x16610 / 0x179dc /
   0x17094 → 0x18b6c → 0x1cce0 (L1DSS_DSI1_setup_config_QNX)`; `0x18b6c` passes ~40 pointers into
   the internal config to `0x1cce0`, and `0x1cce0` is where `DSI_VM_TIMING1..3` and
   `DISPC_TIMING_H/V` get their values. One focused pass over `0x1cce0` closes it, **and** it will
   simultaneously yield the PLL values and the polarities.
2. **DSI PLL configuration** (`DSI_PLL_CONFIGURATION1/2`) — the last unknown for a working video
   stream. Same function.
3. **`DSI_DSIPHY_CFG*` (DDR/HS-LP timing)** values — the 13 refresh-dependent numbers at record
   `+0x84…+0xb4` are almost certainly their inputs. Same function.
4. **TC358764 programming — settled: nothing programs it, and it needs no programming.**
   Its control port is MIPI DSI generic packets (16-bit address + 32-bit data), so it is not an
   I2C device and the "no 16-bit-address I2C table in `winch_lcdctl`" observation was the expected
   result, not evidence of a missing driver.  Report 122 swept the whole QNX boot set
   (`setup-core-inactive`, the PMIC tools, SPI/I2C/MMC drivers, TZ loader, wdtkick, `resource_seed`
   and the RCFS) and found no bridge programming; a scan of the sealed IFS finds no DSS/DISPC/DSI
   literals outside `winch_lcdctl`; and the second-stage eMMC bootloader carries no display
   constants at all (2026-11-15).  The mask boot ROM *cannot*: a DSI host with PHY/PLL/packet
   engine is required.
   > **The IFS splash proves it in one observation:** `splash_script` →
   > `winch_lcdctl -s splash` puts the logo up before the RFS is mounted
   > (`GFX_SIZE 0x003F01ED` = 494x64 at `GFX_POSITION 0x010C0109` = 265,268 in a
   > 1024x600 field), i.e. **DISPC + DSI + the SPI TCON init + the LM3532
   > backlight all work with the TC358764 untouched — the bridge needs no
   > programming on this board.**  It runs from its power-on/strapped state.
   Registers, for reference: `SYS_ID 0x0580`, `SYS_RST 0x0504` (I2CS 0, I2CM 1,
   LCD 2, BM 3, DSIRX 4), `PPI_STARTPPI 0x0104`, `DSI_STARTDSI 0x0204`,
   `VP_CTRL 0x0450`, `LV_CFG 0x049C`.  **Do not write `SYS_RST <- 0x1f`**: it
   demonstrably degrades the *reference* display until a cold battery pull
   (report 121 §7.6, trap 28).
5. **Which DISPC channel** (`LCD` vs `LCD2`) feeds DSI1. The `DIGITALENABLE/GODIGITAL` mask is
   proven; the manager number is inferred.
6. **`0x92←0x30` semantics** on I²C slave `0x49`.
7. **The `-p` "force clocks" path** (`0x140c8`) — the only place in the image that would write
   PRCM registers from `winch_lcdctl`; not decoded. Low risk (QNX only uses it from HDMI/menu paths,
   not from `splash_script`).

## 9. Ranked next steps toward "something appears on the panel"

All of these are **static/offline-safe** except where marked *(needs one test boot)*.

**R1 — Close the timing/PLL unknown (highest value, zero hardware risk).**
Reverse `0x1cce0` (≈300 instructions, `0x1cce0…0x1d1bc`) — it is the `L1DSS_DSI1_setup_config_QNX`
callee and receives, as stack pointers, the internal config fields the translator filled. Extract
(i) which of `{137,161,19}`/`{12,12,0}` lands in `DSI_VM_TIMING1` (HBP/HFP/HSA) vs `VM_TIMING2`
(VBP/VFP/VSA), (ii) the `DSI_PLL_CONFIGURATION1/2` values, (iii) `DSI_DSIPHY_CFG0/1/2` and
`DISPC_POL_FREQ`. Everything in §3.4/§6.1 becomes "proven" and the `display-timings` node can be
written with confidence.

**R2 — Make the panel *lit* independently of userspace.**
Add an LM3532 `backlight` node and, in the panel's `enable`/`prepare` hook, write
`0x38: 0x70←0xFF, 0x17←0x19, 0x13←0x06, 0x1D←1, 0x12←(level|level<<3), 0x70←level`. Rationale: QNX's
own ordering means nothing else turns the light on at splash time (§4.3).

**R3 — Prove the DSS/DSI registers are reachable before writing any driver.**
From early boot, `ioremap(0x48040000, 0x8000)` and log:
`DSS_REVISION` (0x48040000), `DISPC_REVISION` (0x48041000), `DSI_REVISION` (0x48044000),
`CM_DSS_CLKCTRL` (0x4A009100).
*Expected:* `DISPC_REVISION` = `0x0000000X` style readable value, `DSI_REVISION` non-zero.
*If* `0xFFFFFFFF`/`0x00000000` ⇒ L4 firewall / secure-side ownership (this is a **secure device**),
and no amount of DSS driver work will help. This one test decides the whole plan and costs one boot.

**R4 — Force the QNX DSS clock state.**
Write `CM_DSS_CLKCTRL.MODULEMODE = 2`, `CM_DSS_CLKSTCTRL.CLKTRCTRL = 2 (SW_WAKEUP)`
(`0x4A009100[1:0] = 2`, exactly `setup-core-inactive`'s value), and (for bring-up)
`CM_CLKSEL_DSS` untouched. Keep `clk_ignore_unused` on the command line.

**R5 — Verify each write by reading it back — success is a *register*, not a picture.**
This is how you get "something on the panel" verifiable with no camera and no human:

| step | read back | success looks like |
|---|---|---|
| clock enable | `CM_DSS_CLKCTRL` (0x4A009100) | `IDLEST[17:16] == 0` (functional) and module mode reads back 2 |
| DISPC alive | `DISPC_SYSSTATUS` (0x48041014) | `RESETDONE == 1` |
| DISPC programmed | `DISPC_TIMING_H` (0x48041064), `DISPC_TIMING_V` (0x…68), `DISPC_POL_FREQ` (0x…6c), `DISPC_DIVISOR` (0x…70), `DISPC_SIZE_LCD` (0x…7c) | **exactly** the values you wrote — a self-checking assertion that needs no display |
| DISPC running | `DISPC_CONTROL` bits 1 & 6, then `DISPC_IRQSTATUS` (0x48041018) | `DIGITALENABLE|GODIGITAL` set; **`FRAMEDONE` (bit 0) and `VSYNC` (bit 4/… ) toggling** — poll `IRQSTATUS` twice 1 ms apart: the bits *change* ⇒ the manager is actually scanning |
| DSI PE alive | `DSI_SYSSTATUS` (0x48044014), `DSI_COMPLEXIO_CFG1` (0x…48) | `RESET_DONE` set in both |
| DSI PLL | `DSI_PLL_STATUS` (0x48044304) | `PLL_LOCK == 1`; also `DSI_IRQSTATUS` (0x48044018) bit 7 `PLL_LOCK`, bit 8 `PLL_UNLOCK` must stay clear |
| DSI TX path | `DSI_VC_IRQSTATUS(0)` (0x48044118) after the first null/short packet | `PACKET_SENT` (bit 2) set, `FIFO_TX_UDF`/`FIFO_TX_OVF`/`ECC_NO_CORR` clear |
| link is really driven | `DSI_COMPLEXIO_IRQ_STATUS` (0x4804404c) | no `COMPLEXIO_ERR`; `DSI_IRQSTATUS` bit 10 clear |
| panel talking back | issue a **DCS read** (`0x0A` get-power-mode or `0x04` get-display-id) on VC0 with BTA and read `DSI_VC_IRQSTATUS(0)` | `BTA` (bit 5) + `CS` (bit 0) set and RX FIFO non-empty (`DSI_RX_FIFO_VC_FULLNESS` 0x4804407c) ⇒ a DCS reply came back. If instead `TA_TIMEOUT` (bit 20 or VC-level) fires, the **bridge** does not forward DCS — which is itself the expected result for a TC358764 and *proves the DSI link is electrically alive*, because a dead link gives no BTA at all. |
| backlight | read LM3532 `0x11/0x12/0x13/0x17/0x1D/0x70` over I²C | the values you wrote (and `0x1D == 1`) |
| panel identity | `GPIO6_DATAIN` bit 16 | matches the board (Hitachi=1 / LG=0) |
| I²C sanity | TWL6030 `0x48/0x1F` (`PHOENIX_START_CONDITION`) | any sane boot-reason byte proves `/dev/i2c0` works at the same time as the display writes |

**R6 — Software-only panel bring-up order** (mirrors §5.2 exactly, so any divergence is a bug):
reset DSS → `DISPC_CONTROL.SOFTRESET` + poll → DSI `DSI_SYSCONFIG.SOFTRESET` + poll `SYSSTATUS`
→ complex-IO lane enable/ULPS-exit → DSI PLL config, `PLL_GO`, poll lock → `DSI_CLK_CTRL` /
`DSI_CLK_TIMING` → PHY DDR timing → `DSI_VM_TIMING1..7` → `DSI_VC_CTRL` → DISPC
timing/size/attributes → `DIGITALENABLE` → `GODIGITAL` → then (once, and only then) the SPI panel
table and the LM3532 enable.

**R7 — Only after R5 goes green**: replay the SPI table (§3.5) and check `DISPC_IRQSTATUS`
`SYNC_LOST` stays clear; a wrong SPI table typically shows up as a stable raster but no image, or
as the bridge dropping the LVDS clock.

**R8 — Kept for last, low value**: name the remaining small enums in the mode record (`+0x40`,
`+0x54`, `+0x5c`, `+0x7c`, `+0xb8…`) — they only matter if you need to reproduce a refresh rate
other than 60 fps.
