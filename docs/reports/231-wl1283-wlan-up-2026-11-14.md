# 231 — The WL1283 WLAN runs under Linux: wlcore boots the firmware and `wlan0` comes up

Date: 2026-11-14 (session 50, Linux-era 44, continued after report 230).
Bench: image **`0x9712A086`** (kernel `7.3.3` #60) + the region-1 rootfs with
the wireless modules and firmware.  Capture:
`docs/captures/wl1283-wlan-up-2026-11-14.txt`.

## 0. Headline

Once report 230's `CLK32KG` fix let the card enumerate, four more pieces were
needed — and the chip now **boots firmware and brings up `wlan0`** (see §6:
the interface is **not yet stable**; the status read times out and wlcore
recovery-loops):

```
mmc4: new high speed SDIO card at address 0001
wlcore: loaded
wlcore: firmware booted (Rev 7.3.10.0.142)
wlan0: <NO-CARRIER,BROADCAST,MULTICAST,UP> ... link/ether 7c:8e:e4:3c:22:62
```

Each piece was a measured failure with its own fix:

| symptom | cause | fix |
|---|---|---|
| driver binds, no probe, no log | no `of_node`; `wlcore_probe_of()` returns `-ENODEV` silently | `ti,wl1283` child under `&mmc5`, `reg = <2>`, WL_IRQ, clocks |
| `wl12xx_sdio_power_on: failed to get_sync(-13)` | card runtime PM disabled; `pm_runtime_resume_and_get(&card->dev)` → `-EACCES` | `cap-power-off-card;` on `&mmc5` |
| first firmware boot OK, later ones `sdio write failed (-110)` | `omap_hsmmc` has no `card_hw_reset`, so wlcore's "brute force HW reset" is a no-op, and WL_EN was a permanent hog — the chip is never power-cycled | `mmc-pwrseq-simple` owns WL_EN: low → 50 ms → high → 120 ms on every power cycle |
| — | — | — |

## 1. The modules and firmware

`CONFIG_WL12XX=m`, `CONFIG_WLCORE=m`, `CONFIG_WLCORE_SDIO=m`,
`CONFIG_MAC80211=m`, `CONFIG_CFG80211=m` were already built but not in the
region-1 rootfs.  Added (stripped, ~2.5 MB total) plus `libarc4` and `crc7`:

```
cfg80211  mac80211  libarc4  wlcore  wlcore_sdio  wl12xx  crc7
```

`rcS` loads them in order — `wlcore_sdio`'s recorded module dependency is
incomplete, so a bare `modprobe wlcore_sdio` can bind it before `wlcore` exists
and the probe then returns `-ENODEV` with no message.

Firmware: the mainline `wl128x-fw-5-sr.bin` + `wl128x-nvs.bin` from the host's
linux-firmware (decompressed from `.zst`), staged under
`local/work/firmware/ti-connectivity/`.  `tools/build_rootfs.py` had a
`--firmware` option and an `install_firmware()` helper that **was never called**
— fixed, and it now prints `firmware : N file(s) in /lib/firmware`.

Region 1 was rebuilt to `local/images/rootfs-region1-wl1283.ext4` and flashed
on its own at `0x2915` (region-0 CRC unchanged at that step).

## 2. The device tree, and the three runtime-PM/wake pieces

```dts
&mmc5 {
	...
	max-frequency = <24000000>;
	cap-power-off-card;          /* enables card/function runtime PM */
	#address-cells = <1>;
	#size-cells = <0>;
	mmc-pwrseq = <&wl1283_pwrseq>;

	wl1283: wlan@2 {
		compatible = "ti,wl1283";
		reg = <2>;                       /* SDIO function 2 = WLAN */
		interrupt-parent = <&gpio2>;
		interrupts = <21 IRQ_TYPE_EDGE_FALLING>;  /* WL_IRQ */
		ref-clock-frequency = <26000000>;
		tcxo-clock-frequency = <26000000>;
	};
};

wl1283_pwrseq: wl1283-pwrseq {
	compatible = "mmc-pwrseq-simple";
	reset-gpios = <&gpio2 22 GPIO_ACTIVE_LOW>;  /* WL_EN, active high */
	reset-delay-us = <50000>;
	post-power-on-delay-ms = <120>;
};
```

* **`reg = <2>`** — `wl1271_probe()` rejects every function but 2
  (`if (func->num != 0x02) return -ENODEV`).  Function 1 (BT) matches the ID
  table and then returns `-ENODEV`; that is expected.
* **`cap-power-off-card`** — `mmc_attach_sdio()` only enables card/function
  runtime PM when `host->caps & MMC_CAP_POWER_OFF_CARD`; without it
  `pm_runtime_resume_and_get(&card->dev)` returns `-EACCES` and wlcore logs
  `failed to get_sync(-13)`.
* **`mmc-pwrseq-simple`** — this replaced the `wl1283-en-hog`.  Every firmware
  boot needs a cold power cycle; `wl12xx_sdio_power_on()` asks for one via
  `mmc_hw_reset()`, which returns `-EOPNOTSUPP` on `omap_hsmmc` (no
  `card_hw_reset`) and is ignored.  The pwrseq performs the reference's own
  sequence on every `mmc_power_up()`: assert (EN low) 50 ms, deassert (EN high),
  120 ms.  `GPIO_ACTIVE_LOW` maps "reset asserted" to the physical LOW.
  VIO (`vwl1283`, `regulator-always-on`) stays powered.

The first firmware load at ~10 s succeeded without the pwrseq (the chip was
fresh from enumeration); `ip link up` later powered the card off/resumed and
the firmware re-download timed out (`-110`) until the pwrseq was added.

## 3. Result

* firmware `Rev 7.3.10.0.142` boots (the reference's is `Rev 7.1.4.10.77` —
  different build, same chip family).
* `wlan0` is a real interface: `<NO-CARRIER,BROADCAST,MULTICAST,UP>`,
  MAC **`14:74:11:8f:9c:c3`** — the assigned address, the same as the
  reference's `ti0`.
* **The MAC was patched into the generic NVS.**  `wl1271_register_hw()` reads
  oui from NVS bytes `11/10/6` and nic from `5/4/3`; the mainline default file
  has `oui = 0xdeadbe`, `nic = 0xef0000` (the "unconfigured" marker), so wlcore
  derived a fuse MAC and warned.  Setting `nic = 0x8f9cc3` and `oui = 0x147411`
  (bytes `c3 9c 8f` and `11 .. .. .. 74 14`) yields the assigned MAC and
  removes both warnings.  The **calibration** data is still the generic file —
  the per-unit `hd5` NVS is the real fix.

## 6. KNOWN ISSUE — the interface is not stable yet (measured after the first draft)

The claims in §0/§3 are about the bring-up reaching firmware and `wlan0`; they
are **not** a working WLAN.  After `firmware booted`, the WL_IRQ threaded
handler's firmware-status read times out and wlcore recovery-loops:

```
wl1271_sdio mmc4:0001:2: sdio read failed (-110)
WARNING: ... main.c:880 at wl12xx_queue_recovery_work ...
wlcore: WARNING Enable for recovery failed
wlcore: Hardware recovery in progress. FW ver: Rev 7.3.10.0.142
wlcore: pc: 0x0, hint_sts: 0x00000020
wl12xx_driver wl12xx.1.auto: Runtime PM usage count underflow!
ieee80211 phy0: Hardware restart was requested
```

`hint_sts 0x20` is `WL1271_ACX_INTR_HW_AVAILABLE` (a normal bit, not an error
code) and the `pc: 0x0` means the recovery could not read the FW PC.  The loop
repeats after every firmware boot, so `wlan0` appears and then goes down.

Tests run against it, all negative / reverted:

* **Reference clock 38.4 MHz** (the reference INI's `STRFRefClock = 2`) instead
  of 26 MHz — firmware still boots, same read timeout/recovery.  Reverted to
  26 MHz (image `0x9712A086`).
* **`IRQ_TYPE_LEVEL_LOW`** — the semantically correct type for an active-low
  level IRQ (trap 123), but WL_IRQ **idles LOW before firmware**, so the level
  IRQ storms at boot, saturates the CPU and wedges the unit (the console and ssh
  both stop).  Recovered with a power-cycle (operator) + a bootrom flash of the
  known-good image.  **Keep `EDGE_FALLING`** (trap 238).
* `cap-power-off-card` + a long host autosuspend delay — no change.

Remaining suspects: the **firmware/chip revision match** (the mainline
`wl128x-fw-5-sr.bin` vs this WL1283C; try `wl128x-fw-4-sr.bin`), the **SDIO
block size / byte-mode** after the firmware boot, and the ELP/status-read path.
The `-110` is a CMD53 timeout, not a calibration symptom — the generic NVS is
not the cause of the recovery loop (the first run used the unpatched NVS and
looped identically).

## 7. What is left (not blocking the bring-up, but the WLAN is not usable)

1. **The per-unit calibration NVS from the `hd5` data** (report 197) — the MAC
   is already correct, but the radio calibration is the generic default.
2. **A userspace supplicant** (`iw`/`wpa_supplicant`) is not in the BusyBox
   root; adding one is what association/scanning needs.
3. `regulatory.db` is absent (`cfg80211: failed to load regulatory.db`); a
   world-domain regdb would remove that line.
