# 120 — The LM3532 is gated by GPIO2_16 (gpio_48) — backlight WORKS under Linux

**Session 6, 2026-10-27.**  The backlight problem is solved, and it was **not**
a rail, not REGEN1, not the TWL PWM block, and not the LM3532's own registers:
it is a single OMAP GPIO that Linux leaves undriven.

| | |
|---|---|
| **enable** | **GPIO2_16** = OMAP `gpio_48` = ball `gpmc_a24` = `CONTROL_CORE_PAD0_G` `0x4A100070[15:0]` |
| required value | pad **mux 3** (`0x0003`) **and** `GPIO2_OE[16]=0` (output), `GPIO2_DATAOUT[16]=1` |
| measured causality | line low ⇒ `0x38` NAKs (`Remote I/O error`); line high ⇒ `0x38` ACKs; low again ⇒ NAK again |
| why Linux failed | the boot path **resets GPIO2** (`OE=0xffffffff`, `DATAOUT=0`, QNX has `OE=0xce3ecd5f`, `DATAOUT=0x31013200`) and leaves pad `0x070` in **safe mode** (mux 7, QNX has mux 3) |
| fixed by | DTS: `pinctrl` state + **gpio-hog** on `&gpio2` line 16 (+ `vin-supply`, + panel `backlight` link) |
| result | `0x38` ACKs at boot with no manual action; `leds-lm3532` binds; `/sys/class/backlight/backlight` exists; **the panel lights** |

Image with the fix: `chainloader/kernel.img` crc **`0xD90E0213`**
(`0xA906E4` bytes).  Boot log state: `GPIO2 OE=0xfffeffff DATAOUT=0x00010000`,
LM3532 `0x1d=0xf9` (bank A enabled), `0x74=0xff`, `bl_power=0`,
`actual_brightness=255`, DISPC still scanning (`LINE_STATUS` moving).

## 0. How it was found (and why 118/119 were not wrong, just incomplete)

Session 5 had exhausted the *plausible* candidates from the reference's GPIO
map, but every test was played back on Linux with **no proof that the pin was
actually connected**.  Three measurement errors were possible and unluckily
all three were in play:

1. **A GPIO write on Linux is not a pin write unless the pad is muxed.**  Most
   GPMC balls come up in **safe mode** (mux 7) on our boot path.  Writing
   `DATAOUT` then changes a register and nothing else.
2. **`GPIO_DATAIN` is not a readback for an output pin here** — the reference's
   own driven-high lines read `0`.
3. **GPIO2 (and GPIO1) are reset by our boot path, but GPIO4 is not.**  GPIO4's
   `DATAOUT` was byte-identical to QNX's (`0x90000120`), so those tests were
   no-ops in the other direction: the reference already had them high.

The fix to the *method* was to stop guessing on Linux and make the reference OS
answer the question.

### 0.1 A QNX-side I²C oracle (new tool, reusable)

`analysis/qnx-i2c.c` → `analysis/pbi2c` (QNX ARM ELF, dynamic, `/usr/lib/ldqnx.so.2`),
built with the QNX 6.6 toolchain already in the workspace:

```bash
Q=/home/psyden/SSDdrive/wsl-migration/home/psyden/qnx660-master
export QNX_HOST=$Q/host/linux/x86 QNX_TARGET=$Q/target/qnx6
$Q/host/linux/x86/usr/bin/arm-unknown-nto-qnx6.6.0eabi-gcc -O2 -Wall -o pbi2c qnx-i2c.c
# deploy (TabletOS running):
cd analysis && timeout 30 ./pbssh.sh 'cat > /tmp/pbi2c' < pbi2c
timeout 20 ./pbssh.sh 'chmod +x /tmp/pbi2c; /tmp/pbi2c probe 0 38'
```

Commands: `probe <bus> <addr7>`, `rd <bus> <addr7> <reg>`,
`wr <bus> <addr7> <reg> <val>`, `scan <bus>`, `dump <bus> <addr7> <from> <to>`.
The devctl ABI is the one recovered in reports 108/119
(`0x80100505` write / `0xC0140507` read; 4-word header `{addr7,2,nbufs,flags}`).

> **This is the most useful new capability of the session.**  It turns the
> reference OS into an oracle for *any* I²C question, and QNX also has the QNX
> ARM toolchain, so any small probe tool can be built and run.  **Do not
> re-derive what the reference can be asked.**

### 0.2 What the oracle answered (and what it killed)

* **The bus is right.** `pbi2c scan 0` → `0x09, **0x38**, 0x48, 0x49, 0x4a,
  0x55, 0x77`.  `scan 1` → only `0x65`.  `/dev/i2c2` does not exist.  So QNX's
  `/dev/i2c0` **is** `0x48070000` = Linux `i2c-0`, and Linux's scan differs from
  QNX's by exactly one device: `0x38`.
* **The TWL "PWM init" write is a red herring.** `0x49[0x92]` reads **`0x00` on
  the running reference too**, and it still reads `0x00` there.  Report 118 §11's
  leading hypothesis is dead.
* **The `0x49/0x04,0x06,0x07` bit-0 difference is not it either.**  QNX has
  `0x05/0x15/0x15`, Linux `0x04/0x14/0x14`.  Clearing those bits **on the
  reference** left `0x38` ACKing.
* **REGEN1 is not the LM3532's supply.**  `pmic-twl6030-ctl set_state regen1
  off` on the reference: `0x38` still ACKs.  (Also note `0x48[0xaf]=0x00`,
  `0x48[0xad]=0x00` on QNX — the resmgr disables and detaches it, as 119 says.)
* **Rails are not it.**  Full reference table (`get_state`/`get_vout`), all at
  PMIC defaults except the ones QNX touches:

  | rail | QNX | | rail | QNX |
  |---|---|---|---|---|
  | vana | ON 2100 mV | | regen1 | ON (GPIO1_2) |
  | vaux1/2/3 | ON 2800 mV (app) | | regen2 | OFF |
  | vcxio | ON 1800 mV | | v1v29 | ON 1140 mV |
  | vdac | ON 1800 mV | | v1v8 | ON 1823 mV |
  | vmmc | OFF | | v2v1 | ON 2127 mV |
  | vpp / vusim | OFF | | vmem | ON 1140 mV |
  | vrtc | ON 1600 mV | | vcore1/2/3 | ON |
  | vusb | ON 3300 mV | | | |

  Linux matches these (`vaux1/2/3` forced in the DTS; the rest are OTP
  defaults), so the rails were never the difference.
* **Pad configuration was the difference.**  A full CORE padconf dump of the
  reference (`memdump3 4a100000 0x200`, saved at `/tmp/qnx-padconf.txt` during
  the session) compared against the same range read from Linux
  (`peek 4a100000 64` ×2) shows QNX muxes a whole block of **GPMC balls to
  GPIO mode 3** that Linux leaves in safe mode 7 — offsets `0x050…0x0e4`,
  `0x17c`, …

* **Candidate set, computed properly** (output high on QNX **and** pad mux 3 on
  QNX): GPIO1_2, 1_14, GPIO2_9/12/13/16/24/28/29, GPIO4_5/8/31.  Of those,
  the pins whose pads Linux also has at mux 3 had already been tested and were
  negative; the untested-and-reachable ones were the GPIO2 GPMC balls.

### 0.3 The decisive experiment

On a Linux boot, with the pads set to the reference's exact words
(`poke 4a100060 0003410b`, `…068 00030003`, `…070 41030003`, `…088 00030003`),
then one pin at a time via sysfs:

```
GPIO2_9  (g553) → 0x38 Remote I/O error
GPIO2_12 (g556) → 0x38 Remote I/O error
GPIO2_13 (g557) → 0x38 Remote I/O error
GPIO2_16 (g560) → 0x38 = 0x33      <-- WORKS
```

then, immediately, the causal pair:

```
write /sys/class/gpio/gpio560/value 0  → i2c r 0 38 70 → Remote I/O error
write /sys/class/gpio/gpio560/value 1  → i2c r 0 38 70 → 0x33
```

**GPIO2_16 gates the LM3532.**  (Note the GPIO2 line ↔ global number map on
this kernel: gpiochip544 = hardware lines 32-63, so GPIO2_n = 544+n; gpiochip512
does exist for bank 1 — an earlier `ls` was truncated and briefly suggested it
did not.)

## 1. The fix in the board DTS

```dts
&omap4_pmx_core {
	panel_en_pins: panel-en-pins {
		pinctrl-single,pins = <
			OMAP4_IOPAD(0x070, PIN_OUTPUT | MUX_MODE3)	/* gpmc_a24.gpio_48 */
		>;
	};
};

&gpio2 {
	pinctrl-names = "default";
	pinctrl-0 = <&panel_en_pins>;

	panel-en-hog {
		gpio-hog;
		gpios = <16 GPIO_ACTIVE_HIGH>;
		output-high;
		line-name = "panel-enable";
	};
};

/ {
	panel_vdd: regulator-panel-vdd {          /* ordering placeholder only */
		compatible = "regulator-fixed";
		regulator-name = "panel_vdd";
		regulator-always-on;
		regulator-boot-on;
	};
};

&i2c1 {
	lm3532: led-controller@38 {
		vin-supply = <&panel_vdd>;
		...
	};
};

&lcd0 { backlight = <&backlight>; };    /* makes drm_panel unblank it */
```

### 1.1 Why a **hog** and not a regulator GPIO

The first attempt modelled the line as `regulator-fixed`'s `gpio` and used
`vin-supply` for ordering.  It is *not* enough: a `regulator-fixed` GPIO is only
driven when the regulator is enabled, i.e. in `regulator_init_complete()`
(`late_initcall_sync`), which races **async device probing**.  Same image, two
boots: one bound `lm3532-led`, the next did not (the chip NAKed at probe and the
i2c driver never retries).  A **gpio-hog** is applied at gpiochip registration,
early and deterministic.  Verified: with the hog, every boot since binds.

`panel_vdd` is kept only so `vin-supply` still gives an explicit probe-order
edge; it has no GPIO and no voltage (the panel rail is not actually switched by
us — see §2.1).

### 1.2 The second half: `bl_power` was 4

Even with the driver bound and the LED registered, **nothing reached the chip**:

* `/sys/class/backlight/backlight/bl_power` read **`4`** (`FB_BLANK_POWERDOWN`),
  so `backlight_get_brightness()` returned 0 and `led_bl` took its
  `led_bl_power_off()` path (which is a no-op while `priv->enabled == false`);
* the LED's own sysfs is `-EBUSY` (claimed by the backlight wrapper), so it
  cannot be poked directly;
* symptom: writing `brightness` succeeds, `actual_brightness` echoes the value,
  and **the chip is untouched**.

Writing `bl_power = 0` made the whole chain work in one step
(`LED brightness 200`, `0x1d=0xf9`, `0x74=0xc8`).  In the DTS this is now
handled by naming the backlight in the panel node, so `drm_panel_enable()`
unblanks it at boot: `bl_power=0` and `actual_brightness=255` with no userspace.

## 2. LM3532 behaviour measured on Linux (for the record)

* Register writes land: `0x1d 0xf8→0xf9`, `0x70 0x33→0xff`, `0x12 0xc0→0xff`.
  Some bits are **read-only/OR-in**: writing `0x13←0x06` reads back `0x86`,
  writing `0x16←0x01` reads back **`0xf1`**.  Do not treat a readback mismatch
  there as a failed transfer.
* Mainline's brightness register is `0x70 + control_bank*5 +
  (ctrl_brt_pointer>>2)`, and `ctrl_brt_pointer = reg 0x16 & 0x1c`.  With the
  chip's `0x16 = 0xf1` (QNX residue) that resolves to **`0x74`**, and
  `0x74 = brightness` is what the driver writes.  It lights the panel, so the
  mapping is fine for this panel — the earlier suspicion that `0x70` only works
  was wrong (what actually lit it the first time was enabling bank A with
  `0x1d`, plus the prior `0x74=0xff`).
* QNX's own splash path for comparison: `0x49[0x92]←0x30` (no observable
  effect/persistent value), `0x38: 0x70←0xFF, 0x17←0x19, 0x13←0x06`,
  `0x12←level|(level<<3)`, `0x1d←1`.
* Baseline on a fresh, enabled chip (no driver): `0x00-0x02=0xff`, `0x10=0xe4`,
  `0x11=0xc0`, `0x12=0xc0`, `0x13=0x82`, `0x17=0xf3`, `0x1d=0xf8`, `0x70=0x33`,
  `0x71=0x66`.

### 2.1 The chip keeps its state across our resets

`0x16=0xf1`, `0x74=0xff`, `0x70=0x33` survive a logout/relogin of Linux, and the
panel is lit *before* the emulator ever sees 0x38 ACK.  So the LM3532 sits on a
rail that is **not** switched by GPIO2_16 — the pin gates the **I²C path**
(a buffer/level-shifter enable on the panel flex), not the chip's VDD.  This is
why the rails never showed a difference, and why "unpowered slave holds the
bus" (118 §9) was the wrong model: with the pad un-muxed there was simply no
I²C connection to 0x38, hence a clean NAK, not a hang.

## 3. Traps added this session

20. **GPIO2 is reset by our boot path** (`OE=0xffffffff`, `DATAOUT=0`) and pad
    `0x4A100070` is left in **safe mode**; GPIO4 is *not* reset and its
    `DATAOUT` is byte-identical to QNX's.  Never conclude "the reference drives
    it high, so Linux does too", and never test a GPIO without checking the pad
    mux first.
21. **`pinctrl-single` pads for GPMC balls are not set by anything in our DT.**
    A GPIO write to an un-muxed ball is a silent no-op.  `peek 4a1000XX` and
    check `[2:0] == 3` before believing a test.
22. **`regulator-fixed`'s GPIO loses the race with async probe.**  Use a
    gpio-hog for anything that must be true before a device probes.
23. **A backlight at `bl_power=4` silently swallows all brightness writes.**
    `actual_brightness` still echoes.  Check `bl_power` first.
24. **`/dev/ttyACM0` is recreated on every enumeration** (`root:uucp 0660`):
    `pkexec chmod 666` after **every** boot, not once per session.  Symptom:
    `pbcon: ... Permission denied`.
25. **The flasher's bootrom window is 300 s.**  A flasher left waiting for
    minutes can expire just as you reboot, and the unit then simply boots Linux
    from media again.  Start the flasher *immediately* before the reboot, and
    check `tail` of its log for "done (N frames)".
26. **`pmic-twl6030-ctl set_state vaux1 off` takes the whole unit down** (USB and
    eMMC die; it needed a physical power cycle).  Never toggle VAUX1 on the
    reference.  A `get_state`/`get_vout` sweep of all 20 rails is safe and is
    what §0.2 used.

Working end-to-end at boot, with no manual steps:

* DSS/DISPC scanning (`LINE_STATUS` advancing), DSI PLL locked, TC358764
  programmed, panel mode 1024×600;
* **panel enable + LM3532 bound + backlight at max** — the screen is lit.

   Note the reference clocks it at **450 kHz**, byte-swapped, with 100 ms waits
