# 201 — How the 1917 QNX driver clocks AIF1: FLL1 from MCLK1, programmed and locked *before* AIF1CLK_ENA is ever set

Date: 2026-11-11 (static analysis only; no device, no bench, no hardware access).
Target: `local/work/1917/base/lib/dll/deva-ctrl-omap4abe-wm8994.so`
(190 844 bytes, QNX ARM ELF `ntoarmv7`, `sha256 2b346de3…d6b719`, stripped but with
a full `.dynsym`, image base 0 — see §1).

## 0. Headline

* **The AIF1 clock source is FLL1, not MCLK1.** The driver writes `R0x200
  (AIF1 Clocking 1)` with mask `0x18`, which is the `AIF1CLK_SRC` field, value
  `0x10` = `0b10` = **FLL1** (`codec_enable_interface`, file `0x1ccbc`). MCLK1
  is not the AIF1CLK source; it is the **FLL1 reference**.
* **FLL1 is fully programmed and enabled at codec power-up, long before AIF1CLK
  exists.** `codec_mixer → FUN_0001decc` (file `0x1decc`, "power-up sequence")
  does: `R0=0x0001` software reset → supplies/PM/AntiPOP → `FLL1` (`R0x220..R0x224`)
  → `delay(50)` → `FLL1_ENA=1` → `delay(100)`. `AIF1CLK_ENA` is **not touched**
  anywhere in that function, so every one of those writes is accepted.
* **`AIF1CLK_ENA` is set last, as the final step of the interface bring-up**
  (`codec_enable_interface`, file `0x1ce80`), after `AIF1CLK_SRC=FLL1`
  (`0x1ccbc`), `AIF1_RATE` (`0x1cd58`), `AIF1_MASTER_SLAVE` (`0x1cd78/0x1cd90`)
  and `AIF1 Control 1` (`0x1ce18`). The order is: *reset → FLL up and locked →
  select FLL1 as AIF1CLK → set rate/format → only then AIF1CLK_ENA=1.*
* **There is an escape hatch and the driver uses it, but only for rate changes
  and shutdown**, never for the FLL: `codec_set_clock_rate` (file `0x1b5f8`)
  writes `0x200 bit0=0` → `0x210` → `0x200 bit0=1`, and `codec_disable_interface`
  (file `0x1b80c`) clears `AIF1CLK_ENA`.
* **The FLL is: MCLK1 ÷1, FRATIO ÷1, N=7, K=0xAE14, OUTDIV ÷8 →
  FVCO 98.304 MHz → FOUT 12.288 MHz (256 fs @ 48 kHz).** Only *one* FLL
  configuration exists in the whole binary: there is **no MCLK2/BCLK/LRCLK
  fallback and no runtime source check**.
* **Free-running FLL (`FRC_NCO`) is never used**: `FRC_NCO` (bit 6) and
  `FRC_NCO_VAL` (bits 12:7) of `R0x224` are never written; the only `0x224`
  write clears bits 4:0 and selects `REFCLK_SRC = MCLK1`.
* **No FLL lock polling.** `R0x732` (Interrupt Raw Status 2) is read only inside
  the jack/accessory IRQ handler and only for bits 4:3; bit 5 (`FLL1_LOCK_STS`)
  is never tested. The driver instead relies on fixed `delay()`s (50 and 100
  around `FLL1_ENA`).
* **No write sequencer.** `R0x110`/`R0x111` are never written and the literals
  `0x8100`/`0x812A` do not occur anywhere in the file.
* **AUXCLK1 is mapped, read-modify-written and unmapped by this `.so`**:
  `codec_mixer` maps `0x4A30A314` (`0x1ecf0`–`0x1ed14`, handle at ctx+0x108) and
  un-maps it on teardown (`0x1eef0`); the power-up sequence then sets **bit 8
  (`|= 0x100`, the AUXCLK1 gate)** in it at `0x1deec`–`0x1def8` — *before the
  first I²C write* — and `codec_power_standby` clears that same bit at
  `0x19e1c`, *after* `FLL1_ENA=0`. The divider/source field (`0x00020100`) is
  left to `startup-playbook`; this driver never touches CORE pad `0x19C`.
* **No clocking comments or strings** exist in the binary: no `FLL`, `MCLK`,
  `AIF1CLK`, `lock` or `startup` text (only `pthread_mutex_lock` and McBSP
  clock vote messages).

## 1. Address convention, symbols and tooling

* `.text` file offset **equals** virtual address (`0x5b4c`–`0x20850`), so every
  address in this report is at once the ELF/QNX address, the Ghidra-minus-0x10000
  address, and an `ntoarmv7-objdump` address. **Ghidra (REA MCP) shows
  `+0x10000`** — e.g. `codec_set_clock_rate` is `0x1b5f8` here, `0x2b5f8` in
  Ghidra.
* The file is "stripped" only in the `.symtab` sense: `.dynsym` carries 148
  `FUNC` entries with names (`codec_*`, `StereoAudioCodec*`, `mcbsp_*`, …). The
  I²C helpers and the rest of the codec block in `0x181c4`–`0x19450` are local
  and unnamed in Ghidra (`FUN_00028xxx` = file `0x18xxx`); they are identified
  here from their bodies.
* Imports were resolved from `.plt` + `.rel.plt` so the call sites quoted below
  can be named: `devctl` = stub `0x503c`, `delay` = `0x5090`, `mmap_device_memory`
  = `0x51c8`, `munmap_device_memory` = `0x515c`, `pad_set_af` = `0x4e2c`,
  `gpio_set_output` = `0x50c0`.
* Register field names/masks are quoted from the mainline WM8994 register header
  (`include/linux/mfd/wm8994/registers.h`), which matches every value observed
  here exactly (see §4.1 for the self-check).

## 2. The register primitive: every codec write is read-modify-write over I²C

`FUN_00018294` (file `0x18294`, `__func__ == "codec_write"`) is the only codec
register writer:

```c
int codec_write(ctx, int reg, uint value, uint mask)      /* 0x18294 */
{
    /* 1. read 2 bytes from 16-bit register address (big-endian) */
    devctl(fd, 0xC0140507, &rd_req, 0x16, 0);      /* returns 16-bit value    */
    /* 2. write back (old & ~mask) | (value & mask) */
    new = (old & ~mask) | (value & mask);
    devctl(fd, 0x80100505, &wr_req, 0x14, 0);
    if (rc) ado_error("… Could not send i2c master data to dev 0x%x reg 0x%x data 0x%04x %s", …);
}
```

Consequences that matter:

* The driver **has no regmap/cache**. Every `codec_write()` is a real read +
  real write on the bus, so there is no "the cache already matches, skip the
  write" path (that was the Linux-side divergence in reports 200/203).
* Because the write is a read-modify-write, a dropped write (frozen control
  interface, report 203 §2) is **silently lost**: the read succeeds, the write
  "succeeds", nothing changes. This driver has no way to notice.
* All register addresses in this report are the first argument of this helper.
  `R0x200` is `reg = 512`, `R0x220` is `544`, … `R0x732` is `1842`.

### 4.1 The FLL1 arithmetic (why the field decode is certain)

`R0x221` decoded per the register header: `FLL1_OUTDIV = [13:8]`, `FLL1_FRATIO =
[2:0]` → `0x0700` = OUTDIV 7 = **÷8**, FRATIO 0 = **÷1**.
`R0x223`: `FLL1_N = [14:5]` → `0x00E0 >> 5` = **N = 7**.
`R0x222` = **K = 0xAE14 = 44564**, i.e. N.K = 7 + 44564/65536 = **7.679926**.
`R0x224` = `REFCLK_DIV = [4:3] = 0` (**÷1**), `REFCLK_SRC = [1:0] = 0` (**MCLK1**).

```
Fref      = MCLK1 = 12.8 MHz        (AUXCLK1 / fref_clk2_out, startup-playbook 0x00020100)
Fref/÷1   = 12.8 MHz                (REFCLK_DIV = 0)
FVCO      = 12.8 MHz × 7.679926 / 1 = 98.303 MHz      (datasheet FVCO window 90–100 MHz ✔)
FOUT      = FVCO / OUTDIV = 98.303 / 8 = 12.288 MHz   (256 fs @ 48 kHz ✔)
```

Two independent confirmations that this is not a coincidence: the result lands
exactly on 256 fs for the 48 kHz rate the interface code selects (`R0x210 =
0x83`, `AIF1_SR = 8`), and the VCO lands inside the only band the part can
produce. Equivalently the driver is doing `12.8 MHz × 7.68 / 8 = 12.288 MHz`;
the K truncation from 0.68 to `0xAE14` costs ≈ 9 ppm, which is irrelevant
because AIF1's bit/frame clocks are derived from the same FLL.

### 4.2 The `R0x220 = 0x0004` step

`R0x220` defines only `FLL1_ENA` (bit 0) in the register header, so bits 2 are
undocumented/reserved in the publicly documented map; the vendor sets bit 2
(`0x0004`) *after* N/K/FRATIO are written and *before* `FLL1_ENA = 1`, and never
touches bits 1 or 3–15. Treat it as "a second pre-enable configuration bit"
(most plausibly the FLL1 bias/charge-pump enable that the datasheet requires to
be asserted before the FLL is started); it is recorded as an open detail in §9
because the public register header does not name it.

## 5. Answers to the nine questions

### Q1. Where are `R0x200`, `R0x220`–`R0x224`, `R0x210` written, in what order?

* **FLL1 (`R0x220`–`R0x224`)** — only in `FUN_0001decc` (file `0x1decc`), steps
  14–25 of the table above: `0x220←0`, `0x224←0`, `0x221←0x0700`,
  `0x221←0`, `0x223←0x00E0`, `0x220←0x0004`, `0x222←0xAE14`, `delay(50)`,
  `0x220←0x0001`, `delay(100)`.
* **`R0x200` (`AIF1CLK_ENA` / `AIF1CLK_SRC`)** — five writes across three
  functions, in this order of occurrence:
  1. `codec_enable_interface` `0x1ccbc`: `0x200 ← 0x10, mask 0x18` →
     **`AIF1CLK_SRC = FLL1`**, `AIF1CLK_ENA` untouched (still 0).
  2. `codec_enable_interface` `0x1ce80`: `0x200 ← 0x1, mask 0x1` →
     **`AIF1CLK_ENA = 1`**.
  3. `codec_disable_interface` `0x1b80c`: `0x200 ← 0, mask 0x1` → ENA = 0.
  4. `codec_set_clock_rate` `0x1b640`/`0x1b71c`: `0x200 ← 0` … `0x200 ← 1`
     around the `R0x210` update.
* **`R0x210` (`AIF1 Rate`)** — `codec_enable_interface` `0x1cd58` (`0x83`, always
  48 kHz on the interface bring-up) and `codec_set_clock_rate` `0x1b708`
  (per-rate code, §5.7).

### Q2. Is `AIF1CLK_ENA` set before, after, or independently of FLL1?

**After — strictly after, and it is the last clocking step of the whole bring-up.**

```
codec_enable_interface:
   codec_power_normal → FUN_0001decc    → FLL1 programmed, FLL1_ENA = 1, delay(100)   [call at 0x1cc30]
   wait for ctx->0x38
   mutex lock
   R0x200 ← 0x10 (mask 0x18)   AIF1CLK_SRC = FLL1         0x1ccbc    (ENA still 0 → writes accepted)
   R0x210 ← 0x83 (mask 0xff)   AIF1_RATE                  0x1cd58
   R0x302 ← master/slave                                 0x1cd78/0x1cd90
   R0x300 ← format/word length                           0x1ce18
   R0x208 ← 0xa (mask 0xa)     AIF1DSPCLK_ENA, SYSDSPCLK_ENA = 1   0x1ce4c
   R0x301 ← 0x4000 (cond.)     AIF1 Control 2             0x1ce6c
   R0x200 ← 0x1 (mask 0x1)     AIF1CLK_ENA = 1  ← LAST    0x1ce80
   R0x005 ← 0x300 (mask 0x300) AIF1 ADC/DAC enable        0x1cea0
   … volumes, R0x01a ← 0x103
```

**Is `AIF1CLK_ENA` ever cleared for register access (the datasheet's escape
hatch)?** Yes, in two places, but *neither is used to program the FLL*:

* `codec_set_clock_rate` (file `0x1b5f8`; reached from outside via `dlsym` —
  it is exported and has no in-module caller):

```c
void codec_set_clock_rate(ctx, m, int rate)              /* 0x1b5f8 */
{
    u = ado_mixer_get_context(*ctx);
    if ((mcbsp_port_status(mcbsp, 1) & 1) == 0) return;  /* McBSP not up: do nothing */
    codec_write(u, 0x200, 0, 1);                         /* AIF1CLK_ENA = 0   ← escape hatch */
    switch (rate) {
    case 8000:  rate_field = 0x09; break;  case 16000: rate_field = 0x36; break;
    case 32000: rate_field = 100;  break;  case 44100: rate_field = 0x73; break;
    default:    rate_field = 0x83;                        /* 48000 */
    }
    codec_write(u, 0x210, rate_field, 0xff);              /* AIF1_RATE */
    codec_write(u, 0x200, 1, 1);                          /* AIF1CLK_ENA = 1 */
}
```

* `codec_disable_interface` (file `0x1b730`): `R0x200 ← 0 (bit 0)` at `0x1b80c`,
  then `R0x208 ← 0 (mask 0x8)` = `AIF1DSPCLK_ENA=0` (`0x1b820`), `R0x208 ← 0
  (mask 0x2)` = `SYSDSPCLK_ENA=0` (`0x1b848`), `R0x005 ← 0 (mask 0x3)` and
  `R0x005 ← 0 (mask 0x300)` = AIF1 ADC/DAC disable.

Note the guard: `codec_set_clock_rate` returns early unless the McBSP port is
already running, so the "ENA=0 … ENA=1" window can never span a period with a
stopped clock source.

### Q3. Which `AIF1CLK_SRC`? Any fallback? Values written to `0x200`/`0x224`?

* Source: **FLL1** (`AIF1CLK_SRC = 0b10`), written once at `0x1ccbc` as
  `R0x200 = 0x10 mask 0x18`. MCLK1 (`00`), MCLK2 (`01`) and FLL2 (`11`) are
  never selected. `AIF1CLK_DIV`/`AIF1CLK_INV` (bits 1/2) are never written and
  stay 0.
* **No fallback, no runtime source check.** The complete list of `R0x200` writes
  in the binary is the five sites above; none of them conditions on a clock
  measurement. Likewise `R0x224` (which holds `REFCLK_SRC`) is written exactly
  once, with `REFCLK_SRC = 0 = MCLK1` (`0x1e0e0`, `0x224 ← 0 mask 0x1f`). There
  is no "try MCLK1, else BCLK" logic anywhere, and `FLL2` (`0x240`–`0x244`) is
  never touched.
* Values written: `R0x200 ← 0x0010` (mask `0x18`, i.e. SRC=FLL1), later
  `R0x200 ← 0x0001` (mask `0x1`, ENA), and `0x0000` when disabled. `R0x224 ←
  0x0000` (mask `0x1f`) → `REFCLK_DIV = 0` (÷1), `REFCLK_SRC = 0` (MCLK1).

### Q4. Is the FLL free-running mode (`OSC_ENA` / `FRC_NCO` / `FRC_NCO_VAL`) ever used?

**No.** `FLL1_FRC_NCO` (bit 6 of `R0x224`) and `FLL1_FRC_NCO_VAL` (bits 12:7) are
never written; the single `0x224` write is `0x0000` with mask `0x001f`, which
touches only bits 4:0 (and therefore preserves the reset value `0x0C80`, i.e.
`FRC_NCO_VAL = 25`, while forcing `FRC_NCO = 0`). There is no `FLL1_OSC_ENA`
style path at all — the part is always locked to MCLK1.

### Q5. Does it poll FLL lock (`0x732` bit 5)?

**No.** `R0x732` is read in exactly two places, both inside
`wm8994_accessory_detect_intr` (file `0x1db10`):

```
0x1dbc8:  movw r1, #1842        ; R0x732 Interrupt Raw Status 2
0x1dbcc:  bl   0x181c4          ; codec_read
0x1dbd8:  mov  r1, #4
0x1dbdc:  bl   0x181c4          ; codec_read R0x004
0x1dbe0:  and  r5, r5, #24      ; bits 4:3 — jack/accessory detect only
0x1dbe4:  cmp  r5, #8
```

`FLL1_LOCK_STS` (bit 5) is never masked or tested. Instead the driver waits with
fixed delays: **`delay(50)` between the last FLL register write and
`FLL1_ENA = 1`** (`0x1e174`), and **`delay(100)` after enabling**
(`0x1e190`). There is no timeout, no retry and no error path if the FLL does not
lock — consistent with a design that assumes MCLK1 is always present.

### Q6. Does it use the WM8994 write sequencer (`R0x110`)?

**No.** `R0x110` (`Write Sequencer Ctrl 1`) and `R0x111` (`Ctrl 2`) are never
written by this module, and the usual start words `0x8100` / `0x812A` do not
occur anywhere in the 190 844 bytes (searched as both `u16` and `u32`, whole
file). Every start-up and shut-down step is an explicit register write from C
code. (`R0x700`/`R0x707`/`R0x708` in the table above are **codec GPIO 1/8/9**,
not sequencer memory — the mainline register header names them
`WM8994_GPIO_1/8/9`.)

### Q7. Where are `R0x210`, `R0x303`, `R0x305` set, and how do they relate to the FLL?

* `R0x210` (`AIF1_RATE`: `AIF1_SR = [7:4]`, `AIF1CLK_RATE = [3:0]`):
  `codec_enable_interface 0x1cd58` writes `0x83` → **`AIF1_SR = 8` = 48 kHz**;
  `codec_set_clock_rate 0x1b708` writes 0x09/0x36/0x64/0x73/0x83 for
  8/16/32/44.1/48 kHz (`AIF1_SR` = 0/3/6/7/8 — the standard WM8994 rate table).
  Both happen **after** the FLL is running, so they are accepted; the
  `codec_set_clock_rate` variant is additionally wrapped in the
  `ENA=0 → write → ENA=1` window.
* `R0x303` (`AIF1_BCLK`) and `R0x305` (`AIF1DAC_LRCLK`) are **never written**.
  The codec either stays AIF1 slave (McBSP provides BCLK/LRCLK) or runs as AIF1
  master with the reset/default dividers; `R0x302` (`AIF1_MSTR`, bit 14) is set
  from the McBSP port configuration at `0x1cd78`/`0x1cd90`.
* Relation to the FLL: `AIF1CLK_RATE` is the codec's *expectation* of
  `AIF1CLK/fs`, and the FLL is fixed at 12.288 MHz for all rates, which is only
  consistent with 256 fs at 48 kHz. (See §9 — the low nibble's encoding does not
  fit the 128/192/256/384/512/768 fs code table for the other rates, so on this
  stack only 48 kHz is provably exact; 44.1 kHz in particular cannot be exact
  from a fixed 12.288 MHz FLL.)

### Q8. SCRM AUXCLK1 (`0x4A30A314`) and CORE pad `0x19C`?

* **AUXCLK1: yes — mapped, modified, unmapped by this `.so`.** This is exactly
  the `0x1ecf0` region the handoff mentioned:

```
codec_mixer, file 0x1ecf0 (= Ghidra 0x2ecf0):
0x1ecf0  movw r2, #0xa314
0x1ecf4  movt r2, #0x4a30          ; r2 = 0x4A30A314  (SCRM AUXCLK1)
0x1ecfc  strd r2, [sp]             ; stack args {0x4A30A314, 0}
0x1ed00  mov  r0, #0               ; where = NULL
0x1ed04  mov  r1, #4               ; len   = 4 bytes
0x1ed08  mov  r2, #0xb00           ; flags
0x1ed0c  mov  r3, r0
0x1ed10  bl   mmap_device_memory   ; PLT 0x51c8
0x1ed14  str  r0, [r4, #0x108]     ; ctx->auxclk1 = ptr   (error path at 0x1ed20 if -1)
```

  The register is then **written** by the power-up sequence, before the first
  I²C access:

```
FUN_0001decc, file 0x1deec:
0x1deec  ldr r3, [r4, #0x108]      ; ctx->auxclk1
0x1def0  ldr r2, [r3]
0x1def4  orr r2, r2, #0x100        ; bit 8 = AUXCLK1 gate/"enable"
0x1def8  str r2, [r3]
```

  and the mirror image on the standby path (`codec_power_standby`, `0x19e1c`:
  `ldr r3,[r7,#0x108]; ldr r2,[r3]; bic r2,r2,#0x100; str r2,[r3]` = gate off),
  with the un-map on the mixer teardown path (`codec_mixer`, `0x1eef0`:
  `ldr r0,[r4,#0x108]; mov r1,#4; bl munmap_device_memory`).
  **Only bit 8 is touched** — source mux and divider (`0x00020100`'s bits 2:1 and
  19:16) are left as `startup-playbook` programmed them. This confirms report
  203's decode (`0x00020100` = gate on, `sys_clkin_ck`, ÷3 → 12.8 MHz) is what
  the QNX stack runs with, and that the vendor driver's contribution is the
  gate bit only — asserted on power-up *before* the codec is reset, and dropped
  on standby *after* `FLL1_ENA=0`.
* **CORE pad `0x19C`: no.** The file contains no `0x4A10xxxx` constant and no
  literal `0x19C`. The only `libhwio` pin calls in the codec path are
  `pad_set_af(0x92, 3)`, `pad_set_af(0x93, 3)`, `pad_set_af(0x94, 3)` at
  `0x1e710/0x1e77c/0x1e80c` (the I²C4 group, opened just before) and
  `pad_set_af(0xa2, 3)` + `gpio_set_output`-family calls on ids `0x9f`/`0xa2` at
  `0x1ec50`–`0x1ec80`. Pad `0x19C` (`fref_clk2_out` mux) belongs to the boot
  loader / `startup-playbook`, not to this driver.
* Ordering: the AUXCLK1 gate is set at `0x1deec`, i.e. **before** the
  `R0x000` software reset (`0x1dfdc`) and before any other codec write. The
  SoC-side clock therefore exists before the codec is told to use it.

### Q9. Start-up ordering comments / strings?

None. A full string scan finds no `FLL`, `MCLK`, `AIF1CLK`, `SYSCLK`, `lock`
(except `pthread_mutex_lock/unlock` and the `*_sleepon_*` names), `startup` or
`xtal`. The only clocking text is McBSP housekeeping
(`"Configuring mcbsp %d to %s, protocol %d, mclk = %uhz, target = %uhz, frame
width=%u"`, `"Clock enabled for McBSP %d"`, …, string offsets `0x2a740`+). The
WM8994 function names present in `.rodata` are `__func__` strings used by
`ado_error()` (`"codec_write"`, `"codec_enable_interface"`, …), not a dispatch
table. The ordering knowledge in §4 therefore comes from the code, and it is
unambiguous.

## 6. Shut-down / standby — the exact mirror image (`codec_power_standby`, file `0x19d44`)

```
0x19d9c  codec_read(ctx, 0x200)             ; AIF1 Clocking 1
0x19da4  tst  r0, #1  / bne 0x19dd0         ; AIF1CLK_ENA still set → abort (just unlock)
0x19db0  codec_read(ctx, 0x204)             ; AIF2 Clocking 1
0x19dbc  tst  r0, #1  / bne 0x19dd0         ; AIF2CLK_ENA still set → abort
0x19dc0  ldr  r3,[r5,#0x4530] ; tst r3,#1 / beq 0x19ddc   ; global "in use" flag → abort if set
0x19de0  ctx->0x38 = 0                      ; "codec not powered" flag
0x19de4  FUN(ctx->0x114, 0, 0)              ; I²C/port teardown helper
0x19df4  codec_write(ctx, 0x002, 0, 0x6000) ; PM2 bits 13:14 = 0
0x19e0c  codec_write(ctx, 0x220, 0, 1)      ; FLL1_ENA = 0
0x19e1c  ldr r3,[r7,#0x108]                 ; AUXCLK1 mapping
0x19e20  ldr r2,[r3] ; bic r2,r2,#0x100 ; str r2,[r3]   ; AUXCLK1 gate OFF (bit 8 = 0)
0x19e2c  …                                  ; codec control line / fd teardown, delay(100) at 0x19e78
```

So on the way down the order is the reverse of the way up: **AIF clocks already
off → PM2 → `FLL1_ENA=0` → AUXCLK1 gate off.** MCLK1 stays alive while the FLL
is being disabled, and `AIF1CLK_ENA` is never left set across a codec
power-down. Together with §5.8 this means the driver owns the AUXCLK1 gate for
the whole codec lifetime.

## 7. What this means for the Linux driver

1. **The reference design is `MCLK1 → FLL1 → AIF1CLK`, and it never enables
   AIF1CLK before the FLL is up.** Our Linux machine driver instead points
   AIF1CLK at MCLK1 first and configures the FLL only at `hw_params`; the DAPM
   `AIF1CLK` supply then sets `AIF1CLK_ENA=1` with `AIF1CLK_SRC=MCLK1`, which is
   precisely the datasheet's frozen-on state (report 203). The QNX order is the
   one to copy:
   `clear AIF1CLK_ENA → program FLL1 (delay ~50 µs) → FLL1_ENA=1 → wait ~100 µs
   (or poll 0x732 bit 5) → AIF1CLK_SRC=FLL1 → AIF1_RATE/format → AIF1CLK_ENA=1`.
2. **Never write `R0x210` (or anything else) while `AIF1CLK_ENA=1` and the
   selected source is dead.** If a rate change has to happen with the clock
   running, use the QNX pattern: `0x200 bit0=0`, write `0x210`, `0x200 bit0=1`
   (and only when the CPU DAI clock is actually running — the reference code
   early-returns from `codec_set_clock_rate` if the McBSP is not up).
3. **The FLL parameters to reproduce for 48 kHz are `REFCLK_SRC=MCLK1`,
   `REFCLK_DIV=÷1`, `FRATIO=÷1`, `N=7`, `K=0xAE14`, `OUTDIV=÷8`.** The
   parameters in reports 200/203 (`REFCLK_DIV=0, FRATIO=0, OUTDIV=7, N=7,
   K=0xAE14`) are confirmed correct; only the *order and the enable point* were
   wrong. The literal order is
   `0x220=0` → `0x224=0` → `0x221=0x0700` → `0x223=0x00E0` → `0x220|=0x4` →
   `0x222=0xAE14` → `delay(~50 µs)` → `0x220=0x0001` → `delay(~100 µs)`.
4. **There is no fallback in the reference either** — it does not try MCLK1 and
   then BCLK, and it does not test lock. So the PlayBook's working stack also
   depends on MCLK1 being real. Our remaining problem is the AUXCLK1 →
   `fref_clk2_out` → pad `0x19C` path, exactly as report 203 concluded; the QNX
   driver only sets AUXCLK1 bit 8 (gate) and leaves source/divider to
   `startup-playbook`, which is what our DTS/`auxclk1_ck` already reproduces.
5. **If we keep the BCLK-referenced FLL workaround**, note that it is *not*
   what the reference does: our `set_pll(..., WM8994_FLL_SRC_BCLK, …)` makes the
   codec driver write `REFCLK_SRC = 3` (BCLK) into `R0x224`, whereas the
   reference only ever leaves `REFCLK_SRC = 0` (MCLK1). That is still a
   legitimate fix for the frozen-codec problem, but it must be paired with the
   *ordering* above, i.e. the FLL must be configured and enabled while
   `AIF1CLK_ENA=0`, and `AIF1CLK_SRC=FLL1` + `AIF1CLK_ENA=1` must come after.
6. **Free-running FLL and the write sequencer are dead ends** for matching the
   reference: neither is used anywhere in the working driver.

## 9. Open details (recorded, not needed for the ordering conclusion)

* **`R0x220` bit 2 (`0x0004`, written at `0x1e158`)** is not named by the public
  register header. Most plausibly an FLL1 bias/charge-pump pre-enable required
  before `FLL1_ENA`; it is never cleared again, and `codec_power_standby` only
  clears `FLL1_ENA`.
* **Codec GPIO values**: `R0x700 ← 0x0001 (mask 0x1f)`, `R0x707 ← 0x4007`,
  `R0x708 ← 0x4008`. GPIO1/8/9 function codes are not in the register header
  used here; bit 14 plus FN 7/8 is consistent with a pin-function mux (GPIO8/9
  are the two clock-capable pins on this part), but the exact function numbers
  were not verified against the datasheet's GPIO table.
* **`AIF1CLK_RATE` low nibble** (`0x210[3:0]` = 9/6/4/3/3 for 8/16/32/44.1/48 kHz)
  does not fit the documented 128/192/256/384/512/768 fs code table; `AIF1_SR`
  (`[7:4]`) does fit perfectly. Only 48 kHz (256 fs from the fixed 12.288 MHz
  FLL) is provably exact; the 44.1 kHz entry cannot be produced by this FLL at
  all, so either that rate is never used on this product or another path
  reconfigures the FLL (none exists in this `.so`).
* **`delay()` unit**: the PLT stub at `0x5090` resolves to the imported `delay`.
  The magnitudes used here (6000, 513, 100, 50) only make sense as microseconds
  (6 ms / 513 µs / 100 µs / 50 µs); either way the *relative* order — 50 before
  `FLL1_ENA`, 100 after — is what the ordering argument rests on.
