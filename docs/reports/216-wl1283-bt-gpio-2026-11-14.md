# 216 — The BT half of the WL1283: `devc-seromap-winbt`, its GPIO, and the .bts script

**Session 49 (absolute), Linux-era 42.  2026-11-14.**
Status: **static, file-only RE; no bench, no device.**  First look at the QNX
Bluetooth stack for the WL1283 combo.  Answers the open lead from report 190
§3.2/§3.3 and 192: *the BT UART driver imports `gpio_init`/`gpio_get_id`/
`gpio_set_output` and formats `"%s: mmap_device_io gpio3_base: %s"` — which pin,
when, and is it a shared enable for the whole combo?*

---

## 0. Headline

1. **The BT driver's GPIO is `gpio 55` = `GPIO2_23` = `BT_EN`**, not WL_EN.  The
   driver names the pin only as the hwio **signal id `0x5D`**; `gpio_get_id(0x5D)`
   resolves it through the board table to gpio id `0x37` (55).
   `hwio-config-winchester.so` `gpio_config` idx 15 is
   `{gpio 55, dir=output, level=0, signal 0x5D}` on pad `0x37` =
   `0x4A10007C` bits 31:16 (the ball next to WL_EN's `gpmc_nwp`).
2. **It is never driven by the driver at start-up.**  The driver only calls
   `gpio_init()` (hwio init: mmap + `dlopen("hwio-config-<board>.so")`; no pin
   writes).  `BT_EN` is driven **low, then high after 50 ms** by
   **`btp-btmgr`** (`UART_Init` → `UART_BTPower(0)` → `usleep(50000)` →
   `UART_BTPower(1)`), via the private devctl **`0x80040501`**.  It is driven
   low again only by the BT stack (`UART_Shutdown`) or on `UART_Init` failure.
3. **The "gpio3_base" is `0x48059000` = GPIO4** (QNX counts banks from 0), and it
   is used by one feature only: the **force-RTS** path of the OMAP serial
   driver, which muxes the **UART2_RTS** pad `0x4A100118` bits 31:16 to GPIO and
   drives **GPIO4_28 (gpio 124)**.  Not a chip enable.
4. The driver's only clock write is **one CM2 register**,
   `0x4A009548` = `CM2_L4PER_UART2_CLKCTRL`, **MODULEMODE = 2** (`0x2`) on
   enable, `0x0` on disable.  **No PRM, no PMIC/I²C, no voltage, no WDT.**
5. **`WL1283.bts` is a pure BT service-pack download** (315 HCI commands, 227 ×
   `HCI_VS_Write_Memory_Block 0xFF05` = 56 771 bytes of patch RAM, then
   `0xFD09` "release Cortex Reset" and `0xFDA8` "Enable Cortex Sleep").  It
   contains **no baud-rate action, no GPIO/power command, and nothing that can
   gate the WLAN core.**
6. **Verdict:** there is **no second enable pin** anywhere in the QNX BT path,
   and `BT_EN` is **not** required for the WLAN core: on the live 1917 with
   `ti0` RUNNING, `GPIO2_OE = 0xCE3ECD5F` / `GPIO2_DATAOUT = 0x31413200` show
   **bit 23 = 0/0, i.e. BT_EN actively driven LOW** (OMAP `GPIO_OE` bit 0 =
   output).  WLAN enumerates and scans in that state.  The "shared enable" idea
   is **disproved for BT_EN**; the remaining unresolvable difference is still
   chip-side (VBAT/TCXO/reset), not a GPIO we have not driven.

## 3. Which pin: `gpio 55`, proved end to end

1. `devc-seromap-winbt` 0x286c: `mov r0, #93` → **`gpio_get_id(0x5D)`** — a
   **hwio signal id**, not a pin number and not a string.
2. `libhwio-omap4.so.1` `gpio_get_id` @ 0x1798:
   ```
   for (i = 0; i < *(u32*)(state+4); i++) {          // state+4 = gpio_config_size
       e = gpio_config + i*32;                       // state+0xC = table
       if (*(u32*)(e+0x18) != arg) continue;         // +0x18 signal id
       if (e[0x14] > rev || rev > e[0x15]) continue; // +0x14/+0x15 rev window
       return *(u8*)e;                               // +0x00 gpio id
   }
   return -1;
   ```
3. `hwio-config-winchester.so` `gpio_config` **idx 15** (file 0x1964+15*32 =
   0x1B44): `gpio id = 0x37 (55)`, `dir = 1 (output)`, `level = 0`,
   `detect = 0`, `rev 0..15`, **signal `0x05D`**.  Only this record carries
   signal 0x5D.
4. `gpio 55` → **bank 1** (`55/32`) = **GPIO2 @ 0x48055000**, **bit 23**
   (`55 & 31`) = **GPIO2_23**, i.e. `GPIO2_OE` bit 23 = 0x48055134,
   `SETDATAOUT` 0x48055194, `CLEARDATAOUT` 0x48055190 with mask `0x00800000`.
   (`libhwio-omap4.so.1` 0x2824–0x285c shows exactly this pattern:
   `bit = 1 << (id & 31)`, `base+0x134 &= ~bit`, `base+0x190 = bit` for
   `gpio_set_output(id,0)`; the `level==1` arm uses `+0x194`.)
5. The pad: signal 0x5D is pad id **0x37** = PADCONF **0x4A10007C bits 31:16**,
   af 3 (GPIO), `extra 0` in the pad table.  That is the ball next to WL_EN
   (`pad 0x36` = `0x4A10007C` bits 15:0 = `gpmc_nwp` = gpio 54); per TRM
   ordering that is `gpmc_nwe` (**inferred** — the hwio tables are numeric and
   carry no ball names, see §5).
6. Independent agreement: `startup-playbook` has the option string
   **`BT_EN_GPIO=55`** and its Winchester GPIO table entry for gpio 55 is
   *output, low* (report 192 §1/§4); the live QNX `0x4A10007C` read is
   `0x00030003` — both halves mux 3 (report 188/192).

**So `devc-seromap-winbt` drives `BT_EN` (`GPIO2_23`), the pin adjacent to
`WL_EN` (`GPIO2_22` = gpio 54, the `devnp-ti1283` pin).**  The two enables are
distinct pins on the same PADCONF word.

## 4. Clock: `omap_clock_enable` (Q3)

* Module: **`CM2_L4PER_UART2_CLKCTRL` = `0x4A009548`** (chosen because
  `startup.sh` line 13 passes port `0x4806c000`; the four supported bases map to
  0x4A009540/48/50/58).
* Value: **`2`** into the register (MODULEMODE field = 2 = *explicit enable*),
  then `poll(reg, 3)` and `poll(reg, 0x30000)` — i.e. wait for the module and
  its clock activity.  `omap_clock_disable` writes `0` and polls `3`.
* `omap_clock_toggle_init` uses the *second* argument of `mmap_device_io` as the
  `0`-length flags word; the address is fully static, so **no syspage lookup is
  involved in choosing the register**.
* **No PRM write, no voltage/OPP change, no TWL6030 access** anywhere in the
  driver (imports and strings prove it).

## 5. Syspage / hwio lookups and the literal strings (Q4)

* **No `hwi_find`, `hwi_tag_find`, or any `hwi_*` import or string.**  The
  driver never reads the syspage hwio tree.
* Board selection happens inside `libhwio-omap4.so.1` `gpio_init` @ 0x1d4c:
  `confstr(0x205, buf, 0x100)` (syspage-provided machine/board name), string is
  lower-cased through `_Tolotab`, then `sprintf` **`"hwio-config-%s.so"`** →
  `dlopen` → `dlsym("gpio_config")`, `dlsym("gpio_config_size")`; a second
  `confstr` and a revision query follow, then `hwio_init` (0x3184) maps the one
  big window.  So the *only* "syspage" influence is the board name.
* Literal strings the driver passes (complete, `.rodata` 0x1264c–0x12944 plus
  the usage text 0x147d9–0x14c9b):
  `"seromap: Failed to init hwio"`, `"omap_clock_toggle_init"`,
  `"omap_clock_disable"`, `"omap_clock_enable"`,
  `"%s: Unrecognized physical address, clock toggling not enabled\n"`,
  `"%s: mmap_device_io clkctrl_base: %s\n"`,
  `"%s: Failed to set module mode to 'disabled'\n"`,
  `"%s: Failed to set module mode to 'enabled'\n"`,
  `"%s: Module failed to report 'fully functional'\n"`,
  `"omap_force_rts_init"`, `"%s: mmap_device_io pinmux_base: %s\n"`,
  `"%s: mmap_device_io gpio3_base: %s\n"`,
  `"io-char: Fail to initialize clocks for PM!"`,
  `"io-char: Fail to initialize force_rts for PM!"`, plus the io-char/usage set
  (`"devc-seromap"`, `"%s: No serial ports found"`, …).
  **No signal-name string is ever used** — the pin is `0x5D`, a number.

### 5.1 `hwio-config-winchester.so` — resolver offset correction

The committed `docs/reference/qnx-hwio/README.md` gives the pad resolver tables
at `0x4FF8` / `0x5394` / `0x5730`.  Those are **0x198 too low**.  The real,
verified arrays (231 × `u32` each, contiguous) are:

| array | file offset | check |
|---|---|---|
| bank (0 = CORE `0x4A100000`, 1 = WKUP +0x21E000) | **0x5190** | `bank[0x04]=bank[0x06]=bank[0x1F]=1`, `bank[0x35]=bank[0x94]=0`, exactly 28 entries = 1 |
| offset | **0x552C** | `off[0x35]=0x078`, `off[0x36]=off[0x37]=0x07C`, `off[0x94]=0x148`, `off[0xB7]=0x19C`, `off[0x7E]=off[0x7F]=0x118` |
| half (0 = bits 15:0, 1 = bits 31:16) | **0x58C8** | `half[0x35]=1`, `half[0x36]=0`, `half[0x37]=1`, `half[0x94]=0` |

With these, every one of the 249 committed `pad-table-winchester.csv` rows
recomputes **exactly** (bank/offset/half/addr) — so the CSV is right, only the

**Correction to the CSV:** `pad_config_size` (data at 0x2264) is **248**, and
`pad_config` is 248 records (0x604 + 248×20 = 0x1964 = `gpio_config`).  The
committed CSV's **last row (idx 248, pad 0xAD)** is not a pad record — it is the

Cosmetic, but do not read it as a board pad.

## 6. `btp-btmgr.so` and `WL1283.bts` (Q6)

### 6.1 Who powers the BT half

`btp-btmgr.so` is **not** stripped of its TI/UART dynamic symbols, which makes
the flow explicit (`ntoarmv7-objdump`):

```
UART_Init (0x54310)                      UART_BTPower (0x53da0)
  open(getDevicePath(), 0x802)             fd = *uart_state
  devctl(fd, …)  set line/baud              if (fd >= 0) {
  UART_BTPower(0)                              arg = level;                 /* 0 or 1 */
  usleep(50000)                  ; 50 ms      devctl(fd, 0x80040501, &arg, 4);
  UART_BTPower(1)              <-- BT_EN     slogf("UART: UART_BTPower %s");
  UART_hcill(0)                            }
  … thread/PPS attach …
  on failure: UART_BTPower(0); close      UART_Shutdown (0x54230):
                                            UART_BTPower(0)  <-- BT_EN low
```
* The serial driver's `0x80040501` handler (`winbt_devctl` → `FUN_0x2864`) is
  the **only** thing in the system that touches `GPIO2_23`.
* Sequence at BT start: **BT_EN low → 50 ms → BT_EN high**, then
  `UART_hcill(0)` which calls `UART_Standby(0)` (devctl `801` →
  `omap_clock_enable`, CM2 `0x4A009548 = 2`) and `UART_SetRTS(0)` (devctl
  `0x80040322`).
* `UART_hcill(state)` (0x53ae4) is the HCI-LL power state machine and drives
  `{Standby, SetRTS}` for each state; `UART_Sleep_Ind`/`UART_Wakeup_Ind`/
  `UART_Wakeup_ACK` all funnel into it.
* `UART_SetSpeed` (0x53e6c) is the only baud changer (it maps the HCI baud
  enum to 9600…3686400 and ends with a 50 ms sleep) — used only if a `.bts`
  script carries a BAUD action.
* No PMIC, regulator, clock-enable, WLAN or power-domain access exists in
  `btp-btmgr.so`; everything goes through devctls on `/dev/ser2`.

### 6.2 `WL1283.bts` — structure

Header: `"BTSB"` (0x42535442) + version `1` + 24 zero bytes (0x20 B total).
Then a flat sequence of actions `{u16 type, u16 size, payload[size]}`; the
consumer is `bts_GetNextAction` (0x53600, plain `read()` of 4 + size) driven by
the loop at 0x51258:

| type | meaning (proved by the loop) |
|---|---|
| 1 | **send HCI command**: payload = `01 <opcode le16> <len> <params>` → `HciSendCommand` |
| 2 | **wait for event**: payload = `u32 msec` + `u32 len` + event bytes → returns 2 to park the script until that HCI event arrives |
| 3 | **set baud**: `u32` → `HCI_SetSpeed(payload/100)` (`umull` by 0x51EB851F, `>>5`) |
| 6 | comment (ASCII `# …`) |

### 6.3 `WL1283.bts` — contents (691 actions, ends exactly at EOF 0x12B2B)

* **61 comments** — `"# Description : Quattro L ROM Initialization Script"`,
  `"# Compatibility: Quattro, 6.0.15 ROM"`,
  `"# Last Updated: 18-Jan-2012  15:58:07.91"`,
  `"# Version     : TI_P6_15.51"`, `"# Quattro LMP Subversion: 2b33"`,

  command-complete wait, 5000 ms timeout `0x1388`, event `04 0E 04 <ncmd> <op> <status>`).

| opcode | count | bytes | meaning |
|---|---|---|---|
| `0xFF05` | **227** | 56 771 | `HCI_VS_Write_Memory_Block` — the patch/service-pack RAM image |
| `0xFD97` | 49 | 10 241 | TI VS block write/CRC (second large payload) |

### 6.4 Baud rate (found in `btp-btmgr`, not in the `.bts`)

`base/etc/system/config/bluetooth.conf`:
```
<btmgr btp-btmgr.so>
    device /dev/ser2
    radiotype TI_UART
    btsfile /lib/firmware/bluetooth/WL1283.bts
    baudrate 3686
</btmgr>
```
`3686` is btmgr's baud **enum**, not a number of bits: `UART_SetSpeed` (0x53e6c)
maps every enum the same way and `3686 → 3 686 400` (`movw r3,#0xE66` /
`movweq r6,#0x384000` at 0x53f28-0x53f34; also 115→115200, 921→921600, …).

Sequence (proved from the disassembly):

| VA | what |
|---|---|
| 0x4d5a4 | `UART_SetSpeed(115)` right after `UART_Init` → the link opens at **115200** (matches `-b115200` in `startup.sh`) |
| 0x52774 (RADIO_Init, case enum 3686) | builds a 19-byte vendor HCI command (`opcode word 0xFC00`, payload bytes 0xFB/0x3A carrying the rate; exact payload layout not decoded) — the TI "update UART baud" command |
| 0x52818 | `HCI_Reset` after the speed command |
| 0x51520 (TI_EventHandler) | on the version-info completion sends **`HCI_VS 0xFF36`** with a 4-byte LE baud value (same enum→rate table at 0x51484-0x51500) |
| 0x4d5a8 / 0x49c30 / 0x148c8 | the only `UART_SetSpeed` call sites |

So QNX runs the BT HCI link at **3.6864 Mbaud** after the first round trips.
`WL1283.bts` itself has **no** baud action — the change is btmgr's.

## 7. Verdict (Q7)

**(a) Is there a second enable pin?**  **No — for the BT half there is exactly
one, and it is `BT_EN` (`GPIO2_23`).**  Complete inventory of every pin the QNX
BT path drives: `GPIO2_23` (BT_EN, devctl `0x80040501`) and `GPIO4_28`
(UART2_RTS ball during force-RTS, devctl `0x80040322`).  No other GPIO, no
regulator, no clock gate, no PMIC register.  This is **proven** from the
binaries (all four dcmds handled, the two producer functions, and the board
tables).

**(b) Is a second enable required for the combo's power/TCXO?**  **No evidence,
and the strongest available measurement is against it.**  With QNX running and
WLAN enumerated, `GPIO2_OE = 0xCE3ECD5F` (bit 23 = 0 → *output*) and
`GPIO2_DATAOUT = 0x31413200` (bit 23 = 0) — **BT_EN is actively driven LOW while
the WLAN works**; the same capture has WL_EN (bit 22) high.  So the WLAN core
does not need BT_EN, and BT_EN is not a combo-wide enable.  (Also, WL1283's
`WLAN_EN` and `BT_EN` are separate balls by construction — the board routes them
to adjacent pins of one PADCONF word, `0x4A10007C`, precisely so they can be
driven independently.)
The 26 MHz TCXO / 32.768 kHz SLOW_CLK / VBAT remain chip-side and unmeasured;
nothing in either the WLAN or the BT software path gates them.

**(c) Is the BT driver's GPIO unrelated (e.g. a wake line)?**  **No — it is the
BT enable.**  Its `gpio_config` record is a plain output held low, `btp-btmgr`
pulses it low→50 ms→high at BT init and drops it in `UART_Shutdown`, and the
HCI link then downloads a 56 KB service pack over the same UART — the exact
shape of "power the BT core, then talk to it".  A wake line would not be pulsed
only at init/shutdown.

**Therefore, for the Linux port:**
* `BT_EN` (`GPIO2_23`) is a **prerequisite for the BT half only**.  If Linux is
  to talk HCI on UART2, it must mux `0x4A10007C` hi to GPIO (mode 3, no pull,
  RXACTIVE off), then drive gpio 55 low, wait ~50 ms, then high, before sending
  `HCI_Reset`.  Our current DTS touches **only** the low half (`0x07c` = WL_EN)
  and never the high half — the ball keeps its reset mux (the GPMC function) and
  is never a driven GPIO, so **BT_EN never goes high**.  **This fully explains
  "HCI_Reset got no response"** and is the one concrete, cheap fix this report
  supplies.  (Proven: driver + btmgr + board table; the 50 ms is the
  btmgr value, not a chip datasheet number.)
* It does **not** explain the silent SDIO card, and it must not be added to the
  WLAN power sequence: BT_EN low is the state in which QNX's WLAN works.
* `GPIO4_28`/UART2_RTS force-RTS is an RS-232-transceiver feature
  (`-a` auto-RTS, `k` usage note) and is irrelevant to the combo.

## 9. Limitations

* Ball names are **not** in any hwio binary; `gpmc_nwe` for pad 0x37 and
  `uart2_rts` for pad 0x7F are **inferred** from the TRM ordering and from the
  pad pair `gpmc_ncs3`/`gpmc_nwp` (0x35/0x36) confirmed in earlier reports and
  from the force-RTS semantics.  The **register addresses and GPIO numbers are
  measured from the files** and are not inferred.
* The `+0x04`/`+0x08`/`+0x0c` `gpio_config` fields are named from
  `gpio_get_id`/`gpio_set_output` usage plus the observed values; `dir`
  (1 = output) is proven by the two combo entries (WL_EN/BT_EN are outputs in
  both QNX and the DTS).
* `UART2+0x40/0x54/0x5C` writes in the clock enable/disable path are UART
  internal registers; we quote the offsets, not the TRM names.
