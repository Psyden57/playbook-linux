# 230 — The WL1283 blocker: the TWL6030 `CLK32KG` (32.768 kHz SLOW_CLK) was never enabled

Date: 2026-11-14 (session 50, Linux-era 44, continued after reports 228/229).
Bench: the unit on our image **`0x69CDAC94`** (kernel `7.3.3` #60) after the fix;
the finding was first made at runtime on `0x17C2E119` (#59) by poking the TWL.
Capture: `docs/captures/wl1283-enumerate-2026-11-14.txt`.

## 0. Headline

**The WL1283's SDIO card was silent because the TWL6030 `CLK32KG` resource — the
32.768 kHz output the WL1283's `SLOW_CLK` needs — is OFF under Linux and ON under
the reference.  Enabling it makes the card enumerate.**

* At boot, TWL slave `0x48` registers `0xBC`/`0xBD`/`0xBE` = `07`/`01`/`00`
  (`CLK32KG` group/transition/state, **state OFF**), and MMC5 says
  `mmc4: Failed to initialize a non-removable card`.
* Writing `0xBE = 0xE1` (the value mainline `clk-twl`'s `prepare` computes) —
  or the reference's own `0xBD/0xBE = 0x05/0x55` — makes the card answer:
  `mmc4: new high speed SDIO card at address 0001`, vendor `0x0097`,
  device `0x4076` (TI WL1283), **two SDIO functions** (`mmc4:0001:1/2`).
* The fix is permanent: build `clk-twl` in and have it enable `clk32kg` at
  probe.  It runs at ~1.88 s, before the MMC5 probe at ~2.99 s.  Verified across
  a reboot: `CLK32KG = 07/01/55` and the card enumerates at boot.

## 1. The address: `0x8C` module-relative **is** `0xBC` physical

Reports 192 and KNOWN-ISSUES §3.30/§3.31 tied themselves in knots over
`CLK32KG`'s address because they mixed two address spaces:

* `twl_i2c_read_u8(TWL_MODULE_PM_RECEIVER, &v, reg)` calls
  `regmap_bulk_read(regmap, twl_map[PM_RECEIVER].base + reg, …)`, and
  `TWL6030_BASEADD_PM_SLAVE_MISC` (the `PM_RECEIVER` base) is **`0x30`**
  (`drivers/mfd/twl-core.c`).  So a *module-relative* register `r` is
  **physical `0x30 + r`**.
* `drivers/clk/clk-twl.c` registers `clk32kg` with `.base = 0x8C` and
  `VREG_GRP/TRANS/STATE = 0/1/2`.  Therefore its group/transition/state are at
  module-relative `0x8C`/`0x8D`/`0x8E` = **physical `0xBC`/`0xBD`/`0xBE`**.
* The driver's probe uses that table for **both** `twl6030-clk` and
  `twl6032-clk` (`hw_data = twl6032_clks` unconditionally; only the
  prepare/unprepare bodies branch on the type).  So `0x8C` is valid for the
  TWL6030 too.
* Physical `0x8C` is **VAUX3** (`twl6030-regulator.c` `VAUX3` offset `0x5C`,
  plus the `0x30` base), which is exactly the register report 192 read with
  `i2cget … 0x8c`.  So report 192's "`0x8C` is `CLK32KG`" read VAUX3, and its
  dismissal of the FreeBSD "`0xBC`" claim was backwards: **`0xBC` was right**.
  KNOWN-ISSUES §3.30's "module index 48" and §3.31's "`0x60` candidate" are both
  wrong; §3.31 is corrected in place.

The group/transition/state values also agree with a clock resource, not a rail:
reference `07/05/55` = group 2, APP 1, state ON.

## 2. The causal test (one variable)

On a fresh boot (`0x17C2E119`), before any write:

```
0xBC..0xBE: 0x07 0x01 0x00
[    2.781372] mmc4: Failed to initialize a non-removable card
```

Then, with nothing else changed:

```
i2ctransfer -f -y 0 w2@0x48 0xbe 0xe1          # clk-twl's prepare value
readback: 0x07 0x01 0x55                        # state ON
echo 480d5000.mmc > /sys/bus/platform/drivers/omap_hsmmc/unbind
echo 480d5000.mmc > /sys/bus/platform/drivers/omap_hsmmc/bind
[   16.963195] mmc4: new high speed SDIO card at address 0001
```

The same result with the reference's exact `0xBD = 0x05`, `0xBE = 0x55`.
Writing `0xBE = 0xE0` (all groups, OFF) reads back `0x00`, but the card stayed
up **in that boot** because it had already been initialized and WL_EN stays
high; a rescan does not cold-reset the chip.  The clean single-variable proof is
therefore the fresh-boot failure followed by the enable, which is what §2 shows.

## 3. The permanent fix

1. `CONFIG_CLK_TWL` is **built in** (`=y`; it was `=m` and nothing loaded it).
2. `drivers/clk/clk-twl.c` enables `clk32kg` in its probe for the TWL6030
   (`clk_prepare_enable(cinfo[i].hw.clk)`), with a board-quirk comment.  The
   clock framework has no "always on" flag that *prepares* a clock, and the
   enable must precede the MMC5 probe, so probe time is the right place.
   `of_clk_add_hw_provider(NULL, …)` is a safe no-op for the MFD cell (no
   `of_node`), so the provider half still succeeds.
3. Probe order, from the boot log: TWL at `1.806 s`, `Skipping twl internal
   clock init…` at `1.882 s`, `clk32kg` enabled by the built-in driver, MMC5 at
   `2.99 s` → `new high speed SDIO card`.
4. Verified image: **`0x69CDAC94`** (`0x93992C`, kernel #60).  Boot readback
   `0xBC..0xBE = 07 01 55`, two SDIO functions, no `Failed to initialize`.

(`Skipping twl internal clock init and using bootloader value (unknown osc
rate)` is the TWL's HFCLK-frequency register, not the 32 kHz output; the
bootloader's value is fine — the output runs once the resource is enabled.)

## 4. Why sixteen sessions missed it

* The "silent" instrument was `WL_IRQ` (GPIO2_21) until report 227; the chip
  never raises it before firmware, so the clock was never looked at.
* `CLK32KG` was never read: report 192 read VAUX3 at physical `0x8C` and
  concluded "on in both"; KNOWN-ISSUES then proposed `0x60` (VCORE3's state).
* The one measured difference, `0xBC`–`0xBE` (QNX `07/05/55`, Linux `07/01/00`),
  was recorded in report 192 §7 as "an unidentified non-regulator control
  resource… not `CLK32KG`" — the one correct lead, dismissed by the wrong
  address.
* `clk-twl` was a module nothing loaded — the resource was never even touched.

## 5. What this closes, and what is next

**Closes** the "the chip does not enumerate" half of ROADMAP item 9.  The card
answers CMD5/CMD52 and the SDIO core is up at boot.

**Next (post-enumeration):** the wireless stack.  `CONFIG_WL12XX=m`,
`CONFIG_WLCORE=m`, `CONFIG_WLCORE_SDIO=m`, `CONFIG_MAC80211=m`,
`CONFIG_CFG80211=m` are built but **not in the region-1 rootfs**, and the SDIO
ID table (`wlcore/sdio.c`, `SDIO_DEVICE(SDIO_VENDOR_ID_TI,
SDIO_DEVICE_ID_TI_WL1271)` = `0x0097:0x4076`) does match this card.  The next
step is to stage stripped `cfg80211`/`mac80211`/`wlcore`/`wlcore_sdio`/`wl12xx`
modules and the mainline firmware (`wl128x-fw-5-sr.bin`, `wl128x-nvs.bin` —
available in the host's `/lib/firmware`, zstd-compressed), rebuild region 1, and
watch `wlcore` boot the firmware.  The per-unit MAC/NVS still come from the
`hd5` calibration and NVRAM `deviceinfo` (`14:74:11:8f:9c:c3`, report 197).
