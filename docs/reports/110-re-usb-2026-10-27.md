# 110 — Static RE of the USB stack in the PlayBook QNX boot set (OMAP4430 "winchester")

Scope: which binaries in `/home/psyden/rea-work/playbook-dev/dumped4869ifs/proc/boot/`
implement USB, which OMAP4430 USB controllers/PHYs the product uses, what the QNX
side programs at startup, the mainline 6.15 DTS recipe, and ranked next steps for
a first Linux USB milestone.

Method (read-only, nothing executed on any target):
`strings`/`readelf`/Build-ID sweep over the whole IFS,
`readelf -l/-S/-n`, targeted `arm-linux-objdump -D -b binary -m arm` on
vaddr-normalised copies of the images (QNX ELF32 `ET_DYN`; for the R-X `LOAD`
segment `file offset == vaddr`, the R-W `LOAD` segment is `vaddr = offset + 0x1000`
for every image in this set), whole-image 32-bit constant scans, pointer/table
walks, and address/bit cross-checks against `swpu231ap.pdf.txt` (OMAP4430 TRM)
and against the local 6.15.11 tree at `/home/psyden/rea-work/playbook-dev/kernel-clean`.

**Headline:** the boot set contains **no USB controller driver, no USB PHY driver
and no USB class/gadget stack**. The USB stack in TabletOS lives on the read-only
`/base` filesystem (`/base/scripts/startup.sh` is the last line of the IFS
`.script`; `sanity.cfg` names the daemon `RIM_usbmgr-Winchester` + `/dev/RIM_usbmgr`),
and that filesystem is **not** part of this dump. What the boot set *does* contain
— and what this report extracts — is:

1. the SoC's **complete TI PRCM clock/power model** (`setup-core-inactive`, and a
   duplicate copy inside `winch_lcdctl`), including every USB clock node and the
   `CM/PRM` instance base-address table, which is what actually answers "what must
   be clocked";
2. the **TWL6030 regulator policy** for the USB rail (`pmic-winchester-twl6030`,
   `/etc/system/config/pmic-twl6030*.cfg`);
3. the **VBUS/ID boot gating** logic (`winchester-bootreason`).

Everything register-level in §3 is therefore *the SoC/PMIC programming the product
performs*, verified against the TRM, plus honest gaps where the value lives in the
missing `/base` binaries.

### 1.2 Where the driver is (proven)

* Tail of `proc/boot/.script`: after `backlight_win`, `rpmb-omap4`,
  `nvram_resource_manager`, `rfs_validator`, `sanityChecking` it execs
  **`/base/scripts/startup.sh`** with `PATH=…/base/bin:…/base/sbin:…`.
  The IFS therefore only brings up console/i2c/pmic/mmc/spi/rpmb; the USB stack
  (and everything else) starts from `/base`.
* `sanity.cfg` (the customer test list) names `RIM_usbmgr-Winchester` and
  `/dev/RIM_usbmgr`, plus `EXISTS c "/pps/services/power/usbconnector"`-style
  resource checks elsewhere in the same file — confirming a userspace USB manager
  plus a PPS-backed USB-connector service.
* Consequences for this report: **the register writes the QNX USB driver makes are
  not statically recoverable from this dump.** Everything in §3 is either (a) the
  SoC-side clock/power model that the boot set *does* contain, or (b) the PMIC
  policy, or (c) hardware-mandated values derived from the TRM + mainline.

### 2.2 What RIM's own clock model says the board has

Recovered from `setup-core-inactive` (data records at vaddr `0x1EB28`–`0x1F4xx`,
indexed by a `{0x17, ptr}` array at `0x28A0`). Each record is 0x68 bytes; the last
four words are `{clkctrl_off, clkctrl_off+4, clkctrl_off, 3, …}` and are
**unambiguous**, because the offsets match the TRM's L3INIT_CM2 map exactly:

| QNX record name | record vaddr | `+0x4C` | resolved register | TRM |
|---|---|---|---|---|
| `prcm_usb_host_fs` | `0x1EB90` | `0xD0` | `CM_L3INIT_FSUSB_CLKCTRL` `0x4A0093D0` | ✓ (`+0xD0`) |
| `prcm_usb_host` | `0x1EBF8` | `0x58` | `CM_L3INIT_HSUSBHOST_CLKCTRL` `0x4A009358` | ✓ (`+0x58`) |
| `prcm_usb_otg` | `0x1EC60` | `0x60` | `CM_L3INIT_HSUSBOTG_CLKCTRL` `0x4A009360` | ✓ (`+0x60`) |
| `prcm_usb_tll` | `0x1ED98` | `0x68` | `CM_L3INIT_HSUSBTLL_CLKCTRL` `0x4A009368` | ✓ (`+0x68`) |
| `prcm_usbphyocp2scp` | `0x1ED30` | `0xE0` | `CM_L3INIT_USBPHY_CLKCTRL` `0x4A0093E0` | ✓ (`+0xE0`) |
| `prcm_xhpi` | `0x1ECC8` | `0xC0` | `0x4A0093C0` (TRM: RESERVED) | ✓ reserved |
| `prcm_unipro1` | `0x1EB28` | `0x40` | `0x4A009340` (TRM: RESERVED) | ✓ reserved |

The USB clock nodes carry a *source-clock id list* (record `+0x18..+0x38`, `-1` =
unused) that cross-references other records in the same table, e.g. `prcm_usb_host`
lists ids `{0x16,0x1D,0x1E,0x16,0x16,0x16,0x19,0x19,0x6E}` where `0x1D`=`prcm_xhpi`,
`0x1E`=`prcm_usbphyocp2scp`, `0x19`=`prcm_unipro1`, and `prcm_usb_otg` lists
`{none,0x17,none×7}`. Struct field `+0x08` is the **clock id** and they are
sequential (unipro1=0x19, usb_host_fs=0x1A, usb_host=0x1B, usb_otg=0x1C, xhpi=0x1D,
usbphyocp2scp=0x1E, usb_tll=0x1F) — i.e. QNX's own clock enumeration indexes the
USB complex in exactly the TRM's order. Fields `+0x3C..+0x48` are
`{1,3,2,5}` for `usb_host_fs` and `usb_host`, `{1,3,2,3}` for `usb_otg`,
`{1,1,2,3}` for `usb_tll`, `{1,1,0,3}` for `usbphyocp2scp`, `{1,3,0,5}` for
`xhpi` — they vary per node and are *not* decoded further (see §7).

Consequence: **the product's clock tree knows and gates all five USB modules
(OTG, HOST, TLL, FSUSB, USBPHY) plus DPLL_USB and the 60 MHz mux.** Existence in
the table is not evidence of use (it is TI's generic OMAP4430 model), so the
host/TLL presence is *not* by itself proof of a host port.

### 2.3 What is actually wired: device mode proven, host mode not evidenced

Evidence for **device (peripheral) mode on the OTG port**:

* The unit enumerates on a PC as `0fca:8010` in TabletOS (given).
* `winchester-bootreason` gates the *boot* on host presence:
  `"Connected to host, continue boot"` / `"Detected USB charger, holding boot"` /
  `"Detected 12V charger, holding boot"` / `"Charger not present, powering off"` /
  `"Power on due to USB ID"`; compiled from `/pps/services/power/usbconnector`
  (`UsbConnector`, `Vbus`) and `usb_charger_detect()` over i2c. That is a pure
  *B-device* (device + charger detect) behaviour.
* `NV_QNX_MAC_USBNET1/2`, `NV_OSSTORE_NETUSB_CONFIG` — the product's USB networking
  is RNDIS/CDC-ECM **in device mode** (MAC addresses per unit).
* No ULPI pin group, no external PHY, no VBUS switch anywhere in the set; the only
  USB-adjacent PMIC rail is `vusb` (the 3.3 V LDO that feeds the OMAP USBPHY and
  the TWL USB comparators), fixed-output.

Evidence for **host mode**: two independent artefacts, and they point away from a
user-visible port:

* `nvram_resource_manager` `popen()`s **`/sbin/probe_ehci_udev_winchester`** from
  `perform_radio_probe()` (`get_radio_support` / `get_pps_radio_support`), parsing
  `VID=`/`PID=` out of the result ("could not determine radio support, unknown
  VID/PID from device (vid=%#x, pid=%#x)"). So the *only* caller of EHCI in
  TabletOS is the **radio (cellular) probe** — the modem presents itself as a USB
  device. Matching NV items: `NV_OSSTORE_TavorPVUsbCal_NUM` ("Tavor" modem USB
  calibration), `NV_OSSTORE_IdenRadioBsn_NUM`, `NV_OSSTORE_GprsRadioFeatures_NUM`,
  `NV_OSSTORE_RADIO_3GPP_CONFIGURATIONS`. This is a 4G-SKU path; a Wi-Fi-only unit
  never runs it.
* OMAP4 EHCI has three ports: port 0 goes through the TLL to an external ULPI PHY,
  ports 1/2 are **HSIC** (`omap4-l4.dtsi` `usbhs-host` exposes exactly
  `port1-mode`, `refclk_60m_ext_p1`, `refclk_60m_ext_p2` for that choice). An
  internal modem on HSIC needs **no** ULPI pins and **no** VBUS, which fits a
  sealed tablet. There is no ULPI PHY and no VBUS source in the dump, and
  `CONTROL_USBOTGHS_CONTROL[6] DRVVBUS` (which would gate a 5 V boost) is a
  read-only PHY output with no evidence of a charge pump behind it.

**Answer to "device, host, or OTG":** the connector is ID-aware (OTG-style — the
boot reason reports the ID pin), the SoC block is a full OTG controller
(MUSB + internal UTMI PHY + `CONTROL_USBOTGHS_CONTROL` mail-box + TWL6030
AVALID/BVALID/VBUSVALID/SESSEND/IDDIG comparators), but the shipped product only
uses **B-device (peripheral) mode**. A-device/host mode would need both a 5 V VBUS
source and (for EHCI/OHCI) an external ULPI PHY; neither is present in the dump.
The TWL6030 itself does **not** contain the HS data PHY — it only supplies the
3.3 V `VUSB` rail plus VBUS/ID/charger comparators. There is no TC358764-style
bridge anywhere in the set (that part is a DSI→LVDS bridge; report 111 territory).

## 3. Startup programming (goal 3)

### 3.1 Proven negative: no USB driver, no USB-PHY register writes in the IFS

* Whole-image scan of every binary for `0x4A0Axxxx` (OTG/PHY/OCP2SCP), `0x4A06[24]xxx`
  (TLL/host), `0x4A0093xx` (L3INIT_CM2), `0x4A0081xx` (DPLL_USB/60 MHz) as a
  32-bit constant: **hits only inside `setup-core-inactive` / `winch_lcdctl`, and
  only as table *base addresses*** (`0x4A008000`, `0x4A008100`, `0x4A009000`,
  `0x4A009300`, `0x4A009E00`, `0x4A002000`, …) — never as a target of a store with
  a recovered value.
* No binary contains a TWL6030 *USB* register id. `pmic-winchester-twl6030` only
  implements the regulator file: `vana…vusim, regen1, regen2` in a 0x20-byte-stride
  table at `0x8170`; the USB one is
  ```
  vusb @0x8290: name="vusb"  field1=0x0002F5A0  vout[0..3]={0,0,0,0}  id=0x0A  flags=0
  ```
  i.e. **no programmable voltage table** (TWL6030 `VUSB` is a fixed 3.3 V LDO),
  regulator id `0x0A`. Nothing in the binary writes `USB_VBUS_CTRL`/`USB_ID_CTRL`
  (`0x04`–`0x15` on the TWL6030 USB module) — those are the missing driver's job.
* The only USB *policy* the boot chain leaves behind is the two config scripts:
  `set_trans vusb sleep=ams act=ams` (keep `VUSB` in active/AMS), `vusb` excluded
  from the "turn off unused LDOs" list.

### 3.2 The clock chain that must be up (recovered structure, TRM-verified values)

Reconstructed from `setup-core-inactive`'s model + TRM bit fields. Order matters
(DPLL before module).

```
1. DPLL_USB                              0x4A008180  CM_CLKMODE_DPLL_USB
     DPLL_EN[2:0] = 0x7 (lock)  [SSC off: [12]=0]
   CM_CLKSEL_DPLL_USB                    0x4A00818C  DPLL_MULT[19:8], DPLL_DIV[7:0]
   CM_DIV_M2_DPLL_USB                    0x4A008190  DIV[6:0], [8]=1 (CLKOUT gating off)
   -> poll CM_IDLEST_DPLL_USB / CM_DIV_M2_DPLL_USB[9] (CLKOUT_M2 status)
2. 60 MHz mux                            0x4A008104  CM_CLKSEL_USB_60MHZ[0] CLKSEL
     (QNX names: prcm_cm2_usb_div8 / prcm_usb_hs_clk_div / prcm_clk_xclk60motg)
3. L3INIT clock domain                   0x4A009300  CM_L3INIT_CLKSTCTRL
     CLKTRCTRL[1:0]: 2 = SW_WKUP (forced awake) | 3 = HW_AUTO (TRM reset = 3)
4. modules (MODULEMODE[1:0]: 1 = ENABLED/forced, 2 = HW_AUTO, 0 = DISABLED)
     CM_L3INIT_USBPHY_CLKCTRL     0x4A0093E0  [8] OPTFCLKEN_PHY_48M = 1
     CM_L3INIT_HSUSBTLL_CLKCTRL   0x4A009368                  (host path only)
     CM_L3INIT_HSUSBHOST_CLKCTRL  0x4A009358  [10:8] OPTFCLKEN_UTMI_P3/P2/P1_CLK  (host path only)
     CM_L3INIT_FSUSB_CLKCTRL      0x4A0093D0                  (TLL FS host, host path only)
     CM_L3INIT_HSUSBOTG_CLKCTRL   0x4A009360  [24] CLKSEL_60M, [10:8] OPTFCLKEN_UTMI_Px
   after each write: poll IDLEST[17:16] == 0 (FUNCTIONAL)
```

QNX's table encodes this exact graph — the record for `prcm_usb_otg` ends
`…, 0x60, 0x64, 0x60, 3, …` (clkctrl `+0x60`, its `+0x64` companion, `+0x60` again,
then the constant `3` = HW_AUTO), and `prcm_usbphyocp2scp` ends
`…, 0xE0, 0xE4, 0xF10, 0xF18, 0xF16, 0xF15, 0` (the extra two ids are the parents it
also needs). **Caveat, stated plainly:** the *numeric* `DPLL_MULT/DPLL_DIV/M2` and
the per-OPP values are inside the undecoded part of TI's `prcm_*` records (and
behind the `dpll_usb_cfg_allopp` / `dpll_usb_cfg_allopp_12` config blobs), so the
values in `0x4A00818C/0x4A008190` are **not** recovered here (see §7). This is the
one place where the missing `/base` driver and the undecoded data structure cost us;
it is also the one place where mainline already has the answer
(`omap4*_clkctrl`/`dpll` CCF drivers compute the same divider set from
`assigned-clock-rates`), so it does not block bring-up.

### 3.3 "Core inactive" is the opposite of what we need (a real trap)

`setup-core-inactive`'s stated purpose is *"one time setup to allow for core
inactive mode"* / *"one time set up for core inactve state"* (QNX_usage), and it
runs in the IFS **before** the USB stack would ever start. In QNX the USB clocks
are therefore **not** left enabled by it; they are enabled later, on demand, by the
clock framework (that is what the `MODULEMODE`/`CLKTRCTRL` machinery in §3.2 is
for). Two practical consequences:

* Reading L3INIT registers from a cold Linux boot tells you nothing about "what QNX
  left on" — QNX left them *idle*.
* Linux must own the whole sequence (its CCF/ti-sysc path does), and must not
  assume any inherited state.

### 3.4 VBUS / ID handling — the part that decides whether anything enumerates

There is **no GPIO and no OMAP register** for VBUS/ID in this product: the
detection is done **inside the TWL6030** (VBUS/ID comparators + charger detect) and
delivered to the SoC through `CONTROL_USBOTGHS_CONTROL` as a *software mail-box*:

```
TWL6030 (i2c, slave 0x48; USB block regs 0x00-0x1A on the "usb" module,
         VUSB_CFG_TRANS/STATE/VOLTAGE 0x71/0x72/0x73 on PM_RECEIVER,
         STS_HW_CONDITIONS 0x21 on PM_MASTER with STS_USB_ID = BIT(2))
    |  VBUS/ID interrupts (TWL IRQ 4 = OTG/ID, IRQ 10 = VBUS per twl6030.dtsi <4>,<10>)
    v
winchester-bootreason  (reads only: "usb_charger_detect", "Connected to host")
    |
    v   (in TabletOS: the missing /base USB driver, on the same IRQ pair)
    writes AVALID/BVALID/VBUSVALID/SESSEND/IDDIG
    v
CONTROL_USBOTGHS_CONTROL 0x4A00233C
    v
OMAP HSUSBOTG OTG state machine (MUSB DEVCTL.IDDIG/BSESSVLD/SESSEND/...)
```

Reset value of `0x4A00233C` is `IDDIG=1, SESSEND=1` (`0x18`) = *no cable*.
Device-mode mail-box value (what mainline's `omap_control_usb_device_mode()` writes,
`drivers/phy/ti/phy-omap-control.c`) is:

```
0x4A00233C: AVALID=1 | VBUSVALID=1 | IDDIG=1 | SESSEND=0  =>  0x15   (device)
host mode   : AVALID=1 | VBUSVALID=1 | IDDIG=0 | SESSEND=0 =>  0x05   (host)
session end : AVALID=0 | VBUSVALID=0 | IDDIG=1 | SESSEND=1 =>  0x18   (= reset)
```

Note on bit 1 (`BVALID`): the TRM says it "is currently unconnected (reserved for
future use)" — do not set it.

The QNX-side evidence that this path is the one in use: `winchester-bootreason`
carries `"Power on due to USB ID"`, `"Detected USB charger, holding boot"`,
`"Connected to host, continue boot"`, `"usb_charger_detect"`,
`/pps/services/power/usbconnector`, and it talks **only** i2c + PPS (no MMIO), i.e.
the ID/VBUS state comes from the PMIC, not from a SoC pin.

### 3.5 What QNX does *not* program (verified absences)

* No ULPI register write anywhere (no `USBTLLHS_ULPI` access; the strings that
  mention it are only the interconnect/firewall names `ATTILA_L4CFG_TA_USBTLL` /
  instance names `USBTLLHS_ULPI`, `USBTLLHS_CONFIG`).
* No `CONTROL_USB2PHY` / `CONTROL_USBOTGHS_CONTROL` (or `CM_*_DPLL_USB`) write in
  **any IFS binary** — these are the missing `/base` driver's business; the IFS side
  only *reads* the PMIC to decide the boot reason.
* No USB clock enablement on purpose (§3.3).
* No GPIO for VBUS drive / ID (no `GPIO`+`USB` string co-occurrence in any binary).

### 3.6 Order of operations, as the product performs it

```
ROM/QNX kernel:  PRCM defaults (DPLL_USB locked by some earlier stage or lazily)
IFS:             setup-core-inactive  -> core-inactive PRCM state (USB idle)
                 i2c-omap35xx-omap4   -> /dev/i2c0 = OMAP I2C1 @ 0x48070000
                 pmic_twl6030_cfg     -> CFG_LDO_PD*, SMPS_OFFSET/MULT, PREQ_MASK
                 pmic-winchester-twl6030 (/dev/pmic/regulator)
                 sh pmic-twl6030-ctl_script -> set_trans vusb sleep=ams act=ams
                 sh splash_script -> winchester-bootreason   <-- USB charger/ID gate
/base/scripts/startup.sh -> RIM_usbmgr-Winchester + USB driver (NOT in this dump)
```

### 3.7 i2c addressing note (worth fixing in the board DTS)

The IFS starts three i2c resmgrs:
`-p 0x48070000` → `/dev/i2c0`, `-p 0x48072000` → `/dev/i2c1`,
`-p 0x48350000` → `/dev/i2c3` (QNX `/dev/i2cN` = OMAP `I2C(N+1)`).
`pmic-winchester-twl6030` opens **`/dev/i2c0`**, i.e. the TWL6030 sits on the
controller at **`0x4807_0000` (OMAP I2C1)** with 7-bit slave `0x48`.
`omap4-winchester.dts` uses the correct node (`&i2c1`) but its comment says
"0x48072000", which is the I2C2 address — a comment/bug-detector worth fixing
before USB work, because the TWL6030 USB comparator interrupts come over that same
i2c/IRQ pair.

## 4. Mainline 6.15 DTS recipe (goal 4)

### 4.1 Minimum needed (all inherited, nothing to write)

`omap443x.dtsi` → `omap4.dtsi` → `omap4-l4.dtsi` already provides: the OTG
target-module + `usb_otg_hs` (MUSB, IRQs 92/93), `ocp2scp` + `usb2_phy`
(`ti,omap-usb2`, `usb_phy_cm_clk32k`, `#phy-cells`), the two `control-phy` nodes

nested-IRQ numbers, resolved through the `twl@48` MFD irqchip that the board file
already instantiates at `&i2c1`).

The board file currently has **no USB content at all** — that is the whole gap.

### 4.2 Additions to `omap4-winchester.dts`

```dts
/* The TWL6030 comparator is what tells the OTG port a cable arrived; without
 * it nothing ever writes CONTROL_USBOTGHS_CONTROL and MUSB stays in session-end. */
&vusb {
	regulator-always-on;		/* QNX: set_trans vusb sleep=ams act=ams */
};

&twl_usb_comparator {
	usb-supply = <&vusb>;		/* same as omap4-panda/sdp */
};

&usb_otg_hs {
	dr_mode = "peripheral";		/* first milestone: device only */
	/* usb-phy/phys/phy-names/ctrl-module/multipoint/num-eps/ram-bits all
	 * come from omap4-l4.dtsi; do not restate them. */
	status = "okay";
};

&usb2_phy  { status = "okay"; };
&usbhstll  { status = "disabled"; };	/* no ULPI PHY on this board */
&usbhshost { status = "disabled"; };
```

Notes / gotchas:

* `dr_mode = "peripheral"` makes musb force B-device mode
  (`MUSB_DEVCTL.SESSION` cleared, `drivers/usb/musb/musb_core.c`) which is the
  cheapest way past a missing ID/VBUS comparator chain.
* If the twl6030 comparator probe defers forever (`omap_usb2_set_comparator()`
  returns `-ENODEV` → `-EPROBE_DEFER`), the UDC still registers; only the
  automatic VBUS/ID mail-box updates are missing ⇒ combine with §4.3.
* `usb2_phy` needs its `wkupclk` (`usb_phy_cm_clk32k`); if the 32 kHz source is not
  running in our boot path the PHY power-on will hang — that clock is in
  `CM_WKUP`/32k domain, worth checking early (see §5 M0).

### 4.3 Forcing that is likely required (no PM/clock-domain policy yet)

Mirroring what report 106/107 established for other targets, and the existing
`&mmc2_target` precedent in this very board file:

```dts
/* The USB target-modules are UNLABELLED in omap4-l4.dtsi (0x4a0ab000 is
 * /ocp/.../segment@80000/target-module@2b000).  Either add labels in-tree or
 * reference by full path.  Purpose: never let l3_init_clkdm gate the interface
 * clock between register accesses (same symptom class as the MMC2 stall). */
&usb_otg_hs_target {			/* add this label in omap4-l4.dtsi */
	ti,no-idle;
	ti,sysc-sidle = <SYSC_IDLE_NO>;
	ti,sysc-midle = <SYSC_IDLE_NO>;
};
```

and, if IDLEST still never clears:

```
CM_L3INIT_CLKSTCTRL 0x4A009300  CLKTRCTRL = 2 (SW_WKUP)   # instead of HW_AUTO(3)
CM_L3INIT_HSUSBOTG_CLKCTRL 0x4A009360  MODULEMODE = 1     # forced ENABLED, not HW_AUTO
CM_L3INIT_USBPHY_CLKCTRL   0x4A0093E0  MODULEMODE = 1, [8] OPTFCLKEN_PHY_48M = 1
```

* `clk_ignore_unused` is already in the winchester `bootargs` — keep it: it is what
  stops `clk_disable_unused` from gating the bootloader-armed WDT2, and it also
  protects the lazily-enabled USB clocks from being reaped before probe.
* The 60 MHz / 480 MHz source: if `CM_CLKSEL_USB_60MHZ` (`0x4A008104`) or
  `CM_CLKSEL_DPLL_USB` (`0x4A00818C`) turns out to be unset in our boot path, add
  `assigned-clocks`/`assigned-clock-rates` on `&usb_otg_hs` (`fck` = 60 MHz) or set
  the DPLL by hand early — mainline's DPLL_USB driver will not lock it unless a
  consumer exists.

## 5. Ranked next steps (goal 5)

Observation channel is fixed: DRAM ring console (`earlyprintk`/`keep_bootcon`) plus a
PID 1 that can write `/dev/kmsg`, dump `/proc` and `/sys` into the ring, and survive a

|---|---|---|---|
| **M0** | Prove the block is reachable *at all*: map `0x4A0AB000`, read `OTG_REVISION` (`+0x400`), `OTG_SYSCONFIG` (`+0x404`), USBPHY `0x4A0AD080`..`+0x58`, OCP2SCP `0x4A0AD000`; and read `0x4A009358/60/68/E0` IDLEST[17:16]. Log raw 32-bit values. | Non-`0xFFFFFFFF`/non-zero REVISION; if it hangs or aborts → the target-module clock/power is off ⇒ go to §4.3 forcing before anything else. | – |

## 6. Proven vs inferred

**Proven (static, reproducible from this dump + TRM):**

1. No IFS binary contains a USB host-controller driver, PHY driver, gadget stack or
   USB manager (§1, §3.1).
2. The USB stack is on `/base`, started by `/base/scripts/startup.sh`; the daemon is
   `RIM_usbmgr-Winchester` (§1.2).
3. All OMAP4 USB instance addresses in §2.1 (TRM tables 3-1319, 23-x, 18-194,
   18-591).
4. `setup-core-inactive`/`winch_lcdctl` contain the PRCM clock model with records
   whose `clkctrl` offsets match `CM_L3INIT_{FSUSB,HSUSBHOST,HSUSBOTG,HSUSBTLL,USBPHY}_CLKCTRL`
   exactly (§2.2).
5. `pmic-winchester-twl6030`'s `vusb` entry: regulator id `0x0A`, **no** voltage
   table, and the shipped policy keeps it in ACTIVE/AMS, never OFF (§1, §3.1).
6. The boot chain requires *host present or charger* to continue booting
   (`winchester-bootreason` strings + `splash_script` RC 60 path).
7. TWL6030 is at i2c slave `0x48` on the controller at `0x48070000` (QNX
   `/dev/i2c0`); `omap4-winchester.dts`'s comment "0x48072000" is wrong.
8. `CONTROL_USBOTGHS_CONTROL` reset = `IDDIG|SESSEND` (= "unplugged"), and it is a
   software mail-box, not a hardware strap.
9. The only EHCI user in TabletOS is the radio probe
   (`perform_radio_probe()` → `popen("/sbin/probe_ehci_udev_winchester")` → parse
   `VID=`/`PID=`), i.e. host mode exists only as an *internal modem* path, never as
   a user-facing port.

**Inferred (physically motivated, not proven from this dump):**

1. Only the OTG port is used for the external connector, in B-device mode; EHCI/OHCI
   + TLL are not wired to a user port (no ULPI PHY, no VBUS) — inferred from the
   absence of any ULPI/VBUS-drive artefact plus the product being a tablet with one
   micro-USB. The one host-mode use (radio probe) is inferred to ride HSIC, because
   an internal modem on ULPI would have required visible pins/PHY.
2. The `vusb` 3.3 V LDO feeds the OMAP USBPHY and the TWL USB comparator block.
3. QNX's USB driver does the `CONTROL_USBOTGHS_CONTROL` mail-box + TWL comparator
   dance (it is the only architecturally possible path on OMAP4430; identical to
   mainline's `omap_control_usb_set_mode()`).
4. `MODULEMODE`/`CLKTRCTRL` values in §3.2 (HW_AUTO=2/3 vs forced=1) — the *shape*
   is from the QNX records (`…, 0x60, 0x64, 0x60, 3, …`), the exact per-module
   value is not.

**Not recoverable from this dump (honest gaps):** the DPLL_USB `M/N/M2` numbers, the
per-module `MODULEMODE` QNX actually chose, the ULPI/VBUS pin mux, and every
register write made by the actual USB driver.

## 7. Residual unknowns

1. **DPLL_USB divider values.** `dpll_usb_cfg_allopp` / `…_12` exist as named blobs in
   `setup-core-inactive`, but the record layout past `+0x48` (the `0xF10/0xF15/0xF16/0xF18`
   "register id" words) is not decoded — those ids index a table we did not find.
   ⇒ cheap external fix: read `0x4A00818C`/`0x4A008190` on a live unit (impossible
   here), or trust mainline's CCF.
2. **Which PRCM struct field is which.** The 0x68-byte clock record decodes cleanly
   for name/clock-id/`clkctrl` offset/source-id list, but `+0x44`, `+0x48`,
   `+0x3C..+0x40` are unresolved (candidates: clock-type, idlest bit position,
   optional-clock count). Not needed for §4, flagged so nobody re-derives it blindly.
3. **Whether the `ATTILA_L4CFG_TA_USB*` firewall entries matter.** The names prove the
   platform model contains L4 target-agent (firewall) descriptors for USBFS/
   USBHOSTHS/USBOTGHS/USBPHY/USBTLL, but no register/value pair for them was
   recovered, and the OMAP4 L4_CFG firewalls are background-permissive by default on
   non-secure builds (consistent with report 106/107's L3 firewall pain being in
   L4PER/L4SEC, not L4_CFG). If M0 (register read) aborts with an L3/L4 custom error,
   this moves to the top.
4. **VBUS drive capability.** `CONTROL_USBOTGHS_CONTROL[6] DRVVBUS` is a PHY *output*;
   whether a 5 V boost exists on the board is unknown. Blocks any host/OTG-A claim.
5. **TWL6030 ID pin wiring.** The boot reason reports "Power on due to USB ID", so the
   connector has an ID contact, but whether it is grounded on the shipped cable/dock
   (A-device) is unknown.
6. **`/sbin/probe_ehci_udev_winchester`** — invoked by `nvram_resource_manager`'s
   `perform_radio_probe()` (§2.2). What it does internally (udev rule? EHCI port
   power? HSIC mode select?) is unknown, as is the modem's USB VID/PID. If host mode
   ever matters (4G SKU, modem recovery), that file on `/base` is the thing to read;
   for the device-mode milestone it is irrelevant.
