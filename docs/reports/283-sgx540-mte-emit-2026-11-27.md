# Report 283 — the stream diff: `MTE_EMIT` is the render stall, not the PDS address

Date: 2026-11-27 (session 82, Linux-era 76).  Bench session on the reference
unit.  Follows report 282 (session 79) and the session-80/81 captures.  Two
measurement boots; six render submissions; no media writes.

**Headline: the DDK's own reference frame builder shows the one structural
difference the previous sessions had not varied — every PDS address in the VDM
stream is `PDSExecBase`-relative, not absolute — and emitting it changes the
stream byte-for-byte but not the stall.  A one-variable bisection of the primary
state record then localizes the wall: it is `MTE_EMIT` (b17).  Clearing that bit
wakes the TE; the vendor's exact state-emit *program* form does not help, so the
state-copy task never reaches its emit.**

## 1. What the reference stream actually is

`eurasia/unittests/sgx_render_flip_test/sgx_render_flip_test.c` builds one kick
as three records: a primary MTE **state** record (`srft_WriteMTEStateToVDM`,
2 words), an **index list** (`srft_WriteIndexListToVDM`, 6 words), and a
**terminate** (`srft_WriteMTETerminateToVDM`, 2 words).  Our 28-word stream has
the same three record classes plus a vertex-secondary state record and an
`empty_state` record, and its state record's fields already match the reference
with the 540's `PARTITIONS` (session 80/81).  The fields the previous sessions
varied and excluded (USEPIPE, PARTITIONS, PDSDMADEPENDENCY, the segment size,
the USE-program variables) are genuinely divergent where they were reported
divergent, and none moves the stall.

## 2. The one structural difference: the PDS address is base-relative

On a core without `SGX_FEATURE_EDM_VERTEX_PDSADDR_FULL_RANGE` — the SGX540 —
the state-record and index-list base-address fields hold
`(program_addr - PDS_EXEC_BASE) >> 4`, where `PDS_EXEC_BASE` is the PDS-pixel
heap base.  Both vendor clients apply it:

* `srft_WriteMTEStateToVDM` subtracts `psSGXInfo->uPDSExecBase` immediately
  before writing the record (`:2488`), and so do the terminate (`:3142`) and the
  index list (the vertex PDS address at `:3017`/`:3064`);
* the GLES2 client subtracts it at `opengles2/validate.c:387-388` (the state
  PDS and SA-update addresses) and `:3062-3063` (the record itself).

The clone's own `docs/UAPI.md:638` states the same rule for this stack.  Our
generator already subtracted it for the pixel PDS words *inside* the state
block (`pds_word()` writes `(addr - heap_base[H_PDSPIXEL]) >> 4`) but wrote the
record headers (`0x40000000 | addr>>4`) and the index-list base absolutely.

**Measured.**  One tool built to emit the relative form everywhere
(`ebf463f3…`): the stream becomes `400c0120 0e022403 80c00003 …` (state[0]'s
field `0xc0120` = `0x0e801200 - 0x0dc00000`, resolving to the same program), and
the render's timeout signature and whole mid-hang state are **identical** to the
baseline — `CLKGATESTATUS 0x001800f0` (TE asleep), `TE_SCREEN 0xf007`,
`DPM_PAGE_STATUS 0`, `EVENT_STATUS 0`, `BIF_FAULT 0`, `0/1 frames right`.  So
the address encoding is a real divergence from the vendor and **not the wall**.
Reverted to absolute (production) and proved: the default build emits the 28
words `40e80120 0e022403 80c00003 …` again.

## 3. The wall is `MTE_EMIT` (b17)

The primary state record is `SD` (b25) | `MTE_EMIT` (b17) | `USEPIPE_1` |
`PARTITIONS`; the vertex-secondary record that **does not** stall is
`SECONDARY` (b8) | `USEPIPE_ALL` (no `MTE_EMIT`).  One-variable variants of the
primary record's second word, one boot, read mid-hang:

| variant | `CLKGATESTATUS` (t=0.5/1.4 s) | TE (b3) |
|---|---|---|
| baseline | `0x001800f0` | asleep |
| **`MTE_EMIT` b17 cleared** | **`0x001800f8`** | **awake** |
| `SD` b25 cleared | `0x001800f0` | asleep |
| `USEPIPE_ALL` (7<<13) | `0x001800f0` | asleep |

Reproduced (two baselines `0x001800f0`, two `NO_MTEEMIT` `0x001800f8`).  `b3`
set is the same signature as removing the state loads (session 81).  So the VDM
waits for the MTE state **emit** that the state-copy task is supposed to send,
and none arrives.

## 4. The vendor's emit form does not fix it

`USEGenWriteStateEmitProgram` (`codegen/usegen/usegen.c:592-700`) on a 540 is the
`mov o,pa` fragment + one `EMITMTE` with flags `EURASIA_USE1_END`, target
`EMIT_TARGET_MTE` (`emit.t1`), `mteCtrl = 0`, `src1 = ui32NumWrites`, and no
`phas`, no prologue, no VCB.  A tool built with exactly that form
(`MKUSSE_VENDOR_STATE=1`, `a0d48593…`) **still stalls** (`0x001800f0`, TE
asleep).  So the emit instruction is not the problem — the task does not get
there.

## 5. What is left

The remaining suspects are the PDS state-copy program's **launch of the task**:
its `DOUTD` (the state DMA) or its `DOUTU` (start the USSE task).  The vendor's
compiled `pds_mte_state_copy` (`…/intermediates/pds_mte_state_copy/…h`) is a
23-word looped program (`17000CE0`) whose `DOUTD` uses `src2` row **0x18**
(`07030203`) — ours is a flat `TST;BRA;DOUTD ×2;DOUTU` with `src2 = 0`.  Two
experiments follow directly:

1. a **GPU-side marker**: a store of a fixed constant at the top of the
   state-emit USE task (and/or right after the `DOUTD`), read from the PDS-vertex
   ring after the render — this says whether the task runs at all;
2. patch our state-copy program to the **vendor's compiled form** (our DMA
   source and USE address), which is the one program-content difference never
   submitted.
