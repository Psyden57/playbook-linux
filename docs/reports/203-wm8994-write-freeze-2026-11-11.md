# 203 — The WM8994 "write blocker" is the datasheet's clocking rule, not a broken bus

Date: 2026-11-11 (session 40, Linux-era 34).
Bench: unit on our Linux image `0xF97CD9C7` (region 0) + the audio/OSS rootfs
`968d2f20…` (region 1).  All codec access was the console (`i2ctransfer -f -y 3`
on `i2c-3` at `0x1a`) plus the driver's regmap tracepoints; no RPMB, NVRAM or MCT
write.

## 0. Headline

> **Corrected by report 204 (same session):** the reference's FLL1 **is locked**
> on this unit (`0x732 = 0x6020` from MCLK1), so "MCLK1 does not clock" below
> means "does not clock **under our Linux image**".  The register-freeze
> mechanism in this report stands; §5's inference was too strong.

* **The codec does not "stop accepting writes after boot".**  It stops accepting
  control-register writes whenever **AIF1CLK_ENA = 1 while its selected clock
  source is not running**.  That is a documented WM8994 rule, quoted in §4.
* **The driver is in exactly that state from boot:** the DAPM `AIF1CLK` supply
  powers the clock with `AIF1CLK_SRC = MCLK1`, and MCLK1 does not clock on this
  unit.  So the codec is frozen before the FLL is ever configured, and the FLL
  configuration written at `hw_params` is silently dropped.
* **The escape hatch works and is measured:** writing `0x200 = 0x0000` (clear
  `AIF1CLK_ENA`) restores register access immediately; a software reset does the
  same.  This is the datasheet's own remedy ("AIF1CLK_ENA must be set to 0 for
  control register access").
* **MCLK1 is dead, measured through the codec:** with the 1917 FLL1 programme
  (REFCLK_SRC = MCLK1, `REFCLK_DIV = 0`, `FRATIO = 0`, `OUTDIV = 7`, `N = 7`,
  `K = 0xAE14`) every FLL register reads back correctly and `0x732` bit 5
  (FLL1_LOCK_STS) stays 0.  A *free-running* FLL1 (the datasheet's no-reference
  mode) also produces no usable AIF1CLK here.
* **So the open problem is one clock, not a write path.**  Either MCLK1
  (AUXCLK1 → `fref_clk2_out` → codec MCLK1) must be made real, or AIF1CLK must
  be enabled only once a live source exists (BCLK), which the mainline ASoC
  ordering does not currently allow (see §6).

## 1. The measurement that reframes the problem

At the first shell prompt after a normal boot, with no stream open:

```
i2ctransfer -f -y 3 w2@0x1a 0x00 0x00 r2   ->  0x89 0x94    (reads: fine)
i2ctransfer -f -y 3 w2@0x1a 0x06 0x01 r2   ->  0x00 0x01
i2ctransfer -f -y 3 w4@0x1a 0x06 0x01 0x00 0x20
i2ctransfer -f -y 3 w2@0x1a 0x06 0x01 r2   ->  0x00 0x01    (write ignored)
```

Now write AIF1CLK_ENA = 0 and repeat:

```
i2ctransfer -f -y 3 w4@0x1a 0x02 0x00 0x00 0x00   # R512 = 0  (AIF1CLK_ENA = 0)
i2ctransfer -f -y 3 w4@0x1a 0x06 0x01 0x00 0x20
i2ctransfer -f -y 3 w2@0x1a 0x06 0x01 r2           ->  0x00 0x20    (write lands)
```

**Clearing one bit restores the whole register map.**  Writes then keep landing
for at least 65 s of idle (measured at t = 0, 5, 15, 35, 65 s), so the freeze is
not a time-out or a bus/PM artefact.

## 2. The freeze is caused by enabling AIF1CLK with a stopped source

Starting from a thawed codec (R512 = 0), with a probe register that is known to
accept writes (`R0x601`, bit 5 = `0x0020`):

| step | write | probe `R0x601` | meaning |
|---|---|---|---|
| A | `R512 = 0x0000` | `0x0020` lands | thawed |
| B | `R512 = 0x0001` (ENA=1, SRC=MCLK1) | ignored | **frozen here** |
| C | `R0x220 = 0x0001` (FLL1 ENA) | — | n/a |
| D | `R0x221 = 0x2b02` | — | n/a |
| E | `R512 = 0x0011` (ENA=1, SRC=FLL1, FLL unlocked) | ignored | frozen |

So the trigger is precisely **`AIF1CLK_ENA = 1` with a source that is not
running** — MCLK1 (dead) or FLL1 (unlocked).  Writing `0x11` reads back as
`0x11`; it is the *subsequent* writes that are dropped, and reads keep answering
(stale values inclusive — `R0x601` keeps my last value).

A software reset (`R0x0000 = 0x0000`) also thaws it: after the reset
`R0x601`, `R0x300` and `R0x200` read their defaults and a write to `R0x601`
lands.  That is why a module reload "fixed" the symptom in earlier sessions.

Ordering detail that cost time: from the frozen state, a write of `0x0011` to
`R512` is itself ignored, but a write of `0x0000` is **not** — clearing ENA is
always accepted.  It is the only register write that behaves this way.

## 3. The boot path puts the codec in that state

The tracepoints (`/sys/kernel/debug/tracing/events/regmap/regmap_reg_write`)
show a clean stream start (28 writes, `pbplay 5 0`):

```
200=1                      <- AIF1CLK_ENA with SRC=MCLK1 (already frozen here)
220=0 221=2b02 223=b00 220=1          <- FLL1 for 8 kHz
200=11 d0=1400 210=3 200=1 ...        <- AIF1CLK to FLL1
220=0 221=700 223=800 220=1           <- FLL1 for 48 kHz
200=11 210=83 200=1 200=11 420=0      <- AIF1CLK to FLL1, DAC unmute
```

Read back during the stream: `0x220 = 0`, `0x221 = 0`, `0x223 = 0`,
`0x224 = 0x0c80` (reset), `0x732 = 0x6000` (no lock) — **none of the FLL
writes landed**, while the driver's cache holds `0220: 0001`, `0221: 0700`,
`0223: 0800`, `0224: 0c83`.  That divergence is what report 200 saw; the cause
is here, not in `regmap_update_bits()`.

The freeze exists before the stream because the codec's DAPM `AIF1CLK` supply
powers up with the rest of the playback path (`rcS` sets `DAC1 Switch` and the
output switches with `pbmix`), and `AIF1CLK_SRC` still has its reset value,
MCLK1.

## 4. The datasheet rule

WM8994 Rev 4.6, "Clocking and Sample Rates → Control Interface Clocking":

> Register map access is possible with or without a system clock. Clocking is
> provided from SYSCLK; the SYSCLK_SRC register selects either AIF1CLK or
> AIF2CLK as the applicable SYSCLK source.
>
> When AIF1CLK is the SYSCLK source (ie. SYSCLK_SRC = 0), and AIF1CLK_ENA = 1,
> then an active clock source for AIF1CLK must be present for control interface
> clocking. **If the AIF1CLK source is stopped, then AIF1CLK_ENA must be set to
> 0 for control register access.**

That is the whole of the "write blocker".  (The datasheet's other ignore rule —
`/POR` asserted, AVDD2 < 1.15 V or DCVDD < 0.56 V — is *not* the cause: a POR
clears the register file, and here it retains the values written before the
freeze.)

## 5. MCLK1 is not clocking — measured with the FLL as the detector

With AIF1CLK_ENA = 0 (so the register map is writable), the 1917 FLL1
programme was written and read back:

```
R0x220 = 0x0001   R0x221 = 0x0700   R0x222 = 0xae14
R0x223 = 0x0700   R0x224 = 0x0c80                 (all read back)
R0x732 = 0x6000   -> FLL1_LOCK_STS (bit 5) = 0
```

So the FLL registers are writable and the FLL is enabled; it simply has no
reference to lock to.  The SoC side reads:

```
0x4A30A314 (SCRM AUXCLK1) = 0x00020100
0x4A10019C (CORE pad 0x19C) = 0x41180000  -> pad 0x19C = mux 0 (fref_clk2_out)
```

`0x00020100` decodes against `omap44xx-clocks.dtsi` as: gate on (bit 8), source
mux bits 2:1 = 0 (`sys_clkin_ck`), divider bits 19:16 = 2 (÷3).  With a 38.4 MHz
`sys_clkin` that is the expected 12.8 MHz, and the clock framework reports
`auxclk1_ck 12800000` with the codec as consumer.  The pad is in the right mux.
**Yet no clock reaches the codec's MCLK1.**  That is now a board/pin fact, not a
register-programming one.

The datasheet's free-running FLL is not an escape either, measured:

```
R0x221 = 0x0700  (OUTDIV = 7)
R0x224 = 0x0cc0  (FRC_NCO = 1, FRC_NCO_VAL = 0x19)
R0x220 = 0x0002  (OSC_ENA) then 0x0003 (OSC_ENA | ENA)
R0x732 = 0x6000  -> no lock
R512   = 0x0011  -> register map freezes
```

## 6. What this means for the Linux driver

* **Never leave `AIF1CLK_ENA = 1` with a stopped source.**  On this board that
  means MCLK1, until it is proven.  The codec driver's own DAPM does it anyway,
  so a board-level workaround has to either keep the pin off or supply a live
  clock first.
* **The mainline ASoC order cannot do it as-is.**  `__soc_pcm_prepare()` runs
  the link `.prepare`, the component `.prepare`, the DAI `.prepare` and *then*
  `snd_soc_dapm_stream_event(STREAM_START)`; the CPU DAI's BCLK only starts in
  `.trigger(START)`, one step after the DAPM power-up that sets
  `AIF1CLK_ENA = 1`.  With a dead MCLK1 the codec is frozen before BCLK can
  exist, so the FLL cannot lock and AIF1CLK from FLL1 is never valid.
* **The two workable shapes**, in order of preference:
  1. **Make MCLK1 real.**  This is the 1917 design and it removes every ordering
     problem.  It needs a pad/clock or board answer, not a driver change.
  2. **Hold `AIF1CLK` off until BCLK runs**: keep the codec's `AIF1CLK` supply
     disabled, clear `R512` in the machine `.prepare` (thaw), configure FLL1 from
     BCLK and set `AIF1CLK_SRC = FLL1` in `.trigger(START)` once the McBSP is
     running, then set `AIF1CLK_ENA = 1` and verify `0x732` bit 5 = 1.  This is
     the experiment to run next; it needs the DAPM pin held off, because
     otherwise the stream event re-enables the clock with MCLK1 selected.
* **Free-running FLL1 is a diagnostic, not a fix** on this unit: it produced no
  lock and no usable AIF1CLK.
* **Operational rule for the bench:** a frozen codec is not broken.  `R512 = 0`
  or a software reset restores it; do not chase the driver's cache.

## 7. Corrections to report 200

* "The chip stops accepting register writes after boot" — it is not *after
  boot*; it is *while `AIF1CLK_ENA = 1` with a stopped source*, which happens to
  be true from boot onward.
* "`regmap_update_bits()` skips the write because the cache already matches" —
  the cache is stale, but the write would be dropped by the codec even if it
  were issued.  The cache divergence is a second-order effect.
* The direct `i2ctransfer` writes in report 200 "returning success without
  changing the register" are exactly this rule.

## 8. Method note (a trap for the next session)

Two early tests of mine concluded "the driver's writes are dropped" while the
codec was **already frozen** from a previous experiment, so they proved nothing.
Whenever a write is being tested, first thaw (`R512 = 0`) and verify with a
write/read pair on a scratch register whose bits are known writable
(`R0x601`, bit 5 works), then run the test.  Also remember reserved bits read
back 0: writing `0x223 = 0x0008` looks "ignored" but the N field lives at
bits 13:4.
