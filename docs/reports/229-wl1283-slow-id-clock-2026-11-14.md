# 229 — A slower identification clock: the card answers at none of 400/300/200/100 kHz (`CTO` only)

Date: 2026-11-14 (session 50, Linux-era 44).
Bench: experiment image **`0x91E22899`** (kernel `7.3.3` #58) flashed to region
0 (block `0x825`) and booted; the reverted image **`0x17C2E119`** (#59) was
flashed back afterwards.  No NVRAM/MCT/RPMB write.  Capture
`docs/captures/wl1283-slow-clock-2026-11-14.txt`.

## 0. Headline

**The "card is slower than the 160 µs `CTO` window" hypothesis is dead.**  The
MMC core's identification ladder tried **400 kHz, 300 kHz, 200 kHz and
100 kHz** and every attempt ended in `attach_sdio no` with
`STAT = 0x00018000` — `CTO` **only** (`CCRC = CEB = CIE = 0`, `RSP0 = 0`,
`PSTATE` `CLEV = 1`).  At 100 kHz the timeout window is 64 card clocks =
**640 µs**, four times the previous 160 µs, and there is still no response.
`CMD0` (a no-response command) reports no error throughout.

## 1. The mechanism (`f_min` and `f_init` are not the same thing)

The first draft of this experiment was going to lower `f_min` and expect the
card to be *identified* at 100 kHz.  That is not what happens, and the
distinction matters:

* `mmc_start_host()` sets `host->f_init = max(min(freqs[0], f_max), f_min)`.
  With `freqs[0] = 400000`, lowering `f_min` to 100000 still leaves
  `f_init = 400000` — the **initial power-up** stays at 400 kHz.
* The retry ladder is `mmc_rescan()`'s
  `static const unsigned freqs[] = { 400000, 300000, 200000, 100000 };`,
  clamped to `max(freq, f_min)`, and it stops at `if (freqs[i] <= f_min) break;`.
  With the shipped `f_min = 400000` every entry clamps to 400 kHz, so **only
  400 kHz is ever tried**.  Lowering `f_min` to 100000 makes the loop try
  400/300/200/100.

So the change is exactly one behavioural variable — the rescan ladder's floor —
and the log confirms it (`PBC: mmc4 try 400000Hz … 300000 … 200000 … 100000`).
The initial power-up is still 400 kHz; the card gets a lower clock only on the
later retries.

`calc_divisor()` gives `dsor = DIV_ROUND_UP(fclk, ios->clock)`; MMC5's
functional clock is 48 MHz (logged `PBX: mmc4 probe-pm fck=48000000`), so
100 kHz is `CLKD = 480`, well under the 1023 maximum, and the decode
`SYSCTL = 0x000e7807` shows `CLKD = 0x1E0 = 480`.

## 2. The instrumentation

The decoded-trace patch archived at
`kernel/archive/wl1283/measurement-instrumentation-2026-11-14.patch`
(`PBX` at `start_command`, `PBIRQ` on the error IRQ, `PBCMD` in
`mmc_wait_for_cmd`) was re-applied so each attempt reports its bus state and
decoded error.  It is logging only; the one behavioural change is `f_min`.

## 3. Result — all four frequencies

```
PBC: mmc4 try 400000Hz (f_min=100000 f_max=24000000 f_init=400000 ios.clock=400000)
PBC: mmc4 attach_sdio no
PBC: mmc4 try 300000Hz (f_min=100000 f_max=24000000 f_init=300000 ios.clock=0)
PBC: mmc4 attach_sdio no
PBC: mmc4 try 200000Hz (f_min=100000 f_max=24000000 f_init=200000 ios.clock=0)
PBC: mmc4 attach_sdio no
PBC: mmc4 try 100000Hz (f_min=100000 f_max=24000000 f_init=100000 ios.clock=0)
PBC: mmc4 attach_sdio no
mmc4: Failed to initialize a non-removable card
```

At 100 kHz the bus and the error decode are unchanged:

```
PBX:   mmc4 CMD5 arg=00000000 reg=05020001 SYSCTL=000e7807 CEN=1 ICE=1
       CLKD=480 HCTL=00000b00 SDBP=1 SDVS=5 CON=00000600
PBIRQ: mmc4 status=00018000 CTO=1 CCRC=0 CEB=0 CIE=0 DTO=0 DCRC=0 DEB=0
       BADA=0 PSTATE=01f40001 RSP0=00000000 CMD=05020001
PBCMD: mmc4 op=5 arg=00000000 flags=000002e1 err=-110 resp0=00000000
```

`CMD52` (SDIO reset) times out identically at 100 kHz, and `CMD0` returns
`err=0` (it asks for no response, so this only shows the controller accepted
it).

The actual divisor per ladder entry, from the decoded trace (fclk = 48 MHz):

| ladder | `CLKD` | `SYSCTL` | actual card clock | `CTO` window |
|---|---|---|---|---|
| 400 000 | 120 | `0x000e1e07` | 400 kHz | 160 µs |
| 300 000 | 160 | `0x000e2807` | 300 kHz | 213 µs |
| 200 000 | 240 | `0x000e3c07` | 200 kHz | 320 µs |
| 100 000 | 480 | `0x000e7807` | 100 kHz | **640 µs** |

All four have `CEN = ICE = 1`, `SDBP = 1`, `SDVS = 5` (1.8 V), `CON = 0x600`.

## 4. A side finding: neither `0x8C` nor `0x60` is `CLK32KG`

The handoff's one newly-open candidate was the WL1283's 32.768 kHz SLOW_CLK,
with the warning that the "`CLK32KG` is ON in both OSes" conclusion was based on
register `0x8C` — which is **VAUX3** (KNOWN-ISSUES §3.30).  §3.30 then proposed
**`0x60`** as "the first candidate".  Reading the QNX regulator table
(report 221 §1.2) settles that `0x60` is **VCORE3's `CFG_STATE`** (`vcore3`
base `0x5E`, so GRP/TRANS/STATE = `0x5E`/`0x5F`/`0x60`).  The live read
`0x5E/0x5F/0x60 = 07/05/55` is that resource — group 2, APP 1, state ON — not a
clock.  So **both addresses cited in the docs are wrong**, and the 32 kHz still
has not been read.

The TWL6030 datasheet (local `hardware/twl6030.pdf`, `SWCS045C`) says
`CLK32KG` is a **software-controlled clock resource** and that it is **ON from
the startup sequence** (Table 11 and the `TWL6030B107` startup figure, cited in
report 192 §7); the register-address table is not in the PDF's extractable
text.  Since neither OS writes it (the regulator resmgr has no clock resource;
`startup-playbook` writes no such register; Linux does not expose it), the 32 k
is expected to be on in both — but that is a **datasheet-and-static**
conclusion, not a measurement, and the address must be taken from a register
map before any read is trusted.

## 5. Revert and proof

* `drivers/mmc/host/omap_hsmmc.c`: `OMAP_MMC_MIN_CLOCK` back to `400000`, the
  `PBX` block and the `linux/string.h` include removed.
* `drivers/mmc/core/core.c`: the `PBCMD` block and the `linux/string.h` include
  removed.
* Proof: both files were re-generated from a pristine 7.3.3 copy with the
  shipped `kernel/patches/0001-playbook-winchester-7.3.3.patch` applied
  (`git apply --include=…`) and are **byte-identical** to
  `local/kernel-tree/` (`cmp`, both `IDENTICAL`).  The board DTS was not
  touched this session and is byte-identical to `kernel/source/`
  (`cmp`, `DTS_IDENTICAL`).
* The reverted image was rebuilt and flashed; it boots as kernel **#59**,
  `crc 0x17C2E119`, and the probe is back to a single 400 kHz attempt ending
  `attach_sdio no`.

## 6. What this closes, and what is left

**Closed.**  "The card is present but slower than 160 µs."  A card that needs
more than 640 µs to answer `CMD5`/`CMD52` is not a plausible WL1283; and the
answer is *no response at all*, not a corrupt or late one.

**Left.**  The card does not answer across 100 kHz – 400 kHz (this session) or
24 MHz (session 35's H1), while the same unit's chip runs under the reference
driver.  That is the signature of a chip whose SDIO function is not
enabled/awake, not of a host timing problem.  The next reference-first
measurement is the **live MMCHS5 state on the reference** at the moment
`ti0` comes up (report 218 listed that block as one of the two never-captured
classes), plus any unmeasured TWL/clock resource; and the QNX-in-Linux harness
(handoff 0b/c) is the way to execute the reference's exact sequence.
