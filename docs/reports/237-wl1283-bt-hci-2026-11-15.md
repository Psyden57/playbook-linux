# 237 — The WL1283's BT core answers: the UART2 CTS/RTS pads were in safe mode

Date: 2026-11-15 (session 52, Linux-era 46).
Bench: image **`0xDD66D8C3`** + region-1 rootfs **`49e318bf…`** (43 modules).

## 0. Headline

**The Bluetooth core answers HCI.**  `pbhci` sends `HCI_Reset` (`01 03 0c 00`)
and the chip replies `04 0e 04 01 03 0c 00` (Command Complete).  The blocker was
not `BT_EN`, the UART clock or the TX/RX pads — it was the **CTS/RTS half of the
UART2 pad pair**: `0x4A100118` was left in the bootloader's **safe mode**
(`0x011F011F`, mux 7) while the reference's idle value is **`0x00000118`**
(both halves muxed to UART2).  Muxing them makes the chip answer immediately.

With the pads in the DTS, the H4 line discipline attaches and **`hci0`
appears**; the kernel's Bluetooth core then exchanges commands with the chip
(§4).

## 1. How it was found

1. Session 50's probe (trap 234) drove `BT_EN` correctly and still got silence.
   Session 52 repeated it with `CLK32KG` on and the WLAN core up — still silent.
2. The reference RE (report 216) lists everything `devc-seromap-winbt` touches:
   `0x4A009548` (`CM2_L4PER_UART2_CLKCTRL` = 2), `0x4A100118` (the **CTS/RTS**
   pair) and `0x48059000` (GPIO4).  `0x4A100118` is the odd one out; the driver's
   "force-RTS" devctl muxes the RTS half to GPIO and drives GPIO4_28.
3. Reading our own pads showed **`0x4A100118 = 0x011F011F`** — mux 7 (safe
   mode) on both halves, exactly the state the reference never leaves it in.
4. Writing `0x00000118` at runtime and re-running the probe produced the reply
   on the first attempt.

The TRM confirms the encoding: `0x118` is
`CONTROL_CORE_PAD0_UART2_CTS_PAD1_UART2_RTS[15:0]` (CTS) and `[31:16]` (RTS), so
the reference's `0x00000118` is CTS = `0x0118` (mux 0, pull-up, input enabled)
and RTS = mux 0.  Ours now match.

## 2. The fix

`kernel/source/omap4-winchester.dts`, `uart2_pins` (pinctrl-single is 16-bit
wide, so the pair is two halfword entries):

```dts
OMAP4_IOPAD(0x118, 0x0118)	/* uart2_cts  (in, pull-up) */
OMAP4_IOPAD(0x11a, 0x0000)	/* uart2_rts  (out) */
OMAP4_IOPAD(0x11c, 0x4118)	/* uart2_rx  (in, pull-up) */
OMAP4_IOPAD(0x11e, 0x0000)	/* uart2_tx  (out) */
```

After a both-region flash the pad reads `0x00000118` at boot and the probe
answers **without any runtime poke** — the fix is durable.

**Why it matters:** with RTS never muxed, the chip's CTS input floats and it
never turns the transmitter around.  That is also why the reference implements
a "force-RTS" path at all.

## 3. The probe (`rootfs/hci.c` → `pbhci`)

```
pbhci [device] [baud] [--no-pulse] [--tries N]   HCI_Reset round trip
pbhci [device] --attach [--hold S]               N_HCI + HCI_UART_H4 -> hciN
pbhci --inquiry [S]                              mgmt power + one inquiry on hci0
```

`--attach` sets `TIOCSETD` to `N_HCI` and `HCIUARTSETPROTO` to `HCI_UART_H4`
(the two ioctls `hciattach` uses) and holds the descriptor open; the kernel then
creates `/sys/class/bluetooth/hci0`.

## 4. What the kernel does with it

`hci0` is created and the core is initialised.  The only messages are benign:

```
Bluetooth: hci0: unexpected cc 0x201c length: 5 < 9
Bluetooth: hci0: Opcode 0x201c failed: -38
```

`0x201c` is a TI vendor op that `hci_uart` sends generically; the chip answers
with a short Command Complete.  The important part is that **commands go out and
answers come back**, i.e. the transport works in both directions.

## 5. What is left for BT

1. **Power the controller.**  `HCIDEVUP` (`_IOW('H', 201, int)`) returns
   **`ENOSYS`** on this kernel, so the device stays `DOWN` and an inquiry fails
   with `Network is down`.  The modern route is the **mgmt** channel
   (`HCI_CHANNEL_CONTROL`, `MGMT_OP_SET_POWERED` 0x0005); the probe's first
   attempt at it did not report a status, so it needs debugging (or BlueZ's
   `bluetoothd`/`bluetoothctl`, which use mgmt).
2. **The service pack.**  The ROM answers HCI, but the WL1283's own service
   pack is `local/work/1917/base/lib/firmware/bluetooth/WL1283.bts` — per report
   216 it is 315 HCI commands (227 × `0xFF05` write-memory-block, 56 771 bytes
   of patch RAM, then `0xFD09` "release Cortex Reset" and `0xFDA8` "enable
   Cortex Sleep").  A userspace loader over H4 is the next tool.  Note the
   handoff's earlier preference for linux-firmware's `TIInit_7.2.31.bts` is
   **unverified** — the reference's file is the one that matches this chip.
3. **A stack.**  Scanning/connecting needs either BlueZ (`bluetoothd` + mgmt)
   or the probe's own HCI socket path once power works.
