# 214 — E10: the WM8994 is on McBSP3; the two-engine Linux path plays stereo at 48 kHz (session 46)

Date: 2026-11-13 (session 46, Linux-era 40).
Bench: the unit is on **our Linux image** region 0 `0xF8BADFF3`
(`0x93993C` B, kernel `7.3.3` **#42**) and region 1 rootfs **`c0719d28…`**
(the stereo fix).  The oracle (1917 minimal IFS) was booted for the routing
probe and the unit was returned to Linux.  No NVRAM/MCT/RPMB write; the
image's own `/init` top-up ran at each boot.

## 0. Headline

**Audio works: `pbplay`'s 440 Hz tone is loud in both ears at 48 kHz ±1 %.**
Two corrections made it happen, and both are now proven:

1. **The WM8994's AIF1 is on McBSP3, not McBSP1/2.**  The oracle's own
   routing log is `AIF 0 Downlink: MM_DL_PORT->MM_EXT_OUT_PORT->MCBSP3`;
   McBSP3 is the only McBSP whose L4_ABE target is active during playback,
   and its pads are the PDM group in mode 1 (`0x106/0x108/0x10a/0x10c` =
   `0x0109/0x0009/0x0109/0x0109`).  `abe_mcbsp1_dx` is a different route
   (the driver's `AIF 4 Downlink: MCBSP1`), not the codec.
2. **The `omap-mcbsp` hw_params guard skipped the stereo reconfiguration.**
   The OSS layer first opens the stream mono at the final rate/width; the
   later 2-channel call returned early because the guard compared only
   `active_rate`/`active_width`.  `XCR2` stayed `0x0041` (`XPHASE` clear),
   so the left slot played and the right was silent.  Comparing the channel
   layout (`XPHASE`) as well reconfigures on the second call; `XCR2` becomes
   `0x8041` and both slots play.

## 1. The oracle: which engine is the codec on

Booted `local/work/ifs-shim-sealed.ifs` at `0x825`, started `io-audio` and
played `/tmp/long30.wav`.  The driver's slog gives the routing:

```
AIF 0 Downlink: MM_DL_PORT->MM_EXT_OUT_PORT->MCBSP3
AIF 0 Uplink:   MCBSP3->MM_EXT_IN_PORT->MM_UL2_PORT
AIF 3 Downlink: MCBSP2
AIF 4 Downlink: MCBSP1
```

The codec during playback: `R0x302 = 0x4000` (AIF1 master), `R0x300 =
0xc018` (DSP_A), `R0x200 = 0x0011`, `R0x732 = 0x6020` (FLL1 locked),
`R0x304 = 0x0040` (AIF2 slave).

Pads during playback (the full CORE range, not just 0xF4–0x100):

| pad | value | meaning |
|---|---|---|
| `0x4A1000F4` | `0x0100000F` | `abe_mcbsp2_clkx` `0x0100` in |
| `0x4A1000F8` | `0x000F1108` | `abe_mcbsp2_dr` in; `abe_mcbsp2_dx` safe |
| `0x4A1000FC` | `0x01000100` | `abe_mcbsp2_fsx` in; `abe_mcbsp1_clkx` in |
| `0x4A100100` | `0x00001108` | `abe_mcbsp1_dr` in; `abe_mcbsp1_dx` **out** |
| `0x4A100104` | `0x01090100` | `abe_mcbsp1_fsx` in; **`abe_mcbsp3_dr` `0x0109` in** |
| `0x4A100108` | `0x01090009` | **`abe_mcbsp3_dx` `0x0009` out**; **`abe_mcbsp3_clkx` `0x0109` in** |
| `0x4A10010C` | `0x000F0109` | **`abe_mcbsp3_fsx` `0x0109` in**; `abe_clks` safe |

The McBSP3 register block (`memdump3 49026000`) reads while it plays:
`SPCR2 = 0x3/0x5` (XRST, no GRST/FRST), `SPCR1 = 1`, `SRGR2 = 0x103f`
(`FSGM = 1`, `CLKSM = 0`), `SRGR1 = 0x0f03`, `PCR0 = 0x3`
(`CLKXM/FSXM/CLKRM/FSRM` clear → **consumer**), `XCR1/XCR2 = 0x140/0x1`.
McBSP1 and McBSP2 user reads `SIGBUS` (their L4_ABE targets are idle); only
McBSP3's target is active.

So the reference's port is a consumer of the **codec's** AIF1 clocks, on the
McBSP3/PDM pad group, and the card's `MM_DL` data goes out `mcbsp3_dx`.
E6's "`abe_mcbsp1_dx` is the codec's DACDAT" reading was the other route.

## 2. The Linux design that works

The card has two ASoC links (both managed by `playbook-wm8994.c`):

* **Link 1 — clocks/codec:** `40124000.mcbsp` + `wm8994-aif1`,
  `I2S | CBC_CFC | NB_NF`.  This is E5: McBSP2 is the bit/frame provider,
  the codec is the AIF1 slave, FLL1 is referenced from our BCLK.  The clock
  link is the only stream that needs to run; `AIF0`'s rate is 48 kHz.
* **Link 2 — data:** `40126000.mcbsp` + `wm8994-aif2`,
  `I2S | CBP_CFP | NB_NF`.  McBSP3 is a clock **consumer** of the same
  BCLK/LRCLK net; its DX is the codec's AIF1 DACDAT.  `wm8994-aif2` is only
  an ASoC stand-in that negotiates S16 (a dummy codec drags the format to
  U8); the physical data still enters the codec on AIF1, whose mixer
  selects `AIF1DAC1` (`R0x601/2 = 1`).

Board DTS: `mcbsp3_pins` uses the oracle's pad values
(`0x106 = 0x0109`, `0x108 = 0x0009`, `0x10a = 0x0109`, `0x10c = 0x0109`);
`&mcbsp3` is enabled; `&mcbsp1` is **disabled** (its DX is the other route);
`mcbsp2_pins` stays the E5 clock output group.

Test: run the clock link on `/dev/dsp` (silence) and the data link on
`/dev/adsp` (440 Hz), both at 48 kHz/S16/2ch.  The second PCM must open at
the card's rate (trap 196), and `pbplay` sets `SPEED` first.

## 3. The stereo fix

The first run played only the left ear.  The raw codec registers showed both
channels fully on (`PM1 = 0x3303`, `PM3 = 0x03f0`, `PM5 = 0x0303`,
`0x02d/0x02e = 1`, `0x601/0x602 = 1`, `0x060 = 0x00ee`), so the fault was
the data, not the codec.  McBSP3's `XCR2` was `0x0041` — bit 15 (`XPHASE`)
clear, i.e. **one word per frame**.  The OSS layer's first `hw_params` is
mono at the final rate/width, and `omap_mcbsp_dai_hw_params` returned early
on the later 2-channel call because its guard compared rate and width only.

The fix is in `sound/soc/ti/omap-mcbsp.c`: the guard also compares the
channel layout the register shadow was programmed for
(`!!(cfg_regs.xcr2 & XPHASE) == (channels > 1 && (I2S || LEFT_J))`).
`XCR2` becomes `0x8041`; the right slot plays.  This is a **module-only**
change, so the region-0 CRC is unchanged (`0xF8BADFF3`) and only region 1
was flashed (trap 190).

## 4. Measured result (operator, headphones)

* Clock link: `pbplay 45 0 /dev/dsp` → **wrote 8 650 752 bytes, done**;
  `hw_ptr` ≈ 48 096 frames/s.
* Data link: `pbplay 40 440 /dev/adsp` → **wrote 7 684 096 bytes, done**
  (the old failure was a 82 176-byte `EIO` after five periods);
  `SPCR2 = 0x0235`, `XBUFFSTAT` toggling, `IRQST = 0x0712`, `XCR2 = 0x8041`.
* Codec: `R0x732 = 0x6020` (FLL1 locked), `R0x200 = 0x0011`,
  `R0x302 = 0x0000` (AIF1 slave), `R0x601/2 = 1`, DAC1 volumes 0xc0.
* **The operator hears the 440 Hz tone loud in both ears.**

The full raw capture is `docs/captures/wm8994-e10-mcbsp3-2026-11-13.txt`.

## 5. What remains (and is not this goal)

* **The speaker path was not exercised.**  The listening test was on
  headphones.  The codec's speaker controls read routed (the ALSA switches
  `SPKL/SPKR DAC1`, `SPKL/SPKR Output` and `Speaker` are on; `PM1` has
  `SPKOUTL/R_ENA`), so the next experiment is the same tone with the
  headphones **unplugged**, plus the `spk`/`hp` board lines and the raw
  `R34`/`R35` speaker-mixer and `R38`/`R39` output-PGA registers.
* **The `pcm:` and `live N:` diagnostics** are still in the drivers and the
  patch; retire them now that the path works.
* **MCLK1** still does not clock at the pin (reports 206/208/209); the
  working design does not need it, so the probe (trap 165) stays optional.
* **Touch cold boot** still needs the GPIO1_14/GPIO4_8 pulse; the warm-boot
  path is proven.
* **WL1283** remains stopped by the operator; the `wl128x-nvs.bin` path is
  still open.

## 6. Corrections

* **Report 212 §10 / trap 192:** the codec's DACDAT is **not**
  `abe_mcbsp1_dx`; it is `abe_mcbsp3_dx` (pad `0x108`).  `abe_mcbsp1_dx` is
  the `AIF 4→MCBSP1` route.  The E6 capture did not quote the McBSP3 pads.
* **Trap 194:** the clock nets are not "split" between mcbsp2 and a data
  engine that cannot see them; the codec's BCLK/LRCLK net reaches **McBSP3**
  (and mcbsp2 drives it in our design).  The E9 stall was the wrong engine
  (mcbsp1), not a missing net.
* **Report 213 §7 / DECISIONS §58:** the ABE is still not needed — the
  working path is the legacy McBSP path.  The corrected E9 described there
  was retargeted from mcbsp1 to mcbsp3.
* **The OSS re-negotiation guard** (rate/width only) is the stereo bug; see
  trap 205.
