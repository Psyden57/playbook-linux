# 112 — Bench probe: display R3 + USB M3 (2026-10-27)

Read-only register probe run from **userspace** (`/dev/mem`, forked child, so a
firewalled access costs a SIGBUS instead of the board) on the live kernel with
the initramfs PID 1.  Answers report 111's **R3** ("is the display reachable at
all?") and report 110's **M3** ("does MUSB see a session?").

Method note: the first version logged through `/dev/kmsg` and lost everything
after the fourth access — printk records written in that window never reached
the DRAM ring, although PID 1 demonstrably continued.  The probe therefore
writes straight into the ring page (`0x88000000`, `+0x80/+0x84/+0x100`, same
protocol as the kernel's `ring_put`) over `/dev/mem`.  That is now the reliable
way to log from userspace.  Capture: `/tmp/ring1_r3c.txt`.

---

## 1. Display (111 R3) — reachable, with one exception

```
PB: PEEK DSS_REVISION           48040000 = 00000040
PB: PEEK DISPC_REVISION         48041000 = 00000040
PB: PEEK DISPC_SYSSTATUS        48041014 = 00000001     RESETDONE=1
PB: PEEK DISPC_CONTROL          48041040 = 00000000     (not enabled, expected)
PB: PEEK CM_DSS_CLKSTCTRL       4a009100 = 00000f02     CLKTRCTRL=2 SW_WAKEUP  <-- exactly QNX's value
PB: PEEK CM_DSS_CLKCTRL         4a009120 = 00040f02     MODULEMODE=2 HW_AUTO, IDLEST=0
PB: PEEK DSI1_REVISION          48044000 = 00000030
PB: PEEK DSI1_SYSSTATUS         48044014 = 00000001     RESET_DONE=1
PB: PEEK DSI1_COMPLEXIO_CFG1    48044048 = 00000000
PB: probe child died on signal 7                        <-- reading 0x48044200 (DSI PHY) aborts
```

**Verdict: the display plan is viable.**  DSS, DISPC, the DSI core, and both DSS
clock registers are readable from the non-secure side, `DISPC` reports
RESETDONE, and the clock-domain state already matches what `setup-core-inactive`
leaves (`0x0f02`).  Nothing needs to be "un-firewalled" for the main path.

The **DSI PHY page (`0x48044200`) aborts on read**, which is expected for a
block whose PLL/power is off — it is a separate target module and mainline's
`ti,omap4-dsi` exposes it as the `phy` register range, only valid once the DSI
PLL is running.  The DSI *PLL* page (`0x48044300`) was not reached (the child
died first) and is the natural next read, after power-up rather than before.

## 2. USB (110 M3) — clocked, session valid, device mode

```
PB: PEEK CM_L3INIT_CLKSTCTRL    4a009300 = 02077302     CLKTRCTRL=2 SW_WAKEUP
PB: PEEK L3INIT_USBOTGHS        4a009358 = 00000002     MODULEMODE=HW_AUTO, IDLEST=0
PB: PEEK L3INIT_USBHOSTHS       4a009360 = 00000101     MODULEMODE=ENABLED,  IDLEST=0
PB: PEEK L3INIT_USBTLL          4a009368 = 00000001     MODULEMODE=ENABLED,  IDLEST=0
PB: PEEK DPLL_USB mode          4a008180 = 00000007     DPLL_EN=7 (lock)
PB: PEEK MUSB_DEVCTL before     4a0ab060 = 00000080     BSESSVLD=1, SESSEND=0, IDDIG=0
PB: PEEK USBOTGHS_CONTROL       4a00233c = 00000015     already AVALID|VBUSVALID|IDDIG
PB: POKE USBOTGHS_CONTROL = 0x15
PB: PEEK MUSB_DEVCTL after      4a0ab060 = 00000080     unchanged (it was already set)
```

**Verdict: the USB OTG controller is already alive in device mode.**  DPLL_USB
is locked, the OTG instance is out of idle, the TLL and host instances are
clocked, `MUSB_DEVCTL` says a session is valid with `SESSEND=0` and `IDDIG=0`
(device role), and the board control register already carries
`AVALID|VBUSVALID|IDDIG`.  Writing it again changes nothing, so **M3 is a no-op:
"cable not seen" is not the problem**.  The next step is M4 — bind a gadget
(`g_serial`/configfs) and watch the PC side enumerate; no PHY or VBUS work is
required first.

## 3. Consequence for the plan

- Display: start with the **real** DSS/DSI driver work (111 §6 DTS recipe +
  R4/R5).  Power up the DSI PLL before touching `0x48044200`, and verify each
  write by readback (`DISPC_TIMING_H/V`, `POL_FREQ`, `DIVISOR`, `SIZE_LCD`,
  then `FRAMEDONE`/`VSYNC` toggling in `DISPC_IRQSTATUS`).
- USB: go straight to a gadget.  Enable `CONFIG_USB_MUSB_*` + `USB_GADGET` +
  `USB_CONFIGFS` (or `USB_G_SERIAL`), add the 110 §DTS recipe, and use
  `idVendor=0x0fca idProduct=0x8010` so the host side is unambiguous.
- Both probes are cheap to repeat: rebuild `initramfs/root/init` only
  (seconds), no kernel rebuild needed unless a driver is involved.

## 4. Trap worth remembering

`/dev/kmsg` from userspace is **not** a reliable log channel when a probe can
disturb the machine: records written around a faulting device access were lost
while the process kept running.  Write the ring page directly
(`/dev/mem` + `0x88000000`) — it is the same DRAM the kernel's DEBUG_LL console
uses and it survives the reset.
