### 1.1 Command set

```
  help                     this text
  ls [path]                list a directory (default /)
  cat <path>               print a file, first 4096 bytes
  peek <hexaddr> [count]   read count 32-bit words via /dev/mem
                           (default 1, max 64), one per line,
                           printed as  <addr>: <value>
  poke <hexaddr> <hexval>  write one 32-bit word, read it back
  kick [on|off]            status / toggle the userspace WDT2 TGR
                           pet (2 s) and show CRR/LDR
  reboot                   reboot now (unit returns to the bootrom)
```

Deliberately no `mkdir`, no `mount`, no shell, no wildcards, no pipes: the
whole point is a bench tool small enough to audit.  Physical addresses only
(`peek 48040000` = `DSS_REVISION`).

### 1.2 Three design decisions that matter on this board

1. **Every memory access runs in a forked worker** with a 3 s `alarm()`.  A read
   of a clock-gated OMAP target aborts the L4 transaction and the kernel then
   delivers SIGBUS to whoever touched it (report 112 §2 lost a whole boot this
   way).  In a child it costs one `fork()`; the console prints
   `!! worker killed by SIGBUS: the access was aborted (gated block / L4
   firewall)` and stays alive.  Verified twice on hardware (§4.3, §4.4).
2. **The console says nothing until the host speaks.**  `gs_open()` in this
   kernel does *not* wait for the host, and anything written while the PC's
   `ttyACM0` still has its default termios is **echoed back to us by the host's
   line discipline** — the console then reads its own banner as if it were
   typed input.  The first version did exactly that (see §6.1).  Staying silent
   until the first real keystroke makes the failure impossible, and the first
   byte prints the banner plus `pb> `.
3. **`reboot` is PID 1's decision.**  The console writes one byte to a pipe
   handed to it as `argv[1]`; `/init` polls that pipe in 500 ms slices and calls
   `sync()` + `reboot(RB_AUTOBOOT)`.  The console only falls back to `reboot(2)`
   itself if the pipe is gone.

## 2. Build (exact commands)

```bash
export PATH=/home/psyden/SSDdrive/wsl-migration/home/psyden/toolchains/armv7-eabihf/bin:$PATH
A=/home/psyden/rea-work/bootdumps-2026-09-11/analysis
C=/home/psyden/rea-work/playbook-dev/kernel-clean

# 1. the two static userspace binaries
cd $A/initramfs
arm-linux-gcc -static -O2 -Wall -Wextra -o root/init    init.c
arm-linux-gcc -static -O2 -Wall -Wextra -o root/console console.c
arm-linux-strip root/init root/console

# 2. re-embed the initramfs and rebuild the kernel
#    (rm is required: the generated cpio's dependency list does not notice a
#     *new* file in the source directory)
cd $C
rm -f usr/initramfs_data.cpio*
make ARCH=arm CROSS_COMPILE=arm-linux- -j12 zImage

# 3. wrap into the chainloader IFS image (unchanged from the documented loop)
cd $A
EP_TICKS=0 ZIMAGE=$C/arch/arm/boot/zImage \
DTB=$C/arch/arm/boot/dts/ti/omap/omap4-winchester.dtb \
python3 build_kernel_image.py
```

The build printed (this is the image that was flashed and verified):

```

zImage     : 7662568 B at image 0x2C0000 (load 0x803BF800) -> 0x84000000
```

`cpio -it` on `usr/initramfs_data.cpio` shows `init` and `console`, both
`-rwxr-xr-x`; `md5sum console` in the cpio equals `md5sum initramfs/root/console`
(`0b2ad33f…`), so the flashed console is the tree's console.

Two traps in this build I hit once each:

* `make ... | head -30` **kills make with SIGPIPE** after `Image is ready` and
  before `piggy`/`zImage` — the chainloader then silently wraps a *stale*
  `zImage` (the image CRC came out identical to the previous build, which is
  how I noticed).  Log to a file, don't pipe to `head`.
* The first `make` after `rm usr/initramfs_data.cpio*` can fail with
  `*** [include/config/auto.conf] Deleting file 'include/generated/autoconf.h'`;
  simply running `make` again succeeds.

## 3. Using it from the host

```bash
# 1. the ACM node comes up root:uucp 0660 and this user is not in uucp:
pkexec chmod 666 /dev/ttyACM0
stty -F /dev/ttyACM0 raw -echo

# 2. a session (one open() for the whole thing — see pbcon.sh)
$A/pbcon.sh 'help' 'peek 4a314028 2'
```

`stty raw -echo` is **not** optional in practice: without it the host's line
discipline echoes the console's output back to the device (and adds a CR to
every LF).  The console survives it, but the transcript is ugly.

The task's one-liner form works too, as long as you accept that the first
~1.5 KB can be lost to the tty hangup when `printf`'s fd closes:

```bash
printf 'help\n' > /dev/ttyACM0 & timeout 5 cat /dev/ttyACM0
```

Each new host session is announced to a host that has been idle for 5 s with a
single `[console idle] pb> ` prompt (the banner itself is printed once per boot,
on the first received byte).

### 4.4 `peek`, `poke`, `kick` — and a real bus abort survived

```
pb> peek 4a314028 2
4a314028: fffcee4a          <- WDT2 CRR: counts UP from LDR
4a31402c: fffc1800          <- WDT2 LDR: 7.812 s window (report 109 §8.1)

!! worker killed by SIGBUS: the access was aborted (gated block / L4 firewall).
   Try a different address.
pb> poke 4a00233c 15

pb> kick
kick: userspace WDT2 pet OFF (every 2000 ms)
kick: kernel pets TGR from a 2 s timer_list unconditionally (no userspace knob)
WDT2: TGR ffffc998 -> wrote 00003667 | CRR fffccb28 -> fffccb28 (LDR fffc1800: no reload?)
pb> kick on
kick: userspace pet ON
WDT2: TGR … | CRR … (RELOADED)
```

The `DSS_REVISION` SIGBUS is the interesting line, not a bug: **the same read
`/init` does at 2.8 s returns `0x00000040` from the console at 50 s.**  The DSS
target-module autoidles in between, the L4PER2 read aborts, and the kernel logs

```
Unhandled fault: external abort on non-linefetch (0x1018) at 0xb6fef000
44000000.l3-noc:L3 Custom Error: MASTER MPU TARGET L4PER2 (Read): Data Access in User mode during Functional access
WARNING: CPU: 0 PID: 56 at drivers/bus/omap_l3_noc.c:133 l3_interrupt_handler+0x230/0x354
CPU: 0 UID: 0 PID: 56 Comm: console Tainted: G  W  6.15.11 #69
```

PID 56 is the *worker child* (`Comm: console`), the console survived, and the
next command ran normally.  This is precisely the failure mode the fork
isolation exists for, and it is a warning for the display work: **enable
`CM_DSS_CLKCTRL` before peeking DSS from userspace**, or every second read is a
coin flip.

`poke` wrote `CONTROL_USBOTGHS_CONTROL` back to the value `/init` already sets
(`0x15`, the no-op write report 112 established) — i.e. `poke` was demonstrated
without risking the USB path the console is running on.

`kick`: the userspace pet toggles and reports `TGR`/`CRR`/`LDR`, and `kick on`
sustains a real 2 s `TGR = ~TGR` kick.  The single-`peek` "no reload?" is a
measurement artefact, not a failure: `CRR` ticks at 32.768 kHz (30 µs) and the
read immediately after the trigger samples before the reload lands, while the
kernel's own 2 s pet reloads `CRR` in the same window.  The A/B run shows the
register behaviour instead (LDR `0xfffc1800`):

```
peek 4a314028 1        4a314028: fffc68c5   (CRR = LDR + 0.63 s)
poke 4a314030 ffffc998 4a314030: wrote ffffc998, readback 00003667  (DIFFERS)
peek 4a314028 1        4a314028: fffc64f0   (CRR = LDR + 0.60 s -> was reloaded)
poke 4a314030 3667     4a314030: wrote 00003667, readback 00003667
peek 4a314028 1        4a314028: fffc9284   (CRR = LDR + 0.96 s)
peek 4a314028 1        4a314028: fffcdf9c   (CRR = LDR + 1.48 s)
```

i.e. `TGR` writes land (the readback flips), `CRR` keeps counting up and is
reloaded every ~2 s, and the definitive "the `TGR` read/invert/write reloads
`CRR`" proof stays report 109 §8.1's (`crr fffd0e91 -> fffc1803 wps=0`), because
from userspace the kernel's pet cannot be paused to isolate a single kick.

Also confirmed by the same session: the board was still answering at
**t+145 s**, i.e. 18× the bootloader-armed 7.8 s WDT2 window — the kernel's 2 s
`timer_list` pet (109 §8.1) is doing its job, and nothing the console does
disturbs it (including the `poke`s to `0x4a314030`).

## 5. Recovery behaviour (bounded lifetime)

`/init` takes `CLOCK_MONOTONIC` at entry and, in the same 500 ms poll loop that
watches the reboot pipe, reboots when `elapsed >= 180`.  Nothing the console
does can extend it; `reboot` can only shorten it.  If the console dies (or its
pipe closes) PID 1 logs `PB: console pipe closed (console gone)` and keeps
counting to 180 — a dead console must not mean a wedged board.

Verified end-to-end in cycle 1, where nothing ever opened `ttyACM0`
(`playbook-live-spare-2026-10-26-clean/console-boot1-ring.txt`):

```
PB: console: /dev/ttyGS0 open, banner sent
PB: console started as pid 53
PB: console up; auto-reboot in 180 s
…
PB: reboot now (lifetime expired)
[  182.125854] PLAYBOOK: rebooting now
[  182.216033] reboot: Restarting system
```

182.1 s of kernel time − 2.5 s to reach `/init` ≈ the 180 s cap.  The restore
tool, started with `--delay 200`, then caught that boot rom and put the media
back by itself, i.e. **an unattended boot returns to the boot rom and to
TabletOS without a power cycle.**

Consequence worth knowing: because the kernel pets WDT2 and `/init` now lives
180 s, a test image on media no longer reset-loops every 7.8 s (as reports
105–109 assumed).  The cadence is `boot rom ~11 s + 180 s lifetime`; a restore
started with a delay > 180 s therefore waits for the *second* boot rom window or
misses it.  That is why cycle 1's `--delay 200` restore took the cap's boot rom
and cycle 3's restore was started with `--delay 0` while the console was up.

## 6. Surprises / traps

1. **The host's line discipline echoes the gadget's output back into it.**
   `gs_open()` does not block waiting for the host (this kernel), so the console
   opened `ttyGS0` at 2.8 s and wrote its banner into the kfifo; by the time the
   PC's `ttyACM0` existed it still had default termios (ECHO on), so the banner
   was echoed back to the device and read as typed input.  First session
   transcript therefore started with `PlayBo` + a `: no such command` — the
   console was parsing its own banner.  Fixed by staying silent until the first
   received byte (§1.2); the workaround if you run the old behaviour is
   `stty -F /dev/ttyACM0 raw -echo` **then** send `^C`.
2. **The ACM node is `root:uucp 0660` and this user is not in `uucp`.**  There is
   no usable `sudo` (password required), but `pkexec` is permitted here, so the
   session ran `pkexec chmod 666 /dev/ttyACM0`.  Nothing was made permanent: the
   node is recreated on every enumerate and TabletOS's `0fca:8010` has no ACM
   interface, so after the restore `/dev/ttyACM*` does not exist at all.  A udev
   rule (`SUBSYSTEM=="tty" … GROUP="wheel"`) would be the durable answer.
3. **A single command per `open()` loses output.**  `printf 'cmd\n' >
   /dev/ttyACM0` closes the fd immediately; the tty hangup drops whatever was
   still queued for the reader.  Hence `pbcon.sh` keeps one fd for the session.
4. **`0fca:8010` is shared with TabletOS**, and this host has a udev rule that
   tries to attach any `0fca:8010` to the `debian-dev` libvirt VM (it is shut
   off, so nothing happened).  Identify the Linux gadget by `iProduct`
   ("PlayBook (Linux bring-up)") or `/dev/serial/by-id` — never by PID alone.
5. The DSS block reads fine from `/init` at 2.8 s and SIGBUSes from the console
   at 50 s (§4.4).  Same kernel, same address — the difference is the target
   module autoidling.  Any future "peek a display register" experiment must
   enable the clock first, and must expect aborts to be *normal*.
6. `make zImage | head` and a partial-pipe reader killed the build after `Image`
   and silently re-wrapped the previous `zImage`; check the printed **CRC** and
   the cpio contents, not just "the build finished".
7. The console transcript in the DRAM ring is what makes this usable in
   practice: after any crash/reboot you can still read what was typed and what
   was answered (`pb_ring.py dump --ring 88000000`), including
   `PB: reboot now (console request)` for the reboot path.  Printk ordering
   against `rlog` writes is *not* chronological in the ring — treat the ring as
   a log, not a timeline.
