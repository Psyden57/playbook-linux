# 188 — WL1283 session 33: the powerman lead is closed, the settle/CMD52 tests are negative, and the chip is still not up

**Session 33 (absolute), Linux-era 27.  2026-11-08.**
Status: **bench + static RE.**  The operator removed the main board from the
device (pack kept connected; the board does not start from USB alone), then
reassembled it.  Region 0 was flashed with two Linux test images and the 1917
IFS for one QNX comparison boot; no NVRAM/MCT/RPMB write.  `BOOTCTR_FCTRY` read
`0x32` on the QNX boot and `0x2F` on the final Linux boot (`pbrpmb topup` left
it alone: `0x2f >= threshold 0x1e`).  Pack Full (4.15 V).

This is the continuation of report 185 / the handoff's item 9 step 4.  The
QNX power manager was the last software layer; it is answered in report 187

## 0. Headline

* **The powerman `winchester` preset has no WLAN rail or clock** (report 187).
  Its WLAN authorities only gate the standby shutdown/OSWR decision; the
  `ldo_vaux1`/`ldo_vaux3` strings are the display/backlight rails (VAUX3 →
  LM3532, REGEN1/2 → the panel).
* **WL_EN is not brought out at the accessible test points.**  GPIO2_22 was
  confirmed (`0x4A10007C` mux 3 = `gpio_54`, TRM table 18-358) and toggled from
  the shell through a 90 s low, a 5 s/5 s square wave and a 2 s/2 s square
  wave; no point on the board followed it.  The 1.8 V points stayed 1.8 V and
  the 0 V points stayed 0 V.
* **The one measurable QNX/Linux difference at the chip is its IRQ output.**
  The rightmost front pad is the chip's IRQ: it is 1.8 V under QNX with WLAN
  up, 0 V when `ifconfig ti0 down` powers the chip down, and 0 V under Linux
  with WL_EN high.  `GPIO2_DATAIN` bit 21 is 1 on QNX (`0x08221018`) and 0 on
  Linux (`0x01000010`).  So the chip is up under QNX and not under Linux.
* **The 200 ms post-power-on settle is negative.**  Image `0x0B38612D`
  (DTB-only: `post-power-on-delay-ms = <200>` on `&mmc5`) booted with
  `delay1 200ms` / `power_on delay 200ms`, and CMD52/CMD8/CMD5 still timed out
  (`err=-110`); the IRQ stayed low.
* **Skipping the SDIO reset (CMD52) is negative.**  QNX's own sequence is
  CMD0 → CMD5; Linux sends CMD52 first.  Image `0xAC98BCAD` adds
  `MMC_CAP2_NO_SDIO_RESET` for the MMC5 host: the sequence became CMD0 → CMD8
  → CMD5, and CMD5 still timed out (`err=-110`, no response).
* **The board-visible state matches.**  All WLAN pads read the same as QNX
  (`0x078 = 0x410B4103`, `0x07A = 0x0003410B`, `0x07C = 0x00030003`,
  `0x148/14C/150 = 0x01180118`), `GPIO2_DATAOUT = 0x31413200` (WL_EN high),
  VIO is 1.8 V at several points, and the Linux regulator list has V1V8/VCXIO/
  VDAC = 1.8 V, VUSB = 3.3 V, V2V1/VANA = 2.1 V, VAUX1/2/3 = 2.8 V, VMMC/VPP/
  VUSIM off.  No 3.3 V **chip** rail is exposed at the probed points; the only
  4.7 V point is a resistor (VBUS side).
* **Remaining candidate:** the 26 MHz TCXO/VBAT at a pin that is not brought
  out, or OMAP HSMMC signal sampling.  The multimeter cannot resolve either;
  a schematic, board view or logic analyser is required.

## 1. The QNX comparison on the bare board

The 1917 IFS (`local/work/ifs-shim-sealed.ifs`, `b52195bb…`) was flashed to
region 0 only and booted.  `ti0` came up UP/RUNNING (`14:74:11:8f:9c:c3`);
`sloginfo` showed `TIWLAN SDIO probe WAS CALLED` and
`SDIO clock Configuration is now set to 24Mhz`.

With WL_EN/WLAN up:

| signal | QNX | Linux (`0xAC98BCAD`) |
|---|---|---|
| `GPIO2_DATAOUT` (`0x4805513C`) | `0x31413200` | `0x31413200` |
| `GPIO2_DATAIN` (`0x48055138`) | `0x08221018` (bit 21 = 1) | `0x01000010` (bit 21 = 0) |
| pad `0x4A100078` | `0x410B4103` | `0x410B4103` |
| pad `0x4A10007A` | `0x0003410B` | `0x0003410B` |
| pad `0x4A10007C` | `0x00030003` | `0x00030003` |
| pads `0x148/14C/150` | `0x0118` | `0x0118` |

`ifconfig ti0 down` on QNX changed `DATAOUT` to `0x31013200` and `DATAIN` to
`0x08021018` (bit 21 dropped); `ifconfig ti0 up` restored both.  **The
rightmost front test point followed exactly that** (1.8 V → 0 V → 1.8 V), so it
is the chip's IRQ/output, not a rail.  Under Linux with WL_EN high it is 0 V.

The accessible DC levels under QNX and Linux were otherwise the same: one front
pad at 1.8 V, about four back pads behind the chip at 1.8 V, the rest 0 V, and
one resistor at ~4.7 V (VBUS).  No 3.3 V point was found on either OS.

## 2. The two Linux tests

Both were built from the session-32 image's tree and flashed region 0 only.

### 2.1 Post-power-on settle — image `0x0B38612D` (negative)

DTB-only change on `&mmc5`:

```dts
post-power-on-delay-ms = <200>;
```

Log (the core's own `PBC:` prints):

```
PBC: mmc4 power_up
PBC: mmc4 delay1 200ms
PBC: mmc4 delay1 done
PBC: mmc4 power_on ios done
PBC: mmc4 power_on delay 200ms
PBC: mmc4 power_on delay done
PBC: mmc4 sdio_reset
PBCMD: mmc4 op=52 arg=00000c00 flags=00000195 err=-110 resp0=00000000
PBCMD: mmc4 op=52 arg=80000c08 flags=00000195 err=-110 resp0=00000000
PBCMD: mmc4 op=8  arg=000001aa flags=000002f5 err=-110 resp0=00000000
PBCMD: mmc4 op=5  arg=00000000 flags=000002e1 err=-110 resp0=00000000
```

The chip has the 400 kHz clock running for ~400 ms before the first command and
still does not answer.  `GPIO2_DATAIN` stayed `0x01000010` (IRQ low).

### 2.2 Skip CMD52 — image `0xAC98BCAD` (negative)

`MMC_CAP2_NO_SDIO_RESET` (bit 30) added to `include/linux/mmc/host.h`, honoured
in `mmc_rescan_try_freq()` (`drivers/mmc/core/core.c`), and set for the
`480d5000` host in `omap_hsmmc_probe()`.  The boot sequence became exactly
QNX's first command:

```
PBC: mmc4 sdio_reset skipped
PBC: mmc4 go_idle
PBCMD: mmc4 op=0 arg=00000000 flags=000000c0 err=0 resp0=00000000
PBCMD: mmc4 op=8 arg=000001aa flags=000002f5 err=-110 resp0=00000000
PBCMD: mmc4 op=5 arg=00000000 flags=000002e1 err=-110 resp0=00000000
PBC: mmc4 attach_sdio no
```

CMD5 still times out and the IRQ stays low.  The CMD52-first sequence is not
the cause.

## 3. The USB re-enumeration regression (side finding)

From the first Linux boots after the QNX trip, the unit needed a physical
unplug/re-plug before the host enumerated it.  The device side was healthy:

```
[    5.591644] udc musb-hdrc.0.auto: binding gadget driver [g1]
[    5.596496] configfs-gadget.g1 gadget.0: acm ttyGS0: ...
[   28.605224] configfs-gadget.g1 gadget.0: high-speed config #1: c
```

The gadget bound at 5.6 s but the host only configured it at 28.6 s — the
re-plug.  Forcing a UDC disconnect/connect from the unit re-enumerated the
host without touching the cable:

```
echo disconnect > /sys/class/udc/musb-hdrc.0.auto/soft_connect
sleep 2
echo connect > /sys/class/udc/musb-hdrc.0.auto/soft_connect
```

The host moved from `Bus 003 Device 117` to `Device 118`.  So this is the
USB PHY/OTG pull-up surviving a warm reset (the host never sees a disconnect).

**Root cause isolated: the session-32 WL_EN reset pulse.**
`pb_wl1283_reset_pulse()` in `omap_hsmmc_probe()` drives GPIO2_22 low for
500 ms and high before `mmc_add_host()`.  The A/B on warm reboots:

| image | FREF2 enable | WL_EN pulse | warm-reboot enumeration |
|---|---|---|---|
| `0xE36C679A` (session 31 known-good) | off | absent | **yes, 12–14 s** |
| `0x5920CAAC` (session-32 code) | on | on | no |
| `0x90BDE221` (session-32 code) | **off** | on | no |
| `0x0353A241` (final) | off | **off** | **yes, 14 s; gadget configured at 5.28 s** |

`0x90BDE221` still fails with the FREF enable removed, and `0x0353A241`
enumerates with the pulse removed: **the pulse is the cause; the FREF enable is
excluded and the session-33 MMC changes are not involved.**  The pulse was a
negative CMD5 experiment anyway, so both it and the FREF enable are removed
from the tree.  The mechanism is consistent with the WL1283's power-down/up
transient disturbing the shared 1.8 V/USB PHY state; the `soft_connect`
disconnect/connect remains a valid workaround, but with the pulse removed it is
not needed.

## 4. What is left

* The chip is alive and enumerable under QNX on the same bare board, and dead
  under Linux with the same pads, WL_EN, VIO, regulator set and command
  sequence.  The difference is at the chip's power/clock pins that are **not
  exposed** at the accessible points, or in the OMAP HSMMC sampling.
* A multimeter cannot measure the 26 MHz TCXO or see whether the chip drives
  CMD; a schematic/board view or a logic analyser is required.  This matches
  the stop condition in report 184 §5.
* **The QNX-side RE is not complete.**  Open targets: the live
  `/pps/services/hw_info/inventory` (`hw_info_pps`) and the hwinfo/HWI `WLAN`
  node; `hwio-config-winchester.so`'s `pad_config`/`gpio_config` arrays; the
  `devb-mmcsd-winchester` powerman client (`system/power/mgr`, `-power`,
  `clock`; does it set the MMC5 functional clock/voltage or bus power?);
  `devpm-omap4.so`'s `system/power/dev` registration and OSWR tables; and the
  full `tiwlan_winchester.ini` clock/power fields.  HANDOFF §1.4 has the list;
  the cheapest next step is one TabletOS boot and the PPS inventory read.
* Do not re-run the closed experiments: `CM_DIV_M5 = 0x329` (trap 116), a
  runtime MMC5 `unbind`/`bind` (trap 120), the FREF request input (trap 117),
  the FREF2 output as a CMD5 fix (trap 118), the init clock (trap 119), the
  WL_EN reset pulse alone (trap 124/185), the 200 ms settle or the CMD52 skip
  (this report).  **The FREF2 enable and the WL_EN reset pulse are removed from
  the tree**: both are negative for CMD5 and the pulse caused the USB
  warm-reset enumeration regression (trap 130).
