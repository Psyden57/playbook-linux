# 232 — The WL1283 `-110` is the chip's ELP wake: the FW-status read times out after it sleeps

Date: 2026-11-14 (session 51, Linux-era 45).
Bench: image **`0x9712A086`** (kernel `7.3.3` #60) + region-1 rootfs
**`7e067560…`** (`local/images/rootfs-region1-wl1283-elpcam.ext4`).
Capture: `docs/captures/wl1283-elp-2026-11-14.txt`.

## 0. Headline

Session 50's recovery loop is **not** a firmware/chip mismatch, **not** the
SDIO block size, and **not** calibration.  It is the chip's **ELP** (the
firmware's own sleep):

* The failing transfer is the **FW-status read**: CMD53 to **`0x1efc0`,
  84 bytes**, byte mode (`fixed = 0`), block size **256**, issued from the
  WL_IRQ thread immediately after `wlcore: firmware booted`.
* It fails **only after the chip has entered ELP**.  Hold the chip in **CAM**
  (`sta_sleep_auth = 0`) and `wlan0` comes up and stays up: one firmware boot,
  no `-110`, no recovery.
* Measured causally on a running, working system: re-enabling ELP at runtime
  (`echo 2 > …/wlcore/sleep_auth`) reproduces the `-110` and the recovery loop
  within seconds; disabling it again restores stability.

The port fix is one field: `wl12xx_default_conf.conn.sta_sleep_auth =
WL1271_PSM_CAM` instead of `WL1271_PSM_ILLEGAL` (which selects ELP).  ELP is a
power optimization; CAM costs battery, not function.

## 1. The failing transfer, measured

The SDIO address/length is invisible in a normal log — `wl12xx_sdio_raw_read()`
prints only `sdio read failed (-110)`.  A one-off instrumented `wlcore_sdio`
that appends `addr`, `len`, `fixed` and `func->cur_blksize` **on the error path
only** (no printing on success, so no perturbation) gave:

```
[ 1093.034545] wl1271_sdio mmc4:0001:2: PBRD addr 0x1efc0 len 84 fixed 0 blksz 256: sdio read failed (-110)
```

* **`0x1efc0`** is the FW-status block (`HW_ACCESS_MEMORY_MAX_RANGE` is
  `0x1ffc0`; the block sits `0x1000` below it).
* **84 bytes = 0x54**, the size of the WL1271 FW status structure.
* **`fixed = 0`** → `sdio_memcpy_fromio()`, i.e. CMD53 in **byte mode** (the
  driver uses `sdio_readsb()` only when the caller asks for block mode).
* **block size 256**, so the 84-byte length is *not* a multiple of the block
  size — and that is legal in byte mode.  The same 84-byte read **succeeds**
  later in the same boot (it is what the recovery path polls), so the transfer
  itself is fine: the chip is in a state where it does not answer.
* Issued from **`irq/132-wl12xx`**, i.e. `wlcore_irq()` →
  `wlcore_irq_locked()` → `wlcore_fw_status()`.
* Time: the kernel prints `firmware booted` and the read's failure about
  **1.5–1.6 s apart**; no `mmc_ios` change (no `PBSIO` line) in between, so the
  card kept its 24 MHz / 4-bit clock the whole time.

The kernel converts this into the observed loop: `wlcore_irq_locked()` returns
the error, `wlcore_irq()` calls `wl12xx_queue_recovery_work()` (the
`main.c:880` WARN — "unintended recovery"), the recovery's own
`pm_runtime_resume_and_get()` fails ("Enable for recovery failed"), `wlcore`
goes down, and `ieee80211_restart_work` then fails `drv_add_interface`
(`util.c:2012`) and re-enters the loop.

## 2. Why `wlcore_sdio dump=1` hides it

`dump=1` prints a hex dump **per transfer** at `KERN_DEBUG`.  With the console
at its normal level those prints reach fbcon, and on this board every printk
drawn to the console costs milliseconds (trap 52: "nothing on this board is
free to print per I/O").  Under `dump=1` the failure did not reproduce in the
same window — the instrument altered what it measured.  That is also why the
session-50 advice ("read the last READ before the `-110` with `dump=1`") cannot
work as written: the address has to come from the error path, not from a
per-transfer trace.

The instrument used here is 4 lines in `wl12xx_sdio_raw_read()`, prints nothing
on success, and was **reverted** afterwards — `sdio.c` is `cmp`-identical to
`local/pristine/linux-7.3.3`.

## 3. The discriminator: ELP, not runtime PM

Three measurements, one variable each:

| # | setting | result |
|---|---|---|
| A | `power/control = on` on `wl12xx.1.auto` (runtime PM off → no suspend, no ELP) | `wlan0` up, stable; 1 firmware boot, 0 failures |
| B | `power/control = auto` (PM on) + `sleep_auth = 0` (CAM, no ELP) | `wlan0` up, stable; the platform device still runtime-suspends |
| C | B, then `echo 2 > …/wlcore/sleep_auth` (ELP) at runtime | the `-110` returns within seconds, then the recovery loop |

C is the causal one: same boot, same firmware, only the sleep authorization
changed.  `docs/captures/wl1283-elp-2026-11-14.txt` is that toggle.

`wlcore_runtime_suspend()` writes `ELPCTRL_SLEEP` only when
`wl->sleep_auth == WL1271_PSM_ELP`; `wlcore_runtime_resume()` writes
`ELPCTRL_WAKE_UP` and — because `WL1271_FLAG_IRQ_RUNNING` is set on this path —
**skips** the wake completion wait, then the caller immediately reads the FW
status.  With the chip asleep, that first read is the one that times out.

## 4. The fix, and how it was verified

`drivers/net/wireless/ti/wl12xx/main.c`, `wl12xx_default_conf`:

```c
		/*
		 * PlayBook/WL1283: ELP is unusable on this board.  When the
		 * chip is allowed to enter ELP the first FW-status read after
		 * wake times out (CMD53 to 0x1efc0, 84 bytes, byte mode) and
		 * wlcore recovery-loops.  Keep the chip in CAM (always awake);
		 * dynamic PS while associated is unaffected.
		 */
		.sta_sleep_auth              = WL1271_PSM_CAM,
```

* Patch export: **58 files / 8 676 lines**, sha256 `1c57e575…` — applied to
  pristine 7.3.3 with **0 rejects and 58/58 files byte-identical**, and the
  tree walk (with the `Kconfig.*` filter) shows this as the only new file.
* `wl12xx.ko` md5 **`1ff6daa7…`** (in-tree build, `--strip-debug`, so it does
  *not* carry the `(O)` out-of-tree taint; the `M=` build did).  Rebuilding the
  whole module set in-tree reproduces every other module byte-identically
  (`cfg80211`, `mac80211`, `wlcore`, `wlcore_sdio` all match the shipped `md5`s).
* Verified **after a real region-1 flash and reboot**, not just by a module
  reload: `ip link set wlan0 up` → `rc=0`, `wlcore: firmware booted (Rev
  7.3.10.0.142)`, one boot, zero failures, `wlan0` `<NO-CARRIER,BROADCAST,
  MULTICAST,UP>`, and the debugfs `sleep_auth` reads **0** (the compiled
  default), while `wl12xx.1.auto` is `suspended` (PM still works).
* Repeated `down`/`up` cycles each re-download the firmware cleanly (the
  pwrseq does its job for every power cycle), with no `-110`.

## 5. What this rules out (measured or by construction)

* **The firmware/chip revision match.**  The session-50 suggestion was to try
  `wl128x-fw-4-sr.bin`.  It is **not usable**: the driver's floor is
  `7.3.10.*.133` and 4-sr identifies itself as **7.3.5.0.98**, so wlcore aborts
  with *"Your WiFi FW version (7.3.5.0.98) is invalid. Please use at least FW
  7.3.10.\*.133"* and `firmware boot failed despite 3 retries` before any
  interrupt work.  The experiment therefore cannot discriminate the `-110` and
  is closed as "not a usable firmware", not as "negative".  `wl128x-fw-5-sr.bin`
  (Rev 7.3.10.0.142) is also the newest blob linux-firmware has for wl128x.
* **The SDIO block size / byte mode.**  `len = 84`, `blksz = 256`, byte mode —
  and the identical read works once the chip is awake.
* **The NVS/calibration.**  Session 50 already saw the generic NVS loop
  identically; the MAC patch is orthogonal.  With CAM, the *generic* NVS is
  stable, so the loop was never a calibration symptom.
* **The 32.768 kHz slow clock.**  `CLK32KG` reads `07 01 55`, the reference's
  own value (physical `0xBC`–`0xBE`).

## 6. What remains open

* **Why the ELP wake is not honoured.**  The wake handshake here is the one
  upstream uses (`ELPCTRL_WAKE_UP` + the IRQ completing `elp_compl`), and
  upstream deliberately skips the completion wait when it is already running in
  the IRQ thread.  On this chip/firmware the first read after that wake is not
  answered.  It could be wake latency versus the immediate read, or the chip
  asserting `WL_IRQ` around the sleep transition; distinguishing them needs a
  finer instrument (a DRAM-ring trace of the ELP writes/IRQs, not printk).
* **Whether CAM is the right long-term answer.**  It is correct for a bring-up
  and for a unit on the bench; it costs power.  If the WLAN is to run on
  battery, the wake path is the thing to fix, and this report is the
  reproduction recipe.
