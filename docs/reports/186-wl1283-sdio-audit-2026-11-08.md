## 0. Headline

* **The default Linux initialization is 400 kHz, not 24 MHz.**
  `f_min = 400000`, `f_init = 400000`, `ios.clock = 400000`,
  `SYSCTL.CLKD = 120`, and the TRM's `CLKD` is a direct ratio on the 48 MHz
  functional clock: **actual 400 kHz**.  The 24 MHz figure in report 185 was
  the deliberate runtime `init_hz` test, not the default.
* **The full Linux sequence at 400 kHz is CMD52 → CMD0 → CMD8 → CMD5(arg 0)
  → CMD55 ×4 → CMD1.**  `mmc_rescan_try_freq()` sends `sdio_reset()` (CMD52)
  before `mmc_go_idle()` and `mmc_attach_sdio()`.  The second opinion is right
  that CMD52 precedes CMD5; report 184's recording note (which looked only at
  `mmc_attach_sdio()`) was incomplete.
* **The card times out on every command, starting with CMD52.**  CMD52
  `0x00000c00` and `0x80000c08` → `-ETIMEDOUT`; CMD8 `0x1aa` → timeout;
  CMD5 arg 0 → timeout (`ocr=0`); CMD55 ×4 and CMD1 → timeout.  Only CMD0
  "succeeds" (it has no response).  The chip is silent from the first command,
  not specifically at CMD5.
* **This confirms the chip-side conclusion, not a host-clock one.**  The
  audit rules out the init-frequency/argument concerns; the remaining
  candidates are the chip's power/clock/reset.  The Motorola guide gives the
  multimeter checks: **VBAT 3.3 V, VIO 1.8 V**, and the 26 MHz TCXO is
  powered from the chip's internal 1.8 V.

## 1. The audit

The audit image is `0x9471F6C9` (`boot/chainloader/kernel.img` at recording).
It has the CMD5 quirk **disabled by default** (`omap_hsmmc.sdio_ocr_quirk=0`,
so the native arg-0 probe runs) and adds:

* `PBC: mmc4 try <Hz> (f_min=… f_max=… f_init=… ios.clock=…)`;
* `PBCLK: mmc4 CLKD=<n> actual=<Hz>`;
* `PBCMD: mmc4 op=<n> arg=<…> flags=<…> err=<…> resp0=<…>` in
  `mmc_wait_for_cmd()`, gated to the `480d5000` host.

The complete mmc4 trace (`local/logs/boot-20261108-sdio-audit.log`):

```

PBCLK: mmc4 CLKD=120 actual=400000Hz
PBC: mmc4 try 400000Hz (f_min=400000 f_max=52000000 f_init=400000 ios.clock=400000)
PBCMD: mmc4 op=52 arg=00000c00  flags=00000195 err=-110 resp0=00000000
PBCMD: mmc4 op=52 arg=80000c08  flags=00000195 err=-110 resp0=00000000
PBCMD: mmc4 op=0  arg=00000000  flags=000000c0 err=0    resp0=00000000
PBCMD: mmc4 op=8  arg=000001aa  flags=000002f5 err=-110 resp0=00000000
PBCMD: mmc4 op=5  arg=00000000  flags=000002e1 err=-110 resp0=00000000
PBC: sdio probe_ocr=00000000 err=-110 ocr=00000000
PBCMD: mmc4 op=55 arg=00000000  flags=000000f5 err=-110 resp0=00000000
PBCMD: mmc4 op=55 arg=00000000  flags=000000f5 err=-110 resp0=00000000
PBCMD: mmc4 op=55 arg=00000000  flags=000000f5 err=-110 resp0=00000000
PBCMD: mmc4 op=55 arg=00000000  flags=000000f5 err=-110 resp0=00000000
PBCMD: mmc4 op=1  arg=00000000  flags=000000e1 err=-110 resp0=00000000
```

Notes:

* `mmc_rescan()` tries `{400k, 300k, 200k, 100k}`, but `f_min = 400k` and the
  loop breaks after the first failure when `freqs[i] <= f_min`; there is
  **one** attempt, at 400 kHz.
* The two CMD52s are `sdio_reset()`'s write to CCCR register 6 and read-back.
* CMD8 (`0x1aa`) is the SD `SEND_IF_COND` path; it is sent before the SDIO
  attach.
* CMD55/CMD1 are the later SD/MMC attach attempts inside the same try; the
  card does not answer those either.

## 2. The correction to report 184

Report 184's recording note said: "Linux `mmc_attach_sdio()` calls
`mmc_send_io_op_cond()` (CMD5) first; it does not send CMD52/CMD0 before it
(`drivers/mmc/core/sdio.c` 7.3.3)."  That is true **inside**
`mmc_attach_sdio()`, but the caller `mmc_rescan_try_freq()` sends
`sdio_reset()` (CMD52), `mmc_go_idle()` (CMD0) and the SD `SEND_IF_COND`
(CMD8) first.  The audit log is the authority: the sequence on the wire is
CMD52 → CMD0 → CMD8 → CMD5 at 400 kHz.

## 3. What the Motorola 148603 guide adds

The 148603 is a WL1283-based module, not the PlayBook's chip-down part, so its
pin numbers must not be copied.  The electrical facts are generic to the
WL1283 and are useful for a multimeter:

| fact | value |
|---|---|
| VBAT | 3.3 V nominal (3.0–3.6 V) |
| VIO | 1.8 V nominal (1.71–1.89 V) |
| 26 MHz TCXO | on-module, powered from the SoC's **internal 1.8 V** |
| WL_EN | input, active high, default pull-down |
| WLAN_IRQ | output, active low, default drive 0 |
| SLOW_CLK | 32.768 kHz square wave, 0–1.8 V, 1 MΩ input |
| SDIO | 1/4-bit, max 26 MHz default / 52 MHz high rate; host pulls up the lines |

**Multimeter checks at the chip:** VBAT ≈ 3.3 V, VIO ≈ 1.8 V, WL_EN ≈ 1.8 V
when enabled, WL_IRQ level, and the SLOW_CLK pin's DC average (~0.9 V if the
32 kHz is running; 0 or 1.8 V if stuck).  The 26 MHz TCXO cannot be checked
for frequency with a multimeter, but its supply can; if VIO is missing the
TCXO is dead with it.

## 4. Next

   SLOW_CLK DC average) on our image and, if accessible, on the reference.
2. **Boot-time WL_EN reset pulse:** drive GPIO2_22 low for ~500 ms and then
   high before the MMC5 probe, replicating `hPlatform_hardResetTnetw`.  The
   session-29 runtime pulse is not the same experiment (it ran after probe);
   this one runs before the first CMD52.
3. If those do not move CMD52, the chip's power/clock/reset path is the
   remaining unknown and the electrical comparison is closed for the available
   equipment.
