## 0. Headline

* **`hw_info_pps` publishes no WLAN node at all.**  It creates
  `/pps/services/hw_info/inventory?nopersist` from runtime probes only
  (`confstr(_CS_MACHINE)`, `/dev/hd0` devctls, `/proc` sysinfo, ALSA mixer) and
  its attributes are `AudioCodec_Name`, `Processor_*`, `Board_*`, `eMMC_*`,
  `CPU_Type`, `RAM_Size`, `Processor_Numbers`.  It links no HWI library and
  there is **no static hwinfo database** in either 1917 tree.  The `WLAN` node
  the driver queries lives in the boot-time QNX **syspage** and is consumed by
  `devnp-ti1283.so`'s own `hwi_find`/`hwi_tag_find`; the PPS inventory is a
  dead end for this question.  (`hw_info_pps` does carry an inert PPS relay for
  `bluetooth/settings`, `camera/control`, `light_controller/status`,
  `light_sensor/status`, `power/battery`, but every call is guarded by a
  pointer that this build leaves zero, so none of them runs.)
* **The board pad/GPIO configuration contains the six WLAN lines and nothing
  else WLAN-specific.**  `pad_config` has 248 records; the resolved WLAN
  entries are `sdmmc5_clk/cmd/dat0..3` (mux 0, signals `0x52`–`0x57`),
  `gpmc_ncs3` = WL_IRQ (mux 3, signal `0x59`), `gpmc_nwp` = WL_EN (mux 3,
  signal `0x58`), the 0x07E companion (mux 3, signal `0x5d`), and
  `fref_clk2_out` at 0x19C (mux 0, signals `0x64`/`0x8a`).  There is **no**
  WLAN rail-enable or clock-control pad.  The WKUP pad `0x4A31E058` is
  configured **mux 3 (GPIO), both halves** — a static corroboration of trap 117.
* **`devb-mmcsd-winchester` has a powerman client, but it only registers a
  binary `-power on/off` mode.**  It requests no voltage, no clock rate and no
  bus power.  Its init does set `SDBP = 1` and `SDVS18` for non-MMC1
  controllers, enables the `CM2_L3INIT` MMC1/2 module clocks and clears
  `PRM_L3INIT` `LOSTCONTEXT`, but touches no CM divider/DPLL and no regulator.
  Its own absolute base constants cover only MMC1/MMC2, and the WL1283 is on
  MMC5, owned by `devnp-ti1283.so` — so this driver is not the WL1283 path.
* **`devpm-omap4.so` registers exactly one powerman device, `iva_opp`.**  It
  has no `system/power/dev` literal, no MMCHS5/`CM_L4PER_HSMMC5` write and no
  TWL WLAN rail.  The `sdmmc5_*`/`gpmc_*` names are four `mmap_device_io()`
  globals that are stored and **never read**; the OSWR wake tables (Winchester2)
  include the WL_IRQ pad (`0x07A`, GPIO2 bit 21) as a wake source and are
  applied **only** on OSWR entry/exit.
* **`tiwlan_winchester.ini`'s clock/power fields are all firmware-time.**
  `TCXO_Clk = 1` (26 MHz), `STRFRefClock = 2` (38.4 MHz, wired-OR, normal
  polarity), settling 5 ms each, `ClockValidOnWakeup = 0`,
  `TCXO_ClockValidOnWakeup = 0`, `TCXO_LDO_Voltage = 0` (the chip's internal
  TCXO LDO set to **2.5 V**), `Platform_configuration = 2` (bits 2:1 = `01`,
  4 mA SDIO drive; no level shifter, no EEPROM, SDIO IB enables 0, HS support
  0).  None is read before SDIO enumeration.

**Result: the QNX software surface is now fully read, and it names no WLAN
rail, clock or extra pad.  The remaining difference is still at the chip's
non-exposed power/clock pins or in OMAP HSMMC sampling (reports 184/188).**

## 2. `hwio-config-winchester.so` — the board pad/GPIO database

Targets: `lib/dll/hwio-config-winchester.so` (13 968 B, data only) and its
consumer `lib/dll/hwio-omap4.so` (the `.dynsym` names and the resolver
functions survive).

### 2.1 Record layouts (from the consumer)

`pad_config` is **248 × 20 bytes**; `gpio_config` is **72 × 32 bytes**; the
exported `pad_config_size`/`gpio_config_size` are `248`/`72`.

`pad_config` record (Ghidra: `pad_get_id`, `pad_get_signal_cfg`):

| off | field |
|---|---|
| +0 | `u32` pad id (0…0xE6) |
| +4 | pad function byte (`af`, low byte), second byte, then `u8 rev_min` (+6), `u8 rev_max` (+7) |
| +8 | `u32` (unused by the getters) |
| +12 | `u32` signal id (`pad_get_id` matches this) |
| +16 | `u32` extra (pull/input config word) |

`gpio_config` record (`gpio_get_signal_cfg`):

| off | field |
|---|---|
| +0 | `u8` gpio id |
| +4 | `u32` direction/level field (0 for gpio 53, 1 for gpio 54); the driver sets the actual direction, so this is not a proven direction encoding |
| +8 | `u8` initial level (0 for both) |
| +0xC | `u32` pull/attr (2 for 53, 0 for 54; interpretation inferred) |
| +0x10 | `u8` detect/attr (1 for 53, 0 for 54; the driver's falling-edge setting is inferred) |
| +0x11…+0x13 | attrs |
| +0x14/+0x15 | `u8` rev_min/rev_max |
| +0x1C | `u32` pad signal id (matches the pad table: 0x59 for 53, 0x58 for 54) |

The pad id → register resolver is in `hwio-omap4.so`: three 0xE7-entry tables
at file VAs `0x4FF8` (bank: 0 = CORE, 1 = WKUP), `0x5394` (offset) and
`0x5730` (half: 0 = bits 15:0, 1 = bits 31:16), with the WKUP bank at
`0x4A100000 + 0x21E000 = 0x4A31E000`.  Ghidra loads this ELF at
`file VA + 0x10000` (its addresses here are quoted as file VAs).

### 2.2 The WLAN entries, resolved

| config idx | pad id | physical pad | af | signal | extra | meaning |
|---|---|---|---|---|---|---|
| 16 | 0x94 | `0x4A100148` low (`sdmmc5_clk`) | 0 | 0x52 | 0xB | mux 0 |
| 17 | 0x95 | `0x4A100148` high (`sdmmc5_cmd`) | 0 | 0x53 | 0xB | mux 0 |
| 18 | 0x96 | `0x4A10014C` low (`sdmmc5_dat0`) | 0 | 0x54 | 0xB | mux 0 |
| 19 | 0x97 | `0x4A10014C` high (`sdmmc5_dat1`) | 0 | 0x55 | 0xB | mux 0 |
| 20 | 0x98 | `0x4A100150` low (`sdmmc5_dat2`) | 0 | 0x56 | 0xB | mux 0 |
| 21 | 0x99 | `0x4A100150` high (`sdmmc5_dat3`) | 0 | 0x57 | 0xB | mux 0 |
| 13 | 0x35 | `0x4A100078` high (`gpmc_ncs3`, **WL_IRQ**) | 3 | 0x59 | 0x100D | mux 3 |
| 85 | 0x34 | `0x4A100078` low (`gpmc_ncs2`) | 3 | 0x96 | 0x1008 | mux 3 |
| 14 | 0x36 | `0x4A10007C` low (`gpmc_nwp`, **WL_EN**) | 3 | 0x58 | 0 | mux 3 |
| 15 | 0x37 | `0x4A10007C` high (0x07E) | 3 | 0x5D | 0 | mux 3 |
| 29 | 0xB7 | `0x4A10019C` low (`fref_clk2_out`) | 0 | 0x64 | 0 | mux 0 |
| 155 | 0xE6 | `0x4A10019C` high | 0 | 0x8A | 0x1008 | mux 0 |
| 190 | 0x1F | `0x4A31E058` low (`fref_clk3_out`) | 3 | 0x9E | 0 | **mux 3, not mux 1** |
| 226 | 0x07 | `0x4A31E058` high (`fref_clk4_req`) | 3 | 0 | 0x5 | **mux 3** |

Every other entry is a normal board pad (display, I²C, UART, SD/MMC1, NAND,
keypad, etc.).  **No pad in the table is a WLAN rail enable or clock gate**;
the only WLAN-adjacent pads are the six above plus the two FREF pads, and the
WKUP `0x058` pair is statically mux 3 on both halves — exactly the live value
`0x000B0003` (trap 117).

### 2.3 The GPIO entries

`gpio_config` contains 72 records.  The WLAN ones are:

| id | +4 field | pull/attr | detect | rev | pad signal | meaning (inferred) |
|---|---|---|---|---|---|---|
| 53 (0x35) | 0 | 2 | 1 | 0–15 | 0x59 | WL_IRQ: input/pull/falling per the driver; the table fields are consistent |
| 54 (0x36) | 1 | 0 | 0 | 0–15 | 0x58 | WL_EN: output/no-pull per the driver; the table fields are consistent |

The `+0x1C` signal id matches the pad table's WL_IRQ/WL_EN signals (`0x59`/
`0x58`), so the two tables agree on the wiring.  The `+4`/`+0xC`/`+0x10`
encodings are not documented in the file; they are reported raw because the
driver's own `set_direction`/detect calls are the authority.  No other GPIO in
the table maps to a WLAN signal; the remaining ids are the board's display,
touch, audio, sensor, charger and modem lines.

## 3. `devb-mmcsd-winchester` — a powerman client, but only `-power on/off`

Target: `local/work/ifs1917-tree/proc/boot/devb-mmcsd-winchester` (85 011 B,
ELF32 ARM, link base `0x80600000`, stripped, `libcam.so.2` + `libc.so.3` only).
Static analysis only.

* **A powerman client is compiled in** (not an import): `_powman_mgr_instance`
  → `.bss 0x14528`, `_powman_pps_root` → `.data 0x144B0` = `"/pps"`,
  `_powman_backchannel_coid`; the PPS object is
  `"/pps/system/power/mgr?wait,delta"` and the client object is
  `…?nopersist,delta,critical,f=REQUESTED_MODE`.
* `mmc_powman_connect` (`0x6C6C`) calls
  `powman_create("devb-mmcsd", unit+0x1C, "storage", modes@0x14430)` and
  `powman_connect(...)` once at attach.  The mode table is exactly one mode:
  attribute **`-power`**, states **`on`/`off`**, cost **3**.
* `mmc_powmon_event` (`0x6E30`) only acknowledges the mode and toggles a
  software flag; the flag's only consumer is the stop path, and `mmc_power()`
  is a no-op unless the `normv` option is set — the Winchester2 board path
  clears it.
* **It requests no voltage, no clock rate and no bus power from powerman.**
* Its own init (`omap_core_pm` `0xC96C`, `omap_mmc_init` `0xC7FC`) enables the
  `CM2_L3INIT` MMC1/2 module clocks (`0x4A009328`/`0x4A009330`, value
  `0x01000002`), clears `PRM_L3INIT` `LOSTCONTEXT` (`0x4A30732C`/`0x4A307334`
  = 2), sets `SYSCONFIG` idle/clock-activity bits, programs `CAPA` VS bits,
  `CON = 0x00000600`/`0x00100600`, `HCTL = 0x00000C00` (MMC1) or `0x00000A00`
  (others), **`SDBP = 1`** and **`SDVS18` for non-MMC1**, and a `CLKD` divider.
  It assumes a 96 MHz `inputclk` (default `0x05B8D800`) and requests at most
  50 MHz; `CLKD = 2` then gives the `SYSCTL = 0x000E0080` pattern.  There is
  **no CM divider/DPLL write and no regulator/PMIC access** (the only I²C is
  two TWL6030 register writes in the Winchester2 board path).
* The driver's absolute base constants are only `0x4809C000` (MMC1) and
  `0x480B4000` (MMC2); the WL1283 is on MMC5 (`0x480D5000`) and is owned by
  `devnp-ti1283.so` (`pidin mem`), so this driver is not the WL1283 path.
  (The MMCHS register offsets are the TRM's absolute `+0x100`; Linux's
  `omap_hsmmc` uses the same offsets via `.reg_offset = 0x100`, so the bit
  semantics are directly comparable.)

Options parsed: `clock=`, `pio`, `bw=`, `bs=`, `noac12`, `nohs`, `maxsg`,
`normv`, `slot`, `idle`, `cmdlog`, `noddr`, `bootp`, `bkops`; no voltage,
bus-power or powerman-mode option exists.

## 4. `devpm-omap4.so` — one `iva_opp` device, OSWR-only pad tables

Target: `lib/dll/devpm-omap4.so` (239 040 B, stripped, `.dynsym` intact).

* **No `system/power/dev` literal exists in the file.**  The only
  `powman_create()` call is in `power_init` (`0xD60C`, call `0xD638`):
  device **`iva_opp`**, class `driver`, modes `opp_50`/`opp_100`/`opp_turbo`
  (50/100/200 MHz).  It connects to the manager, reads the allowed mode and
  calls `act_on_mystate`/`powman_mode_set`.
* `cpupm_init` (`0x0FCB4`) maps four pad registers and stores the results in
  globals named `gpmc_clk_gpmc_nwp`, `sdmmc5_clk_sdmmc5_cmd`,
  `sdmmc5_dat1_sdmmc5_dat0`, `sdmmc5_dat3_sdmmc5_dat2` (`0x4A10007C`,
  `0x4A100148`, `0x4A10014C`, `0x4A100150`).  **Nothing in the library ever
  reads or writes those mappings**; they are not wake-table entries.
* The real OSWR pad tables (`core_oswr_gpio_init` `0x12E14`) are per board
  (`Colt`/`London`, `Winchester2`, default).  The Winchester2 table includes
  the `gpmc_ncs3` pad (`0x4A100078` high = `0x07A`, GPIO2 bit 21 = **WL_IRQ**)
  as a wake source, but the consumer (`0x10684`) runs only from
  `omap4_core_state_set`/`omap4_core_state_restore` — i.e. only on OSWR
  entry/exit, never at boot.
* No boot-time write touches MMCHS5, `CM_L4PER_HSMMC5` (`0x4A009560`) or a TWL
  WLAN rail.  `MMCHS5`/`ATTILA_L4PER_TA_HSMMC5` appear only as CRED database
  names; `PRM` is touched only by the generic VC/VP/power-domain init.

## 5. `tiwlan_winchester.ini` — all clock/power fields are firmware-time

`/base/lib/firmware/ti1283/tiwlan_winchester.ini` (the driver is loaded with
`-o nvram,firmdir=/lib/firmware/ti1283`):

| field | value | meaning |
|---|---|---|
| `TCXO_Clk` | `1` | 26 MHz main clock |
| `STRFRefClock` | `2` | 38.4 MHz FREF, wired-OR CLK_REQ, normal polarity |
| `STRFRefClockSettingTime` | `5` | 5 ms from CLK_REQ to valid FREF |
| `ClockValidOnWakeup` | `0` | FREF not valid on wakeup |
| `TCXO_SettlingTime` | `5` | 5 ms from CLK_REQ to valid TCXO |
| `TCXO_ClockValidOnWakeup` | `0` | TCXO not valid on wakeup |
| `TCXO_LDO_Voltage` | `0` | chip's internal TCXO LDO = **2.5 V** |
| `Platform_configuration` | `2` | bits 2:1 = `01` → 4 mA SDIO drive; no level shifter, no EEPROM, SDIO IB enables 0, HS support 0 |

All of these are consumed by the firmware **after** SDIO enumeration
(`wl128x_boot_clk()` runs during firmware init).  The board must supply the
26 MHz TCXO and the 32.768 kHz slow clock from power-on; the `.ini` does not
configure them.  The `TCXO_LDO_Voltage = 0` is the chip's own LDO setting
(2.5 V), not the module's 1.8 V supply wording in the Motorola guide; either
way it is not a pre-enumeration host action.

## 6. What this settles, and the one live read left

**Settled, with static evidence:**

* the QNX powerman preset (report 187) and `devpm-omap4.so` do not switch a
  WLAN rail or clock;
* the MMC driver's powerman client only acknowledges `-power on/off` and
  requests no clock/voltage/bus power;
* the board pad/GPIO database contains only the six known WLAN lines (plus the
  two FREF pads), with the same muxing the live 1917 reads show;
* the WLAN `.ini` clock/power fields are firmware-time, after enumeration;
* the PPS `hw_info` inventory does not contain a WLAN node, and no static HWI
  database exists in the 1917 trees.

**The one live read left** is the syspage `WLAN` hwinfo node itself, because it
is not a file.  `tools/qnx-hwi.c` prints it (`hwi_find` is a driver-local
helper, so the tool implements the by-name walk over libc's
`hwi_off2tag`/`hwi_next_tag`/`__hwi_find_string`).  **It was run on the live
1917 in this session and contains only `WLAN_EN_GPIO=54,WLAN_INT_GPIO=53` —
see §8.**  Even the node's own `location` tag is all zero, and its only
documented consumers are those two pin options (`devnp-ti1283.so`'s own option
names); the whole-binary audit shows the driver touches no PMIC, CM/DPLL or
regulator.  So the read can change the pin numbers at most, not the
power/clock conclusion.

**Conclusion: the QNX software surface is exhausted.  The remaining candidate
is the chip's non-exposed VBAT/TCXO pins or OMAP HSMMC sampling, which needs a
schematic/board view or a logic analyser (reports 184 §5, 188 §4).**

## 8. Addendum — the live syspage read (same session, TabletOS 2.1.0.1917)

The 1917 IFS (`local/work/ifs-shim-sealed.ifs`) was flashed to region 0 and
booted for the one live read.  The door needed a restart: a stale
`BerryShell-V4` holder from 09:48 and the new one were killed by **explicit
PID** (never `pgrep -f`/`pkill -f`), then a fresh `setsid tools/door-hold.sh`
authenticated and uploaded the key.

-static`): the device's 2014 libc does **not** export the low-level hwinfo
