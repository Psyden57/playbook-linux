## §0 TL;DR

### 0.1 The headline: this unit uses **GPIO**, not a regulator register

`regulator_info[regen1].type == 1` (a *"extreg"* class). For `type == 1` the resmgr diverts to
`winchester_extreg_set_state` / `winchester_extreg_get_state`, which **never touch I²C**. They poke
one OMAP GPIO module. On a unit whose board revision is ≥ 5 (or unparsable) — i.e. DVT3+ — the
diversion is taken; on rev ≤ 4 the call returns 1 and the code falls through to the normal
TWL6030 register path (§3.3).

| Command on **this** (DVT3+/MBID≥5) unit | Slave | Register(s) | Value(s) | Confidence |
|---|---|---|---|---|
| `set_state regen1 on [groups]` | **none — no I²C** | OMAP `GPIO1` @ `0x4A310000` + **`0x194`** (`GPIO_SETDATAOUT`) | **`0x00000004`** (bit 2) | **proven** |
| `set_state regen1 off` | none | `GPIO1` + **`0x190`** (`GPIO_CLEARDATAOUT`) | `0x00000004` | **proven** |
| `set_state regen2 on` / `off` | none | same two registers | `0x00008000` (bit 15) | **proven** |
| `set_state vaux3 on app` | **`0x48`** | burst-read `0x8C`(4 B, only if force-update), then **`0x8E` ← `0x21`**, then read-back `0x8E`(1 B) | `0x21` | **proven** |
| `-p regen1,vaux3` | none | — (sets `reg_desc_tbl[idx].+8 = 1` and starts the powerman client) | — | **proven** |
| `get_state regen1` | none | `GPIO1` + **`0x13C`** (`GPIO_DATAOUT`) read; test bit 2; `app = ldo = (bit?2:0)`, `con = mod = 0` | — | **proven** |
| `get_state vaux3` | `0x48` | read `0x8C` (4 B burst) or cached; **decode `buf[2]` = register `0x8E`** | — | **proven** |

**Registers/bits for `get_state` (this is the ground-truth decode to compare Linux against):**

```
byte v = CFG_STATE  (0x48 / 0x8E for vaux3; 0x48 / 0xAF for regen1 — but regen1 never uses it here)

ldo = tbl[v & 3]        tbl = {0:OFF, 1:ON, 2:OFF, 3:SLEEP}      @ resmgr 0x6ce0
app = tbl[(v>>2)&3]
con = tbl[(v>>4)&3]
mod = tbl[(v>>6)&3]
```

**What `-p` does:** nothing to the PMIC. It only flags the named rails as powerman-managed
(`reg_desc_tbl[idx].+8 = 1`) and then `main` blocks in a powerman client loop; the actual state
change happens later when powerman sends a `REQUESTED_MODE` and the callback issues the *same*
`0x80140505` `set_state` devctl. Details §1.2.

**Proven structural fact:** `pmic-twl6030-ctl` itself emits **zero I²C**. It has no
`/dev/i2c*` string, no `devctlv` import, and only `devctl()`. It is a client of
`/dev/pmic/regulator`, served by `pmic-winchester-twl6030`. All slave addresses/registers below come
from that server. §2.

## §1 Command dispatch and the `-p` option (`pmic-twl6030-ctl`)

### 1.1 `main` @ `0x30d8`; options

`getopt` string @ `0x5350` = **`"c:f:p:ivU:"`** (verified by raw hexdump, not just the string list).
Branch table over `c - 'U'`, 34 slots (`0x3140 addls pc,pc,r3,lsl #2`, base `0x3148`):

| opt | target | effect |
|---|---|---|
| `-c file` | `0x31dc` | `[sp+0] = optarg` — newline-delimited command file |
| `-f path` | `0x31ec` | `fp = optarg` — **overrides `/dev/pmic/regulator`** |
| `-p list` | `0x31f8` | `fcn.0000300c(optarg)`, then `r9 = 1` (powerman mode) |
| `-i` | `0x31d0` | `[sp+8] = 0` — "don't background" |
| `-v` | `0x3210` | `verbose++` (`verbose` @ absolute `0x7404`, = `GOT 0x7000 + 0x404`) |
| `-U user` | `0x3220` | `strdup(optarg)` → `[sp+4]` |
| other | `0x3234` | `"\npmic-twl6030-ctl[ERROR]: Invalid option: '%c'"` |

Default path `fp = 0x530c = "/dev/pmic/regulator"` (`lit[0x368c]=0xffffe30c`).

> **Documented/actual mismatch (real defect, worth knowing):** `QNX_usage` @ `0x655b` advertises
> `-r resmgr_path`. The shipping `getopt` string accepts **`-f`**; `-r` is rejected as invalid.

### 1.2 `-p <regulator>` — exact behaviour

`fcn.0000300c` (180 B, @ `0x300c`):

```
0x3018  strdup(optarg)
0x302c  strtok(copy, ",")
0x305c  fcn.00001ac4(token)          ; name -> index 0..19  (see 1.4)
0x3064  cmn r0,#-1 -> "\npmic-twl6030-ctl[ERROR]: Unknown regulator: %s\n", abort
0x3094  add r0,r0,r0,lsl#1           ; idx*3
0x3098  add r0,r5,r0,lsl#2           ; r5 = &reg_desc_tbl  ->  idx*12
0x309c  str r7,[r0,#8]               ; r7 == 1  ==>  reg_desc_tbl[idx].powerman = 1
0x30a0  strtok(NULL, ",")  ... loop
```

So `-p` writes **exactly one byte of process-local state per name** and nothing else. Then
`main` (`0x35e8`, `r9 != 0`) calls `fcn.00003b84`, the powerman client:

* attaches to `system/power/mgr` (`0x59e4`), `CONNECT::%d,%s,%s\n` is the login verb;
* registers `ldo_<name>?nopersist,delta,critical,f=REQUESTED_MODE` per flagged rail
  (`0x580c "ldo_%s"`, `0x5964 "%s?nopersist,delta,critical,f=REQUESTED_MODE"`);
* on each `REQUESTED_MODE::` pulse → `"\npmic-twl6030-ctl[INFO]: Setting %s to power mode: %s"`,
  then issues the **same `0x80140505` set_state devctl** (§1.4) that the CLI would — built at
  `0x37d4`–`0x3810` as `{reg, app=1, con=1, mod=1, state}` (i.e. it requests *all three* groups,
  not just `app`), so the powerman path and the config-file path do **not** produce the same byte
  for a `type==0` regulator;
* honours the guard `/dev/shmem/ldo_ctl_disable` (`0x5674` / `0x5690`) — the CLI/config path does
  **not** check that file.

So `pmic-twl6030-ctl -p regen1` **on its own changes no hardware**; it just becomes the powerman
slave for regen1.

### 1.3 Command table @ `0x729c` (23 × 8 B `{char *name; int type}`) and `reg_desc_tbl` @ `0x71ac`

```
get_groups 0   set_groups 1   get_trans 2   set_trans 3   get_state 4   set_state 5
get_vout 6     set_vout 7     get_pd 10     set_pd 11     lock_offset 12  unlock_offset 13
lock_mult 14   unlock_mult 15 get_offset 16 set_offset 17 get_mult 18    set_mult 19

```

`reg_desc_tbl` @ **`0x71ac`**, 20 records × 12 B `{const char *name; int index; int powerman}`.
The `index` is the **wire regulator id** handed to the resmgr (it equals the resmgr's
`regulator_info[]` slot, see §3):

| idx | name | | idx | name | | idx | name | | idx | name |
|---|---|---|---|---|---|---|---|---|---|---|
| 0 | `vana` | | 5 | `vdac` | | 10 | `vusim` | | 15 | `v2v1` |
| 1 | `vaux1` | | 6 | `vmmc` | | **11** | **`regen1`** | | 16 | `vmem` |
| 2 | `vaux2` | | 7 | `vpp` | | **12** | **`regen2`** | | 17 | `vcore1` |
| **3** | **`vaux3`** | | 8 | `vrtc` | | 13 | `v1v29` | | 18 | `vcore2` |
| 4 | `vcxio` | | 9 | `vusb` | | 14 | `v1v8` | | 19 | `vcore3` |

Lookup `fcn.00001ac4` @ `0x1ac4`: `strcmp(name, tbl[i].name)`, 20 iterations, returns `tbl[i].index`.

Executor `fcn.00001c70` (4420 B) `strtok`s on `" \t\r\n"` (`0x50c4`), matches token 0
(`cmp r4,#23`), then `0x1d04 addls pc,pc,r5,lsl #2` (base `0x1d0c`) dispatches on the *type*.

### 1.4 `set_state <reg> <state> [group…]` — operand decoding, `0x226c`

State/group tokens are matched against the string pool (`0x7000 + word`):

| token | address | field | value |
|---|---|---|---|
| `off` | `0x5198` | `+16 state` | **0** |
| `sleep` | `0x519c` | `+16 state` | **1** |
| `on` | `0x51d4` | `+16 state` | **2** |
| `app` | `0x515c` | `+4` | 1 |
| `con` | `0x5160` | `+8` | 1 |
| `mod` | `0x5164` | `+12` | 1 |

Request buffer built at `sp+0xDC`, 20 bytes `{int reg; int app; int con; int mod; int state;}`.
(`str r0,[sp,#220]` = reg; `[224]/[228]/[232]` = app/con/mod; `[236]` = state.)

```
0x23b0  str r3(=0),[sp]                  ; devctl arg 5 = 0
0x23b8  r0 = reg_fd                      ; lit[0x2d00]=0x1a8 -> GOT 0x71a8
0x23c0  movw r1,#0x0505 ; movt r1,#0x8014  => r1 = 0x80140505
0x23c8  r2 = sp+0xDC ; 0x23cc r3 = 20
0x23d0  bl devctl
```

`get_state <reg>` @ `0x21bc`: same 20-byte buffer, `r1 = 0xC0140504`
(`movw #0x0504` / `movt #0xC014`), then prints
`"Groups and LDO states:"` + `APP`(buf+8) `CON`(buf+12) `MOD`(buf+16) `LDO`(buf+4)
via `fcn.00001bdc`, whose enum is **0=`OFF` (0x50c8), 1=`SLEEP` (0x50f8), 2=`ON` (0x5100)**,
else `*UNKNOWN*` (0x50e4).

That ordering is exactly why the reference OS line reads
`APP: ON / CON: OFF / MOD: OFF / LDO: ON`.

## §2 The "I²C write helper" — there is none in `pmic-twl6030-ctl`

* Imports: `devctl` only (`ir` JUMP_SLOT `0x708c`). **No `devctlv`.**
* No `/dev/i2c*` string in all 31 151 bytes; the only device paths are
  `/dev/pmic/regulator` (`0x530c`) and `/dev/shmem/ldo_ctl_disable` (`0x5674`).
* `reg_fd` (`GOT 0x71a8`) is set by `open(fp, 2)` at `0x326c`–`0x3278`.

Devctl ABI it speaks (class **`0x05`**; DCMD fields verified at every call site:
bits 16..23 = payload size, bits 8..15 = class, bits 0..7 = command):

| DCMD | cmd | shape | meaning |
|---|---|---|---|
| `0xC0140500` | 0 | R, 20 B | `get_groups` |
| `0xC0140504` | 4 | R, 20 B | **`get_state`** → `{reg, ldo, app, con, mod}` |
| `0x80140505` | 5 | RW, 20 B | **`set_state`** ← `{reg, app, con, mod, state}` |
| `0x80140514` | 0x14 | RW, 20 B | `mask_preq` ← `{preq1, preq2, preq3, …}` |
| `0x80140515` | 0x15 | RW, 20 B | **`unmask_preq`** |
| `0x8004/0xC014 0506/0507` | 6/7 | | force-update get/set (`set_force_update 1` makes all later reads hit I²C) |

So the last line of `pmic-twl6030.cfg`, `unmask_preq 1`, is literally
`devctl(reg_fd, 0x80140515, {1,0,0,0,0}, 20, 0)`.

**The actual I²C is in the server** — `/dev/pmic/regulator` is attached by
`pmic-winchester-twl6030` (`izz` 0x685c `"/dev/pmic/regulator"`, `0x67cc` `"/dev/i2c0"`,
`resmgr_attach() failed…`). That binary has the two helpers referenced by
`"pmic-twl6030:   twl6030_i2c_read fail\n"` (0x66ec) and `"…write fail"` (0x6714):

**write** — `twl6030_i2c_write(handle, addr, reg, valp, n)` @ `0x1c74`
```
hdr[16] @ sp+0x30 = { addr, 2, n+1, 1 }        ; 0x1c8c..0x1ca4
iov[3]  @ sp+0x18 = { {&hdr,16}, {&reg,1}, {valp,n} }   ; 0x1ca8..0x1cc8
fd = ((struct*)handle)->+0x74                  ; 0x1ccc
0x1ce4  r1 = 0x80100505
0x1cec  r2 = 3                                 ; sparts = 3
0x1cf0  bl devctlv(fd, 0x80100505, 3, 0, iov, NULL, NULL)
```
**read** — `twl6030_i2c_read(handle, addr, reg, outp, n)` @ `0x1b8c`
```
desc[20] @ sp+0x1c = { addr, 2, 1, n, 1 }      ; 0x1ba0..0x1bbc
iovA[2]  @ sp+0x40 = { {&desc,20}, {&reg,1} }  ; 0x1bc4..0x1bd8   (send)
iovB[2]  @ sp+0x30 = { {&desc,20}, {outp,n} }  ; 0x1bdc..0x1be8   (receive)
0x1c00  r1 = 0xC0140507
0x1c10  sparts = rparts = 2
0x1c18  bl devctlv(fd, 0xC0140507, 2, 2, iovA, iovB, NULL)
```
i.e. the same QNX OMAP-I²C 4-word header pattern as `108-re-wdtkick-pmic.md` §3.1
(`{addr, len, nbufs, flags}`), wire effect: `S <addr>(W) <reg> [Sr] <addr>(R) <n bytes> P`
for reads, `S <addr>(W) <reg> <n bytes> P` for writes. Bus speed is set to 100 kHz
(`0x80040502`, cf. report 108). The register byte is always **8-bit** (`strb r2,[sp,#23]`).

### 2.1 "TWL module base constants" — there are none

The resmgr does **not** use `TWL6030_BASEADD_PM_MASTER`-style macros or the QNX PMIC API. The
register number for every regulator is data, read out of the descriptor table:

`regulator_info` @ **`0x9168`**, 20 records × **32 B**, laid out

| off | field | notes |
|---|---|---|
| +0 | `int id` | 0 … 19 (same as the array slot) |
| +4 | **type** | 0 = LDO, **1 = "extreg" (regen1/regen2)**, 2 = SMPS-aux, 3 = VCore SMPS |
| +8 | `const char *name` | `0x76bc "vana"` … `0x7750 "vcore3"` |
| +12 | `u8 base_reg` | first register of the 4-register block (only this byte is ever used) |
| +13 | `u8` | `0xf4` for `vana…vpp`, `0xf5` for `vusb/vusim`, `0x00` for `vrtc`, `0x01…0x06` for SMPS — never read by the code |
| +14 | `u8` | `1<<n` position for LDOs (`vana`=1, `vaux1`=2, `vaux2`=4, `vaux3`=8, `vcxio`=0x10, `vdac`=0x20, `vmmc`=0x40, `vpp`=0x80); 0 for `vrtc`/`regen1`/`regen2` |
| +15 | `u8` | 0 in every record |
| +16.. | `u16 vout_table[]` | allowed mV values, null-terminated/`0`-padded |

(`+13`/`+14` are never dereferenced by any function I traced — grep for `[rX,#13]`/`[rX,#14]` on a
`regulator_info` base returns nothing. Only `+0, +4, +8, +12` and the `+16..` vout table are read.)

The **only** slave addresses in the whole PMIC path:

| slave (7-bit) | used for |
|---|---|
| **`0x48`** | every PMIC register write/read in this code path — LDO bank `0x80–0xAF`, config `0xE0–0xF6`, `MSK_TRANSITION` `0x20` |
| `0x49` | `pmic_twl6030_cfg` only (`0x07←0xFF`, `0x06←0x05`, `0x04←0x05`) — report 108 |
| `0x4A` | ES-revision probe `reg 0x87` — report 108 / `pmic_twl6030_cfg` |

## §3 REGEN1

### 3.1 Table entry

`regulator_info[11]` @ `0x92C8` (raw words: `0x0000000b 0x00000001 0x00007710 0x000000ad
0 0 0 0`):

```
+0  = 0x00000000  (word) -> id / slot 11
+4  = 0x00000001        <-- type == 1  ("extreg")
+8  = 0x00007710 "regen1"
+12 = 0x000000AD        <-- base_reg = 0xAD  (+13 = 0x00, +14 = 0x00, +15 = 0x00)
+16..+28 = 0            (no vout table)
```
`regen2` @ `0x92E8` is identical with `base_reg = 0xB0`.

`regen1`'s `base_reg` is used **only** by `winchester_init` (§3.4) and by the generic cache fill,
never by `set_state` on a DVT3+ unit.

### 3.2 The DVT3+ decision (proven)

`winchester_init` @ `0x5e34`:

```
0x5e58  mov  r0,#4096 ; movw r2,#0 ; movt r2,#18993 (0x4A31)
0x5e68  bl   mmap_device_io(0x1000, 0x4A310000)      <-- OMAP GPIO1
0x5e6c  r3 = GOT+0x438 (=0x9438)
0x5e74  str  r0,[r3,#4]                              ; global GPIO base -> 0x943C
...
0x5eb4..0x5ef0   confstr(5, buf,128) ; strstr(buf, "Rev:")
                 strtoul(buf+4, …, 10) ; errno
0x5f14  if (value == 0 && errno == 22)   -> 0x5f24 : slogf("… Unable to determine board revision
                                                    so setting regen1 and regen2 GPIO controlled")
                                        0x5f3c  [0x9438] = 1
0x5f4c  else if (value > 4)              -> 0x5f54 : slogf("… Detected MBID=5+, regen1 and regen2
                                                    GPIO controlled")
                                        0x5f6c  [0x9438] = 1
0x5f7c  else (value <= 4 = DVT2- and earlier) : [0x9438] stays 0
```

**`[0x9438] != 0` ⇔ "GPIO-controlled regen1/regen2" (DVT3+).** The two globals are
`0x9438` = flag, `0x943C` = mapped GPIO base.

### 3.3 `set_state regen1 on` — the exact write

Dispatcher: DCMD `0x80140505` → `0x1940` → `twl6030_set_state` @ `0x4ea0`:

```
0x4eb0  r6 = handle ; r5 = req
0x4eb4  r3 = req->reg ; [sp+4] = r3
0x4ec0  r2 = &regulator_info ; 0x4ec8 r3 = &info[reg]
0x4ecc  r3 = type
0x4ed0  cmp r3,#1
0x4ed4  bne 0x4ee4                       ; not extreg -> normal TWL path
0x4ed8  bl  0x5c80                       ; winchester_extreg_set_state
0x4edc  cmp r0,#0
0x4ee0  ble 0x4fcc                       ; r0 == 0  -> done (GPIO written)
                                         ; r0 == 1  -> fall through to TWL path (DVT2-)
                                         ; r0 == -1 -> return -1
```

`winchester_extreg_set_state` @ **`0x5c80`** (the whole function):

```
0x5c8c  ldr r3,[pc,#144]  lit=0x438  ->  0x5c90  ldr r3,[GOT+0x438]      ; *(0x9438) = flag
0x5c94  cmp r3,#0 ; 0x5c98 moveq r0,#1 ; popeq   ; not GPIO-mapped -> return 1
0x5ca0  ldr r3,[r1,#16]                          ; req->state
0x5ca4  cmp r3,#0
0x5cac  ldr r3,[pc,#112] lit=0x438 -> 0x5cb0 r3 = 0x9438
0x5cb4  ldr r0,[r3,#4]                           ; r0 = *(0x943C)  = GPIO base
0x5cb8  add r0,r0,#404   (state != 0)            ;   + 0x194 = GPIO_SETDATAOUT
0x5cc0/0x5cc8 add r0,r0,#400  (state == 0)       ;   + 0x190 = GPIO_CLEARDATAOUT
0x5cd0  ldr r3,[r1]                              ; req->reg
0x5cd4  cmp r3,#11                               ; regen1
0x5cd8  moveq r3,#4
0x5cdc  streq r3,[r0]                            ; *(u32*)(GPIO+0x194) = 0x00000004
0x5ce0  moveq r0,#0 ; popeq                     ; return 0
0x5ce8  cmp r3,#12                               ; regen2
0x5cec  moveq r3,#32768                          ; 0x8000
0x5cf0  streq r3,[r0]                            ; *(u32*)(GPIO+0x194) = 0x00008000
```

So for `set_state regen1 on`:

> **`*(volatile uint32_t *)(GPIO1_BASE + 0x194) = 0x00000004;`** — and nothing else.
> `off` → `*(volatile uint32_t *)(GPIO1_BASE + 0x190) = 0x00000004;`
> `sleep` (state==1) is treated identically to `on` (both take the `state != 0` branch).

`GPIO1_BASE = 0x4A310000` per the OMAP4430 TRM L4_WKUP map
(`swpu231ap.pdf.txt:17775-17776`: `0x4A31 0000 … 0x4A31 0FFF 4KB Module  GPIO1`).

Notes, all proven from the instruction stream:

* **No** `GPIO_OE` (`+0x134`), **no** `GPIO_CTRL` (`+0x114`), **no** `GPIO_IRQSTATUS*`, and **no**
  padconf write anywhere in the resmgr. The module offset `0x134`/`0x114` never appears as a
  constant. ⇒ the pin must already be muxed to GPIO mode **and** output-enabled by QNX
  `startup`/`procnto`, which is not in this binary. Linux must do both itself (§6).
* The write is **not** read-modify-write; a whole 32-bit `1`-in-one-bit value is stored to the
  set/clear alias, so other GPIO1 lines are unaffected.
* The group arguments (`app`/`con`/`mod`) are **ignored** on this path — the store happens before
  any group field is examined. Same for `state == sleep` vs `on`.

### 3.4 What init does to regen1's *registers* on a DVT3+ unit

`winchester_init`, immediately after setting `[0x9438] = 1` (only on the GPIO branch):

```
0x5f8c  r3 = *(0x913C)          ; == 0x9168 == &regulator_info[0]
0x5f94  r2 = *(u8*)(r3 + 364)   ; 364 = 0x16C -> regulator_info[11].base_reg = 0xAD
0x5f98  r2 += 2                 ;  -> 0xAF  = regen1 CFG_STATE
0x5fa0  r1 = 72 (0x48) ; r3 = 224 (0xE0)
0x5fac  bl twl6030_i2c_write(handle, 0x48, 0xAF, &0xE0, 1)   ; "Failed to disable regen1"

0x5fdc  r2 = *(u8*)(regulator_info + 364) = 0xAD              ; GRP register
0x5ff0  r3 = 0
0x5ff4  bl twl6030_i2c_write(handle, 0x48, 0xAD, &0x00, 1)   ; "Failed to detach regen1 from
                                                              ;  all groups"
```

⇒ On boot of a DVT3+ unit: **write `0x48`/`0xAF` ← `0xE0`; write `0x48`/`0xAD` ← `0x00`**
(regulator disabled + detached), and only then does the GPIO own the rail. (The analogous regen2
block follows.)

### 3.5 DVT2- branch (for completeness)

If the flag is 0, `winchester_extreg_set_state` returns 1 and `twl6030_set_state` falls through at
`0x4ee4` to the normal path, which for `regen1` (`type == 1`) does:

* `twl6030_reg_read(handle, 11, mode)` @ `0x48f0` type-1 arm (`0x49a8`): one **3-byte** burst read
  from `base_reg` = `0xAD`, into the per-regulator 4-byte cache; then
  `cache[+3] = 0xFF` (`0x49e0-0x49e4`).
* `twl6030_write_state(handle, 11, v)` @ `0x43ec`: `write(0x48, 0xAD+2 = 0xAF, v)`.
* read-back `twl6030_read_state` @ `0x4308`: `read(0x48, 0xAF, 1)`.

So on DVT2- the target register would be `0xAF` — **not used on your unit.**

## §4 VAUX3

### 4.1 Table entry

`regulator_info[3]` @ `0x91C8` (raw words: `0x00000003 0x00000000 0x000076d4 0x0008f48c
0x04b003e8 0x07080514 0x0af009c4 0x00000bb8`):

```
+0  = 3                 <-- id / slot
+4  = 0x00000000        <-- type == 0 (LDO)
+8  = 0x76d4 "vaux3"
+12 = 0x0008f48c        <-- base_reg = 0x8c  (+13 = 0xf4, +14 = 0x08, +15 = 0x00)
+16..+29 = u16 vout table: 1000 1200 1300 1800 2500 2800 3000 mV
```

The four registers of the block are therefore `0x8C`, `0x8D`, `0x8E`, `0x8F` — confirmed by the
type-0 cache fill `fcn.000048f0` @ `0x4974`: `read(0x48, base_reg, 4 bytes)` into `cache[reg*4 .. +3]`
(`n = 4` at `0x498c`, `out = cache + reg*4` at `0x4998`, `bl 0x1b8c` at `0x499c`).
Cross-check: `pmic_twl6030_cfg` writes the repeating pattern `{+0:0x01, +1:0x03, +2:0x21, +3:0x13}`
at `0x84/0x88/0x8C` (report 108 §3.1) — for vaux3, `0x8C←0x01, 0x8D←0x03, 0x8E←0x21, 0x8F←0x13`.

### 4.2 `set_state vaux3 on app` — exact sequence

`twl6030_set_state` @ `0x4ea0` → `type != 1` ⇒ straight to `0x4ee4`:

```
0x4ee4  mov r0,r6 ; add r1,sp,#4 ; bl 0x4df8     ; (a) get_state into the local copy
0x4ef8  r3 = req->app   ; if 0 -> 0x4f14
0x4f04  r2 = req->state ; r1 = local.app ; if equal -> 0x4f14     ; "no change" shortcut
0x4f68  r0 = 0x20                                                  ; APP group bit
0x4f6c  r3 = req->con ; if !=0 -> r1 = 0x40
0x4f7c  r3 = req->mod ; if !=0 -> r3 = 0x80
0x4f8c  r2 = req->state ; if >2 -> r2 = 0
0x4f98..0x4fa4  r2 = state_map[state]     (table @ 0x6E98 = {0, 3, 1})
0x4fa8  r1 |= r0 ; 0x4fac r3 = r1|r3 ; 0x4fb8 r2 |= r3
0x4fbc  bl 0x43ec                        ; twl6030_write_state(handle, 3, r2)
```

`state_map` @ `0x6E98` (`ldrbls r2,[r2,#472]`, tables resolved from `0x6cc0 + 0x1d8`):
**state 0(off) → `0b00`; state 1(sleep) → `0b11`; state 2(on) → `0b01`** in the low 2 bits.

Then `twl6030_write_state` @ `0x43ec`:

```
0x4404  r2 = &regulator_info[reg] ; 0x4410 r3 = type
0x4414  cmp r3,#3 ; bhi skip                    ; type 0..3 -> I2C
0x4424  r2 = &info[reg] ; 0x4428 r2 = *(u8*)(r2+12)   ; = 0x8C
0x442c  add r2,r2,#2                                  ; -> 0x8E
0x4430  r1 = 72                                       ; slave 0x48
0x4434  r3 = value (from r2 at 0x4400)
0x4438  bl 0x1d30  -> twl6030_i2c_write(handle, 0x48, 0x8E, &value, 1)
0x4480  bl 0x4308  -> twl6030_read_state(handle, 3, NULL)   ; 1-byte read-back of 0x8E
```

`twl6030_read_state` @ `0x4308`:
```
0x4344  r2 = *(u8*)(info[reg]+12) = 0x8C ; 0x4348 r2 += 2 -> 0x8E
0x434c  r1 = *(0x9154)                   ; per-regulator 4-byte cache pointer
0x4358  r1 = 72                          ; slave 0x48
0x4360  r3 = cache + reg*4 + 2            ; out
0x4364  bl 0x1c58 -> twl6030_i2c_read(handle, 0x48, 0x8E, out, 1)
0x43c4  *out = cache[reg*4+2]
```

And step (a) `twl6030_get_state` @ `0x4df8` → `0x4e3c ldr r2,[r5,#128]` = `handle->force_update`:
`twl6030_reg_read(handle, reg, force)`; in `0x48f0` `cmp r2,#0 ; beq 0x4af4` means
**force == 0 ⇒ no I²C, use the cache**.

> **Exact I²C emitted by `set_state vaux3 on app` on a default (force_update == 0) system:**
>
> 1. `0x48` / reg `0x8E` ← **`0x21`** (one byte) — `0x20` (app) | `0x01` (state_map[on])
> 2. `0x48` / reg `0x8E` → read 1 byte (cache refresh / verify)
>
> With `set_force_update 1` an extra step precedes (1): a **4-byte burst read** of `0x48`/`0x8C`
> (registers `0x8C 0x8D 0x8E 0x8F`).
>
> **There is no read-modify-write of `0x8E`, no PREQ/PWR_REQ handshake, no wait-for-transition,
> no second register touched.** The `set_trans`/`unmask_preq` machinery is entirely separate (§5.3).
>
> **Caveat on the value:** `0x21` is what the *config-file / CLI* path produces (`app` only). The
> `-p` powerman callback (`pmic-twl6030-ctl` `0x37d4`) always requests **all three groups**, so the
> same rail set through powerman yields `0x20|0x40|0x80|0x01 = 0xE1` instead. If you are matching a
> live capture, check which of the two paths ran.

### 4.3 Bit fields — and a genuine inconsistency you must know about

The resmgr contains **two mutually inconsistent readings of `CFG_STATE`**:

| | bit assignment | evidence |
|---|---|---|
| **encoder** (`set_state`, `winchester_init`) | `0x20`=APP, `0x40`=CON, `0x80`=MOD, `[1:0]`=state | `0x4f68/0x4f74/0x4f84`; `0x5fa8 r3=0xE0` |
| **decoder** (`get_state`) | `[1:0]`=LDO, `[3:2]`=APP, `[5:4]`=CON, `[7:6]`=MOD | `0x4e54/0x4e64/0x4e74/0x4e84` |

Both are proven instruction-for-instruction. Consequences:

* `set_state vaux3 on app` writes **`0x21`**. The encoder's intent is
  *"APP group enabled, regulator state = ON"*, which is also exactly what `pmic_twl6030_cfg`
  programmed at boot and what `0xE0` ("all three groups, state OFF") means in the init disable path
  — so the encoder is self-consistent in two independent places.
* Feeding `0x21` into the *decoder* yields `LDO: ON, APP: OFF, CON: OFF, MOD: OFF`
  (`[1:0]=01→ON`, `[3:2]=00→OFF`, `[5:4]=10→OFF`, `[7:6]=00→OFF`).
  Your live unit prints **`APP: ON`** for vaux3, which under the decoder requires `[3:2]=01`,
  i.e. `0x8E ∋ 0x04`. So the live byte is **not** `0x21`.

Which one matches silicon cannot be settled from these two binaries — it needs the **TWL6030
datasheet** (the supplied `swpu231ap.pdf.txt` is the OMAP4430 TRM and does not cover the TWL).
See §7 item 1. **The I²C bytes (`0x48`/`0x8E`/`0x21`) are not in doubt**; only what the hardware
means by them is.

## §5 `get_state` read path

Dispatcher: DCMD `0xC0140504` → `0x1918` → `bl 0x4df8` (`twl6030_get_state`).

### 5.1 `get_state regen1` — no I²C at all

`0x4e14`: `type = regulator_info[11].type == 1` ⇒ `0x4e28 bl 0x5d34`
(`winchester_extreg_get_state`), `cmp r0,#0 ; pople` → r0 ≤ 0 returns.

`winchester_extreg_get_state` @ **`0x5d34`**:

```
0x5d40  r3 = *(0x9438) ; 0x5d48 cmp 0 ; 0x5d4c moveq r0,#1 ; popeq    ; not mapped -> 1
0x5d54  r3 = req->reg
0x5d58  cmp r3,#11  (regen1)
0x5d60  r3 = *(0x943C)          ; GPIO base
0x5d6c  r3 += 316               ;   + 0x13C = GPIO_DATAOUT
0x5d70  r3 = *(u32*)r3
0x5d74  and r3,r3,#4            ;   bit 2
0x5d7c  cmp r3,#12  (regen2) -> and r3,r3,#0x8000        ; bit 15
0x5dc8  cmp r3,#0
0x5dcc  movne r3,#2  / moveq r3,#0
0x5dd4  str r3,[req+8]          ; APP  = 2 (ON) or 0 (OFF)
0x5dd8  r0 = 0
0x5ddc  str r0,[req+12]         ; CON  = 0   (always OFF)
0x5de0  str r0,[req+16]         ; MOD  = 0   (always OFF)
0x5de4  str r3,[req+4]          ; LDO  = same as APP
```

⇒ `get_state regen1` on your unit reads **`GPIO1` + `0x13C` (`GPIO_DATAOUT`), bit 2**, and
synthesises `APP = LDO = (bit?ON:OFF)`, `CON = MOD = OFF`. That is an exact match for the live
`APP: ON / CON: OFF / MOD: OFF / LDO: ON` when the rail is on — strong independent confirmation
that the GPIO bit (not a TWL register) is the real mechanism on this board.

(Note: it reads `GPIO_DATAOUT` (the output latch) at `+0x13C`, not `GPIO_DATAIN` at `+0x138`.)

### 5.2 `get_state vaux3`

`0x4e34`: `twl6030_reg_read(handle, 3, force_update)` — with `force_update == 0` this returns the
cached 4 bytes with **no bus traffic**; the cache is (re)filled at init and after every
`twl6030_write_state`. Then:

```
buf = cache[3*4 .. 3*4+3]  ==  registers 0x8C, 0x8D, 0x8E, 0x8F
v   = buf[2]               ==  CFG_STATE (0x8E)
req->ldo = tbl[v & 3]
req->app = tbl[(v>>2)&3]
req->con = tbl[(v>>4)&3]
req->mod = tbl[v>>6]
tbl @ 0x6ce0 = {0: OFF enum 0, 1: ON enum 2, 2: OFF enum 0, 3: SLEEP enum 1}
```

So the "ground truth" comparison you want from Linux is:

```c
v = i2c_smbus_read_byte_data(c, 0x8E);           /* vaux3 CFG_STATE */
raw2s[4] = {OFF, ON, OFF, SLEEP};                /* resmgr enum */
printf("LDO:%d APP:%d CON:%d MOD:%d\n",
       raw2s[v & 3], raw2s[(v>>2)&3], raw2s[(v>>4)&3], raw2s[v>>6]);
```

with `0 → OFF`, `2 → ON`, `1 → SLEEP` in the ctl's numbering (0=OFF,1=SLEEP,2=ON).

### 5.3 `unmask_preq` / PWR_REQ — what it actually is

DCMD `0x80140514` (mask) and `0x80140515` (unmask) both land on `0x1aa8` → `0x3850`
(`access_preq_mask`):

```
0x3774(handle, 0)                       ; refresh
0x387c  r2 = (req->preq1 ? 0x20 : 0)
0x388c/0x3894  | (req->preq2 ? 0x40 : 0)
0x389c/0x38a4  | (req->preq3 ? 0x80 : 0)
0x38b0  if (dcmd == 0x80140514 /*mask*/)   cache[0] |=  r2
0x38d0  if (dcmd == 0x80140515 /*unmask*/) cache[0] &= ~r2
0x3900  r1 = 72 (0x48) ; r2 = 32 (0x20)          ; MSK_TRANSITION_REG
0x3908  r3 = cache[0]
0x390c  bl twl6030_i2c_write(handle, 0x48, 0x20, &cache[0], 1)
```

⇒ `unmask_preq 1` = **read-modify-write of the cached byte for `0x48`/reg `0x20`
(`MSK_TRANSITION_REG`), clearing bit 5**; then a **single-byte write of that byte**.
`unmask_preq 2` → bit 6, `unmask_preq 3` → bit 7. No PREQ status is ever polled, and the
`set_state` path does **not** perform any PWR_REQ handshake — it is a plain state write.

## §6 Paste-ready Linux C snippet

```c
/* ------------------------------------------------------------------
 *  PlayBook / OMAP4430, TWL6030, board rev >= DVT3 ("MBID 5+", PVT4)
 *  Reconstructed from pmic-winchester-twl6030 (QNX resmgr) only.
 * ------------------------------------------------------------------ */
#include <linux/i2c.h>
#include <linux/io.h>

#define TWL6030_I2C_ADDR      0x48      /* 7-bit; proven at 0x4358/0x5fa0/0x5ff0/0x3900 */

/* ---- regen1 / regen2:  NOT a TWL6030 register -- OMAP GPIO1 ---- */
#define OMAP4_GPIO1_BASE      0x4A310000UL     /* TRM L4_WKUP, 0x4A31_0000..0x4A31_0FFF  */
#define GPIO_DATAOUT          0x13C
#define GPIO_CLEARDATAOUT     0x190
#define GPIO_SETDATAOUT       0x194
#define GPIO_OE               0x134
#define REGEN1_BIT            (1u << 2)        /* 0x00000004  (resmgr 0x5cd8) */
#define REGEN2_BIT            (1u << 15)       /* 0x00008000  (resmgr 0x5cec) */

/* resmgr: *(u32*)(GPIO1+0x194) = 4  for "on"/"sleep";  +0x190 = 4  for "off" */
static void regen1_set(bool on)
{
        void __iomem *g = ioremap(OMAP4_GPIO1_BASE, 0x1000);

        /* The QNX resmgr never touches OE or padconf: it relies on startup
         * having done it.  Linux must do it, hence: */
        writel(readl(g + GPIO_OE) | REGEN1_BIT, g + GPIO_OE);      /* output */
        /* + padconf: see caveat in the report ($7 item 2) */

        writel(REGEN1_BIT, g + (on ? GPIO_SETDATAOUT : GPIO_CLEARDATAOUT));
        iounmap(g);
}

/* ---- vaux3:  0x48 / 0x8E  (regulator_info[3].base_reg 0x8C, +2) ---- */
#define VAUX3_BASE_REG        0x8C
#define VAUX3_CFG_STATE       0x8E             /* base_reg + 2 */

/* exact QNX order for  set_state vaux3 on app :
 *   1. (only if force_update) 4-byte burst read of 0x8C
 *   2. write 0x8E = 0x21
 *   3. read  0x8E                        */
static int vaux3_on(struct i2c_client *c)
{
        u8 buf[4];
        int ret;

        ret = i2c_smbus_read_i2c_block_data(c, VAUX3_BASE_REG, 4, buf);   /* step 1 */
        if (ret < 0)
                return ret;

        ret = i2c_smbus_write_byte_data(c, VAUX3_CFG_STATE,
                                        0x20        /* APP   (resmgr 0x4f68) */
                                      | 0x01        /* state_map[on] (0x6E98) */);
        if (ret < 0)
                return ret;

        return i2c_smbus_read_byte_data(c, VAUX3_CFG_STATE);              /* step 3 */
}

/* ---- get_state, i.e. the reference decode ---- */
static int vaux3_get_state(struct i2c_client *c)
{
        /* resmgr enum -> name:  0 OFF, 1 SLEEP, 2 ON */
        static const int raw2enum[4] = { 0, 2, 0, 1 };   /* table @ 0x6ce0 */
        u8 b[4];
        int ret = i2c_smbus_read_i2c_block_data(c, VAUX3_BASE_REG, 4, b);

        if (ret < 0)
                return ret;
        pr_info("LDO:%d APP:%d CON:%d MOD:%d\n",
                raw2enum[b[2] & 3], raw2enum[(b[2] >> 2) & 3],
                raw2enum[(b[2] >> 4) & 3], raw2enum[b[2] >> 6]);
        return 0;
}

/* regen1:  identical registers to the QNX path, but no i2c at all  */
static int regen1_get_state(void)
{
        void __iomem *g = ioremap(OMAP4_GPIO1_BASE, 0x1000);
        int on = !!(readl(g + GPIO_DATAOUT) & REGEN1_BIT);   /* resmgr 0x5d6c */
        iounmap(g);
        /* resmgr: ldo = app = (on ? 2 : 0); con = mod = 0 */
        pr_info("LDO:%d APP:%d CON:0 MOD:0\n", on ? 2 : 0, on ? 2 : 0);
        return 0;
}
```

**Do not** write any TWL register to move regen1 on this unit. On DVT3+ the resmgr deliberately
*writes it off and detaches it* at init (`0x48`/`0xAF` ← `0xE0`, `0x48`/`0xAD` ← `0x00`, §3.4) and
drives the rail from GPIO1 bit 2. It also never calls `i2c_smbus_*` for regen1 at all once the GPIO
path is armed; the only regen1/regen2 I²C that ever happens on this unit is that init-time disable.

If you *do* want the DVT2- behaviour for reference: `0x48`/`0xAF` is `regen1`'s `CFG_STATE` and
`0x48`/`0xAD` its group register — but that is not what your board does.

## §7 Residual unknowns (explicit)

1. **TWL6030 `CFG_STATE` bit-field authority — needs the TWL6030 datasheet.**
   The resmgr's encoder (`0x20`/`0x40`/`0x80` = APP/CON/MOD, `[1:0]` = state) and its decoder
   (`[1:0]`=LDO, `[3:2]`=APP, `[5:4]`=CON, `[7:6]`=MOD) contradict each other (§4.3). The supplied
   `swpu231ap.pdf.txt` is the **OMAP4430 TRM** and contains no TWL6030 register definitions, so the
   ground truth is not available in this workspace. The bytes (`0x48`/`0x8E`/`0x21`) are certain;
   what the silicon does with `0x21`, and therefore whether your live `APP: ON` implies the encoder
   or the decoder is right, is **not** determinable here. If the encoder is right, `0x21` powers
   vaux3 in the APP group; if the decoder is right the live byte is `0x05` and `0x21` would mean
   `CON=2/reserved`. **Take as given:** the low-2-bit state encoding `00=off, 01=on, 11=sleep`
   comes from two independent tables in this binary (`0x6e98` encoder, `0x6ce0` decoder) and is
   self-consistent.
2. **Which GPIO bank the *ball* is on — needs the PlayBook schematic or a live readback.**
   The binary unambiguously targets `mmap_device_io(0x1000, 0x4A310000)` = **GPIO1** and bits
   **2 / 15** (§3.2, §3.3). But the OMAP4430 TRM pad table puts the signals named in the config
   comment on CORE pads:
   `gpio_2` = `CONTROL_CORE_PAD0_K`, padconf `0x190`, mux `0x3` (`swpu231ap.pdf.txt:254667`,
   `:290152`); `gpio_15` = `CONTROL_CORE_PAD0_D`, padconf `0x1B4`, mux `0x3` (`:254738`,
   `:291773`) — i.e. CORE-domain GPIO (GPIO2 bank @ `0x48055000`), not the WKUP-domain GPIO1.
   Either the PlayBook routes that ball to a GPIO1 line on this package, or the resmgr writes the
   "wrong" bank. Since the reference QNX OS demonstrably works, GPIO1[2] is almost certainly
   correct on this hardware — but I cannot prove it statically. **Verify with one live readback**
   (QNX `get_state regen1` vs. `rzi`/peek of `GPIO1_DATAOUT` bit 2 / `GPIO2_DATAIN` bit 2), which
   costs nothing and settles it.
3. **`GPIO_OE` and padconf for regen1/regen2 are not in this binary.** No reference to `+0x134`,
   `+0x114` or any padconf offset exists in `pmic-winchester-twl6030`. Some other QNX component
   (startup / `procnto`, not in scope) must mux and output-enable the pin. **Unknown: which.** Linux
   must do both; if it only writes `SETDATAOUT` the rail will not move.
4. **`0xE0` semantics in the init "disable regen1" write** (`0x48`/`0xAF` ← `0xE0`): clearly
   "all three groups, regulator off" under the encoder reading, but the exact intent needs the
   datasheet (§7 item 1).
5. **Board-revision source.** `winchester_init` does `confstr(5, buf, 128)` then
   `strstr(buf, "Rev:")` + `strtoul(buf+4, …, 10)`; `value > 4` or `value == 0 && errno == EINVAL`
   ⇒ GPIO mode. I did not identify which `confstr` name 5 is on QNX 6.5 nor which string carries
   `"Rev: N"`. It does not change the answer on a unit that is already known to be DVT3+.
6. **regen2 was not traced end-to-end in `get_groups`.** The `REGEN2 OFF` line you see comes from
   the `get_groups` path (`0x48`/`0xB0`, group register) reported as detached, consistent with §3.4;
   I did not decompile `get_groups` (`0x46c4` area) to the last instruction because it is outside
   the question.
7. **`twl6030_i2c_read`'s 20-byte descriptor field meaning.** The literal contents are proven
   (`{addr, 2, 1, n, 1}` at `sp+0x1c`, plus separate send/receive iovs); the *names* of words 3/4
   are a driver-side detail of `i2c-omap35xx-omap4` and not needed to reproduce the traffic. The
   write path (`{addr, 2, n+1, 1}`, DCMD `0x80100505`) matches report 108 §3.1 exactly.
8. **No display / LM3532 / RPMB content was inspected**, per the task's scope limit.
