**Question (report 108 §6.3):** is the ~1.4–2.2 s global CPU halt anchored to a
*hardware* epoch (always-on/secure timer, PMIC, reset) or to *kernel entry*
(PRCM/VC/MPU state the kernel sets up)?

**Answer: kernel entry.** Inserting a calibrated 1000 ms delay before the
kernel's first instruction (in the chainloader, before any kernel timer) moved
kernel entry by exactly +1000 ms and changed the halt time in kernel time by
**0 ms** (2240 ms → 2240 ms, jitter ≤ 10 ms over four runs). A hardware epoch
would have moved it by −1000 ms.

Two extra facts fell out and matter more than the original question:

1. On the Linux boot path the always-on **WDT2 period is 7.81 s, not 58.6 s**
   (`LDR = 0xfffc1800`, re-armed 7 ms before the chainloader starts), so the
   unit **reset-loops every ~7.8 s** while a test image is on media. The "~55 s
   reset" in reports 105/108 is an artifact: the restore flasher's
   `--delay 30` catches a bootrom after several loop iterations.
2. The chainloader's own pre-kernel phase is **1.77–4.78 s** and varies between
   boots (12 × `0x04000000`-iteration uncached delay loops in `blink_n`). That
   variance is larger than any D worth adding and it is what moved the
   observed wall between 1.44 s and 2.24 s.

## 1. Instrumentation added (this session)

`analysis/chainloader/chainloader_kernel.S.in`, build parameter `EP_TICKS`
(injected by `build_kernel_image.py` from the environment, default 0 ⇒ the call
is compiled out, so baseline builds are the pristine loader):

- **Delay:** hold kernel entry for `EP_TICKS` ticks of the always-on **WDT2
  CRR** (`0x4A314028`, 32.768 kHz, counts **up** from `LDR` toward
  `0xffffffff`; overflow = reset). No MMU, no caches, no interrupts, no kernel
  timer. A three-poll "is it actually ticking" check falls back to a fixed
  iteration count (status bit0/bit1) if the counter reads constant.
- **Epoch block** at breadcrumb `+0x88` on all four pages (`BC_PRIMARY` +
  mirrors). The kernel never writes this gap: `pb_event.h` owns `+0x00..+0x7C`,
  `ring_put` owns `+0x80/+0x84/+0x100..`, the pages are `no-map` reserved in
  the DTS, and the loader's own `clear_ring` (which covers `+0x80..+0x107F`)
  runs before the block is written.

| off | meaning |
|---|---|
| `+0x88` | magic `0x48435045` "EPCH" |
| `+0x8c` | status: b0 counter ticking, b1 anomaly, b2 delay done, b3 WDT2 sampled, b4 32k sampled, b8 delay-capable loader |
| `+0x90` | CRR at loop start | 
| `+0x94` | CRR last read (**re-published every iteration**) |
| `+0x98` | elapsed ticks = last − start |
| `+0x9c` | loop iterations |
| `+0xa0` | target ticks |
| `+0xa4` | LDR (arming value) |
| `+0xa8` | CRR on entry to the chainloader |
| `+0xb0` | 32k sync counter `0x4A304010` at kernel entry |

The block is re-published every iteration, so a halt *inside* the delay would be
recorded directly in always-on ticks with no kernel involvement.

`pb_events.py` now reads `0xb4` bytes and decodes the block (it prints LDR, the
owning period, hand-over split, loader duration, CRR at kernel entry, and the
32k value).

Artifacts: `chainloader/kernel-d{0,1000,2000,3000,4000}.img`
(`kernel.img` = D=0), captures `playbook-live-spare-2026-10-26-clean/epoch-*.txt`.

### 1.1 Verified pre-kernel hardware access

Read-only, from the loader, with MMU/caches off: `WDT2 CRR/LDR` (`0x4A314000`)
and the **32k sync counter** (`0x4A304010`) both read correctly. Neither had any

armed per boot, so it is a per-boot clock, not an absolute one.

### 2.1 The decision (runs 3 vs 4/5/6)

- D=0: entry 2771 / 2780 / 2771 → halt **2240 / 2240 / 2240** (jitter ≤ 10 ms).
- D=1000: entry **3771** (exactly +1000) → halt **2240**.

`t_halt(D) − t_halt(0) = 0`, not −1000 ⇒ **not a hardware epoch**. The delay is

(the whole boot shifted) and their absolute halt differs by *exactly* the same
299 ms while the kernel-time halt is identical.

### 2.2 Two freeze lines, plus a hard cut-off

The data is not one wall. It is `halt ≈ min(entry + 2240, WDT2 overflow)` with a
third, earlier hazard visible once entry is late:

| entry | halt (kernel) | halt (abs, after arming) |
|---|---|---|
| 2771 / 2780 | 2240 | 5011 / 5020 |
| 3771 | 2240 | 6011 |

- The **kernel-relative freeze at +2240 ms** is the one the epoch test was
  about: reproducible to ≤10 ms, independent of D and of entry time.
- A second freeze is visible at **~6.26 s after the WDT2 arming** (6232, 6294):
  it only shows when entry is late enough that it arrives *before* entry+2240.
  It is not the WDT2 (7.81 s), and it did **not** fire inside the loader: run 8's
  4000 ms delay ran to completion across the 6.26 s point.
  **→ Superseded by §5.2**: that arithmetic omitted the 1520 ms between the
  loader jump and kernel time 0.  With it included, these are the **WDT2

- The earlier session-3 cluster (**1.38–1.53 s**) is the same second line, not

## 4. What this means for the bring-up

The wall is **created at or after kernel entry**: same kernel, same boot path,
and 1000 ms of extra pre-kernel time changes nothing. That selects the
`setup-core-inactive` / PRCM-VC-VP-MPU family (report 106) over the
hardware/secure-timer family (report 107), and it makes the "inherited PRCM/VC
state" part of 106 the prime suspect — but with a sharper constraint than
before: the state must be one the *kernel* either preserves or sets, because
pre-kernel time alone does not shift the wall.

It also explains why the wall looks like two different numbers session to
session: there is one wall (kernel-relative, +2240 ms) and one watchdog kill
(WDT2, 7812 ms after arming).  Which one you see depends only on how late the
chainloader's uncontrolled 1.77–4.78 s blink phase puts kernel entry: late
entry, and the watchdog arrives first (that is the session-3 1.38–1.53 s
cluster).  §5.2 has the corrected arithmetic.

### Next steps, in order

1. **Put kernel entry on the record.** Write a marker (and the 32k value) from
   `arch/arm/kernel/head.S` at the first kernel instruction, so `entry` is
   measured by the kernel itself and every future capture can be expressed in
   arming-relative time. This closes the ≥2-freeze-line question and makes
   captures comparable across boots.
2. **Shrink the chainloader's pre-kernel phase** (delete/parameterise the
   `blink_n` delays, or gate them on a build flag). 12 × `0x04000000`
   uncached iterations costing 1.8–4.8 s is both a big uncontrolled variable and
   a waste of the 7.8 s WDT2 window.
3. **Bracket the 2240 ms freeze** with the existing event log at higher density
   (IRQ-enter/done already covers it) plus the two registers report 107 §E3
   names (`CM_MPU_CLKSTCTRL 0x4A004300`, `CM_MPU_MPU_CLKCTRL 0x4A004320`,
   `PM_MPU_PWRSTST`): read them in the tick heartbeat so the last heartbeat
   carries the domain state.
4. **Then** the report-106 replication: `PRM_VC_VAL_BYPASS 0x4A307BA0 ←
   0x013A5612 / 0x01405512`, `PM_MPU_PWRSTST`, `CM_SDMA_STATICDEP`,
   `CM_MPU_STATICDEP[14]` (report 107 H3), and the `CM_MPU_STATICDEP` /
   `CM_L4SEC_CLKSTCTRL` pair QNX sets.
5. **WDT2 neutralisation is now urgent, not cosmetic.** Its period here is
   7.81 s: every experiment has ~7.8 s of run time and the unit reset-loops in
   between. Kick `TGR` (`+0x30`) every ~2 s, or write `LDR` (`+0x2c`) then kick,
   to get a 58 s window (report 108 §6.2 also covers the TWL `0x48/0x2C=0x7F`
   pet).

## 5. Follow-up run: MPU domain state at the wall, and the missing offset

Second instrumentation pass (`drivers/irqchip/irq-gic.c`): on every timer tick
(INTID 29/37) sample `CM_MPU_CLKSTCTRL 0x4A004300`,
`CM_MPU_MPU_CLKCTRL 0x4A004320`, `PM_MPU_PWRSTST 0x4A306304`,
`CM_IDLEST_DPLL_MPU 0x4A004164` and the 32k counter `0x4A304010` into ring
`+0xb4..+0xe8` (first sample, last sample, change count and the jiffies of the
last change).  Capture: `playbook-live-spare-2026-10-26-clean/mpustate-run1.txt`.

### 5.1 The MPU domain does not transition

```
290 samples, 121 changed, last change jiffies 0x8b52 (= 1300 ms)
CM_MPU_CLKSTCTRL   first=00000102 last=00000102
CM_MPU_MPU_CLKCTRL first=00000001 last=00000001   (MODULEMODE=ENABLED, IDLEST=0)
PM_MPU_PWRSTST     first=000003f7 last=000003f7
CM_IDLEST_DPLL_MPU first=00000000 last=00000000   (locked)
```

Everything is identical from the first tick to the last, and the transients all
stop at **1300 ms**, i.e. ~950 ms before the freeze.  So no PRCM/secure actor
walked the MPU domain out of ON in the last second before the halt — the A9 is
**locally held** (monitor/FIQ/clock), or the transition is exactly simultaneous
with the freeze and therefore invisible to a tick that never runs.  That rules
out branch A (external domain actor) as the *observable* mechanism and sends us
to 107 E1/E6 (SMC liveness probe, GIC Group-0 census).

Caveat: a same-instant transition cannot be seen this way.  Distinguishing
"held" from "transitioned in the same cycle" needs a sampler that survives the
freeze — e.g. a register latched by hardware, or reading PRM state from QNX
after the reset before the boot rom reprograms it.

### 5.2 The missing 1520 ms, and what it does to the model

`32k first=31345 ms` (first tick) vs `32k=29826 ms` at the loader's pre-jump
sample: **kernel time 0 is 1519 ms after the jump** (decompressor + early
boot).  Adding that offset removes the "~6.26 s after arming" hazard entirely —
it was arithmetic, not hardware:

| run | entry (arming) | + decompress | + kernel halt | = halt after arming |
|---|---|---|---|---|
| 4/5/6 | 2771 | 1520 | 2240 | 6531 |
| this run | 2771 | 1519 | 2250 | 6541 |
| D=2000 | 4772 | 1520 | 1460 | **7752** |
| run 2 | 4784 | 1520 | 1510 | **7814** |
| D=4000 | 6780 | ~900 | ~130 | **7812** |

The last three land on the **WDT2 overflow at 7812 ms after arming**.  So there
is exactly **one wall — kernel-relative, +2240 ms after kernel time 0 — plus
the 7.81 s watchdog**.  The session-3 "1.38–1.53 s" cluster was the watchdog,
not the wall: those loaders left kernel entry late enough that 7812 ms arrived
first.  That also re-reads the session-3 busy-spin results (`spin start 1350,
death 1410`) as watchdog kills.

This strengthens the epoch-test conclusion rather than changing it: the wall is
anchored to kernel time 0, i.e. to state the kernel itself establishes.

### 6.1 Trap: the monitor clobbers r4-r12

The first two probe runs looked like "the SMC never returns": heartbeat stopped
at 300 ms, mask bit never set.  It was not the monitor — it was a **NULL-pointer
write at `gic_handle_irq+0x324`** (`str r0, [r8]`, `r8 = 0`):

```
[0.314483] Unable to handle kernel NULL pointer dereference ... when write
[0.316040] PC is at gic_handle_irq+0x324/0x458
[0.325286] Kernel panic - not syncing: Fatal exception in interrupt
```

The monitor clobbered r4-r12 — which is exactly why `trustzone-omap4`'s thunk
does `push {r4-r12,lr}` — and the compiler had live values (the ring pointer
among them) in those registers.  Fixed by pushing r4-r12/lr inside the asm.
**Any Linux SMC thunk must save r4-r12**, not just r0-r3/r12.

Second trap from the same runs: `loglevel=0` hides the panic, so an "instant
death" with the console off is uninformative.  Boot probe images with
`ignore_loglevel`.

## 7. Traps confirmed/added this session

1. `EP_TICKS=0` builds must not touch WDT2 at all in the delay path — the call
   is `.if`-compiled out. The always-taken pre-jump *sample* is two reads and is
   harmless.
2. `epoch_delay` must RMW the status word, not store it (a store erased the
   "sampled" bit and hid run 3's LDR). Fixed.
3. `+0xa8` (chainloader entry CRR) is written early and must not be re-zeroed
   by the later block init. Fixed.
4. WDT2 CRR counts **up**; `sub start, now` silently turns every delay into
   0 ms. Fixed (session 3's correction).
5. `pb_ring.py dump` cannot read a `loglevel=0` boot (count 0). Use
   `pb_events.py`, and `pb_ring.py --ring 90000000` for the decompressor's ring.
6. A test image on media makes the unit reset-loop every 7.8 s; the captured
   log is always the **last** boot before the restore, so never assume it is the
   first one.

### 8.1 WDT2 writes are dropped — the current blocker

The chainloader now writes `LDR = 0xffe2b400` and kicks `TGR`
(read → invert → write), and the kernel kicks `TGR` every 15 s.  **Neither took
effect:** the epoch block still reads `LDR = 0xfffc1800` (7.812 s) at the
pre-jump sample, and the kernel still died at the un-extended window.

Reads of WDT2 are fine (CRR/LDR are live and self-consistent), so the module is
clocked — the writes are being silently dropped.  What the follow-up established (four cycles) — **resolved**:

| attempt | result |
|---|---|
| loader: write `LDR=0xffe2b400` + kick `TGR` (WPS-polled) | `LDR` unchanged; kick had no effect |
| loader: same + `CM_WKUP_WDT2_CLKCTRL` at `0x4A31C030` | **wedged the loader** — `0x4A31C000` is the *keypad* target-module, not the CM |
| kernel at gic init, `0x4A307830` (the real address) | **works, and tells us everything** |
| kernel, kick from the timer *tick* every 2 s | still died at 8.64 s |
| kernel, kick from a `timer_list` every 2 s | **survives indefinitely** |

`CM_WKUP_WDTIMER2_CLKCTRL` is `0x4A307830` = WKUP_CM (`0x4A307800`, TRM
Table 3-769) + 0x30, not `0x4A31C030`.  Readback at gic init:

```
PLAYBOOK WDT: clk0=00000002                      (MODULEMODE=HW_AUTO, IDLEST=0 - already on)
PLAYBOOK WDT: ldr0=fffc1800  ldr1=fffc1800 wps=0 (DROPPED - LDR writes really are ignored)
PLAYBOOK WDT: crr fffd0e91 -> fffc1803 wps=0     (RELOADED - the TGR kick works)
```

So the module clock was never the problem; **`LDR` writes are dropped but the
`TGR` kick reloads `CRR`**, exactly as QNX's kicker does.  The window can
therefore not be *lengthened*, but it can be *petted*.

> **Corrected (session 31, 2026-11-08):** the window **can** be lengthened —
> `WLDR` writes are dropped only while the timer is *running*.  TRM §22.3.4.9:
> disable first with `WSPR` `0xAAAA` → `0x5555`, write `WLDR`, re-enable with
> `WSPR` `0xBBBB` → `0x4444`; the new load takes effect on the next `TGR` kick.
> Verified live: `WLDR` read back `0xFFE2B400` and `WCRR` reloaded to it
> (58.6 s), with the 2 s pet still running.  See trap 115.

Two implementation traps:

1. **Kick from a timer, not from the tick.**  With `/init` idle the kernel is
   tickless: the sampler ran only 315 times in 8.6 s, so a `jiffies % 200` kick
   missed its slot and the board still reset (last heartbeat 8.64 s).
2. `late_initcall` is the earliest point a `timer_list` can be armed
   (`init_timers()` runs after `init_IRQ()`), so the gic-init kick covers the
   gap from 0.8 s to 2.3 s.

Result with a 2 s timer: heartbeat **22140 ms**, and `/init` printed
`STILL ALIVE at 20 s, no panic, no reset` at 22.30 s before rebooting.  The
watchdog is no longer a constraint on any experiment.

Also still true from the earlier probe: the reset we see *is* WDT2, and
`0x4A318000` (`REV = 0x15`, no 32k countdown) is not a watchdog, so report
107's "always-on secure timer" candidate is a misidentification.

Historical options (kept for the record):

1. Find the *correct* WDT2 module-clock control (the DT says
   `l4_wkup_clkctrl` `OMAP4_WD_TIMER2_CLKCTRL`, `CLKCTRL_INDEX(0x30)`, but
   `0x4A31C030` aborts — the clkctrl node is `clk@20` inside a larger CM
   window, so the real offset needs pinning down from the TRM/`omap4-cm.dtsi`)
   and enable MODULEMODE before writing.  That is what `omap_wdt` does via
   runtime PM; `clk_ignore_unused` only prevents gating.
2. Get a *cold* boot (not via `force_reset_loader`) and check whether `LDR`
   is then 58.6 s like QNX's.
3. Live with ~5.4 s: design each experiment to fit, and rely on the 7.8 s
   reset loop for the boot rom window.  This is workable for the eMMC card
   init (CMD0/1/2/3/9/7/6 fit easily), just tight.

## 9. eMMC card init: works (2026-10-27)

With the watchdog neutralised the card path was re-run with the console on.
The card had been answering all along; the host was misconfigured:

```
PBOCR: arg=00000000 resp=40ff8080 host_avail=00000000 busy
PBOCR: arg=40ff8080 resp=c0ff8080 host_avail=00000000
PBVOLT: card_ocr=c0ff8080 host_avail=00000000
omap_hsmmc 480b4000.mmc: no support for card's volts      <- -EINVAL, not a timeout
```

`mmc_select_voltage()` masks the card's OCR with `host->ocr_avail`, which was
**0**: the `&mmc2` node declared neither `voltage-ranges` (which has no
in-tree caller for this host) nor a `vmmc-supply`, and `omap_hsmmc` only takes
`ocr_mask` from legacy platform data.  Fix: model the soldered eMMC's fixed
3.3 V rail as a `regulator-fixed` (`vemmc`, always-on) and add
`vmmc-supply = <&vemmc>`; the core then derives `ocr_avail = 0x00300000`.

Result:

```
PBVOLT: card_ocr=c0ff8080 host_avail=00300000
mmc1: new high speed MMC card at address 0001
mmcblk1: mmc1:0001 MCGAFA 59.4 GiB
mmcblk1boot0: mmc1:0001 MCGAFA 512 KiB
mmcblk1boot1: mmc1:0001 MCGAFA 512 KiB
mmcblk1rpmb: mmc1:0001 MCGAFA 128 KiB, chardev (250:0)
```

Samsung MCGAFA, 59.4 GiB, high speed, both boot partitions, RPMB as chardev
only.  Nothing mounted, nothing written, RPMB untouched.

Notes for the next session:
- `host_avail = 0x00300000` is the 3.2-3.4 V window from the fixed regulator.
  If the card is ever run at 1.8 V (HS200/HS400) this must become a real
  regulator with a voltage switch.
- The card came up at **high speed** (DDR52 not negotiated) and 8-bit; the
  bus-width switch worked.
- The `blk` device appearing means `CONFIG_MMC_BLOCK=y`; for probe-only builds
  keep using `CONFIG_MMC_BLOCK=n` so nothing can bind a filesystem.
- `CONFIG_MMC_RPMB` **no longer exists** in 6.15 (no Kconfig symbol, not in
  core/Makefile): the `mmcblk1rpmb` chardev is part of `mmc_block`
  unconditionally.  So the documented "RPMB off" state is now "never open
  `/dev/mmcblk1rpmb`", not a config choice.
