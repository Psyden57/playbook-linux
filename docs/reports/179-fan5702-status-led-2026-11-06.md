## 0. Headline

* **A mainline `leds-fan5702` driver probes the chip**: `3-0036 <-
  leds-fan5702`, and `/sys/class/leds/` gains the three channels.  Writing
  `brightness` 1/0 turns the corresponding channel on/off.  **The operator
  confirmed red, green, blue, white and off on 2026-11-06.**
* **The protocol came from the existing LED-RE report** (a separate project,
  `~/SSDdrive/wsl-migration/home/psyden/playbook-dev/LED-RE.md`) and the QNX
  `led-fan5702.so`: `GENERAL (0x10)` bits 1/2/3 = red/green/blue,
  `CONFIG (0x20) = 0`, `CH3/4/5 (0x30/0x40/0x50) = 0x36` (the bootloader's
  value), and **EN = GPIO1_13: low resets, a low→high pulse enables**.
* **The EN/pad was the whole problem.**  On this unit the pad at `0x1B0`
  (GPIO1_13) boots in safe mode, and the raw `devmem` EN attempts left the chip
  in reset (every I2C access was `ENXIO`).  The driver's pinctrl state (pad
  `0x1b0` mux 3) plus `enable-gpios = <&gpio1 13>` pulses EN high, and the
  chip answers at 400 kHz.
* **400 kHz is fine.**  The vendor driver sets 100 kHz, but the FAN5702
  (datasheet: 400 kHz max) works on the sensor bus at 400 kHz, so the shared
  `&i2c4` speed is unchanged.

## 1. The change

**Driver** `drivers/leds/leds-fan5702.c` (tracked `kernel/source/
leds-fan5702.c`), `CONFIG_LEDS_FAN5702=m`:

* `compatible = "fairchild,fan5702"`, three `led@0/1/2` children; each child
  has a `reg` (0..2) selecting `GENERAL` bit `1+reg`.
* probe: optional `enable-gpios` (GPIO1_13) with a low→high pulse, then the
  vendor init `0x10=0`, `0x20=0`, `0x30/0x40/0x50=0x36`.
* `brightness_set_blocking`: shadow the GENERAL byte and write it; `brightness`
  is on/off (the vendor driver has no dimming either — the per-channel
  registers stay at the bootloader's value).

**DTS** (`&i2c4`):

```
status_led: led-controller@36 {
        compatible = "fairchild,fan5702";
        reg = <0x36>;
        enable-gpios = <&gpio1 13 GPIO_ACTIVE_HIGH>;
        pinctrl-0 = <&fan5702_pins>;
        led@0 { reg = <0>; label = "red:status"; };
        led@1 { reg = <1>; label = "green:status"; };
        led@2 { reg = <2>; label = "blue:status"; };
};
/* &omap4_pmx_core */
fan5702_pins: fan5702-pins {
        pinctrl-single,pins = <OMAP4_IOPAD(0x1b0, 0x0003)>;
};
```

## 2. Measured

```
PBR: 3-0036 <- leds-fan5702
leds-fan5702 3-0036: using DT ... for 'enable' GPIO lookup
$ ls /sys/class/leds
playbook:playbook:red:status  playbook:playbook:green:status  playbook:playbook:blue:status
$ echo 1 > .../red:status/brightness     # red on (0x10 |= 0x02)
$ echo 0 > .../red:status/brightness     # red off
```

The operator saw **red, green, blue, white** (all three bits) and off, each
held for 6 s; `dmesg` had no LED errors.

The **`playbook:playbook:` duplicate** is cosmetic: the LED core prepends
`devicename = "playbook"` to the `label`, and the first build's labels already
said `playbook:red:status`.  The DTS labels are now `red:status` etc., so the
next build yields `playbook:red:status`.  (The media image is `0xB759C3A2`,
with the duplicate names.)

`i2cget -y 3 0x36 0x10` now returns "Device or resource busy" because the
driver owns the client — use the LED class, not raw I2C.

## 3. Why the raw attempts failed

The QNX driver maps GPIO1 and toggles bit 13.  On Linux the pad `0x1B0` read
`0x00030118` (mux 0, safe mode), and raw `devmem` writes of
`0x4A1001B0 = 0x00030003` + `GPIO_OE`/`SETDATAOUT` did **not** make the chip
answer.  The driver's `pinctrl-single` entry and `devm_gpiod_get_optional()`
are what put the pad in GPIO mode and drive EN high; after that the init
writes succeed.  This matches the external LED-RE report: EN low resets the
FAN5702, and the QNX sequence ends with EN high.
