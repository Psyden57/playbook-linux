## 0. Answers in brief

1. **Entry and boot flow.** Reset vector `0x40028000` = `EA000242`
   (`b 0x40028910`); the 7 fault vectors are `E59FF018` (`ldr pc,[pc,#0x18]`)
   into a literal block holding `0x4030D004…0x4030D01C`, i.e. every fault is
   re-routed into OCM RAM. CPU0 sets `VBAR = 0x00028000`, `SP = 0x4030D000`,
   stages a 4-record copy table from `0x4002FF80` into IRAM, then drops to
   Thumb-2 at `0x40028A18`. The first stage's medium is chosen from **SYS_BOOT**:
   `CONTROL_STATUS` (`0x4A0022C4`) low byte indexes a **32 × 16-byte command
   table at `0x4002F7C4`** whose entries are short command lists — media
   commands `1..8` (XIP/RAM, flash/GPMC, MMC/SD) and image-source commands
   `'A'..'F'` (`'A'..'D'` = UART1..UART4, `'E'`/`'F'` = USB device). The first
   read from the selected medium is **sector 0 (LBA 0), 512 bytes**, scanned as
   **16 × 32-byte records with an ASCII name at +0x14** matched against a 14-name
   table (`CHSETTINGS, CHRAM, CHFLASH, CHMMCSD, MLO, PRIMAPP, X-LOADER, ULO,
   HLO, 2ND, ISSW, KEYS, R&D, CH`). So the project's "catalogue at user-area
   offset 0" belief is **confirmed for MMC**, with three refinements: the
   catalogue is the ROM's own 16×32-byte TOC (not a CH header), `MLO` is only one
   of 14 names, and the ROM never selects an eMMC boot partition (no CMD6 /
   `PARTITION_CONFIG` write exists anywhere in the image). **No authentication
   code is present in this window** — no crypto block, no certificate parser, no
   key handling: `KEYS`/`ISSW` appear only as *names in the TOC*. The hand-off is
   an `SMC #0` with `r12 = 0xF0` (veneer `0x4002CEB0`), i.e. to the secure side,
   with the image staged at `0x40300000`/`0x40304000`; the one *direct* jump in
   the ROM is the ARM `bx r0` to `0x08000000` in the GPMC island.
2. **USB / peripheral boot.** USB is entered when the command list contains
   `'E'` or `'F'` — true for every SYS_BOOT value in the table except
   `0x1D`/`0x1E` (empty). SYS_BOOT `0x1F` yields **`'E','C'` only** (USB then
   UART3, no storage). A host then sees a **single-configuration device whose one
   interface is vendor-specific (`bInterfaceClass 0xFF`), with two bulk
   endpoints, `idVendor = 0x0000`, `idProduct = 0x0000`** (the ROM template is
   literally zero and nothing in the
   ROM patches the VID/PID fields), `bcdUSB 0x0210`, high-speed enabled, 512-byte
   bulk max-packet in the HS block and 64-byte in the FS/other-speed blocks. It
   **does answer `GET_DESCRIPTOR`**: `wValue>>8` indexes a `tbb` table at
   `0x4002D860` with live cases for DEVICE(1), CONFIG(2), STRING(3),
   DEVICE_QUALIFIER(6), OTHER_SPEED_CONFIG(7); the DEVICE case returns the
   18-byte descriptor at `0x4030D10E`. No string descriptors exist (all string
   indices are 0). So a dead unit *can* appear on a host as a USB device — with
   VID:PID 0000:0000, which is why it looks like nothing at all.
3. **Failure behaviour.** Nothing halts and nothing resets. The config parser is
   an **infinite retry loop** (`0x40028B40`, back-edge `0x40028BF4`): a failed
   command leaves the next command byte in the table to be tried (that is the
   fall-back path), and when the list is exhausted the whole list is retried
   forever. Only the image-download step is bracketed by the watchdog
   (WDTIMER2 `0x4A314000`: start `0x4002A430`, stop `0x4002A454`), and it is
   explicitly **stopped again** after every attempt (success or failure). There
   is **no GPIO, no I2C, no PMIC, no LED** access anywhere in the 48 KiB — see §8.
4. **Public API.** Two tables, both enumerated in §5: the 48-entry Thumb export
   table at `0x40028400` (TRM "API table" at ROM offset `0x28400`), and the
   IRAM trampoline block at `0x4030D000` whose 8 vector slots
   (`0x4030D000`/`004…01C` → `0x4030D020…03C`) resolve to `0x00028090,
   0x00028080, 0x00028084, 0x000289E4, 0x000289F0, 0x00028090, 0x00029420,
   0x00028098`. `0x4030D004…0x4030DC1C` are **not service entry points**; they
   are **RAM vector slots** — eight `ldr pc,[pc,#0x18]` words living in OCM RAM,
   not ROM functions; the rest of the `0x4030D0xx`/`0x4030DCxx` space the ROM
   points at is IRAM *data* (progress bitmap, reset-reason ring, USB descriptor
   template, config result record, request blocks). The ROM — and, per report
   150 §5, the bootloader — reach all of it by pointer, never by `bl`.
5. **The 7.35 s cycle.** **Nothing in the ROM can produce it.** `0xFFFC1800`
   does not occur anywhere in the image [P]; there is no periodic timer reset, no
   self-re-arm; the only watchdog programming is a **180-second** WDTIMER2 load
   (constant `0x2BF20` = 180000 → 180 s at 32.768 kHz, computed with the
   fractional multiplier `0xC49BA5E2`) that is stopped immediately afterwards.
   All other ROM delays are milliseconds-scale (40 ms, 0.5 s at 32 kHz). A
   ~7.35 s/7.8 s periodic reset therefore originates in a **later** stage (MLO's
   own WDT2 arming, report 150 §5) or on the reset-input side, not here.

## 2. Entry point and boot flow (Q1)

### 2.1 Reset vector and the IRAM indirection

```
40028000  ea000242  b    0x40028910          ; reset: straight to A32 init
40028004  e59ff018  ldr  pc,[pc,#24]         ; undef
40028008  e59ff018                          ; swi
4002800c  e59ff018                          ; prefetch abort
40028010  e59ff018                          ; data abort
40028014  e59ff018                          ; reserved
40028018  e59ff018                          ; irq
4002801c  e59ff018                          ; fiq
40028020  1cf48309                          ; signature / checksum word
40028024  4030d004  4030d008  4030d00c  4030d010
40028034  4030d014  4030d018  4030d01c     ; -> the 7 fault slots in OCM RAM
```
[P]. `0x40028080`–`0x4002809C` is a 16-word `EAFFFFFE` (`b .`) hang cluster [P].
`0x40028400`–`0x400284BF` is the 48-word export table (§5.1) and Thumb code
resumes at `0x400284C0`, so the table length is fixed by the code boundary [P].

### 2.3 The "SYS_BOOT==3" island (`0x40028C00`) — GPMC/flash + direct jump

```
40028C00  mov r7,lr
40028C04  bl  0x40028740      ; CM1 CM_CLKSEL_CORE/DPLL + GPMC timing (0x50000060/78)
40028C08  bl  0x4002B740      ; pad-mux GPMC pads: 0x4A100040..0x5E := 0x18,
                              ;                   0x4A100060..0x72 := 0x00
40028C18  mov r0,#0x08000000
40028C1C  ldr r1,[r0]         ; probe the XIP/flash window
40028C20  ldr r3,=0
40028C24  cmp r1,r3
40028C28  bxeq r7            ; all-zero  -> not bootable, return
40028C2C  ldr r3,=0xFFFFFFFF
40028C30  cmp r1,r3
40028C34  bxeq r7            ; all-ones  -> not bootable, return
40028C38  bx r0             ; else JUMP to 0x08000000 in ARM state
```
[P] (`0x40028740` writes `[0x50000060] = (x & ~0x00403300) | 0x1200` and
`[0x50000078] = 0xF48`; `0x4002B740` loops over padconf offsets `0x40..0x5E`
with value `0x18` and `0x60..0x72` with value `0`, halfword RMW).
This is the only place in the ROM that transfers control *directly* to a
load address. `0x4A100040` is `CONTROL_CORE_PAD0_GPMC_AD0` [P/T​RM], so the pads
muxed are the GPMC data bus [I].

### 2.4 IRAM bootstrap table (`0x4002FF80`) and the A32→Thumb switch

The walker `0x40028834` (bounds from literals `0x00007718`/`0x00007758` added to
PC) iterates 4 records of 16 bytes at `0x4002FF80`, calling `{fn}(a,b,c)`:

| # | a | b | c | fn | effect |
|---|---|---|---|---|---|
| 0 | `0x0002FFC0` | `0x4030D000` | `0x40` | `0x00028870` | copy the IRAM vector block |
| 1 | `0x00030000` | `0x4030D100` | `0x08` | `0x00028870` | zero 8 bytes (IRQ save) |
| 2 | `0x00030008` | `0x4030D108` | `0x98` | `0x00028870` | copy the USB descriptor template |
| 3 | `0x000300A0` | `0x4030D1A0` | `0xABC` | `0x00028898` | zero `0xABC` bytes (BSS) |

[P] (bytes at `0x4002FF80`: `0002FFC0 4030D000 00000040 00028870 …`).
The copied 64-byte vector block is:
`8 × E59FF018` then `00028090 00028080 00028084 000289E4 000289F0 00028090
00029420 00028098` = `0x4030D020`…`0x4030D03C` [P].

`0x400288D0` then does `ldr sp,=0x4030D000; blx 0x400288C4; ldr r12,=0x00000135;
add r12,r12,pc; bx r12` → **Thumb execution at `0x40028A18`** [P].

### 2.5 Thumb main (`0x40028A18`)

```
40028A18 push {r2,r3,r4,lr}
40028A20 bl   0x4002A4C0      ; read PRM_RSTST into *sp (reset reason)
40028A26 bl   0x4002A51C      ; progress(1)
40028A2A movs r1,#1 / movs r0,#6 / bl 0x40029AE6   ; PRCM module 6 clock on
40028A32 bl   0x4002A41C      ; WDTIMER2 WDSC |= 2 (soft-reset config)
40028A36 bl   0x4002A430      ; WDT "start"  (WSPR 0xAAAA then 0x5555)
40028A3A ldr  r0,=0x0002BF20  ; = 180000  (decimal!)
40028A3C bl   0x4002A478      ; WDT load: timeout = 180000 * 32.768 kHz = 180 s
40028A40 bl   0x4002A454      ; WDT "stop"   (WSPR 0xBBBB then 0x4444)
40028A44 ldr  r0,[sp] / cmp r0,#1 / bne 0x40028A5E
40028A4A ..                   ; cold boot only: progress(2), flags|=1,
40028A5A ldr  r0,=0x4A326A00 / str r4,[r0]        ; clear SAR-RAM boot-config ptr
40028A60 bl   0x40028DB6      ; read boot-config block type 2 (optional)
40028A6A bl   0x40028A7C      ; config parser -- DOES NOT RETURN
```
[P]. The watchdog is therefore **armed and disarmed within the first 40
instructions**, long before any medium is touched [P].

### 2.6 How the boot mode picks the medium — `CONTROL_STATUS` + the 32-entry table

`0x40029794` returns `CONTROL_STATUS & 0xFF` [P]:

```
40029794 ldr r0,=0x4A0022C4 ; ldr r0,[r0] ; uxtb r0,r0 ; bx lr
```

TRM corroboration: `CONTROL_STATUS` (`0x4A0022C4`) bits[10:0] are `DEVICE_TYPE`,
the sampled SYS_BOOT configuration, mirrored in `STD_FUSE_PROD_ID_0`
(`0x4A002214`, `0xF0` = GP device) [TRM Table 1-7 / its footnote]. So the ROM's
selector is **DEVICE_TYPE[7:0]** (called "SYS_BOOT" below), and the
`bits[10:8] == 3` test in `0x40028910` is on the upper part of the same field
[P for the reads, TRM for the field name].

The config parser (`0x40028A7C`) uses two different sources for the command
list:

1. **If the caller's `flags` bit 0 is clear**, it first asks the SAR-RAM
   boot-config block (`0x4002B64E(1, buf)` at `0x40028AAE`): a linked list
   starting at `[0x4A326A00]`, bounded by `0x4A327000`, each node headed by
   `(0xCF00AA00 | type)`; on a match it copies the node's payload into the 8-byte
   command buffer and sets bit 9 (`0x200`) in `flags`, plus flag bits 3/4/5/6/7/8
   from the payload's bits 0..4 [P]. This is the TRM's
   `PUBLIC_SW_BOOT_CFG_ADDR` (`0x4A326A00`, inside SAR_RAM_1
   `0x4A326000`–`0x4A326FFF`) [P/TRM].
2. **`0x40028E72(flags, dst, src)`** then produces the 8-byte command list. If
   `flags` bit 9 is **set** (i.e. a stored config block was found) it copies the
   four `u16` command bytes from that block (bytes `src+2`/`src+3` of each
   entry, `0x40028E90`–`0x40028EA6`) [P]. If bit 9 is **clear** it indexes the
   **32-entry device table at `0x4002F7C4`** with `SYS_BOOT[4:0]`
   (`0x4002A560`, stride 16, `idx ≤ 0x1F`) [P].
3. In the table path, `CONTROL_STATUS[6]` selects the first or the second half of
   the 16-byte record, and each half is 4 × `u16` where one `u16` encodes one or
   two command bytes; bit 15 marks an entry as **always** emitted, while an entry
   without bit 15 is emitted only when `flags` bit 0 is set (the "no stored
   config" case) [P].

### 2.7 What is read first, from which offset

The media handler `0x4002AD5C` is the answer to "offset 0 or a catalogue?":

```
4002AD60  movs r6,#0                 ; <<< requested LBA = 0
4002AD66  mov  sl,r0                 ; flags
4002ADA0  ldr  r0,[sp,#0x234]        ; media descriptor (0x4030D238 …)
4002ADF4  str  r6,[sp,#0x228]        ; request.sector = 0
4002ADEC  ldr  r1,[sp,#0x14]
4002ADF2  cmp  r1,#3
4002ADF8  ldrh r4,[r0,#0x16]         ; else count = desc[0x14]
4002ADFC  ldrh r4,[r0,#0x14]
4002ADE8  add  r1,sp,#0x28           ; 512-byte stack buffer
4002AE00  ldr  r1,[sp,#0x23c] / ldr r2,[r1,#4] / blx r2   ; dev->read(dev,&req)
4002AE0C  add  r2,sp,#0x18
4002AE0E  add  r1,sp,#0x28
4002AE10  bl   0x4002C254            ; match names in the 512-byte buffer
```
[P]. The frame is `0x240`; the buffer at `sp+0x28` is exactly `0x200` bytes and
the request record sits at `sp+0x228` [P]. `0x4002C254` then walks **16 records
of 0x20 bytes** (`adds r5,r5,#0x20`, `cmp r4,#0xe` over the 14-name table,
`cmp r6,#0x10`) comparing the NUL-terminated name at **record+0x14** with the
pointer table at `0x4002FA84` [P]:

```
0x4002FA84 -> 0x0002FF7B "ISSW"      0x0002FF62 "X-LOADER"  0x0002FF31 "2ND"
              0x0002FF56 "ULO"       0x0002FF52 "MLO"       0x0002FF4E "HLO"
              0x0002FF76 "KEYS"      0x0002FF5A "PRIMAPP"   0x0002FF2D "R&D"
              0x0002FF3D "CH"        0x0002FF6B "CHSETTINGS" 0x0002FF48 "CHRAM"
              0x0002FF40 "CHFLASH"   0x0002FF35 "CHMMCSD"    0x00000000 (end)
```
[P] (byte-exact; strings are NUL-terminated at those offsets).

**Conclusion for the project's belief.** The catalogue *is* at LBA 0, and
`"MLO"` is one of its recognised names — but:

* the record shape is **32 bytes with the name at +0x14**, 16 records per
  512-byte sector [P];
* the load/execute side never needs a filesystem: no FAT BPB parse, no MBR/GPT
  parse, no directory walk exists in the image [P — no code references the BPB
  signature `0xAA55`, and the only 8.3-style name in the image,
  `"MLO        "` at `0x4002BC00`, has **no 32-bit pointer and no ADR anywhere
  in the 48 KiB** → its role is [U]; it is *not* evidence of a FAT parser);
* the ROM never constructs a `CMD6` argument with `EXT_CSD` index 179
  (`PARTITION_CONFIG`) — there is no `0x03B3xxxx` word, no `movw #0x3B3` and no
  `#179` immediate anywhere in the image — so an **eMMC boot partition is never
  selected** [P]. It *does* read `EXT_CSD` (`CMD8`, descriptor `0x083A0010` at
  `0x4002EBB0`, 512 bytes) and takes capacity from `EXT_CSD[0xD4]`
  (`SEC_COUNT`) [P]; the wider card-init sequence
  (`CMD0 → CMD8(0x1AA) → CMD55 → ACMD41/CMD1 → CMD2 → CMD3 → CMD9 → CMD7 →
  CMD16`) is the earlier reports' observation (`docs/reports/10-boot-media.md`,
  summarised in `BOOTROM-0x40028000-REPORT.md` §4.2) and is consistent with the
  command-descriptor words this pass re-read [P for the descriptor encoding,
  [I] for the ordering], i.e. plain user-area access from LBA 0.

### 2.8 Authentication — what this window does *not* contain

* **No cryptographic engine is touched**: no literal for AES/DES/SHA/RNG/PKA
  (`0x4B20xxxx` region) appears anywhere in the image [P].
* **No certificate parser, no key table, no `CertPK`/`CertPPA`/`CertISW`
  strings**: the strings `KEYS` and `ISSW` exist only as *TOC section names*
  (`0x4002FF76`, `0x4002FF7B`) [P].
* The only security-adjacent instructions are the **8 A32 `smc` sites** (a
  byte scan of the whole image: `(word & 0xFFFFFFF0) == 0xE1600070` at 4-byte
  alignment; **no Thumb `smc`** — `0xF7F0|imm4,0x8000` matches nothing) [P]:

  | # | address | encoding | `r12` | context |
  |---|---|---|---|---|
  | 1 | `0x40028134` | `E1600070` | `0x107` | CPU1-wake path A |
  | 2 | `0x4002813C` | `E1600070` | `0x103` | same path: read AUX_CORE_BOOT_0/1 |
  | 3 | `0x400289C8` | `E1600070` | `0x107` | CPU1 secondary path |
  | 4 | `0x4002CEB8` | `E1600070` | `0x0F0` | A32 veneer `0x4002CEB0` — **terminal image hand-off** |
  | 5 | `0x4002F4C8` | `E1600071` | `0x000` | cache wrapper A (`0x4002F4AC`) |
  | 6 | `0x4002F4E8` | `E1600071` | `0x0FE` | dormant alt entry |
  | 7 | `0x4002F510` | `E1600071` | `0x000` | cache wrapper B (`0x4002F4F4`) |
  | 8 | `0x4002F530` | `E1600071` | `0x0F1` | dormant alt entry |

  Veneer bytes at `0x4002CEB0`: `f6 ff ff fa | f0 c0 a0 e3 | 70 00 60 e1` =
  `blx 0x4002CE90 ; mov r12,#0xF0 ; smc #0` [P].

So in this window the "authentication order" question has a negative answer:
**the NS-visible ROM performs no certificate or key verification itself.** It
locates a named section in the TOC, stages it into OCM RAM, and hands off through
`SMC #0` with `r12=0xF0`; whatever checks `KEYS`/`ISSW`/certificates lives on the
secure side or in the next stage [I].

## 3. Peripheral / USB boot (Q2)

### 3.1 Exact entry conditions

USB is entered **iff** the command list for the current boot contains `'E'` or
`'F'`. Per §2.6 that is every SYS_BOOT value except `0x1D` and `0x1E` (which
produce an *empty* command list → nothing is tried at all) [P].

* `CONTROL_STATUS[6] == 1` puts `'E'`/`'C'`/`'F'` **first**, i.e. peripheral
  before storage [P].
* SYS_BOOT `0x1F` gives `'E','C'` with **no** media command — the pure
  peripheral-boot setting [P].
* `'E'`/`'F'` are the *optional* (`u16` bit15 clear) entries in most records, so
  they are attempted regardless of whether the storage command succeeded: the
  media command and the peripheral command are independent attempts from the same
  list [P] (see §4).

`'A'`…`'D'` are UART boot on **UART1 `0x4806A000` / UART2 `0x4806C000` /
UART3 `0x48020000` / UART4 `0x4806E000`** (table at `0x4002FA48`, indexed by
`cmd-0x41`) [P]. The UART open (`0x4002BD5D`) writes the standard 8250-style
register set: `+0x54 = 2` (clock source), `+0x08 = 7` (FIFO enable/reset),
`+0x0C = 0xBF` (8-bit, DLAB set), `+0x00 = 0x0D` **or** `0x1A` (divisor 13 or
26 → **230.4 kbaud or 115.2 kbaud** at 48 MHz), then clears DLAB, sets `+0x10`,
`+0x1C`, `+0x40`, and `+0x44` [P for the offsets/values; baud maths [I]].
The choice between the two divisors is made by testing `[desc+0x11] == 0x38`
[P — meaning [U]].

### 3.2 The `'E'` (USB) path — init, PHY, connect

Entry `0x4002C03F`; the pieces it calls [P]:

```
4002C0C0/C0C4/C0C8  PRCM module 3 enable (0x4A… clock, via 0x4002A95A/0x40029AE6)
4002C0E2  bl 0x4002CF5A        ; MUSB OTG init
4002CF5A  bl 0x4002CEBC
4002CF62  ldr r0,=0x4A0AB000   ; HSUSBOTG
4002CF64  poll [r0+0x408] until != 0        ; OTG_SYSSTATUS.RESETDONE
4002CF6E  [r0+0x414] = 0                    ; OTG_FORCESTDBY = 0
4002CF72  [r0+0x404] = 0x1008               ; OTG_SYSCONFIG: SIDLEMODE=1, MIDLEMODE=1
4002CF80  [r0+0x40C] &= ~3, |= 1 (arg0=0)   ; OTG_INTERFSEL.PHYSEL := 1
4002CF8C  [r0+0x006] |= 1                   ; MUSB INTRTXE (EP0)
4002CF94  [r0+0x00B] = 4                    ; MUSB INTRUSBE (reset int)
4002CF98  [r0+0x00E] = 0                    ; MUSB INDEX = 0
4002CF9C  [r0+0x062] = 3 / [r0+0x063] = 3   ; endpoint-0 setup bytes
4002CFA4  [r0+0x064] = 0 / [r0+0x066] = 0   ; (exact MUSB register identity [U])
4002CFAC  [r0+0x001] |= 0x20                ; MUSB POWER |= HSENAB (high speed)
4002CFDC  bl → [r4+1] |= 0x40               ; MUSB POWER |= SOFTCONN (bus connect)
4002CFF2  movw r0,#0x51E                     ; 1310 ticks @32.768kHz = 40 ms
4002CFF6  poll DEVCTL[4:3] with a 40 ms timeout on the 32 kHz timer
```
[P for bytes/offsets; the MUSB register *names* are the Inventra MUSBMHDRC ones
(the TRM documents only the TI-specific `OTG_*` block, `0x4A0AB400`+) → [I]].
The PHY is powered explicitly [P]:

```
0x4002E0A8  [0x4A100620] |= 0x40000000   ; CONTROL_USB2PHYCORE, bit30
0x4002E0B6  [0x4A100620] &= ~0x40000000  ;        (off)
0x4002E0CE  read [0x4A100620] bit13       ; status
0x4002E0DE  read [0x4A100620] bit14       ; status
0x4002E0FC  [0x4A00233C] |= 1, |= 4, …    ; CONTROL_USBOTGHS_CONTROL
```
`0x4A100620` = `CONTROL_USB2PHYCORE`, `0x4A00233C` =
`CONTROL_USBOTGHS_CONTROL` [P/T​RM]; `CM_ALWON_USBPHY_CLKCTRL` (`0x4A008640`)
and `L3INIT_PRM` (`0x4A307300`) are also touched by the PRCM helpers [P].

`'E'` then waits for the host with a **timeout taken from the descriptor**
(`[r4+0x24]` ticks, compared against the 32 kHz timer at `0x4002C17A`–`0x4002C190`)
and a 0.5 s (`0x4000` = 16384 ticks) pre-connect wait at `0x4002C10C` [P].

### 3.3 What a host sees — the descriptor template

The template lives in ROM at `0x40030008` (0x98 bytes) and is copied to IRAM
`0x4030D108` by bootstrap record 2 [P]. Layout [P]:

| IRAM | ROM | bytes | meaning |
|---|---|---|---|
| `0x4030D108` | `0x40030008` | `C0 32 00 00` | template header: `bmAttributes=0xC0`, `bMaxPower=0x32` (100 mA) |
| `0x4030D10C` | `0x4003000C` | `01 00` | header: `bConfigValue=1` |
| `0x4030D10E` | `0x4003000E` | `12 01 10 02 00 00 00 40 00 00 00 00 00 00 00 01` | **Device descriptor** |
| `0x4030D120` | `0x40030020` | 4 × 32-byte config blocks at +0x18/+0x38/+0x58/+0x78 | configurations |

Decoded device descriptor (18 bytes) [P]:

| field | value |
|---|---|
| bLength / bDescriptorType | `0x12` / `0x01` |
| bcdUSB | **`0x0210`** (USB 2.1 — L1/BOS-capable encoding) |
| bDeviceClass / SubClass / Protocol | `0x00` / `0x00` / `0x00` (class defined per interface) |
| bMaxPacketSize0 | `0x40` (64) |
| **idVendor** | **`0x0000`** |
| **idProduct** | **`0x0000`** |
| bcdDevice | `0x0000` |
| iManufacturer / iProduct / iSerialNumber | `0` / `0` / `0` |
| bNumConfigurations | `1` |

Configurations [P]:

| block | type | wTotalLength | iface | endpoints | wMaxPacketSize |
|---|---|---|---|---|---|
| A `0x40030020` | `0x02` CONFIG | `0x20` | 1 (`class 0xFF, sub 0xFF, proto 0xFF`), iInterface=2 | `0x81` IN bulk, `0x01` OUT bulk | **`0x0200` (512)** |
| B `0x40030040` | `0x02` CONFIG | `0x20` | same | same | `0x0040` (64) |
| C `0x40030060` | `0x07` OTHER_SPEED_CONFIG | `0x20` | same | same | `0x0040` (64) |
| D `0x40030080` | `0x07` OTHER_SPEED_CONFIG | `0x20` | same | same | `0x0040` (64) |

`bmAttributes = 0xC0` (self-powered, no remote wakeup) in all four blocks [P].

**Speed.** `POWER |= 0x20` (HSENAB) at `0x4002CFAC` plus a 512-byte bulk
max-packet block means high-speed is enabled and expected; the 64-byte blocks are
the full-speed / other-speed views [P for bytes, I for HS negotiation]. No
`0x20`/`0x10` value is written to `DEVCTL` for speed forcing in the connect path
(the `strb r0,[r1,#15]` at `0x4002DB88` writes 32 or 16 there, but that routine is
reached from the *host-role* helper at `0x4002DB7E` and is not on the `'E'` path)
[P/I].

**VID/PID answer.** Nothing in the ROM writes the descriptor's vendor/product
fields: the only template writers are `0x4002DB8C` / `0x4002DB92`, which store a
single byte at template `+0` and `+1` (`bmAttributes`, `bMaxPower`), and
`0x4002DB18`, which uses `+4` (`bConfigValue`). The aligned-word scan for
pointers into `0x4030D000`–`0x4030DFFF` returns **no** reference to
`0x4030D114`/`0x4030D116` (the `idVendor`/`idProduct` fields) [P]. There is also
no eFuse/OTP read for a USB ID: `CONTROL_ID_CODE` is never addressed, and the
only fuse access is `CONTROL_STD_FUSE_CONF` (`0x4A002220`) bits 12/13 [P].
Therefore a host will enumerate this device as **VID 0x0000 / PID 0x0000** [P
for the descriptor bytes; [I] that no later patch exists].

### 3.4 Does it answer `GET_DESCRIPTOR`? — yes

`0x4002D830` is the setup/control handler. State byte at `0x4030DC38`; the setup
packet is at `0x4030DC3E` (`bmRequestType`, `bRequest`, `wValue` at `+2`,
`wIndex` at `+4`, `wLength` at `+6`) [P]:

```
4002D84A  movs r2,#0x20
4002D84C  ldr  r4,=0x4030DC38 ; adds r4,#6      ; r4 = setup packet
4002D850  add  r3,r4,#0xa                       ; r3 = 0x4030DC48 (request blk)
4002D854  ldrh r1,[r4,#2]                       ; wValue
4002D856  lsrs r6,r1,#8                         ; r6 = descriptor type
4002D858  cmp  r6,#8 / bhs 0x4002D8E0           ; >7 -> reject
4002D85C  tbb  [pc,r6]                          ; table at 0x4002D860 = 40 04 09 24 40 40 1f 14
```
[P]. `tbb` targets (base `0x4002D860`, entry × 2) [P]:

| wValue>>8 | target | handled |
|---|---|---|
| 0 | `0x4002D8E0` | rejected |
| **1 DEVICE** | `0x4002D868` | `r0 = [0x4030D10C]+2 = 0x4030D10E`, length `0x12` → `str [r3,#4]`, `strh 0x12,[r3,#8]` |
| **2 CONFIG** | `0x4002D872` | config path |
| **3 STRING** | `0x4002D8A8` | string path |
| 4, 5 | `0x4002D8E0` | rejected |
| **6 DEVICE_QUALIFIER** | `0x4002D89E` | qualifier path |
| **7 OTHER_SPEED_CONFIG** | `0x4002D888` | other-speed path |

The response is expressed as `{ptr at 0x4030DC4C, len at 0x4030DC50}` and
transferred by the endpoint engine (`0x4002D0BA` = TX/IN setup,
`0x4002D126` = RX/OUT setup) [P]. So: **the ROM enumerates, answers
`GET_DESCRIPTOR` for device/config/string/qualifier/other-speed, and services
both bulk endpoints** — consistent with the enumeration state machine at
`0x4002D724`/`0x4002D830` driving `0x4030DC38` through states 2/3/4 [P for the
code, state meanings [I]].

**Strings.** `iManufacturer = iProduct = iSerial = 0`, and there is **no UTF-16
string anywhere in the image** (ASCII scan shows only the TOC names of §2.7) [P].
A `GET_DESCRIPTOR(STRING)` request can only ever return the language-ID entry or
be stalled; there is no product/manufacturer string to read, so a host shows a
blank product name [I].

**Practical consequence.** A dead unit *would* show up on a host as
`0000:0000` — indistinguishable from a broken/no-name device, and rejected by
any udev/tool rule that matches a real TI VID — **provided** the ROM reaches the
`'E'` command (i.e. SYS_BOOT is not `0x1D`/`0x1E`, and the unit gets as far as
the config parser). If the ROM dies earlier (bad DDR/clock/PMIC, or SYS_BOOT
selects only storage that never returns), no USB device appears at all [I].

## 4. Failure behaviour (Q3)

### 4.1 The retry loop

`0x40028A7C` never returns. Its inner structure (all [P]):

```
40028B40  (loop head)  r0 = 0xFFFFFFFF ; store to result[0x64] ; memset via 0x4002F2D0
40028B50  r4 = 0                       ; command index
40028B50  cmd = table[r4]
40028B52  if (cmd-1) < 8      -> 0x4002AD5C(flags, cmd, result+0x64)   ; media
40028B6C  if (cmd-0x41) >= 6  -> next command (byte silently ignored)
40028B72  else: progress(5); WDT start (0x4002A430)
            r6 = 0xFFFFFFFF
            image_handler 0x4002AFFE(flags, cmd, &r6, result+0x64)
            WDT stop (0x4002A454)
40028B94  if (r6+1 == 0)          -> next command        ; 0xFFFFFFFF = "not found"
40028B98  if (r6 == 0xF0030003)   -> next command        ; "section absent"
40028BAA  if ((r6 & ~0xFF00) == 0xF0030006)
              progress(9); table[i+1] = r6>>8;           ; "remap: next cmd = res>>8"
40028BC4  if (r6 == 0xF0030002)   -> next command
40028BCC  else: progress(8);
              for (j=0;j<8;j++) if (table[j] >= 0x40) table[j] = 0;  ; drop all image cmds
40028BE6  r4++ ; if (r4 < 8) goto 0x40028B50
40028BF4  b 0x40028B40                                   ; <<< retry forever
```
[P].

So, for the specific question *"if the first stage cannot be read or fails
authentication, what happens?"*:

* **Cannot be read** (media `open`/`read` fails, no TOC, or no matching name):
  the handler returns `0xFFFFFFFF`/`0xF0030003` and the loop simply takes the
  **next command byte in the list** — this is the fall-through to USB/UART, not a
  branch to a special "recovery" routine [P]. When the list is exhausted, the
  same list is **re-tried from the top, forever** (`b 0x40028B40`) [P].
* **Fails authentication**: this window has no authentication to fail (§2.8).
  The equivalent event is the secure side refusing the `SMC #0`/`r12=0xF0`
  hand-off, which is outside the NS-visible ROM [U].
* **Halt?** Only three halt-like paths exist: the abort handlers
  `0x400289E4`/`0x400289F0` (capture IFAR/IFSR or DFAR/DFSR into `r0`/`r1` then
  `ldr pc` into the `0x40028088`/`0x4002808C` `b .` cluster) and the
  `0x40028080`–`0x4002809C` stub cluster [P]. The normal failure path does **not**
  reach them.
* **Retry?** Yes — unconditional, infinite, with no delay other than whatever the
  individual handlers do [P].
* **Fall to USB?** Yes, but only because USB is another command in the same list;
  there is no "all media failed → USB" code path separate from the table [P].
* **Reset?** No. The only reset-producing write in the window is
  `PRM_RSTCTRL = 1` at `0x400280EC`, in the unreferenced `0x400280C0` stub [P].

### 4.2 Watchdog bracket

The only WDT interaction on the boot path is the pair around the image handler
(`0x40028B78` start, `0x40028B8E` stop) plus the arm/disarm in Thumb main
(§2.5) [P]. Because the stop is unconditional after the handler returns, a failed
image attempt leaves the watchdog **disabled**; the ROM cannot self-reset through
it [P].

## 5. The public API (Q4)

There are two distinct "API" surfaces. Neither is a function-call table of
*services* at `0x4030D0xx`; that range is IRAM **data**.

### 5.1 ROM export table at `0x40028400` (48 entries)

= a Thumb entry point in the boot alias; the table ends exactly where Thumb code
resumes at `0x400284C0`, which fixes its length [P]. The TRM's ROM memory map
independently places the "API table" at ROM offset `0x28400` [TRM]. Nothing in
the image references `0x40028400`, which is expected for an export table called
from outside [P]. Entries I can characterise from the bytes (target address is

## 6. The 7.35 s cycle (Q5)

**Verdict: nothing in this ROM can produce a ~7.35 s / ~7.8 s periodic reset.**

* `0xFFFC1800` — **absent** [P]: a full-word scan finds no such word; the
  halfword `0x1800` occurs only at `0x4002FFBF`, inside the copy-table record 3
  length field [P]. No related constant (`0x3E800`, `0xC350`, `0xEA60`, `0x7530`,
  `0x1E8480`) appears as a word either [P].
* **The only watchdog programming** is WDTIMER2 (`0x4A314000`) [P]:
  * `0x4002A41C`: `WDSC (+0x10) |= 2`, poll `WDST (+0x14)` bit0.
  * `0x4002A430`: `WSPR (+0x48) = 0xAAAA`, poll `WWPS (+0x34)`, then `0x5555`.
  * `0x4002A454`: `0xBBBB` then `0x4444`.
  * `0x4002A478(sec)`: `WCLR (+0x24) |= 0x20`; then
    `ticks = high32(sec * 0xC49BA5E2) + (sec << 5) = sec * 32.768`;
    `WLDR (+0x2C) = WTGR (+0x30) = -ticks`.
  * Caller passes `0x0002BF20` = **180000** → **180 s** [P for the arithmetic
    and constant; "seconds" is the semantic reading, [I]].
  * It is **stopped** immediately (`0x4002A454`) and again after each image
    attempt (`0x40028B8E`) [P]. A watchdog left running would be a 180-second
    reset, not 7.35 s.
* **Other time bases**: the 32 kTimer (`0x4A304000`, `+0x10`) is read at 22 sites
  for **short** deltas — e.g. `movw r0,#0x51E` = 1310 ticks = **40 ms** in the
  USB connect wait (`0x4002CFF2`), `mov.w r0,#0x4000` = 16384 ticks = **0.5 s**
  pre-connect (`0x4002C10C`) [P]. Both are bounded one-shot waits, and both can
  only *delay* a retry, never reset the SoC.
* **The retry loop has no delay of its own** (`0x40028BF4` → `0x40028B40`), so its
  period is whatever the handlers take; a device that returns instantly gives a
  tight loop, not a 7.35 s one [P].

Therefore a periodic ~7.35–7.8 s reset observed on hardware must come from
(a) the next stage — report 150 §5 proves MLO arms and kicks WDT2 at
`0x800094F0`, and any hang there *does* reset the SoC — or (b) an external/reset
domain source (PMIC, TWL6030 `PWRHOLD`/watchdog, or the debug board), not from
`0x40028000`–`0x40033FFF` [I].

For reference, 7.35 s ≈ 240845 ticks @32.768 kHz and 7.8125 s = 256000 ticks
(exactly `0x3E800` — a value that does **not** occur in the image) [P].

## 9. Open questions

1. **`0x4030D0xx` after hand-off.** Who re-installs the IRAM vector block after a
   payload overwrites `0x4030D000`–`0x4030D03F` (the stack lives there too)?
   Report 150 shows the bootloader carrying its own copies of the *pointers*, so
   the IRAM block is not strictly required after hand-off — but the mechanism is
   [U].
2. **USB state semantics.** `0x4030DC38 ∈ {2,3,4}` drives three different code
   paths in `0x4002D724`/`0x4002D830`; states 3/4 clearly mean "setup received",
   state 2 is [U].
3. **`0x4002F9F8` media-8 descriptor** (`80800C00 000000C3 110D1624 3058161B`)
   is only partially decoded — used by the media-8 `open` at `0x4002BC26`
   together with helper `0x4002A2CA` (API entry 28) [U].
4. **`'E'` vs `'F'`** resolve to the *same* handler set, yet the boot table
   distinguishes them (records 0x0F–0x15 and 0x18/0x1A use `'F'`). Possibly
   "USB with different PHY/port settings" — [U].
5. **`0x400280C0`** (warm reset + reset-reason clear) has no in-image reference;
   its caller is outside this window [U].
6. **`"MLO        "` at `0x4002BC00`** has no pointer and no ADR; whether it is
   dead data from a FAT-capable variant or reached by an odd construction is [U].

## 10. Reproduce

```sh
cd /home/psyden/SSDdrive/playbook-linux
. tools/env.sh
B=local/proprietary/device-binaries/bootrom-0x40028000.bin
sha256sum "$B"            # fc2ad391…b4961
arm-linux-objdump -D -b binary -m arm       --adjust-vma=0x40028000 "$B" > /tmp/rom-arm.txt
arm-linux-objdump -D -b binary -m arm -M force-thumb --adjust-vma=0x40028000 "$B" > /tmp/rom-thumb.txt
```
(The `-M force-thumb` listing is a linear sweep and mis-decodes inline literal
pools; the recursive-descent pass with Capstone used for this report is the
authoritative one. Note that `-m thumb` alone is rejected by this binutils:
`can't use supplied machine thumb`.)

Key raw reads used for the quoted tables:

```sh
xxd -s 0x7F80 -l 0x40  "$B"   # copy table 0x4002FF80
xxd -s 0x7FC0 -l 0x40  "$B"   # IRAM vector block image 0x4002FFC0
xxd -s 0x77C4 -l 0x200 "$B"   # SYS_BOOT device table 0x4002F7C4
xxd -s 0x7A84 -l 0x3C  "$B"   # 14 name pointers 0x4002FA84
xxd -s 0x8008 -l 0x98  "$B"   # USB descriptor template 0x40030008
xxd -s 0x400  -l 0xC0  "$B"   # 48-entry API table 0x40028400
```
