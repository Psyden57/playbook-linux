## §1 The function — and what the call graph really looks like

### 1.1 `0x1cce0` (the R1 target): what it is

Entry `0x1cce0`, size 1244 B (`0x1cce0…0x1d1b8`), stack frame 8 B + 8 saved regs, sole caller
`0x18b6c` (a 364-byte wrapper). `0x18b6c` computes the **HAL parameter block base** and passes
38 pointers into it:

```
18b74  ldr r2,[pc,#348]  @0x18cd8 = 0x12480 ; 18b78 add r2,pc,r2 → r2 = 0x2B000   (anchor)
18b7c  ldr r3,[pc,#344]  @0x18cdc = 0x35C4  ; 18b80 add r3,r2,r3 → r3 = 0x2E5C4   (HAL param block)
       → stack args: r3+0x214, *(0x2B104), r3+0x308, 0x314, 0x320, 0x328, 0x32C, 0x330, 0x334,
         0x338, 0x33C, 0x340, 0x344, 0x348, 0x34C, 0x350, 0x354, 0x358, 0x35C, 0x360, 0x370,
         0x390, 0x39C, 0x3A0, 0x3A8, 0x3B0, 0x3E0, 0x224, 0x3EC, 0x274, 0x3F4, 0x3FC, 0x410(+4,+8,+12),
         0x420, *(0x2B15C)
       → r0..r3: r3+0x2B8, r3+0x2CC, r3+0x2DC, r3+0x2E8
18cc8  bl 0x1cce0
```

`0x1cce0` then only stores `0`, `1`, `2`, `3`, `4` and `0xFF`/`0xB8` bytes/words into those
structures (`strb r1,[r0…]`, `str r3(=1),[r7]`, `mov r0,#2; str r0,[r7,#0x14]`, … ,
`mov r7,#0xff; strh r7,[r0]` at `0x1cee4-0x1cef4`). Example (data-lane/VC array default):

```
1d06c  str   r3(=1),[r5,#0x0c]     1d074 mov r0,#2 ; str [r5,#0x14]
1d080  mov   r0,#3 ; str [r5,#0x1c]  1d08c mov r7,#4 ; str [r7,#0x24]   1d098 str r3(=1),[r5,#0x2c]
```

⇒ **`0x1cce0` is `L1DSS_*_defaults_init()`, the QNX port's "set every parameter struct to its
reset value" step. No register is addressed anywhere in it** (no CRED-table load, no `str`
through a peripheral pointer; every target is a stack-passed pointer into `0x2e5c4…0x2ea00`).

### 1.2 The real register-programming call tree

`0x19020` = top-level display setup (`L2DSS_Easy_QNX_Display`, string @0x275c8), 976 B,
args `(r0 = cfg struct, r1 = "have new mode")`:

```
190e8  bl 0x18ce8            ; defaults init #1  (calls 0x4fd4, 0x4638, 0x47f8)
190ec  bl 0x18b6c            ; defaults init #2  → 0x1cce0

1910c  bl 0x162ec            ; 240-B mode record → HAL params (0x2E5C4+0x00…0x94)
19110  bl 0x18a7c            ; ***DISPC register programming*** (instance 52)
1911c  bl 0x179dc            ; ***DSI reset / CLK_CTRL / PLL / PHY / VM-timing*** (55,56,57)
19124  bl 0x16610            ; DSS_CONTROL (0x48040040) RMW
19144  bl 0x17094            ; DSI FIFO + VC sizing (55)
19184  bl 0x16bd8 / 0x16bc0 → 0x16a00   ; DSI VC enable / disable

```

The immediate callees of `0x162ec` (the translator) and of `0x18a7c`/`0x179dc` are **generated
accessor stubs**: `f(instance_idx, param_ptr)` where the register offset is hardcoded and the
base is `CRED[instance_idx]` from the relocated instance table at **vaddr 0x2B1D4** (444 u32,
sorted physical bases; verified by reading it: `CRED[51]=0x48040000`, `CRED[52]=0x48041000`,
`CRED[55]=0x48044000`, `CRED[56]=0x48044200`, `CRED[57]=0x48044300`, `CRED[58]=0x48045000`).
The CRED *pointer* is the GOT entry at `0x2B164` (anchor 0x2B000 + 0x164 = 0x2B164 → 0x2B1D4),
loaded by the idiom `ldr r3,[pc,…]` (pool word 0x164) / `ldr r3,[anchor,r3]` / `ldr r3,[r3,rN,lsl #2]`
then `add r3,r3,#<reg offset>`.

## §2 H/V assignment

### 2.1 The proof — `fcn.00007768(52, cfg+0x00)` (DISPC timing accessor)

Called from `0x18a7c` at `0x18af4` with `r0 = 52` (DISPC) and `r1 = r4+0x00`, where `r4` is the
HAL parameter block `0x2E5C4`. `0x162ec` (the translator, called at `0x1910c` before this) wrote
that block's first six u16 slots (`0x16304…0x16340`, already established in 111):

```
+0x00 = u16(rec[0x3c] − 1) = 137      +0x02 = u16(rec[0x34] − 1) = 161
+0x04 = u8 (rec[0x38] − 1) =  19      +0x06 = u16(rec[0x30])     =  12
+0x08 = u16(rec[0x28])     =  12      +0x0a = u8 (rec[0x2c] − 1) =   0
```

`0x7768` body (exact):

```
7780  ldrh  r7,[r1]          ; r7 = cfg+0x00 = 137
7784  ldrh  sl,[r1,#2]       ; sl = cfg+0x02 = 161
7788  ldrb  r8,[r1,#4]       ; r8 = cfg+0x04 =  19
77e0  add   r2,r2,#100       ; r2 = CRED[52] + 0x64  == DISPC_TIMING_H1 (0x48041064)
77e4  orr   r7,r8,r7,lsl #20 ;       = 19 | (137<<20)
77e8  movw  r3,#0xff00 ; 77ec movt r3,#0x0f      ; r3 = 0x000FFF00
77f0  and   sl,r3,sl,lsl #8  ;       = (161<<8) & 0x0FFF00
77f4  orr   r3,r7,sl
77f8  str   r3,[r2]          ; DISPC_TIMING_H1 <= 0x0890A113

77fc  ldrh  r7,[r1,#6]       ; {12
7800  ldrh  sl,[r1,#8]       ; {12
7804  ldrb  r8,[r1,#10]      ; { 0
785c  add   r2,r2,#104       ; CRED[52] + 0x68 == DISPC_TIMING_V1 (0x48041068)
7860  orr   r7,r8,r7,lsl #20 ;       = 0 | (12<<20)
786c  and   sl,r3,sl,lsl #8  ;       = (12<<8) & 0x0FFF00
7870  orr   r3,r7,sl
7874  str   r3,[r2]          ; DISPC_TIMING_V1 <= 0x00C00C00

7878  ldrb  r7,[r1,#11]      ; cfg+0x0b = 1
787c  ldrb  r5,[r1,#12]      ; cfg+0x0c = 2
78d4  add   r3,r3,#112       ; CRED[52] + 0x70 == DISPC_DIVISOR1 (0x48041070)
78d8  orr   r5,r5,r7,lsl #16 ;       = 2 | (1<<16)
78dc  str   r5,[r3]          ; DISPC_DIVISOR1 <= 0x00010002
```

TRM Table 10-124 (`DISPC_TIMING_Ho`): `HBP = [31:20]`, `HFP = [19:8]`, `HSW = [7:0]`, each
"bit field value + 1". Same layout for `TIMING_V` with `VBP/VFP/VSW`.

⇒ **`{137,161,19}` = HBP/HFP/HSW goes to `DISPC_TIMING_H`; `{12,12,0}` = VBP/VFP/VSW goes to
`DISPC_TIMING_V`. Proven by the store offsets 0x64/0x68 and the shift positions.**

Panel-side numbers (field + 1):

| | DISPC field | value | panel value |
|---|---|---|---|
| H | HBP [27:20] | 137 | **138** |
| H | HFP [19:8] | 161 | **162** |
| H | HSW [7:0] | 19 | **20** |
| V | VBP [27:20] | 12 | **13** |
| V | VFP [19:8] | 12 | **13** |
| V | VSW [7:0] | 0 | **1** |
| H total | 1024+138+162+20 | | **1344** |
| V total | 600+13+13+1 | | **627** |

Pixel clock = 1344 × 627 × 60 = **50.56 MHz**, and `DISPC_DIVISOR.PCD` (bits 7:0) = **2**
⇒ the DSS functional clock feeding the LCD manager must be **≈101.1 MHz** (`2 × 50.56`). This is
self-consistent: the divisor field is *proven* to be 2, and the record field `rec[0x60] = 2`
feeds it (111 read that byte as "data lanes" — it is the **pixel-clock divider PCD**, and
`rec[0x64] = 1` is `DISPC_DIVISOR.LCD`, bits 23:16).

Colt record (1280×768) for cross-check: `{44,125,0}` → H (HBP 45, HFP 126, HSW 1, total 1452),
`{3,9,3}` → V (VBP 4, VFP 10, VSW 4, total 786); 1452×786×60 = 68.5 MHz.

### 3.2 `DSI_PLL_CONFIGURATION1` (0x4804430c) — accessor `0x1d398`, store at `0x1d4a8`

Parameter block `p = 0x2E5C4+0x248` (=`0x2EE0C`, same object as the record +0x…); filled at
`0x17db8…0x17dd8`:

```
17db8  r3=[r5,#0x78] ; strb → p[0] = rec[0x78]
17dc0  r3=[r5,#0x74] ; strb → p[1] = rec[0x74]
17dcc  r2=h[r5,#0x80]; strh → p[2:3] = rec[0x80]
17dd4  r3=[r5,#0x7c] ; strb → p[4] = rec[0x7c]
17ddc  mov r3,#0 ; strb → p[5] = 0
```

Packing (`0x1d478…0x1d4a8`):

```
r7 = p[0]  → (p[0] << 26) & 0x7C000000          ; bits [30:26]
r8 = p[1]  → (p[1] << 21) & 0x03E00000          ; bits [25:21]
sl = p[5]  →  p[5] & 1                          ; bit  0
r9 = u16@p[2] → (r9 << 9) & 0x001FFE00          ; bits [20:9]
fp = p[4]  → (p[4] << 1)                        ; bits [8:1]
CONFIG1 = that OR-sum
```

TRM field names: `[20:9] PLL_REGM`, `[8:1] PLL_REGN`, `[25:21]/[30:26]` = the PLL clock
selector/multiplier nibbles (CLOCKP/CLOCKM family; the TRM's own setup text uses
"`M multiplier … CONFIGURATION1[20:9] PLL_REGM`" and "`N divider … [8:1] PLL_REGN`").

For the PlayBook 60 fps record `rec[0x74]=5, rec[0x78]=5, rec[0x7c]=95, rec[0x80]=756`:

```
(5 & 0x1f) << 26          = 0x14000000
(5 & 0x1f) << 21          = 0x00A00000
(756 << 9) & 0x001FFE00   = 0x0005E800     (756 = 0x2F4)
(95 << 1)                 = 0x000000BE
p[5] & 1                  = 0x00000000
----------------------------------------
DSI_PLL_CONFIGURATION1    = 0x14A5E8BE
```

⇒ `REGM = 756`, `REGN = 95`, plus the two 5-bit high fields = 5 and 5.

**Bit-rate check.** TRM §"DSI PLL": `PLL output = CLKIN × (REGM+1) / (REGN+1) / 2^?`, with the
HSSYSCLK divided by `HSDIV`. Two structural facts from the code are certain: `REGM = rec[0x80]`
and `rec[0x80] = 12.6 × fps` (111 §3.4) — i.e. the *refresh-proportional* number is the PLL
multiplier. With `REGM = 756` at 60 fps and `REGN = 95`:
`756/95 × 12.5 MHz` SYS_CLK ≈ **99.5 MHz** PLL out ⇒ /2 = 49.7 MHz DDR clock ⇒ ×2 (DDR) =
**≈100 Mbps per lane, ≈200 Mbps aggregate**. That bracket (~200 Mbps) is the same order as the
`3/2 × 50.56 MHz = 75.8 Mbps/lane ⇒ 152 Mbps aggregate` expectation from 111: the code's
REGM/REGN pair lands within ~30 % of it without any correction factor, so the "≈150 Mbps
aggregate" figure in 111 remains plausible but is **not** confirmed exactly — the missing link is
the input clock and the HSDIV exponent (see §7 U2).

### 5.2 `DISPC_POL_FREQ` — accessor `0x751c`, store at `0x7620`

`0x18a7c` calls `0x751c(52, cfg+0x10)`. The translator's defaults (`0x16344…0x16430`) are
`cfg+0x10=0, +0x14=1, +0x18=1, +0x1c=0, +0x20=0, +0x24=0, +0x28=0, +0x29=0, +0x2c=0, +0x2d=0`.

```
r7 = p[0]   → (p[0] << 18) & 0x00040000          ; bit 18
r8 = p[4]   → (p[4] << 17) & 0x00020000          ; bit 17  ONOFF
r9 = p[8]   → (p[8] << 16) & 0x00010000          ; bit 16  RF
fp = p[0xc] → (p[0xc] << 31) >> 16 → bit 15      ; IEO
[sp+20]=p[0x14] → bit 14
[sp+16]=p[0x18] → bit 13                         ; IVS
[sp+12]=p[0x1c] → bit 12                         ; IHS
[sp+8] =p[0x10] → (p[0x10] << 8) & 0xF00         ; bits 11:8 (AC bias)
sl = p[0x1d]     → bits 7:0                      ; PCD-free "ACBIAS/clock gating" byte
```

⇒ **`DISPC_POL_FREQ1 = 0x00030000`**: `ONOFF=1`, `RF=1`, and **`IEO=IVS=IHS=0`** — i.e. HSYNC and
VSYNC are *not* inverted, AC-bias gating off. Under the TRM's convention (bit=0 ⇒ active-low
sync as driven) this is the "TI default" polarity set. This **confirms** 111's inference that no
polarity inversion is applied, and it does so with the register value rather than by absence.

### 5.3 DSI side polarities

No DSI polarity register exists in this generation; the only polarity-ish bits are in
`DSI_CTRL` (0x48044040), written by `0x21994` / `0x221bc` with bit fields taken from the
`cfg+0x…` blocks (`0x16bd8`/`0x179dc` call sites 0x16c04, 0x16f18, 0x174c0, 0x18228, 0x1823c,
0x18438, 0x18808). Those blocks are the DSI "video mode / blanking mode" parameters and are
**not** derived from the six DISPC blanking numbers. Bit-level decode of `0x21994` was not
completed (see §7 U4); what *is* proven is that the DSI path never touches `DISPC_POL_FREQ`, and
the DISPC polarity word is the one in §5.2.

### 5.4 `DISPC_CONFIG1` (0x48041044)

Two RMW sites:
* `0x751c` @0x7748: `bic r3,r3,#0x180` (bits 8:7), then bit8←`cfg+0x30`, bits7:0←`cfg+0x34`
  (`and r4,r4,#1` → bit 0), `bic #0x60` (bits 6:5) then bit6←`cfg+0x38`, bit5←`cfg+0x3c`,
  `bic #0x11` (bits 4,0) then bit4←`cfg+0x20`, bit0←`cfg+0x34&1`.
* `0x78fc` @0x7a00: `bic r2,r2,#0x300` then bits 23,22←`cfg+0x64/0x68`, bit16←`cfg+0x6c`.
* `0x11acc` @0x11bb8: direct write of `DISPC+0x44` from two scalars `cfg+0xd8/0xdc`.

With the 60 fps record every one of those source fields is 0, so **bits 8..0 and 23,22,16 of
`DISPC_CONFIG1` end up 0** (no FIFO merge, no tile/rotation, no alpha blending). Denote the
final value `0x00000000` modulo any bits outside those masks.

### 5.5 `DISPC_CONTROL1` bits set by this path

`0x16610` (called at `0x19124` with `r0 = cfg`) RMWs **`DSS_CONTROL` (0x48040040)**, not
DISPC_CONTROL:

```
16670  r6 = CRED[51] + 0x40                 ; DSS_CONTROL
166cc  r2 = read ; bic #0x300 ; orr ((cfg+0x288)<<8 & 0x300) ; str
16790  r2 = read ; bic #0x2   ; orr ((cfg+0x28c)<<1 & 0x2)   ; str   ; DIGITALENABLE
16854  r2 = read ; bic #0x1   ; orr ( cfg+0x294    & 0x1)    ; str   ; LCDENABLE
```

`cfg+0x288/0x28c/0x294` are board-level enable flags; the Winchester boot path leaves
`DIGITALENABLE`/`LCDENABLE` to be set later by `L1DSS_DISP_LCD1_Enable` (`DISPC_CONTROL1` bits

## §7 Residual unknowns (explicit)

* **U1 — the second record timing block (`rec+0x40…+0x5c`).** Proven: it feeds
  `DSI_VM_TIMING1/2/3`. Not proven: a pixel-level meaning for each byte, and why its H total
  (1262) differs from the DISPC H total (1344). Resolving this needs the TRM's DSI video-mode
  timing chapter cross-read against `dsi_config_video_mode()` in
  `kernel-clean/drivers/gpu/drm/omapdrm/dss/dsi.c` *or* a hardware readback of VM_TIMING1/2
  after boot. It does **not** block a DISPC-only port.
* **U2 — DSI PLL input clock / HSDIV exponent.** `PLL_REGM=756`, `PLL_REGN=95` are proven; the
  resulting bit rate depends on the SYS_CLK fed to the PLL and on `CONFIG2.HSDIV`, which is
  unresolved (U3). The ≈150 Mbps aggregate expectation from 111 is therefore neither confirmed
  nor refuted.
* **U3 — `DSI_PLL_CONFIGURATION2` numeric value.** Its fields come from `cfg+0x24e…0x262`; the
  bytes `cfg+0x24e…0x252, 0x258, 0x25b, 0x25d, 0x25f…0x262` are never written on the
  Winchester path, so they hold the defaults set by `0x1cce0`/`0x4fd4`. I did not finish
  decoding `0x4fd4` (a 470-instruction defaults initializer) — that is the single remaining
  read needed, and it is a pure static read of `0x4fd4` (callee of `0x18ce8` @0x18d60).
* **U4 — `DSI_CTRL` (0x48044040) and `DSI_CLK_CTRL` (0x48044054) bit assignments.** The field
  order is visible (`0x21994`, `0x221bc`, `0x1e5a8`) but the 13/20 single-bit `and`/`orr` pairs
  were not transcribed field-by-field against the TRM's DSI_CTRL table.
* **U5 — `DSI_TIMING1/2`, `CLK_TIMING`, `STOPCLK_TIMING`, `TX/RX_FIFO_VC_SIZE`, `COMPLEXIO_CFG1`
  numeric values.** Their accessors are located (`0x20f10`, `0x20e40`, `0x203ac`, `0x20c3c`,
  `0x21200`, `0x21498`, `0x1ded4`) and their *offsets* are proven; the byte→field transcription
  of each was not completed.
* **U6 — GFX pipeline registers** (`GFX_BA0/1`, `GFX_SIZE`, `GFX_ATTRIBUTES`, `GFX_ROW/PIXEL_INC`,
  `GFX_TABLE_BA`, `GLOBAL_ALPHA`, `GFX_BUF_THRESHOLD`) are written by `0x12120`/`0x11f00`/
  `0x11cd0` from `cfg+0x98/0x9c/0xa0/0xb4/0xb8/0xbc/0xc0` — decoded at accessor granularity
  only. They matter for the splash blit, not for the timing question.
* **`DISPC_SIZE_LCD1` bit placement** is derived from the TRM field table
  (`LCDSIZEY[26:16]`, `LCDSIZEX[10:0]`) plus the proven fact that `0x162ec` puts
  `height−1 = 599` at `cfg+0x88` and `width−1 = 1023` at `cfg+0x8a`; the exact shift inside
  `0x7ba0` was not transcribed.
