  **ball AD4** mapping is not in the local TRM text; not verified here.
* The clock distinction is real: `wl128x_boot_clk()` in
  `drivers/net/wireless/ti/wl12xx/main.c` says TCXO is the main clock and FREF
  is for GPS/cellular sync, used as the WLAN/BT main clock only when the TCXO
  is 16.368/32.736 MHz or in XTAL modes; it runs during firmware
  initialisation, **after** SDIO enumeration.  The binding
  (`ti,wlcore.yaml`) has separate `ref-clock-frequency` and
  `tcxo-clock-frequency`, with `ref-clock-frequency` required for WL1283.
* `omap_hsmmc.init_hz` does **not** change `host->f_min`; it only overrides a
  400 kHz request while the module parameter is set (default 0), so a normal
  image initialises at 400 kHz (`drivers/mmc/host/omap_hsmmc.c`).
* Linux `mmc_attach_sdio()` calls `mmc_send_io_op_cond()` (CMD5) **first**;
  it does not send CMD52/CMD0 before it (`drivers/mmc/core/sdio.c` 7.3.3).
  **Corrected in session 32 (report 186):** that is true only *inside*
  `mmc_attach_sdio()`.  Its caller `mmc_rescan_try_freq()` sends

  (CMD8) before it.  The audit log shows **CMD52 → CMD0 → CMD8 → CMD5** at
  400 kHz, and the card times out on all of them.

## The opinion, as received

I see one concrete SoC-side test that appears to be missing from the investigation.

Your agent tested the OMAP's FREF_CLK2_OUT output at `0x4A10019C`. But the OMAP4430 has a separate FREF_CLK2_REQ input: it is available in mode 1 of the `FREF_CLK3_OUT` pad, at ball AD4. That pad belongs to the wakeup-control pad bank, and its register is `0x4A31E058`, not `0x4A100058`.&#x20;

This matters because the legacy TI configuration describes `STRFRefClock=2` as 38.4 MHz with wired-OR, normal-polarity clock-request settings. The previous experiment forced an output clock; it did not establish whether the corresponding request input is correctly routed and configured.&#x20;

I would investigate that before declaring every SoC-side possibility exhausted.

## What I would do next

I would stop changing MMC5, CM2 and DPLL_PER registers blindly. Your agent has already done a lot of useful elimination. The next step should be to identify the actual signal or event that differs between QNX and Linux.

### 1. Investigate the missing CLK_REQ input

The OMAP4430 pin multiplexing table identifies:

| Signal        | OMAP pad            | Function                |
| ------------- | ------------------- | ----------------------- |
| FREF_CLK2_OUT | Core pad `0x019C`   | Clock output            |
| FREF_CLK2_REQ | Wakeup pad `0x0058` | Clock request input     |
| GPIO_WK31     | Same wakeup pad     | GPIO alternate function |

The `FREF_CLK3_OUT` pad supports `fref_clk2_req` on mux mode 1 and `gpio_wk31` on mode 3.&#x20;


I would ask your agent to:

1. Read `0x4A31E058` in QNX while WLAN is working.
2. Read the same register in Linux.
3. Compare the complete pad configuration, including input enable and pull settings.
4. Establish whether the PlayBook actually routes that ball (AD4) to the WL1283's CLK_REQ signal.
5. If it does, compare the CLK_REQ level and transitions during WLAN startup.

Do not immediately force mode 1. First establish that the board has this connection and that QNX uses it. If the pin is unrelated to the WLAN chip, discard this hypothesis.

Also, avoid repeating the experiment that changed `CM_DIV_M5_DPLL_PER`: you've already established that it can disturb the display clock.

### 2. Verify which clock the WL1283 actually uses

There is an important distinction in TI's own Linux driver.

The WL128x has two clock sources:

- TCXO: normally the main clock.
- FREF: used for synchronization with GPS and the cellular modem, and used as the WLAN/BT main clock in certain special configurations.

The Linux driver explicitly checks these separately in `wl128x_boot_clk()`.&#x20;

The Linux binding also has separate `ref-clock-frequency` and `tcxo-clock-frequency` properties.&#x20;

This means I would not automatically interpret `STRFRefClock=2` as proof that the OMAP must supply a continuous 38.4 MHz clock before the WL1283 can answer CMD5.

That configuration is a useful clue, but the WLAN driver's clock-selection logic runs during firmware initialization, after SDIO enumeration. Your current failure occurs earlier.

I'd establish these facts independently:

- What is physically connected to the WL1283 TCXO input?
- Is that clock present while WL_EN is asserted?
- Is FREF actually connected to the OMAP?
- Does the reference OS configure the FREF request input, or does it rely on an already-running clock?

The distinction could eliminate a lot of unnecessary clock experimentation.

### 3. Check the actual SDIO initialization frequency

This is an easy software-side sanity check.

Linux's MMC core normally attempts initialization at 400, 300, 200 and 100 kHz. However, each frequency is clamped against `host->f_min`. If your custom `init_hz` implementation raises `f_min` to 12 MHz, Linux won't actually perform the normal 400 kHz initialization attempt.&#x20;

Have your agent report these values:

```
host->f_min
host->f_max
host->f_init
host->ios.clock
OMAP HSMMC SYSCTL.CLKD
Actual MMC5 clock measured at the pin
```

For a controlled test, make sure CMD5 is actually being issued at 400 kHz.

I would also compare the command sequences. Linux sends an SDIO reset (CMD52), then CMD0, then CMD5. The QNX driver might use a different initialization sequence.&#x20;

A logic-analyzer trace would establish whether that difference matters.

### 4. Don't use the Bluetooth test as a WLAN diagnostic

The separate WL1283 integration documentation identifies `BT_GPS_FM_EN` as an additional host signal required to enable Bluetooth, independently of WLAN's `WL_EN`.&#x20;

That document describes a different WL1283 module, so its exact wiring should not be assumed for the PlayBook. Nevertheless, it demonstrates why a silent HCI Reset does not establish that the WLAN core is dead.

I'd put Bluetooth aside until SDIO works, then investigate its enable and UART wiring independently.

### 5. Get one good electrical comparison

This is now probably the highest-value experiment.

Since QNX works, you have an excellent known-good reference state. Capture the following signals during a cold boot on both operating systems:

Recommended logic-analyzer / oscilloscope channels

1. MMC5_CLK

   Confirm initialization frequency, clock edges and startup timing.
2. MMC5_CMD

   Determine whether the WL1283 responds to CMD5.
3. MMC5_DAT0

   Check whether the card drives the response/data line.
4. WL_EN

   Compare assertion time and voltage at the actual chip.
5. CLK_REQ

   Determine whether a clock request occurs and whether the host reacts.
6. 32.768 kHz and the actual fast-clock input

   Confirm that the clocks physically reach the device.

Also measure VBAT and VIO at the chip itself, preferably including their behavior during startup.

The key observation is whether CMD5 gets an actual response on the wire.

| What you observe                             | What it suggests                                             |
| -------------------------------------------- | ------------------------------------------------------------ |
| QNX gets R4, Linux doesn't                   | Compare startup timing, clocks, enable and command sequences |
| WL1283 never drives CMD low on Linux         | Power, reset, clock, strap or initialization problem         |
| WL1283 drives a response but Linux times out | Host sampling, pinmux, voltage or controller configuration   |
| CLK_REQ changes on QNX but not Linux         | Investigate the request input and clock-gating path          |
| Rails or clocks differ at the chip           | Investigate board-level sequencing                           |

A PMIC register reading proves what the PMIC was programmed to do. It does not prove that the actual voltage and clock waveforms are present at the WL1283 pins.

**WL1283 investigation — next phase**

The existing MMC5, GPIO, padconf and PMIC comparisons have substantially exhausted the obvious SoC-side differences. Do not repeat the previous DPLL_PER_M5 output-clock experiment.

1. **FREF clock request input**
   - Identify the OMAP4430 WKUP pad `FREF_CLK3_OUT`, ball AD4.

   - Verify the actual MMC5 initialization frequency.

5. **Stop condition**
   - If the request pin is not connected to the WL1283, eliminate that hypothesis.
   - If electrical traces show identical valid initialization conditions but different CMD5 responses, investigate OMAP HSMMC signal sampling and initialization protocol.

Deliver a short report identifying the first measurable difference between QNX and Linux, rather than another list of registers that happen to match.

My suspicion: the separate `FREF_CLK2_REQ` path is worth checking because it is a specific untested candidate, but I would not bet the entire investigation on it. The biggest breakthrough now will come from observing what the WL1283 actually sees on its pins during a successful QNX initialization versus a failed Linux initialization.

I would prioritize getting that trace over spending another round modifying the kernel.
