**One-paragraph answer.**  The WL1283 is a TI WiLink 7.0 combo on OMAP MMC5
(`0x480D5000`, GIC SPI 59), enabled by GPIO2_22 (`gpio 54`), with its interrupt
on GPIO2_21 (`gpio 53`).  Under QNX 2.1.0.1917 it enumerates and scans (24 MHz,
CMD0 → CMD5 arg `0x00FFFF00` → CMD3 → CMD7).  Under Linux 7.3.3 it is silent
from the first command: CMD52, CMD0, CMD8 and CMD5 all time out (`err=-110`),
and it never drives its IRQ.  Most accessible SoC/board state matches QNX
(pads, PMIC rails, CM2/PRM, MMC5 CON/HCTL/SYSCTL/CAPA), **but the GPIO OE
banks are not identical**: QNX drives several GPIO1/GPIO2 outputs that Linux
leaves as inputs (report 191), and the QNX `startup-playbook` binary and the
TWL `CLK32KG` resource have not been audited.  The QNX software surface is
otherwise fully read: no QNX layer names a WLAN rail, clock or extra pad.  The
remaining difference is at the chip's non-exposed power/clock pins (VBAT,
26 MHz TCXO, 32.768 kHz SLOW_CLK, reset/straps) or in OMAP HSMMC sampling —
**but there are still cheap software-side tests**, chiefly the exact QNX
sequence (no CMD52 and no CMD8), the QNX-only GPIO outputs, and the startup/TWL
decode.  See §11 and report 191.

**Unit state at this dossier:** known-good Linux image **`0xE36C679A`** in
region 0 (restored after the session-34 QNX read), region 1 the 7.3.3 charger
rootfs (`ba275807…`, 17 modules), `BOOTCTR_FCTRY = 0x31`, pack Full 4.126 V /
+265 mA / charging.  The 1917 IFS is **not** on media; the way back is
`local/work/ifs-shim-sealed.ifs` at block `0x825` (region 0 only).  The QNX
reference boot was done in session 34 for the syspage read.

## 1. The question, and what "works" would look like

**Question.** Why does the WL1283 combo enumerate and scan under the reference
QNX 2.1.0.1917, but never answer SDIO under our Linux 7.3.3 image, when every
accessible SoC/board state matches?

**Minimum success criterion.** `mmc5`/`mmc4` completes CMD5 with a response
(R4), the SDIO card is registered, and the chip drives its IRQ line
(`GPIO2_DATAIN` bit 21 = 1) with `WL_EN` high.  After that, the `wl12xx` driver,
firmware/NVS and BT/GPS are separate work.

**What is already true.** The bus controller probes and clocks, the pads are
muxed exactly as the reference, `WL_EN` is high and `WL_IRQ` is configured as
an input, all PMIC rails match, and the card is silent from the very first
command (CMD52), not just CMD5.

## 3. The QNX reference: exactly what works

### 3.1 Observation

On the bare board with the 1917 IFS:

* `ti0` is `UP,BROADCAST,RUNNING,OACTIVE,SIMPLEX,MULTICAST`, MAC
  `14:74:11:8f:9c:c3`, 40+ `scan_results` in `/pps/services/wifi/status`,
  `wifi_power::on`.
* `sloginfo`: `TIWLAN SDIO probe WAS CALLED: initializing mmc device`,
  `SDIO clock Configuration is now set to 24Mhz`,
  `sdioAdapt_ConnectBus: Send commands sequence: 0, 5, 3, 7`.
* `GPIO2_DATAOUT = 0x31413200` (bit 22 WL_EN high),
  `GPIO2_DATAIN = 0x08221018` (bit 21 WL_IRQ high).
* `ifconfig ti0 down` drops `DATAOUT` to `0x31013200` and `DATAIN` to
  `0x08021018`; `ifconfig ti0 up` restores both.  The rightmost front test
  point follows exactly that (1.8 V ↔ 0 V), so it is the chip's IRQ/output,
  not a rail.
* `/pps/services/hw_info/inventory` has **no WLAN attribute**; the WLAN
  hwinfo node is in the syspage and is only
  `WLAN_EN_GPIO=54,WLAN_INT_GPIO=53` with an empty `location` (report 189 §8).
* `/pps/services/wifi/status` and `/pps/services/wifi/control` are the only
  WLAN PPS objects; `/pps/services/hw_info/inventory` is board/eMMC/CPU/audio.

### 3.2 The driver's enumeration (static RE of `devnp-ti1283.so`)

* **Clock/power registers** (`sdio_core_pm`, report 180 §5 correction):
  `SYSCONFIG = (v & ~0x331D) | 0x320D`;
  `HCTL |= 0xA00` (**SDVS18**, bits 11:9 = `0b101`);
  `CAPA [0x240] |= 0x04000000` (VS18);
  `HCTL |= 0x100` (**SDBP**) and poll;
  `ISE = 0`; `IE = 0x317F0137`; `STAT = ~0`;
  `CON &= ~0x20`; `HCTL |= 2` (DTW);
  `SYSCTL = (v & ~4)`, then **`0x000E0080`** (CLKD=2, DTO=14).
  It also enables `CM_L4PER_HSMMC5` (`CM2 0x4A009560`, MODULEMODE=2) and
  writes `PRM 0x4A307564 = 1`.
* **Sequence** (`sdioAdapt_ConnectBus`): **CMD0 → CMD5(arg `0x00FFFF00`) →
  CMD3(arg 0) → CMD7(arg `0x00010000`)**, then function enable.  There is
  **no CMD52 and no CMD8**.  The card clock is **24 MHz** from the first
  command; there is no 400 kHz phase.
* **Enable**: `hPlatform_DevicePowerOn` sets gpio 54 high and waits **120 ms**;
  `hPlatform_hardResetTnetw` drives it low **500 ms** then high.
* **Pads written by the driver**: the 32-bit word at `0x078` covers
  `0x078` = gpio_52 and `0x07A` = gpio_53 (WL_IRQ; mux 3, pull-down);
  `0x07C` (gpio_54 → mux 3), `0x148`/`0x14C`/`0x150` (sdmmc5, mux 0 +
  pull-up).  It does not write `0x19C` or the WKUP pads; the FREF2 output is
  enabled elsewhere in the BSP.
* **hwinfo**: `hwi_find("WLAN")` + `hwi_tag_find("WLAN_EN_GPIO")` /
  `"WLAN_INT_GPIO"`; defaults 54/53 when the node is absent.  The live node
  says exactly 54/53.
* **No PMIC, regulator, CM divider, DPLL, or 32 kHz write**.  The chip's
  rails and slow clock must already be on.

### 3.3 The rest of QNX (session-34 RE, report 189)

* `bin/powerman` `winchester` preset: 94 authorities, 47 edges, 6 dependency
  groups, 35 initial states.  The WLAN authorities
  (`activity/wifi_driver/active|idle`, `air_needs_wifi`, `wlan_needs_DMA`,
  `WLAN_NEEDS_PREVENT_OSWR`) only gate the standby shutdown/OSWR decision.
  No group or edge touches a regulator, I²C device or clock.
* `lib/dll/devpm-omap4.so`: one powerman device **`iva_opp`** (50/100/200 MHz);
  no `system/power/dev` literal; no MMCHS5/`CM_L4PER_HSMMC5` write and no
  WLAN rail.  The `sdmmc5_*`/`gpmc_*` names are four `mmap_device_io()`
  globals that are stored and **never read**; the OSWR wake table (Winchester2)
  includes the WL_IRQ pad (`0x07A`, GPIO2 bit 21) only on OSWR entry/exit.
* `proc/boot/devb-mmcsd-winchester`: has a statically linked powerman client,
  but it registers only a binary **`-power on/off`** mode (cost 3) and requests
  no voltage, clock rate or bus power.  Its init sets `SDBP=1`/`SDVS18`, enables
  `CM2_L3INIT` MMC1/2 module clocks and clears `PRM_L3INIT` `LOSTCONTEXT`; it
  writes no CM divider/DPLL and touches no regulator.  Its base constants are
  **MMC1/MMC2 only**, and the WL1283 is on MMC5 (owned by `devnp-ti1283.so`).
* `lib/dll/hwio-config-winchester.so` (`pad_config` 248 × 20 B, `gpio_config`
  72 × 32 B; resolver in `hwio-omap4.so`): contains only the six known WLAN
  lines — sdmmc5 pads at mux 0 (signals `0x52`–`0x57`), WL_IRQ `0x07A`
  mux 3/signal `0x59`, WL_EN `0x07C` mux 3/signal `0x58`, 0x07E mux 3/signal
  `0x5D`, FREF2_OUT `0x19C` mux 0, and WKUP `0x4A31E058` **mux 3 on both
  halves**.  There is no WLAN rail-enable or clock-control pad.
* `lib/firmware/ti1283/tiwlan_winchester.ini`: `TCXO_Clk = 1` (26 MHz),
  `STRFRefClock = 2` (38.4 MHz wired-OR, normal polarity),
  `STRFRefClockSettingTime = 5`, `TCXO_SettlingTime = 5`,
  `ClockValidOnWakeup = 0`, `TCXO_ClockValidOnWakeup = 0`,
  `TCXO_LDO_Voltage = 0` (internal LDO **2.5 V**), `Platform_configuration = 2`
  (bits 2:1 = 01 → 4 mA SDIO drive; no level shifter, no EEPROM, SDIO IB
  enables 0, HS support 0).  All are firmware-time, after enumeration.
* `bin/hw_info_pps`: runtime-probed inventory; **no WLAN node**.

**Conclusion of the QNX RE: the software surface is exhausted and names no
WLAN rail, clock or extra pad.  The chip-side pins or host sampling remain.**

## 4. The Linux side: what it does today

### 4.1 Device tree (current `local/kernel-tree`, `kernel/source/omap4-winchester.dts`)

* `&mmc5` enabled: `pinctrl-0 = <&sdmmc5_pins &fref_clk_pins &fref_clk2_out_pins>`,
  `vmmc-supply = <&vwl1283>`, `bus-width = <4>`, `ti,non-removable`,
  `non-removable`.
* `vwl1283: regulator-wl1283` is a fixed **3.3 V** supply (`0x325AA0`),
  `regulator-always-on`, **not** GPIO-controlled.  It is a dummy OCR window,
  not a board rail; the comment says it does not switch a rail.
* `sdmmc5_pins`: `0x148`/`0x14a`/`0x14c`/`0x14e`/`0x150`/`0x152` =
  `PIN_INPUT_PULLUP | MUX_MODE0` (0x118).
* `fref_clk_pins`: WKUP pad `0x18` (absolute `0x4A31E058`) = `0x000B0003`
  (mux 3, the reference's value).
* `fref_clk2_out_pins`: CORE pad `0x19c` = `0x0000` (mux 0, fref_clk2_out).
* `wl1283_ctrl_pins`: CORE pad `0x07c` = `0x0003` (WL_EN mux 3).
* `&gpio2`: `ti,no-reset-on-init`; hogs: panel-enable (GPIO2_16 high), display
  bits 9/12/13/28/29 high, GPIO2_20 **low**, **GPIO2_22 (WL_EN) high**.
  GPIO2_21 is **not** hogged (the comment says it is the chip's IRQ input).
* `&gpio4`: hogs GPIO4_5/_8/_28/_31 high, matching the reference.
* `&mmc2` (eMMC): `no-sdio; no-sd;`.
* No `wlcore`/`ti,wl1283` child node under `&mmc5`; the card would come up as a
  bare SDIO device first.

### 4.2 `omap_hsmmc` and the MMC core

* The driver uses the TRM's absolute register offsets via
  `.reg_offset = 0x100` (SYSCONFIG `0x110`, HCTL `0x128`, SYSCTL `0x12C`,
  CON `0x12C`? — see the driver's macros; the key point is the offsets match
  the TRM and QNX).
* Default init: **one 400 kHz attempt** (`f_min = f_init = ios.clock =
  400000`, `SYSCTL.CLKD = 120`, actual 400 kHz), not 24 MHz.
* The rescan sequence (`mmc_rescan_try_freq`, 7.3.3) is:
  `mmc_power_up` → `mmc_hw_reset_for_init` → `sdio_reset` (CMD52, unless
  `MMC_CAP2_NO_SDIO`) → `mmc_go_idle` (CMD0) → `mmc_send_if_cond_pcie`
  (CMD8, unless `MMC_CAP2_NO_SD`) → `mmc_attach_sdio` (CMD5 arg 0) → SD/MMC
  attach (CMD55/CMD1 etc.).  The measured log is
  **CMD52 `0x00000c00` → CMD52 `0x80000c08` → CMD0 → CMD8 `0x1aa` →
  CMD5(arg 0) → CMD55 ×4 → CMD1**; every command returns `err=-110`
  (`-ETIMEDOUT`, `resp0=0`) except CMD0.
* **The custom knobs in the tree:** `omap_hsmmc.init_hz` (override a 400 kHz
  request), `omap_hsmmc.sdio_ocr_quirk` (CMD5 arg `0x00FFFF00`, default off),
  `PBCLK`/`PBCMD`/`PBC` diagnostic prints, and two unused helpers
  `pb_enable_fref_clk2()` and `pb_wl1283_reset_pulse()` (marked
  `__maybe_unused`, not called).
* `mmc_attach_sdio` has a custom `MMC_CAP2_SDIO_OCR_PROBE_FFFF00` path, but
  the quirk is default-off.
* The final tree **does not** have `MMC_CAP2_NO_SDIO_RESET` or
  `post-power-on-delay-ms`; those were session-33 test builds and were
  reverted.

### 4.3 Driver/module/firmware state

* `CONFIG_WL12XX=m`, `CONFIG_WLCORE=m`, `CONFIG_WLCORE_SDIO=m` are set.
* The region-1 rootfs (17 modules) does **not** include the `wl12xx`/`wlcore`
  module closure, and there is no `wlcore` child node; that is deliberate for
  enumeration-only.
* `build_rootfs.py --firmware DIR` can install `/lib/firmware` blobs, but it
  was never run with a firmware tree.  The linux-firmware blobs
  (`ti-connectivity/wl128x-fw-5-sr.bin`, `wl128x-nvs.bin`) are not in the
  repository.

## 5. The failure, measured

On our Linux image, with `GPIO2_DATAOUT = 0x31413200` (WL_EN high) and the
pads identical to QNX:

```
PBC: mmc4 try 400000Hz (f_min=400000 f_max=52000000 f_init=400000 ios.clock=400000)
PBCLK: mmc4 CLKD=120 actual=400000Hz
PBCMD: mmc4 op=52 arg=00000c00 flags=00000195 err=-110 resp0=00000000
PBCMD: mmc4 op=52 arg=80000c08 flags=00000195 err=-110 resp0=00000000
PBCMD: mmc4 op=0  arg=00000000 flags=000000c0 err=0    resp0=00000000
PBCMD: mmc4 op=8  arg=000001aa flags=000002f5 err=-110 resp0=00000000
PBCMD: mmc4 op=5  arg=00000000 flags=000002e1 err=-110 resp0=00000000
PBC: sdio probe_ocr=00000000 err=-110 ocr=00000000
PBCMD: mmc4 op=55 ... err=-110
PBCMD: mmc4 op=1  ... err=-110
```

`GPIO2_DATAIN = 0x01000010` (bit 21 = 0) — the chip never drives its IRQ.
`attach_sdio no` → `mmc4: Failed to initialize a non-removable card`.

**The card is silent from the first command, not specifically at CMD5.**  This
is the single most important diagnostic: it points at the chip not being up
(power/clock/reset), not at a CMD5 argument or OCR mismatch.

Also eliminated in session 29:

* **Init clock 12 MHz** (new `init_hz` knob): commands run ~100 ms instead of
  5 ms, still `attach_sdio no`.
* **WL_EN driven by a `regulator-fixed` at MMC power-up** (+120 ms, after pads
  muxed): no card.
* **`ti,no-reset-on-init` on `gpio2_target`** (so WL_EN is never dropped): no
  card.
* **EN high 5 s before the probe**: IRQ stays low, no card.
* **Full power cycle**: no change; QNX still scans after restore.
* **HCI Reset on UART2** (`0x4806C000`, 115200 8N1, via `/bin/pbhci`): no bytes.
* **`MMCHS_CON` "difference"**: wrong — `0x000E0080` goes to **SYSCTL**
  (CLKD=2, DTO=14), not CON; CON is only `&= ~OD` in both.
* **"The MMC5 functional clock is 96 MHz on QNX"**: wrong — the OMAP4 table

### 6.2 Session 31 (FREF output route)

* **`CM_DIV_M5_DPLL_PER = 0x329` + FREF pad `0x4A10019C = 0x41000000`**, WL_EN
  high: MMC5 still silent and UART2 HCI still silent.  The write **changed the
  DSS clock** (`dpll_per_m5x2_ck` is the DSS parent), glitched the panel;
  `0x204` restores it.  **Trap 116 — do not repeat.**
* The panel glitch was isolated: GPIO2_22, the FREF pad and the WDT2 writes
  were clean; only `0x329` glitched.

### 6.3 Session 32 (second opinion: FREF_REQ and FREF2_OUT)

* **`0x4A31E058 = 0x000B0003` on QNX with WLAN up**: pad0 **mux 3
  `gpio_wk31`**, input off; pad1 `gpio_wk7`.  The `FREF_CLK2_REQ` input (mux 1)
  is **not used** (trap 117).
* **FREF2 output**: `0x4A10019C = 0x41000000` (mux 0), `AUXCLK1 = 0x4A30A314 =
  0x00020100` (SYS_CLK/3 = 12.8 MHz, enabled).  Linux had both off.
* `0xF521AB06` (pad mux + AUXCLK1 gate, divider 1) and `0x18D49C22`
  (`AUXCLK1 = 0x00020100`, 12.8 MHz) **did not actually test CMD5 with the
  clock on**: the enable was a `late_initcall` (level 7), after the
  `omap_hsmmc` device-init probe (level 6).  Trap 124.
* `0xF38CF87E` moves the enable into `omap_hsmmc_probe()` before
  `mmc_add_host()`: `PLAYBOOK: fref_clk2_out 12800000 Hz enable=0` at 2.567 s,
  `PBM: 480d5000.mmc add_host` at 2.567 s — CMD52/CMD8/CMD5 still time out.
  **The FREF2 output is not causal.**
* **QNX protocol**: 24 MHz (CLKD=2) from the first command, no 400 kHz phase;
  CMD5 arg `0x00FFFF00`; sequence CMD0 → CMD5 → CMD3 → CMD7.  Linux's 400 kHz
  and arg 0 are not the difference: a 24 MHz runtime attempt
  (`SYSCTL=0x000e0087`) and a CMD5-arg quirk both fail.
* **WL_EN reset pulse**: image `0xAF4FC103` drives GPIO2_22 low 500 ms → high
  in `omap_hsmmc_probe()` before `mmc_add_host()`; CMD52/CMD8/CMD5 still time
  out.  It also **broke USB warm-reset enumeration** (trap 130) and was
  removed.
* **SDIO audit** (image `0x9471F6C9`): default is one 400 kHz try with
  CMD52 → CMD0 → CMD8 → CMD5(arg 0) → CMD55 ×4 → CMD1, every command
  `err=-110`, card silent from CMD52.
* **BT driver is not the enable**: `devc-seromap-winbt`'s `gpio3_base` is
  GPIO4 (`0x48059000`); its automatic line is GPIO4 bit 28 (force RTS) high,
  which Linux matches; its `gpio_set_output` line is GPIO2 bit 23 (BT_EN), low
  in both captures.  It enables only `CM_L4PER_UART2_CLKCTRL` and touches no
  PMIC/regulator.

### 6.4 Session 33 (powerman RE and electrical comparison)

* **QNX `winchester` powerman preset has no WLAN rail or clock** (report 187).
* **Bare-board comparison**: QNX `ti0` UP, `GPIO2_DATAIN=0x08221018` (bit 21 =
  1); Linux `DATAIN=0x01000010` (bit 21 = 0) with `DATAOUT=0x31413200`.
  `ifconfig ti0 down` on QNX drops both; the rightmost front pad follows the
  IRQ (1.8 V ↔ 0 V).
* **WL_EN is not exposed** at any accessible point: pad `0x4A10007C` mux 3 =
  `gpio_54` confirmed; toggled through a 90 s low, 5 s/5 s and 2 s/2 s waves;
  no point moved.
* **All WLAN pads match QNX**: `0x078 = 0x410B4103`, `0x07A = 0x0003410B`,
  `0x07C = 0x00030003`, `0x148/14C/150 = 0x01180118`; `GPIO2_DATAOUT` matches.
  VIO 1.8 V; no 3.3 V chip rail exposed; the ~4.7 V point is a VBUS-side
  resistor.
* **200 ms post-power-on settle** (DTB-only `post-power-on-delay-ms = <200>`,
  image `0x0B38612D`): clock runs ~400 ms before the first command; CMD52/

  but note it still sends **CMD8**; see §11 H1.
* **USB warm-reset regression** isolated to the session-32 WL_EN reset pulse:
  `0x90BDE221` (FREF off, pulse on) fails; `0x0353A241` (FREF off, pulse off)
  enumerates by itself in 14 s.  The pulse and FREF2 enable are removed.

1. **Wrong bus.** It is MMC5, not MMC1 (`pidin mem`/`pidin irq`; sdmmc5 pads

## 10. What remains (the actual unknowns)

1. **Chip power-up at the pins.** Is VBAT 3.3 V actually present at the
   WL1283 BGA pads? Is the 26 MHz TCXO running? Is the 32.768 kHz SLOW_CLK
   present? Is there a reset/strap pin held wrong?  The accessible points show
   1.8 V and 0 V; no 3.3 V chip rail is exposed.  A multimeter cannot measure
   the TCXO or see CMD; a scope/logic analyser or a board view is needed.
2. **A board-level rail/load switch not visible in the PMIC, pads, GPIO banks
   or QNX software.**  Could be a discrete P-FET/load switch controlled by a
   line that QNX drives and Linux does not, or by a PMIC resource not decoded.
   The 12 TWL non-rail differences and the `0x4A31E05C` pad are candidates.
3. **OMAP HSMMC sampling / sequence.**  The controller sees no response at
   all; if the chip is actually driving CMD (unknown without a capture),
   Linux's sampling/sequence could be wrong.  The exact QNX register-write
   order and the absence of CMD8/CMD52 are not fully reproduced.
4. **The chip's power-on straps / interface selection.**  SDIO vs WSPI, TCXO
   vs crystal, 1.8 vs 3.3 V straps are not documented in the public material;
   a board view or a known-good module schematic is needed.
5. **The 32.768 kHz slow clock path.**  The TWL `CLK32KG` is on in both, but
   the actual waveform at the chip and the pad mux (`SYS_32K` on WKUP 0x5E)
   are unverified.

## 11. Fresh-eyes hypotheses and proposed experiments (ranked)

### H1 (best software-only test) — reproduce QNX's *complete* sequence: no CMD52 **and no CMD8**

**Why it is still open.** The session-33 "CMD52 skip" test set
`MMC_CAP2_NO_SDIO_RESET`, which removed `sdio_reset()` (CMD52), but the rescan
still ran `mmc_send_if_cond_pcie()` (CMD8) because it is guarded by
`MMC_CAP2_NO_SD`, not by `MMC_CAP2_NO_SDIO_RESET`.  The measured sequence was
CMD0 → **CMD8** → CMD5.  QNX sends **CMD0 → CMD5** and nothing else.

**Exact change.** For the `480d5000` host only, set **both**
`MMC_CAP2_NO_SDIO_RESET` and `MMC_CAP2_NO_SD` (and optionally
`MMC_CAP2_NO_MMC`) in `omap_hsmmc_probe()`.  In 7.3.3
`mmc_rescan_try_freq()`:

```c
if (!(host->caps2 & MMC_CAP2_NO_SDIO)) { sdio_reset(host); }   /* CMD52 */
mmc_go_idle(host);                                             /* CMD0 */
if (!(host->caps2 & MMC_CAP2_NO_SD)) {
        mmc_send_if_cond_pcie(host, host->ocr_avail);           /* CMD8 */
        ...
}
if (!(host->caps2 & MMC_CAP2_NO_SDIO)) { mmc_attach_sdio(host); } /* CMD5 */
```

With `NO_SDIO_RESET | NO_SD | NO_MMC`, the sequence is CMD0 → CMD5 only.
Also set `omap_hsmmc.sdio_ocr_quirk=1` (CMD5 arg `0x00FFFF00`) and
`omap_hsmmc.init_hz=24000000` to match QNX's first command.  This **specific
combination** has not been booted.

**Implementation note (external review, report 191).**
`MMC_CAP2_NO_SDIO_RESET` is a session-33 **custom** capability, not upstream
and **not in the current tree**.  Add the quirk at the `sdio_reset()` call
site (`if (!(caps2 & MMC_CAP2_NO_SDIO) && !(caps2 & MMC_CAP2_NO_SDIO_RESET))
sdio_reset(host);`) or use a custom rescan.  **Do not set
`MMC_CAP2_NO_SDIO`** — it would skip CMD5 entirely.

**Decision table.** If CMD5 now answers, the difference was the SD command
path (CMD8) or the exact first-command state.  If it still times out, the card
is not up and the chip-side evidence is mandatory.

**Cost:** one region-0 build/boot.  **Risk:** low; it is a host quirk, not a
power change.

### H2 (corrected by the external review) — verify `HCTL`/`CAPA`; the 3.3 V OCR does not select SDVS33 on MMC5

**Finding.** The known-good image `0xE36C679A`'s DTB has
`regulator-wl1283` = **1.8 V** (`0x1B7740`) and the mmc5 pinctrl **without**
`fref_clk2_out_pins`; the current tree / `kernel/patches/0001-...7.3.3.patch`
/ final image `0x0353A241` have **3.3 V** (`0x325AA0`) and add
`fref_clk2_out_pins` (see §13).

**Correction (report 191).**  `ti,dual-volt` is on **`mmc1` only**
(`omap4-l4.dtsi:2164`); `&mmc5` has no such property.  In `omap_hsmmc.c` the
non-dual-volt branch selects **`hctl = SDVS18; capa = VS18;`** unconditionally
(lines 719–729, 1614).  The `vwl1283` 3.3 V is an **OCR advertisement** (the
chip's VBAT is 3.3 V), not the signalling voltage; MMC5 still uses 1.8 V
signalling.  So the 3.3 V window is **not** a 3.3 V-signalling hazard and
**do not blindly revert it** to 1.8 V.

**Do instead.** Record `HCTL = 0x00000B00` (SDVS18 | SDBP) and `CAPA` VS18
immediately before/after the first command; if either differs, investigate.
If a 1.8 V I/O model is wanted, add a `vqmmc-supply` (the I/O rail) rather
than changing the OCR `vmmc`.  The known-good/current DTB difference is still
a tree-state difference; it is not the cause of the CMD5 timeout.

### H3 — replicate QNX's exact MMC5 register-write order

**Why.** QNX's `sdio_core_pm` writes `SYSCONFIG`, `HCTL` (SDVS18), `CAPA`
(VS18), `HCTL` SDBP, `ISE`, `IE`, `STAT`, `CON`, `HCTL` DTW, then `SYSCTL`
(CLKD=2/DTO=14).  Linux's `omap_hsmmc_set_ios`/`set_power` order is different:
clock/power-up, `CON`, `HCTL`, then the core's command.  The reports compared
the *values* but not the *order/timing*.  A boot-time trace of every MMC5
register write (address, value, timestamp) and a side-by-side against the QNX
sequence is cheap and may reveal a sequencing requirement (e.g. SDBP before
the clock, or `CAPA.VS18` before `SYSCTL`).

**Exact change.** Add a one-shot `writel` trace in `omap_hsmmc` gated to
`480d5000`, or use the existing `PBD:` dump plus a `regmap`-style trace; compare
with report 180 §5's QNX sequence.  If a difference is found, replicate the
QNX order in `omap_hsmmc_set_power()`/`set_ios()`.

### H4 — decode the 12 TWL6030 non-rail differences and the `0x4A31E05C` pad

**Why.** The full TWL map was compared, but the 12 differences were never
individually decoded: `0x00`, `0x01`, `0x20`, `0x2d`, `0xb0`, `0xb1`, `0xb2`,
`0xbd`, `0xbe`, `0xe4`, `0xf4`, `0xfa`.  Some are likely interrupt/status/ADC,
but one could be a GPIO/eVT/oscillator/32k control.  Separately, WKUP pad
`0x4A31E05C` differs on its low half: QNX `0x0100000B` vs Linux `0x01000108`
(pad0 `FREF_CLK4_OUT`: mux 3 vs mux 0+input; pad1 `SYS_32K` high half 0x0100
both).  The report 185 called only `AUXCLK1` functional, but this pad was not
explained.

**Exact work.** Read the TRM register descriptions and the TWL6030 datasheet
for those 12 registers; compare the QNX and Linux values bit by bit; check
whether any is a GPIO/REGEN/CLK32KG/oscillator control.  Decode `0x4A31E05C`
from TRM Table 18-673 and establish whether the board routes `SYS_32K` or
`FREF_CLK4_OUT` to the WL1283.  Static, no boot.

### H5 — measure the chip's power/clock at the pins (decisive external evidence)

**Why.** The QNX software surface is exhausted; the accessible DC points show
1.8 V/0 V but not VBAT, the 26 MHz TCXO, or the 32.768 kHz.  A PMIC register
read proves programming, not the waveform at the chip.

**What to measure, QNX vs Linux on the same bare board:**
* VBAT (3.3 V nominal), VIO (1.8 V) at the chip's supply pins/BGA;
* 26 MHz TCXO (frequency and amplitude) at the TCXO/crystal pins;
* 32.768 kHz SLOW_CLK (0–1.8 V square wave, ~0.9 V DC average on a meter);
* WL_EN (1.8 V high) and WL_IRQ (1.8 V when up, 0 V when down);
* MMC5_CLK/CMD/DAT0 with a cheap 1.8 V USB logic analyser (400 kHz or 24 MHz);
* current draw on the 3.3 V rail before/after WL_EN, QNX vs Linux (a bench
  supply with a current display is enough to split "chip unpowered" from
  "chip powered but silent").

**Decision table.** If QNX has a signal Linux lacks (e.g. 26 MHz or 32 kHz),
that is the missing variable.  If the traces are identical and the chip still
does not drive CMD, the chip is not starting despite valid conditions — then
the strap/reset/board view is the remaining evidence.

### H6 — verify the 32.768 kHz SLOW_CLK path

**Why.** The Motorola 148603 guide says the WL1283 needs a 32.768 kHz square
wave (0–1.8 V, 1 MΩ).  The TWL `CLK32KG` is ON in both OSes, but the actual
routing to the chip and the `SYS_32K` pad (`0x4A31E05C` high half) are
unverified.  The QNX driver does not configure the slow clock; the board/BSP
must supply it.  If it is missing only under Linux, the chip may not boot its
digital core.

**Exact work.** Identify the `SYS_32K`/`CLK32KG` net on the board (pad
`0x4A31E05C` pad1); measure the waveform at the chip's SLOW_CLK pin; compare
QNX vs Linux; check the TWL `CLK32KG` control/resource registers beyond
`CFG_STATE`.

### H7 — WL_EN timing relative to VIO/VBAT

**Why.** The loader leaves WL_EN low; QNX raises it at driver load, after the
PMIC rails.  Linux's boot-time hog raises it early, possibly before
VBAT/VIO/TCXO are stable.  The session-29 "regulator-driven at MMC power-up
(+120 ms)" test may have covered this, but the exact timing (WL_EN low until
after the regulator framework and the TWL rails are up, then high with 120 ms)
is worth one controlled boot.

**Exact change.** Remove the `wl1283-en-hog`; drive GPIO2_22 high from
`omap_hsmmc_probe()` after regulators/`mmc_add_host` prerequisites, with a
120 ms delay (a variant of `pb_wl1283_reset_pulse()` without the 500 ms low).
Do not re-add the 500 ms reset pulse as a CMD5 test; it is negative and it
breaks USB enumeration (trap 130).

### H8 — check the chip's power-on straps / interface selection

**Why.** The WL1283 supports SDIO/WSPI, TCXO/XTAL and 1.8/3.3 V options.  The
`.ini` fields are firmware-time; a strap pin (not exposed) could select the
wrong interface or clock.  Public documentation is NDA-limited; the Motorola
148603 guide's typical application schematic is the best public reference
(report 186 §3/§5).

**Exact work.** Obtain a PlayBook board view/schematic or compare the strap
pins against the Motorola typical application.  Check `Platform_configuration`
(bits 2:1 = 4 mA drive, bit 0 level shifter, bit 7 HS) only after enumeration;
it is not a strap.

### H9 — one more controller-level check: `SYSCONFIG`, `IE`, `ISE`, `STAT`, `PSTATE`

**Why.** The reports compare `CON`, `HCTL`, `SYSCTL`, `CAPA`, `STAT`, but not
the full `SYSCONFIG`/`IE`/`ISE`/`PSTATE` set at the first command.  QNX writes
`SYSCONFIG = (v & ~0x331D) | 0x320D`, `IE = 0x317F0137`, `ISE = 0`,
`STAT = ~0`.  Linux's values may differ in ways that affect command completion
or error signalling, even though the card's silence is likely chip-side.

**Exact work.** Add a one-shot dump of `0x110/0x114/0x128/0x12C/0x130/0x134/
0x138/0x140/0x224/0x228/0x22C` before the first CMD52; compare with the QNX
sequence.  Static/one boot.

### H10 — do not forget the simpler explanation: the chip is not powered

The most likely remaining explanation is still **VBAT missing at the chip** or
**the 26 MHz TCXO not running**.  The board has no exposed 3.3 V chip rail;
the ~4.7 V point is VBUS.  The QNX side works, so the board *can* power it;
the question is whether a QNX service or the bootloader sets a load switch that
Linux does not.  The full TWL map and GPIO banks were compared, but a discrete
load switch controlled by a line not yet identified is possible.  A board view
or a current measurement at the chip is the fastest way to settle it.

before the hypotheses.

I extracted the DTB from both region-0 images and decompiled it:

| property | known-good `0xE36C679A` | current tree / `0x0353A241` |
|---|---|---|
| `regulator-wl1283` | **1.8 V** (`0x1B7740`) | **3.3 V** (`0x325AA0`) |
| `&mmc5` `pinctrl-0` | `<&sdmmc5_pins &fref_clk_pins>` | `<&sdmmc5_pins &fref_clk_pins &fref_clk2_out_pins>` |
| FREF2_OUT pad `0x19C` | not in the mmc5 pinctrl | muxed to `fref_clk2_out` |
| `AUXCLK1` enable | not called | not called (the helper is `__maybe_unused`) |
| `MMC_CAP2_NO_SDIO_RESET` / `post-power-on-delay-ms` | no | no (session-33 tests reverted) |
| WL_EN hog / GPIO4 hogs / `ti,no-reset-on-init` | yes | yes |

The **known-good** image is the session-31 1.8 V configuration; the **current
tree and the 7.3.3 patch** are the session-32/33 3.3 V + FREF2-pad
configuration.  A clean rebuild from `kernel/patches/0001-playbook-
winchester-7.3.3.patch` therefore does **not** reproduce the known-good
baseline.  The final image `0x0353A241` is not a known-good baseline (report
188).

**Why it matters (corrected by the external review).**  MMC5 has no
`ti,dual-volt`, so the controller uses SDVS18 regardless; the 3.3 V `vmmc` is
an OCR advertisement (VBAT 3.3 V), not the signalling voltage.  The
known-good/current difference is a tree-state difference, not a 3.3
V-signalling hazard.  **Do not blindly revert; verify `HCTL = 0x00000B00` and
`CAPA` VS18.**

**Also note:** the known-good image does not mux `0x19C`; the current tree does.
The FREF2 *clock* is off in both (the enable helper is not called), so the pad
mux alone should be inert, but it is another difference from the known-good.

### Reproduce the QNX reference

```bash
# from our Linux image, region 0 only:

    --dest-block 0x825 --from-bootrom --password 0000 --apply > /tmp/f.log 2>&1 &
```
