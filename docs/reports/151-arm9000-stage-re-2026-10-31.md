## 0. Layout, base, and one correction to the brief

### 0.1 Correction: where the stage ends

`bootblob_arm9000.bin` is **86016 = 0x15000** bytes, and `cmp` over all of it
shows it is byte-identical to `emmc-first1mb.bin[0x9000 : 0x1E000]`, **not**
`[0x9000 : 0xE9000]` as the task brief states. So:

| item | value |
|---|---|
| ARM stage | file **0x009000 – 0x01E000**, i.e. address **0x80009000 – 0x8001E000** |
| size | 0x15000 (86016) bytes — exactly `bootblob_arm9000.bin` [P] |
| trailer/data table | file 0x01E000 – 0x020000 (another 8 KiB of descriptor records) |
| rest of the 1 MiB | file 0x020000 – 0x100000 is **all `0xFF`** (erased) [P] |

`bootblob_arm9000.bin` is therefore **not independent** and was not used.

### 0.2 Base

Address = 0x8000_0000 + file offset, as given. Every internal reference in the
stage is consistent with this: e.g. `80019264: faffeda6 blx 0x80014904` lands on
`main` at file 0x14904, and `800149c4: 496d ldr r1,[pc,#436] @ (0x80014b7c)`
lands on a literal pool word at file 0x14b7c.

## 1. Q1 — Entry and control flow

### 1.1 Where it starts, and how it gets there

**[P] Entry is `0x80009000`** (the vector table's first word, which branches to
`0x80019224`); the duplicate branch at 0x8009030 targets the same address, so a
loader that jumps either to the section base (0x80009000) or to the recorded
entry (0x80019224) lands in the same place.

**[P] It receives no arguments in registers and reads none.** The whole prologue
is:

```
80019224: e3a000d3  mov  r0, #0xd3        ; SVC mode, IRQ+FIQ masked
80019228: e121f000  msr  CPSR_c, r0
8001922c: e59f0084  ldr  r0, [pc, #132]   ; -> 0x800517c0
80019230: e580d000  str  sp, [r0]         ; save the incoming (ROM) stack pointer
80019234: e59f0080  ldr  r0, [pc, #128]   ; -> 0x80024674
80019238: e2800b06  add  r0, r0, #6144    ; 0x1800
8001923c: e1a0d000  mov  sp, r0           ; sp = 0x80025E74
80019240: e24dd004  sub  sp, sp, #4       ; sp = 0x80025E70
```

The only value inherited from the previous stage is **SP**, stashed at
0x800517C0. The stage then builds its own parameter/hand-off block
0x80024674–0x80025E74 (6144 bytes) and uses 0x80025E74 as its stack top.

### 1.5 Answer to Q1 (summary)

* Starts at **0x80009000** (`b 0x80019224`), takes **no arguments**; only the
  incoming **SP** is preserved (→ 0x800517C0) [P].
* Sets SVC mode with IRQ/FIQ masked, builds a 6 KiB parameter block at
  0x80024674–0x80025E74, **enables the MMU** with tables at 0x80054000 [P].
* Before any OS image work: console bring-up, **WDT2 armed**, clock/table init,
  SRAM hook swap, boot-status block update [P].
* Policy (`main`): banner → **boot mode** (FACTORY/PRODUCT from the NV item
  `BOOTCTR_FCTRY`) → **boot-state word** at media 0x2040 (0..8, `tbb` dispatch)
  → read **NvOSRegionStruct** (193 B @ media 0x2074) → pick region 0/1, check
  `counter < limit` → **load (unverified, then verified)** → probe the loaded
  image header → read media 0x2004 for `0xAAAAAAAA` → disable MMU → print
  "Leaving bootrom and entering OS" → `bx` to `*(0x80025E74)` [P].

```
8001483c: 2105        movs r1,#5 ; str.w r1,[r8]   ; err 5 = CRC mismatch
```

The three CRC primitives are literal one-liners in ARM [P]:

```
8001a7b4: e3e00000  mvn  r0,#0            ; crc_init()  = 0xFFFFFFFF
8001a7b8: e12fff1e  bx   lr

8001a7c8: e3e01000  mvn  r1,#0
8001a7cc: e0200001  eor  r0,r0,r1          ; crc_final() = ~ctx   (0xFFFFFFFF)
```

Init `0xFFFFFFFF`, reflected update routine at 0x80013770, final complement —
i.e. **CRC-32/ISO-HDLC** (the zlib/ethernet CRC-32), not a plain
"poly 0x04C11DB7 MSB-first". The constant `0x04C11DB7` at file 0x13F2C sits in
an unrelated table-building routine and is *not* the update polynomial.

**What is covered:** `[start, end-4)`, where `start`/`end` come from the region
descriptor (two pointers, `[desc+8]` and `[desc+0xC]`), and the expected value
is the 32-bit word at `end-4`. Nothing else is hashed at this point.

without the monitor image.

`0x80018420` (bignum exponentiation with `clz`-based normalisation at 0x800187D8)
is an RSA-style public-key verify over a SHA-2 digest, not a bare hash compare.
The exact digest width cannot be stated from these bytes alone **[U]**.

### 2.6 Answer to Q2

* It verifies **the region image it is about to jump to** — not "region 0", not
  the 0x2BFE10 IFS as such, and **not the RCFS** [P]. Explicit negatives from a
  full-image scan: the constant `0x002BFE10` occurs **nowhere** in the 1 MiB, and
  the strings `IFS`/`ifs`/`RCFS`/`rcfs` occur **nowhere**. The region is selected
  by `NvOSRegionStruct` (NV record at media offset 0x2074), with A/B fallback and
  a per-region **boot counter vs limit** gate [P].
* Algorithm: **CRC-32/ISO-HDLC** over `[start, end-4)` against the word at
  `end-4` (0x80014788, primitives 0x8001A7B4/C0/C8) — this is the path taken in
  FACTORY mode for type-6 images; otherwise a **0x230-byte-trailer
  public-key/SHA-2 signature check** (`0x80018688`, cert magic
  `0xB5A60BFD` at +0xB8) [P].
* Structure checks: size ≥ 0x20000, `0xC3D0E193` at +0x9C, `0xD7C82D1F` at
  end-8, length at end-4 [P].
* Keys: **none in this image** — the expected digest is fetched with selector
  0x85 through `0x8001AFEC` [P]/[U].
* Result branches: table in §2.5; region flip + `"Verification of regions
  failed"` on exhaustion; `0x0F`/`5`/`7` status codes; abort (2) from the
  service hook [P].

## 3. Q3 — Load and jump

### 3.1 Headline: **`arm9000` never reads offset 0x100000 and never copies the IFS** [P]

Evidence:

1. Every media access in the stage goes through `0x8000A9D8` (read) /
   `0x8000A9FE` (write). There are 30 call sites; the **largest transfer is 512
   bytes** and the largest read offset is **0x2819**:
   full table in §6.3. No call passes 0x100000, 0x200000, 0x8100000 or any
   multi-megabyte length.
2. A 32-bit-constant scan finds **no** occurrence of `0x08100000`
   (media 0x8100000) anywhere in the 1 MiB image, and `0x00100000` appears only
   inside unrelated arithmetic/strings, never as a media argument.
3. The verifier hashes **memory** (`0x80014788`, §2.2) and performs **no** media
   I/O in its loop.
4. `main`'s only "load" calls (`0x80014548`, `0x8001453C` → `0x800142A8` →
   `0x80014148`) take the image address from an **out-parameter** that the
   caller supplied (`&sp[4]`), i.e. from a structure that already exists [P].

**Therefore the IFS at region-0 offset 0x100000 is placed in DRAM by an earlier
stage (MLO / PRIMAPP at file 0x4000–0x8D70, or the ROM) and `arm9000` only
selects, sanity-checks, measures and jumps into it.** [P] for "arm9000 does not
do it"; [I] for "MLO does it" (the MLO blob at 0x4000–0x8D70 is in the same 1 MiB
and would be the natural place; not proven here).

### 3.2 Where the entry value comes from [P]

### 3.5 Answer to Q3 — and a correction to the chainloader assumption

* **`arm9000` does not find, copy or container-verify the region-0 IFS at
  0x100000.** It has no read of that offset and no bulk copy; the only media
  traffic is 4–512-byte NV records (§6.3) [P].
* It **does** verify the *loaded* image in memory: container magic/size
  (§2.3), then CRC-32 or the 0x230-trailer signature (§2.2/§2.4), and it
  range-checks the entry against `header+0x7C` (§3.2) [P].
* The jump is `bx r0` at **0x800192A8** with **r0 = `*(0x80025E74)` = the
  image's entry**, SP restored to the ROM stack, MMU/caches off.

> **Correction to the project's chainloader assumption** (`r0 = 0`, `r1 = ~0`,
> `r2 = DTB`): *this stage establishes none of that.* It passes exactly one
> meaningful register, **r0 = entry**, and leaves **r1/r2 undefined**. Any
> `r0=0 / r1=~0 / r2=DTB` convention must therefore come from the **entry stub
> inside the image** that is being jumped to (i.e. from the project's own
> chainloader/IFS entry), not from the bootloader. Equally, the DTB address is
> not communicated by this stage at all — if the chainloader relies on r2, it
> must compute or embed it itself [P].
>
> Also note the stage clears the parameter block 0x80024674–0x80025E70 (6144 B)
> when `0x800158E4` returns 0, so **no boot parameters survive in that block**
> except the single entry word at 0x80025E74 [P].

* **GET_DESCRIPTOR: cannot be answered** — there is no descriptor table and no
  VID/PID anywhere; `0x0FCA` does not occur [P]. Stated explicitly as requested.
* Reachable only via the verify/hash service hook `0x80012516` [P]; i.e. the

  path exists for this platform it must live in the MLO stage at file

### 5.5 Could a corrupt input cause a **fault** rather than a clean halt?

**[I] Yes — several ways, all reachable from corrupted media:**

1. **MMU on with externally-supplied tables.** TTBR0 = 0x80054000 (§1.3) is not
   in this image. If the earlier stage did not build (or built a wrong) table,
   every instruction fetch after 0x80019258 aborts. The abort then goes through
   0x80009010/0x80009050 → SRAM slots 0x4030D010/0x4030D018, whose contents are
   **[U]** (not programmed here) — i.e. an abort before 0x8000983C runs has no
   known handler.
2. **Unbounded hash range.** `0x80014788` takes `start`/`end` from the region
   descriptor and only checks the *pointers themselves* (0x80013FDC); the length
   `end-start` is never bounded. A corrupt descriptor pointing into unmapped
   DRAM gives a **data abort** inside the CRC loop, not a clean failure. The
   same loop's only escape is the service hook (0x800145F8 → 0x80012516).
3. **Trusted header pointers.** `0x80014148`/`0x80014610` dereference
   `[header+8]`, `[[header+8]+0]`, `[header+0xC]`, `[[header+0xC]+0]` in
   sequence. Each is checked with 0x80013FDC (alignment + a two-bound window
   whose *upper* bound is the literal at 0x800143DC = 0x800102B0, which is
   smaller than its *lower* bound 0x800FF800 as stored — see §8), so the
   effective window is **[U]**; if the check is weaker than intended, a corrupt
   header dereferences an arbitrary word.
4. **Console init hangs before any error path exists.** 0x80014BC8 (called from
   the entry stub at 0x80019244/0x8001924C) does
   `80014bd0: b109 cbz r1,0x80014bd6` … `80014bd6: e7fe b .` — a **silent
   infinite loop** if the console handle at `[0x80014BC4]+0xA0` is 0.
5. **PMIC/halt path never returns** (`0x800094BE`), and the post-jump word at
   0x800192AC is `b .` — so a failed `bx` target is a hang, not a fault.
6. **The two "RAM pointer" literals that land in text** (0x800158E4's table at
   0x8001431C and 0x800135FC's frame at 0x80014654) would, if executed with
   those literals, zero-fill live code. They are only reached on the
   "wipe pending" and "halt" paths — see §8 [U].

## 7. What this changes for the project

1. **The chainloader's entry contract is not provided by `arm9000`.** The stage
   jumps with **r0 = the entry address from the image header** and leaves r1/r2
   undefined (§3.4/§3.5). If the project's payload needs `r0=0, r1=~0, r2=DTB`,
   that must be done **by the payload's own entry stub**, or by whatever stage
   really loads the IFS — not by `arm9000`.
2. **`arm9000` is not the stage that reads media 0x100000.** If the project
   needs to know where the IFS comes from, the answer is *not in this 0x15000
   bytes*: it is the MLO stage at file 0x4000–0x8D70 or the ROM (§3.1). This
   directly answers report 146's "step 0.1": the arm9000 blob contains no IFS
   load and no 0x100000 reference.
3. **The ARM stage's own verification is CRC-32/ISO-HDLC in factory mode**, and
   a 0x230-trailer signature otherwise (§2.2/§2.4). Anything that puts a
   CRC-only region image in front of this stage must also satisfy the container
   checks (`size >= 0x20000`, `0xC3D0E193` at +0x9C, `0xD7C82D1F` at end-8,
   CRC at end-4), and the entry must match `header+0x7C` outside bits 16–23.
4. **The factory boot budget is a 4-byte NV item `BOOTCTR_FCTRY`** (1..50, 0x32
   written to re-arm). Exhausting it prints `"BootModeCount expended"` and
   halts (§1.4). This is a *software* limit in this stage, independent of RPMB.
5. **Nothing in this stage can enumerate on USB** (§4), so any "USB is
   available before the OS" belief must be sourced from MLO, not from here.
6. **Fault, not clean failure, is the realistic outcome of a corrupt region
   descriptor** (§5.5) — the CRC loop's bounds are not validated, and the MMU is
   on with externally supplied tables.
