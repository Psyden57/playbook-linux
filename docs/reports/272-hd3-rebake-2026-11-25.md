## 1. Why the bake is file-level, not `apk --root`

The original `tools/rebake-hd3.sh` assumed host root, a loop mount and a host
`apk`.  On the bench host there is **no `apk`**, and sudo needs a password; more
importantly, `apk --upgrade` of the two APKs is *wrong* for this image (the
initrc clobber and its file conflict).  The rewrite (`tools/rebake_hd3.py`,
called by `tools/rebake-hd3.sh`) applies the delta file by file:

* extracts the two APKs with `tar`, installs `usr/bin/catacomb`,
  `usr/bin/epitaph` and the desktop file — **not** `etc/catacomb/initrc`;
* writes the shim, the wrapper and the `.desktop` `Exec=`;
* replaces `/lib/modules/7.3.3` from a pulled copy of the live tree;
* installs the permissions set and adds `playbook` to `video`;
* splices the `catacomb`/`epitaph` records into `/lib/apk/db/installed` and
  their world lines from a snapshot of the live root (apk's `C:` identity
  hashes are opaque, so they are copied, not recomputed);
* runs as **root** (loop mount) or as a **normal user** (`debugfs`), with the
  same delta, and verifies every file, the initrc md5, the versions, the
  pvrsrvkm vermagic, `modules.dep`, and the permissions before printing the
  hash.

The package records and module tree are pulled with:

```sh
mkdir -p local/work/rebake-ref local/work/rebake-modules
tools/pbssh.sh 'cat /lib/apk/db/installed' > local/work/rebake-ref/installed.live
tools/pbssh.sh 'cat /etc/apk/world'        > local/work/rebake-ref/world.live
tools/pbssh.sh 'tar -C /lib/modules -cf - 7.3.3' > /tmp/modules.tar
tar -C local/work/rebake-modules -xf /tmp/modules.tar
DBMFIX_SO=$PWD/local/work/dbmfix.so tools/rebake-hd3.sh
```

## 2. The ARMv6 module discovery (trap 356)

The image is the session-59 state.  Its `pvrsrvkm_omap4_sgx540_120.ko` had
vermagic `7.3.3 mod_unload modversions ARMv6 p2v8` and sat in a **flat**
`/lib/modules/7.3.3/kernel/` with 44 `.ko`.  The running `#109 SMP` kernel is
ARMv7, and the live root carries 842 modules in the full
`kernel/drivers/...` layout with vermagic `7.3.3 SMP mod_unload modversions
ARMv7 p2v8`.  The session-70 delta was measured from
`/lib/apk/db/installed` and package files, so it never looked at
`/lib/modules`.  A flash would have booted and then failed `modprobe pvrsrvkm`,
`wlcore`, `wl12xx`, … — a black desktop and no WLAN, with no obvious cause.

Verified after the write: the image's pvrsrvkm is sha256 `afdca89d…`, vermagic
`7.3.3 SMP … ARMv7 p2v8`, and `modules.dep` has 842 entries pointing at the new
paths.

## 3. The initrc trap (trap 357)

`/etc/catacomb/initrc` is owned by **`postmarketos-ui-catacomb`**, and the
image's copy is the bench-tuned pvr variant (md5 `00fdff84…`: wvkbd, no swayidle,
tabula, pb-touchwake).  The `catacomb-1.5.0-r10003.apk` carries a **different**
default (`f829d28d…`: squeekboard, swayidle, bash).  An `apk --upgrade` of that
APK would:

* file-conflict with `postmarketos-ui-catacomb` (which owns the path), and
* if forced, replace the working initrc with a configuration whose programs
  (`squeekboard`, `swayidle`, `bash`-isms) are not the bench setup.

The tool therefore installs only the binary and desktop files and leaves the
initrc alone, checking its md5 after the write.

## 4. Flash, first boot, and the DSI wedge

The flash is the documented loop:

```sh
python3 tools/bbusb.py flash \
    --component local/work/nura/images/blackberry-playbook-root-gpu-20261125.img \
    --dest-block 0x4915 --from-bootrom --password 0000 --apply
```

**Start the flasher, then reset with `reboot -f`; a physical power cycle is not
needed.**  `bbusb.py` waits up to 60 s for the bootrom (`bb.open([0x0001,
0x8001])`), and a warm reset runs it.  The 626 MB write completed in about four
minutes at ~2.6 MB/s (the old "~20 min" estimate is conservative).

**First boot:** the root grew to 62.5 G and the desktop started, but at boot+31 s
the eMMC logged `Card stuck being busy` plus a lost async write, and at boot+37 s
the DSI link wedged (`Failed to set dsi_if_enable to 0`, `NO PACKET_SENT` on
VC0/VC1, TCON table re-sent) — the trap-353 signature.  The panel went black
with the backlight on; `catacomb` stayed alive and answered `catacomb msg dpms`
(`on`), and the touch controller was healthy (IRQ 118: 20,126 events).  **The
likely trigger is the power-button release binding**: the initrc binds
`XF86PowerOff` release to a DPMS toggle, and a DPMS off on this kernel wedges
the DSI.  A `reboot -f` cleared it; **the second boot had 0 DSI errors** and the
desktop was responsive.  This is a standing footgun on the image (the only
physical button can black the panel until a reboot), not a rebake defect; the
binding is unchanged from the pre-rebake root.

## 6. The permissions set (brightness, Wi-Fi, zram)

The operator reported that brightness and Wi-Fi still failed.  Measured: both
rule directories were empty, `playbook` was not in `video`, the backlight node
was `root:root 0644`, and `postmarketos-zram-swap` was stopped because the
kernel has only LZO and the service default is zstd.  Installing
`rootfs/README-permissions.md`'s three files and adding the group fixed all
three, measured live:

* backlight node → `root:video 0664`; `echo 200 > …/brightness` succeeds as
  `playbook`;
* `nmcli radio wifi off; on` succeeds as `playbook` (the NetworkManager polkit
  rule);
* `postmarketos-zram-swap` → **1489 MB lzo-rle swap** active.

**`udevadm trigger` defaults to `--action=change`**, which does not match the
rule's `ACTION=="add"`; without `--action=add` the node silently stays
`root:root` (trap 358).  The set is now baked into the image and the group is in
`/etc/group`, so the first login after a flash has `video`.

**After the flash the bar's brightness works**, and gorm launches on the
compositor and scans ≈10 APs as `playbook` (`nmcli -t dev wifi list --rescan
yes`).  The bar's radio toggle changes `WirelessEnabled` (`true → false →
true`, checked with `busctl`).  **The icon is connection-state-driven, not
radio-state-driven:** a bare radio toggle leaves it unchanged, but once the
operator joined `TeleCentro-AW-5G` the icon changed — `wlan0` got DHCP
`192.168.0.231`, and the gateway, `1.1.1.1` and DNS all work.  So this is not a
refresh or permission defect; an earlier reading of it as one is withdrawn
(trap 359).  The cellular-proxy `org.freedesktop.ModemManager` (no `1`)
`GetAll` warning is cosmetic.
