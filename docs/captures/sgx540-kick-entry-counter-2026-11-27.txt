----------------------------------------------------------

0x3d/0x3e, placed AFTER the WO/RO read) read 0 in every build, so the count now
sits on the **FIRST instruction of the `kick` entry** — it counts the entry

Free-word verification, done mechanically BEFORE writing any store (trap 403's
check, redone for this tree):

  * every ctlblk-range constant in `cores/sgx540.py` listed and scanned:
    0x3d/0x3e/0x3f are named by none of them (0x3f is UK_REARM's flag word and
    UK_FRAMEPROF's FP_COUNTS — both flags OFF in this build);

    `ukernel.py` scanned with the flags off: none touches 0x3d/0x3e/0x3f;

    offset field takes, and it fits;

        ld.a.d r4, r17, #63 [moe] / wdf / limm r0,#1 / imae r4,r0,#1,r4 /

The store is ctlblk-relative through r17, valid at the kick label: every path
into `kick` is a same-task branch (`ba kick` from the bare-doorbell fallthrough

INTERPRETATION — HANDOFF §0b's FIRST OUTCOME
--------------------------------------------
"kick counter 0 with resets moving = the core resets before the event program
is ever fetched for a kick.  That is the trap-388 timeout path, so the fault is
upstream of the event program (job submission, CCB, doorbell)."

Consistent with everything earlier: eight host kicks on fix1 left entry at 2
(now reproduced with the kick instrument in place), the `kick`/empty counters
read 0 in every earlier build, and `ccb wo 0 ro 0` after the window.

NEXT (per HANDOFF §0b): the doorbell — read `EUR_CR_EVENT_KICK` (0xac8) and

TWO INCIDENTAL FINDINGS THIS BOOT (both recorded, neither blocks the above)
---------------------------------------------------------------------------
1. **tick(0x2c) = 0 on this boot, where the session-76 capture reports
   tick(0x2c) = 1 for `fix1`.**  The timer path is byte-identical between the
   two builds (the kick counter is off it; verified in the disassembly), and
   the tick store is verified (`st.a.d r17, #44` = word 0x2c).  So either
   fix1's "tick = 1" was a misparse of the adjacent mystery word (see 2 — 0x2a
   is the 3rd word of row 6, 0x2c the 5th; an eyeball slip is plausible), or
   the second fetch's identity genuinely differs between the boots.  Either
   way **"one init pass and one dispatch pass, and the dispatch pass is the
   timer's" (session 76's corrected reading) is now UNPROVEN**: no boot whose
   dump was parsed by word index has ever shown the tick counter increment.
   With entry = 2, tick = 0 and kick = 0, the second fetch took the init
   branch again (HC_INIT still 0 when it read — the host writes INIT_COMPLETE
   ~20 ms after the kick) or died between the entry counter and the dispatch.
   Re-measure fix1's tick before citing "the dispatch pass is the timer's".
2. **Control-block word 0x2a reads 1** on this boot, from boot onward, stable,
   and NOTHING in the image stores there: the full `st.a.d` inventory of the
   disassembled image contains no r17 store at #42 and no rebased store whose
   target is r17+0xa8; the driver memsets the block and writes only words
   0x00-0x17.  Candidate (unverified): the PDS0 launch stub's DOUTU deposit —
   our stub's data word DS1[0] is exactly 0x00000001, and our loader does no
   per-word DOUTU address patching (the vendor patches DOUTU1 at [1],[5],[9],
   [13] etc., sgxinit.c:2507-2510), so a misrouted deposit address is
   plausible.  Do not build on this word until identified.
3. **The STATUS-snapshot store (`UK_ENTRYLOG`'s word 0x39) is broken by the
   trap-403 unit bug family, in fix1 as well.**  The code intends "word 0x39 →
   byte 0xe4" (its own comment says so) but executes
   `limm r5, #0x39 / imae r5, r5, #1, r17 / st.a.d r5, #0, r4` — the limm
   loads **0x39 bytes**, not 0xe4 (`imae rD,rA,#imm,rB` = rA*imm + rB, no
   scaling — cf. `imae r6, r3, #32, r6` for the CCB command address).  The
   store therefore lands at byte 0x39 (misaligned), which is why word 0x39 has
   read 0 in every dump of every build.  Harmless to behaviour, but it means
   the "dispatch-pass STATUS snapshot" instrument has never worked; fix the
   limm to `#{ENTRY_STATUS * 4}` before ever citing word 0x39.

## BOOT 3 — the complete dispatch-register dump, and the sharper conclusion
##############################################################################

    EVENT_PIXEL_PDS_EXEC 0x0a5c 0x00000000   *** the PIXEL pair: all zero ***
    EVENT_PIXEL_PDS_DATA 0x0a60 0x00000000
    EVENT_PIXEL_PDS_INFO 0x0a64 0x00000000

    EVENT_KICK3          0x0ad8 0x00000000

    ctlblk: entry(0x07)=2  tick(0x2c)=0  kick(0x3f)=0  word 0x2a=1
            (the same baseline as boots 1 and 2, third boot running)

**THE SHARPER CONCLUSION — the dispatch path is dead after launch, for every
trigger.**  Three independent measurements now say the same thing:

  1. The kick-entry counter (boot 1): the kick entry never runs, across 8
     kicks that each cost a GPU reset.  If a doorbell landed AND the EDM
     fetched, the entry counter would climb — our entry takes `ba kick` on a
     bare doorbell (no STATUS bit) and would count.  It does not.
  2. b29 TIMER has been latched since boot while the timer register cycles:
     if the timer dispatched the event program, our entry would ack b29
     (masked to its own snapshot) and the tick counter would climb at 1 kHz.
     Entry is static at 2 and tick is 0 — so the timer does NOT dispatch
     either.  **"One init pass and one dispatch pass, and the dispatch pass is
     the timer's" (session 76's corrected reading) is WRONG in its second
     half**: there is no dispatch pass.  The tick=1 reading the correction was
     built on was very likely the adjacent word 0x2a misparsed (0x2a is the
     3rd word of row 6, 0x2c the 5th).
  3. The `relaunch` node (session-76 wrap-up, valid word-0x07 instrument):
     re-writing EVENT_KICK2 — the register whose boot write DID dispatch —
     does not re-fetch either.

So: the EDM fetched the event program **twice during launch** (entry = 2; the
launch sequence evidently fetches it twice, cf. the vendor's
INITUKERNELPRIMARY1/SECONDARY/PRIMARY2 and our five PDS stubs all DOUTUing to
entry 0x0) and **never again** — not for a timer tick, not for a job kick, not
for a re-issued launch kick.  Every PDS_ENABLE-masked source is dead; only the
launch path ever dispatched.  This is the "task admission" class session 76
suspected, and it is UPSTREAM of the doorbell question §0b started with: the
doorbell may well land; nothing dispatches regardless.

WHAT DIFFERS BETWEEN THE LAUNCH AND EVERYTHING ELSE (the candidate list the
next session works from — one variable per boot, cheapest first):
  * **The remaining launch-script registers the driver never writes**:
    `EUR_CR_DMS_AGE` (vendor: `ENABLE | PVRSRV_SGX_MAX_DMS_AGE`; ours 0 —
    measured above), `EUR_CR_PDS_DMS_CTRL2`, `EUR_CR_USE_G0/G1`,
    `EUR_CR_USE_CTRL`, `EUR_CR_USE_MOE`, and whether `EUR_CR_USE_CODE_BASE`
    is written (HANDOFF §5 listed these as unchecked).  DMS_AGE is the
    natural first write experiment: if the DMS holds the launch task(s) as
    never-completed and aging is disabled, every later dispatch would be
    blocked — which is exactly the observed shape.
  * The PIXEL event-PDS pair being zero (measured above): if any source
    routes through it, that fetch goes to offset 0.  The vendor's comment
    ("host kick events always enabled") suggests kicks use the OTHER pair we
    program, but the routing is not measured on this core.
  * `PVRSRV_SGX_MAX_DMS_AGE` remains underivable from the DDK 1.8 drop
    (every header grepped, session 76) — a write experiment must pick a value
    (e.g. ENABLE | 0x2c, the age our init already writes into 0xa78's field)
    and read the entry counter for the verdict.

WHERE THIS LEAVES THE BLOCKER
-----------------------------
The event pipeline jams after the FIRST dispatched event task: one service-
queue item outstanding (SERV_EVENT count 1), the loopback FIFO full
(LOOPBACK b0 = 1), and every later event edge (timer re-latches proven) is
refused.  The emit fires with the vendor's operand derivation and does not
fetch -- consistent with a pipeline that admits nothing while the first
task's completion is outstanding.  The open question is now narrow: **what
completes an event task in the EDM's book?**  The vendor's task end is bare
(no phas anywhere, no cfi -- WRITEBACK_DCU is not set for the 540); its
EventHandler EMITS A LOOPBACK before ending (emit.t2 at 0xea8/0xec0 in the
release image precede nop [end]) -- which our kick5 life also did, with
correct operands, and the FIFO then read FULL with the stub never fetched.

NEXT CANDIDATES (one per boot, cheapest first):
  * Read LOOPBACK/SERV_EVENT at BOOT (before any dispatch) -- is the FIFO
    born full, or does the first dispatch fill it?  One more dump line, no
    new variables.
  * The vendor's EventHandler emits with r16 = the EVENTS BEING HANDLED (the
    loopback re-publishes them as IR0).  Our emit used LOOPBACK_TAEVENTS.
    An emit whose r16 = 0 is skipped by the vendor's own guard; the FIFO may
    also require the DOUTU task control words the host patches
    (INPUT_DOUTU1/2 etc.) -- our stub's DOUTU words are computed, not
    patched, and may describe a task the EDM cannot admit.
  * The pending-loopback protocol (ta3dctl word 0x34 in the vendor layout --
    OUR image uses that word as SC_RTENTRY): the vendor never emits the same
    event twice while pending.  Without the protocol our single emit may
    have been correct anyway; revisit when the FIFO is understood.

NET STATE OF THE BLOCKER (end of session 78's bench run)
--------------------------------------------------------
Per microkernel life: the launch fetches the event program once (init pass);
the FIRST timer edge dispatches it a second time (dispatch pass: tick
0x100 -> 0x101, STATUS snapshot taken, markers set); every later timer edge
(proven to re-latch by the timer_edge probe), every job kick, and the
correctly-operand-ed task-end emit produce NO further fetch.  The event
pipeline registers read idle (LOOPBACK b0 = 1 = space; USE0/1_SERV_EVENT
count 1 / EMPTY set).  The remaining structural difference against the
vendor's working design is the DOUTU task-control words: ours are computed
