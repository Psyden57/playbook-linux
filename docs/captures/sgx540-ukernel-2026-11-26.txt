# SGX540 microkernel: what was built, and the real blocker (session 73)

## What now works

**The SGX540 microkernel assembles and passes its offline tests.**

* `ukernel/cores/sgx540.py` — a core config derived from the SGX545's.  Its delta
  from the 545 image is **exactly three bytes**: the `MISC_CORE` immediate
  (545 → 540) and the `CORE_ID`/`CORE_REVISION` register words (0x1c/0x20 →
  0x20/0x24, per `sgx540defs.h`).  Everything else is carried over and **marked as
  hypothesis**, because the microkernel-facing register offsets (0x618, 0x62c,
  0x694, TA kick 0x200, 3D kick 0x428 …) are in **no** GPL header — not the
  SGX545's either.  They are hardware behaviour the closed microkernel proves and
  never documents.
* `sgx-asm` had to learn the core: a `SGX_ISA_CORE_SGX540` enum, one clause in
  `sgx_isa_core_supported()`, and the `<gen>` range widened from `54500-54599` to
  `54000-54599`.  Justified because the SGX540 is the same USSE1 ISA with 4 USE
  pipes.  **The SGX545 image stayed byte-identical to its golden hash
  `83b5b0a7…`,** so nothing regressed.
* `ukernel/test_emu.py` now takes a core argument, so both images get the same
  assertions; **all 7 pass for sgx540**.
* Image: 14,536 B, `core sgx540`, features 2 (SECURE).

## What the hardware said

Two flashed boots, both with `powervr_sgx` in the image, `pvrsrvkm` blocked, and
`allow_unisolated=1`:

```
powervr_sgx 56000000.gpu: [drm] SGX core id 0x01140000 revision 0x00010200:
                               TI OMAP4430 (SGX540 1.2.0)
powervr_sgx 56000000.gpu: [drm] *ERROR* powervr_sgx/sgx540_ukernel.bin:
                               not a microkernel file
```

Two real findings:

1. **The firmware must be in the initramfs.**  The probe runs at t≈0.9 s, before
   hd3 is mounted, so `request_firmware()` cannot see `/lib/firmware` on the real
   root.  With the image in `initramfs/root/lib/firmware/powervr_sgx/` the file is
   **found** (error changes from `-2` to "not a microkernel file").  The path is
   now gitignored as a built artifact.
2. **The kernel blacklist does not stop OpenRC.**  `modprobe.blacklist=` only
   affects alias-based autoloading; `/etc/init.d/modules` runs `modprobe` by exact
   name, which bypasses it.  The working block is a modprobe.d
   `install <mod> /bin/false` (or removing it from `/etc/modules`).

## The real blocker: the image is built for `srvinit`, not `powervr_sgx`

"not a microkernel file" is `ukfw_parse()` returning `-ENOENT`: the file has no
`SGX5`/`UKRN` header.  The microkernel needs wrapping by `drm/tools/mkukfw.py`,
and that wrapper enforces a requirement this image cannot meet:

* a **single-context** core must declare `PVRSGX_UKFW_SINGLE_CONTEXT` and **not**
  `SECURE`, and must carry a **`pdtable` patch**;
* the driver then allocates a PD table at `kernel_code.base + 0xf000` and fills
  every slot with its kernel PD, and the microkernel must **load directory list 0
  from that table**.

The image does not do this, and cannot without real work: it routes the TA/3D
requestors to **list 1** via `BIF_BANK0` and relies on list 0 being the shared
kernel PD that `srvinit` sets up.  The source says so in as many words —

> under srvinit list 0 is a shared PD that happens to map them; under
> `powervr_sgx` list 0 is an empty idle PD and the transfer BIF-faults on a
> client address (BANK0=0x0f, DIR_LIST_BASE0=idle, FAULT on 0x3e001000).  We do
> NOT write the ctx PD into list 0 — that clobbers the kernel PD the 3D/ISP/PBE
> read through and wedged srvinit.

So **the SGX545 microkernel is a two-context image for a 32-bit core driven by
`srvinit`.**  Making it run under `powervr_sgx` on a **one-context, 28-bit** core
is the next real piece of work, not a packaging step:

1. Add the `pdtable` patch site (a `limm` the loader fills with the table address)
   and make `init` load list 0 from it.
2. Give the image the single-context feature bits (drop `SECURE`, set
   `SINGLE_CONTEXT`) — the deferred `CLEANUP_V2`/`DONE_SEQ` semantics still need
   checking against what the driver expects.
3. Re-check every place the image assumes list 1 exists (39 references to
   `list 1`/`BANK0`/`0xc78`), because on this core there is only list 0.
4. Only then does the unmeasured register-table hypothesis (0x618, 0x62c, …) get
   tested — and that needs a working kick, i.e. after 1–3.

## Bench after this work

Region 0 carries the microkernel image `0x290569CA` (the firmware embedded in the
initramfs).  The GPU has **no driver bound** on that image (`pvrsrvkm` blocked,
`powervr_sgx` failing on the firmware), so the desktop renders **in software**:
`catacomb`, `tabula`, `epitaph` and `wvkbd` all run, the top bar and the OSK handle
bar drew, and the wallpaper did not — then the panel blanked with a DSI
`dsi_if_enable` error and did not recover (`bl_power` returned to 0 on a
`dpms on` but the errors grew).  `BOOTCTR_FCTRY` `0x2d`.

The way back to the working bench is re-flashing `local/work/kernel-restore-20261126.img`
(`0xBC5FB130`).
