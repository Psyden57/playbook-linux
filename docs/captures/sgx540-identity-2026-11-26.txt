# SGX540 identity read — live, session 73 (2026-11-26)

The first hardware read of the SGX540's own registers (fact sheet Gaps 1 and 2,
report 276 step 1/2).  Zero-risk: read-only, 4-byte loads through `/dev/mem`
(`CONFIG_STRICT_DEVMEM` is off), while `pvrsrvkm` clocks the GPU.

Unit: Linux `7.3.3 #109 SMP` on hd3, region 0 `0x3547D613`, `pvrsrvkm_omap4_sgx540_120`
bound (`56000000.gpu`, `renderD129`, `card1`), booted 31 min, `BOOTCTR_FCTRY 0x28`.

Tool: `tools/bench/gpu/sgxcoreid.py` (pushed to `/tmp/sgxcoreid.py`, run as root).
Offsets are the SGX540 ones from the vendored GPL DDK (`sgx540defs.h`).

The read set is exactly the registers the upstream kernel guide calls safe to read
before the reset sequence has run (`docs/porting/kernel.md` §2), plus the identity
group; the write-only `*_CLEAR` registers were not read.  `BIF_INT_STAT` bit 15 is
`FLUSH_COMPLETE` (`sgx540defs.h:495`) — the DDK's BIF in a completed-flush state,
which is what an idle bound GPU should show.  Every other `BIF_CTRL`/event/gating
register reading 0 is the quiescent state, not a claim about bit meaning.

## What it confirms (now tag C)

| Fact | Value | Tag |
|---|---|---|
| `CORE_ID` at 0x0020, `CORE_REVISION` at 0x0024 | as the DDK header says, **not** the SGX545's 0x001c/0x0020 | **C** |
| `CORE_ID` id field | **0x0114** (the SGX545's is 0x0115; the SGX530's is 0x0110) | **C** |
| `CORE_REVISION` | **0x00010200** = major 1, minor 2, maintenance 0 → **"Rev 120"** | **C** |
| `DESIGNER_REV_FIELD1/2` | 0x0028/0x002c, both read 0 on this unit | **C** |
| `CLKGATECTL`/`2`, `CLKGATESTATUS`, `CLKGATECTLOVR`, `SOFT_RESET` offsets | the header's offsets return sane, quiescent values (all 0 at idle) | **C** (offsets) |
| ti-sysc module registers | `rev` @ 0x5600fe00 = `0x40000000` (major 1, minor 0 → 1.0); `sysc` @ 0x5600fe10 = `0x0000003c` | **C** |

The `CORE_ID` id field **0x0114** is the load-bearing new fact: it is one below
the SGX545's 0x0115 and well above the SGX530's 0x0110, so the open driver can
distinguish the three cores from the ID alone.  The expected `0x00010200`
`CORE_REVISION` **matches**, so the DDK's rev-120 assumption and the DT binding's
"Rev 120" agree with the silicon.

## What is still open (unchanged)

* `USE_CODE_BASE` presence (fact sheet Gap 7) — needs a write/read-back test on
  0x0a0c+n, not a read; only a USSE task settles whether the registers stick.
* The 28-bit/single-context BIF behaviour (Gap 6) and the DPM/TA/ISP/TSP/PBE/PDS
  state (Gap 10) — neither is in the GPL headers.
* No write of any kind was made; the GPU stayed bound and the desktop unaffected.
