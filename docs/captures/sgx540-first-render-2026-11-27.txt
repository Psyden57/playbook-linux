BOOT 3 — kick12inv (`81d7a183…`): the mask 0x1f -> 0x17
-------------------------------------------------------
`sgx540defs.h`'s `EUR_CR_PDS_CACHE_STATUS` defines exactly FOUR done bits —
CSC_INV b0, DSC_INV0 b1, DSC_INV1 b2, DSC_INV3 b4.  **There is no bit 3.**
The core config's own comment listed those four fields and then wrote
"0x1f is every bit this core defines" — the arithmetic error: b0+b1+b2+b4 =
0x17.  Fixed `INV_DONE_TA/INV_DONE_3D = 0x17`.  Null family intact.

ONE RENDER: still `_wait8`, still a timeout.  A mask bit whose invalidate was
never REQUESTED never sets: bit 4 (DSC_INV3) belongs to `EUR_CR_PDS_INV3`
(0x0adc), and the µkernel's `invalidate()` pulses only 0xad0 (INV0) + 0xae0
(CSC) + MADD + 0xa08 (USE).  (trap-397's rule in both directions: a header
naming a mask is not evidence, and neither is an arithmetic sum over one.)

BOOT 4 — kick13inv (`688bfb8f…`): per-request masks 0x03 / 0x05
---------------------------------------------------------------
The vendor's own per-side derivation is the shape to copy
(`sgxdefs.h`, the `FIX_HW_BRN_31474` branch — and 31474 IS in the rev-120
list, marked "workaround in uKernel"): the TA side waits DSC_INV0 only, the
3D/pixel side DSC_INV1 only, because each request register drives exactly one
done bit:

    EUR_CR_PDS_INV0   0xad0 -> done b1      EUR_CR_PDS_INV3  0xadc -> done b4
    EUR_CR_PDS_INV1   0xad4 -> done b2      EUR_CR_PDS_INV_CSC 0xae0 -> b0

Our `invalidate()` requests INV0 + CSC -> wait b1|b0 = **0x03**;
`invalidate3d()`/the transfer path request INV1 + CSC -> wait b2|b0 = **0x05**.
Fixed `INV_DONE_TA = 0x03`, `INV_DONE_3D = 0x05`.  Null family intact.

ONE RENDER, polled: **the wait id moves past _wait8/_wait9/_wait10 to
_wait15** (stage byte 0x3a = 0x01 = do_ta).  Then a timeout (resets 1) — the
"render done" the tool printed was trap 388's fence path, not completion.
_wait15 disassembled: `limm r6, #4096; ldr r5, #70` — 70*4 = 0x118
EUR_CR_EVENT_STATUS2, mask 0x1000 = **bit 12**; ack 69*4 = 0x114
EVENT_HOST_CLEAR2.

BOOT 5 — kick14otpm (`f1b16422…`): the OTPM mem-clear wait dropped
------------------------------------------------------------------
STATUS2 bit 12 on the SGX545 = `OTPM_MEM_CLEARED` — a field the 540's
`EUR_CR_EVENT_STATUS2` does not have (the 540 defines only bits 0-4: DPM
free-load and TRIG_TA/3D/DL).  It was `dpm_load()`'s third wait, after the
OTPM `CSM_INV` invalidate — whose 540 done bit (EVENT_STATUS b20 `OTPM_INV`)
the previous line already waits, and which provably completed (the code got
past it).  Also corrected the OP write itself: the µkernel wrote 9 (CSM_INV |
bit 3); the 540's `EUR_CR_MTE_OTPM_OP` (0x24c) defines only bits 0-2 — bit 3
is the 545's mem-clear, so the 540 now writes **1**.  Per-core constants:
`OTPM_OP_INV_CLEAR` (9 on the 545, 1 here) and `STATUS2_OTPM_CLEARED`
(0x1000 on the 545, 0 here — the wait is compiled out); the SGX545 golden
stayed byte-identical through the refactor.  Null family intact.

ONE RENDER, polled: **NO WAIT SPINS AT ALL** (word 0x35 = 0 through the whole
hang window), stage = do_ta set — and the timeout line reads

    job timed out (ccb 3, consumed 2, done word 0x0 for 0x1,
                   events 0x00000000/0x00000010); resetting

**EVENT_STATUS2 = 0x10 = TRIG_TA (b4) — the TA TASK WAS KICKED AND STARTED.**
`EUR_CR_EVENT_STATUS = 0` — TA_FINISHED (b13) never latched: the TA task ran
and never finished.  It wrote nothing before stalling (region headers, tail
pointers and ta88 all still zero; BIF_FAULT 0).  The µkernel's task ended
correctly after the kick; the completion was expected to come back through
the TA_FINISHED event dispatch, which never happened because the TA itself
never completed.

WHERE THIS LEAVES §0b (the outcome table, answered)
---------------------------------------------------
* kick stays-0-with-ccb-advancing (the CMDTA packing): RULED OUT — the µkernel
  consumes the kick, both TA commands' worth of protocol, and kicks the TA.
* do_ta set but no ta_finished: **THIS IS THE STATE** — "the TA register
  tables are wrong, walk one register at a time against sgx540defs.h (the
  0xb14 discovery is the precedent)".  Three SGX545-shaped bugs of exactly
  that class were already found and fixed on the way (the 0x138 masks, the
  OTPM OP bit 3, the STATUS2 mem-clear wait); the tables that program the TA
  itself (0x200/0x428 and friends — the carried-over hypothesis registers)
  are the remaining suspect, along with the DPM free list the TA allocates
  from and the VDM stream fetch.
* BIF fault / lockup+reset: not the failure mode (BIF_FAULT 0 throughout; the
  reset is the driver's 2 s watchdog on a silent TA).

THREE NEW TRAPS (the 0xb14 class, register-per-register this time)
------------------------------------------------------------------
1. **A done-bit mask must name only bits whose request register the same path
   pulses** — each 0x138 done bit belongs to one request register
   (b1=0xad0, b2=0xad4, b4=0xadc, b0=0xae0); a sum over "the bits the header
   defines" waits on invalidates that were never requested.
2. **A bit the header does not define can still be waited on by arithmetic**
   (0x1f over a four-bit field list).
3. **EVENT_STATUS2 is a different register on the 540** — the 545's
   OTPM_MEM_CLEARED b12, VDM_*/MTE_* b13-15 do not exist; the 540's OTPM done
   bits live in EVENT_STATUS b19-21, and its TRIG_TA/3D/DL are b4/b3/b2 where
   the 545 has b7/b6/b5.  Every STATUS2 wait needs the 540 header's field
   list, not the 545's.

THE VENDOR CROSS-CHECK (all static, sgx540defs.h + the vendor release binary
+ ta.asm/sgx_mkif_client.h)
---------------------------------------------------------------------------
* **The TA register block matches field-for-field.**  The vendor's
  `SGXMKIF_TAREGISTERS` (540 config: 17 words, TE_AA .. BIFTAReqBase +
  MTEMSCtrl) maps onto exactly the registers our `TA_TE` programs from the
  same-shaped command words; `BIF_TA_REQ_BASE`'s vendor derivation
  (`(params-heap base >> 20) << 20`) equals our `params_base`; the vendor's
  `USE_LD_REDIRECT`/`USE_ST_RANGE` come from the kick and the only producer
  in the whole DDK tree writes 0 — our zeros match.
* **The vendor's TA cache-invalidate acks 0x140 with 2 — DSC_INV0 (b1) only**,
  the BRN_31474 shape our `INV_DONE_TA = 0x03` already carries (ours also
  waits the CSC bit b0, which our CSC request does set).
* **The vendor's HOSTKICKTA is a queue stub** (a linked-list insert on the
  render contexts, then `ba` into the shared TA-queue body); the body does
  settle loops, a per-kick `DMS_CTRL` MAX_NUM_VERTEX_PARTITIONS update (ours
  never touches it per kick — ours is nonzero at reset, 32), the
  invalidate/`DIR_LIST_BASE0`/`BIF_CTRL` sequence we already do.
* **Two defects found in OUR TA_TE tail, not yet fixed**: it maps cmd+0x2a4
  (`rt_flags` = 0x88) onto 0x230 `MTE_OTPM_CSM_FLUSH_BASE` — the vendor uses
  0x230/0x234 as ADDRESSES for its OTPM CSM flush/load (OP 4 / OP 2), so a
  flag word there is bogus (inert until a CSM flush runs, but wrong); and it
  writes a tail of SGX545-only registers the 540 lacks (0x2a8 TE_TPC,
  0x2b0/0x2b4/0x2d0/0x2d4 GSG*, 0x324, 0x364/0x368/0x370/0x374 the VDM
  PDS-program pointers, 0x520, 0x74c) — the vendor's 540 build writes none
  of them (the SGX545-only block is `#if defined(SGX545)`).
* **The client's VDM control stream is present and well-formed** (dumped with
  an `SGXGEN_DUMP_PROGS` addition to `tools/gen/sgxgen.c`, frame tool
  `efaefc61…`): 28 words at 0x42000 — STATE_LOAD records whose PDS programs
  sit in the PDS-vertex heap (0x0e801200 + 0x140-span), two 3-vertex PRIM
  records with index data in the general heap, and the two kick terminates.
  The record encodings came from 545 captures.

WHERE THE STALL SITS NOW
------------------------
Inside the VDM's control-stream EXECUTION: the stream is fetched from a
correctly-mapped-looking base, the VDM and MTE are clocked awake, the DPM
never allocates a page, the TE never starts, and nothing faults.  The
remaining suspects, in order:
1. **A VDM control-stream record format that differs on the 540** — the
   encodings are 545-capture-derived; the STATE_LOAD record's PDS-address
   field width and the PRIM record's fields are the ones to check against
   sgx540defs.h (the 0xb14 method, now on the stream format).
2. **The client state-load PDS/USE programs** (PDS-vertex heap) — same check
   for the 540's USSE/PDS encoding; dumpable with the frame tool.
3. The µkernel tail defects above (prune the 545-only writes; fix the 0x230
   mapping) — cheap hygiene, unlikely to be the stall.

BUILD 1 — `kick17ccbtrace` (`79bffc34…`): the measurement was INVALID
------------------------------------------------------------------
Built with the handoff's usual flags **including `UK_WAITLOG=1`** plus
`UK_CCBTRACE=1`.  `do_ta` did store `cmd+0x04` to word 0x38 (disassembly
verified: `st.a.d r17, #56, r5` after `ld.a.d r5, r9, #1`), but the value read

the once-per-`do_ta` CCBTRACE store.  It also writes 0x37 = `EVENT_STATUS`,

the trap-403 class again (new trap **422**).  One boot spent; result discarded.

UK_TIMERDIV=100 UK_CCBTRACE=1`.  Both gates passed (test_emu all-OK, SGX545
golden `83b5b0a7…`).  In this build word 0x38 belongs **only** to CCBTRACE;
word 0x37 is `UK_TICKLOG`'s tick-site marker (`0x22222222`) and must not be read

`0x38` is the client command's `ta_flags` word (struct offset 0x04).  `0x71` =

command after the host had written it** — delivery is clean, not a stale or
torn read.

What this settles
-----------------
* **The µkernel sees `LASTKICK` when a kick carries it** (`-k 1` → `0x73`).
* With the frame tool's default `-k 2`, kick 0 is **FIRST only** (`0x71`);
  LASTKICK is on **kick 2**, which the µkernel never services because kick 1's
  TA never finishes (`do_ta` count stays 1).
* Therefore **LASTKICK cannot be the cause of the stall** — it is downstream of
  it.  A last-kick branch in `ta_finished` can never run for a TA that never
  finishes.  HANDOFF-81 §0b's premise ("the frame tool submits 2 kicks, so
  kick 1 carries LAST") was wrong: with `nkicks=2`, `last = (k == 1)`.
* The stall remains inside kick 1's TA execution: unchanged timeout, `resets`
  1→2, `0/1 frames right`, pixels black (centre/corner both 0).

DDK DROP READING (static) — the launch stub, and what it rules out
------------------------------------------------------------------
Read after the IDXFIFO test, per the operator's clearance (DECISIONS §118).
Nothing here is a new defect; it is the "next discriminator" from the handoff,
closed.

* **The vendor's launch** (`sgx_init.use.asm.preproc`, release tree): Primary1
  is a USE program that reads `HostCtl.ui32InterruptClearFlags & 1` and issues
  **one `emitpds.tasks.taske`** (`#0, r0` = PDS const size, `r2` = PDS dev
  addr, `r4` = that flag, imm `0x0C42`) — a PDS task, not a MOVS/DOUTU stub.
  Primary2 writes `IUKP2_PDSExec/Data` (0x0a68/0x0a6c), calls
  `InitConfigRegisters` (`lapc`), updates HWPerf, sets `ui32InitStatus = 1`,
  and `StartTimer` (`EUR_CR_EVENT_TIMER |= ENABLE`).  Ours is a driver-side
  init plus one `kick`; that is the known structural difference (DECISIONS
  §115), not a per-register bug — there is no single register to change.
* **The per-kick path matches.**  The vendor's `KickTA` copies
  `SGXMKIF_CMDTA.sTARegs` into `TE_AA … BIF_TA_REQ_BASE` (17 words; the
  GSG*/VDM-PDS tail is `#if defined(SGX545)`) and then
  `VDM_START <- PULSE_MASK`.  Our `TA_TE` order is identical (trap 418); the
  vendor's extra `DPM_TA_RENDER_TARGET_MAX` / `TE_TPC` /
  `MTE_MULTISAMPLECTL` writes are 545-or-feature gated (the 540 release
  binary's write set has none of them), and its per-kick `DMS_CTRL`
  vertex-partition override only matters if the command asks for more than the
  reset 32.
* **`USEPIPE = 7`** in the state records is the header's
  `EURASIA_TAPDSSTATE_USEPIPE_ALL` for a 4-pipe core (shift 13) — not a
  divergence.
* **The `MADD_CACHE_INVALCOMPLETE` (b26) wait and ack is implemented**:
  `invalidate()` waits `EVENT_STATUS` 0x04000000 and clears it through
  `EVENT_HOST_CLEAR`; the b26 seen latched at the timeout is a later latch,
  not a missing ack.
* **The pixel event-PDS pair** (0x0a5c/0x0a60/0x0a64) is written only by
  `do_3d` from the render details (`D3_RD`), so it reads 0 until the 3D starts;
  the vendor also installs a pixel event program at init.  Given the spec's
  §6.2.3/§6.2.4 (a scene is renderable only on LASTKICK, and the 3D starts from
  the 3D run list), this is a consequence of the stall, not evidence about it.

Conclusion: the launch stub is a structural difference, not a register defect;

SESSION 83 CONTINUATION — a REAL 545-shaped port bug: DMS_CTRL's vertex-partition
field, and the timeout became a specific page fault
================================================================================

THE BUG (provable from the vendor's own source)
-----------------------------------------------
`EUR_CR_DMS_CTRL` (0xa74) carries the DMS's partition limits, and its
`MAX_NUM_VERTEX_PARTITIONS` field is at a DIFFERENT PLACE ON EACH CORE:

  sgx545defs.h  MASK 0xF8000000  SHIFT 27   (5 bits)
  sgx540defs.h  MASK 0x0E000000  SHIFT 25   (3 bits)
  sgx535defs.h  MASK 0x0E000000  SHIFT 25
  sgx543defs.h  MASK 0x3C000000  SHIFT 26

Our kernel sent one constant for every core: `TA_CTL = 0x50000000`, which is
`10 << 27` — the SGX545's default (`SGX_DEFAULT_MAX_NUM_VERTEX_PARTITIONS 10`,
sgxinfo_client.h).  On the SGX540 that value is entirely outside the 3-bit
b25-27 field, so

    0x50000000 & 0x0E000000 >> 25  ==  0

i.e. **the SGX540 was given ZERO vertex partitions at every TA**, and the
microkernel copies the command's control words into that field
(ta.asm:3507-3548: read 0xa74, clear the VP mask, OR the command's
`ui32NumVertexPartitions`, write back).  The vendor's client derives the word
per core: `SGX_DEFAULT_MAX_NUM_VERTEX_PARTITIONS << shift`
(sgxkick_client.c:1024), 4<<25 = **0x08000000** for the SGX540.

That is the same shape as every other defect this port has found: a value that is
right for the core the code was written on and wrong here (DECISIONS 112).

Same story for the pixel side: the microkernel ORs
`HWRENDERDETAILS.ui32NumPixelPartitions` (+0x6c) into DMS_CTRL at the 3D
(3d.asm:2914-2920) and in SPM (spm.asm:2692-2698).  Our render-details struct had

MEASURED: the stall changed from a silent timeout to a specific page fault
--------------------------------------------------------------------------
Before (module 92e14ad4, sessions 79-82):

After (module 91729a08 / 21833840, three renders, reproduced every time):
    job page fault at 0x00401000 (BIF status 0x0000e000, requestor 0x2000, write); resetting

`BIF status 0xe000` decodes as FAULT (b0-13) | **PF_N_RW b14 = 1, a WRITE** |
FLUSH_COMPLETE b15.  `requestor 0x2000` is bit 13 of the fault-requestor mask.

used absolutely, and it lies in no heap this VM maps (general starts
0x04400000, PDS pixel 0x0dc00000, PDS vertex 0x0e800000, USSE 0x0f400000+).
So the GPU now tries to WRITE to an address nothing maps instead of silently
waiting: the job gets far enough to run a memory access, which is new.

2 s timeout).  Null family unaffected; boot clean

THE CANDIDATE (from the vendor source, not a guess)
---------------------------------------------------

the RT-data entry's tail-pointer word (`cores/sgx540.py:363`,
`(0x234, 0x1c//4)`).  Two facts from the drop make that wrong:

* 0x234's field is a **device address in 16-byte units**
  (`ADDR_MASK 0x0FFFFFF0`, `SHIFT 4`, sgx540defs.h:935-937), not a tail-pointer
  word: the pointer we supply is a byte address, so the MTE would treat it as a
  multiple of 16 — a shifted, unmapped target.  And the fault is a **write**,
  which is what an MTE CSM load does.
* **The vendor's own 540 path never writes an OTPM base at all.**  In `ta.asm`
  the CSM-base write is inside `#if defined(EUR_CR_MTE_OTPM_CSM_BASE)`

  defines that register (`sgx545defs.h:1425`, also 0x234).  Our core takes the
  `#else /* !SGX_FEATURE_RENDER_TARGET_ARRAYS */` branch, whose only OTPM action
  is `str #EUR_CR_MTE_OTPM_OP >> 2, #CSM_INV` (ta.asm:4252).  So the 540 has no
  CSM base to set, and writing one is a 545-shaped carry-over — the same class of
  defect as trap 431, found the same day, in the same register block.
* Supporting: the 540's `MTE_OTPM_OP` defines CSM_INV b0, CSM_LOAD b1, CSM_FLUSH
  b2 and **no CSM_OTPM_MEM_CLEAR** (the 545's bit 3), which our core file already

SESSION 83, FOURTH PART — a second `TA_RD` defect found the same way, and the
hint that costs nothing: the fault address moves with the stream
==================================================================
Two findings after the 0x234 exclusion, both from the vendor source.

A. `TA_RD` writes `EUR_CR_TE_STATE` (0x274) from a render-details pad we never
   fill.  The vendor loads TE_STATE from a REAL field:
       ta.asm:4340-4344
         MK_MEM_ACCESS_BPCACHE(ldad)  r2, [R_TA3DCtl, #DOFFSET(SGXMK_TA3D_CTL.sTARenderDetails)], drc0
         mov  r4, #OFFSET(SGXMKIF_HWRENDERDETAILS.ui32TEState[0])

   **Not yet tested against the fault** (needs the correct word, and our flat
   render-details layout does not match the 1.8 struct's `SGXMKIF_3DREGISTERS
   s3DRegs` prologue, so the 1.8 offset 0x5c is NOT directly usable -- see B).

B. **A structural fact worth recording: our render-details layout is a FLAT
   reconstruction of a struct the vendor defines NESTED.**  Compiling the 1.8
   `SGXMKIF_HWRENDERDETAILS` gives `ui32TEState` at **0x5c**,
   `ui32NumPixelPartitions` at **0x74**, `sizeof` **0x90** -- it begins with a
   `SGXMKIF_3DREGISTERS s3DRegs` block and carries `PVRSRV_DEVICE_SYNC_OBJECT`
   arrays, none of which our 0x1ec-byte flat struct models.  So (i) my earlier
   hand-parsed "0x6c" for `ui32NumPixelPartitions` was wrong (it double-counted
   the nested struct), and (ii) the per-core values I put at **our** +0x6c
   (trap 431) are correct for **our** layout but the *field identity* rests on
   our own reconstruction, not on the 1.8 offset.  The live dump confirms the
   value lands where our struct says (`rd+0x6c = 0x01800000`, 6<<22), so the
   mechanism -- "the µkernel reads a pixel-partition word we never wrote" -- is
   proven for our layout even though the 1.8 byte offset differs.  Trap 431's
   measured effect (the fault replacing the timeout) stands on its own.

C. **The fault address moves with the stream, which is a free discriminator.**
   Same firmware (`kick18ccb`), same boot, three variants:
       baseline            -> page fault at 0x00401000  (write, requestor 0x2000)
       SGXGEN_NO_PRIM      -> page fault at 0x00401000  (write)
       SGXGEN_NO_STATE     -> page fault at 0x0dc00000  (write, requestor 0x2000)
       -k 1 (single kick)  -> page fault at 0x00401000  (write)

   to the byte, and `0x00401000` is 4 MiB + 4 KiB, just above the general heap's

   heap base -- the signature of a DMA whose base register holds a heap base and
   whose offset/size is 0 or a page.  Removing the state loads changes *which*
   heap the bogus write lands in, so the writer is downstream of the state-load
   path, and the state record's own fields are still implicated even though
   session 81/82 excluded the *record encodings* -- what is new is that a write
   actually happens now (the DMS fix, trap 431).

   which record class selects 0x00401000 vs 0x0dc00000; the answer names the
   writer.  Then point that record's DMA at a known-mapped page and watch the
   fault move or clear.

TWO LEADS CLOSED BY READING THE VENDOR'S CODE (cheap, no boots)
---------------------------------------------------------------
1. **`TE_STATE` = 0 is CORRECT, not a defect.**  `ta.asm:4340-4344` loads

   it: `sgxkick_client.c:2098-2101  psHWRenderDetails->ui32TEState[i] = 0;`.  Ours

   vendor sends is 0 as well, so `TA_RD = [(0x274, 0x124//4)]` is harmless as long

   real field**; the value would still be 0.  (Our struct is a flat
   reconstruction of a struct the vendor defines nested -- see the fourth-part
   note -- so the 1.8 offset 0x5c does not apply to us anyway.)
2. **`TE_PSG` = `0x01000000` (b24 `ENABLE_CONTEXT_STATE_RESTORE`) is CORRECT.**
   Session 80 left this open ("the vendor 540 µkernel only ORs those on the
   terminate/context-switch paths").  `ta.asm:4346-4352` ORs it on **every TA
   kick**, unconditionally, right after the TE_STATE load, and ORs
   `ZLOADENABLE` on top only when the RT data's common status says so.  So the
   "always bit" is the vendor's own behaviour; trap 418's open note can be closed.

WHAT IS LEFT
------------
The writer is a per-kick register or structure the kernel/microkernel programmes
regardless of stream content, and it writes to a heap base with a zero offset.
Candidates still standing, in order, each one gated build + one boot:
 1. `TE_PSG`'s neighbour `TE_PSGREGION_BASE` (0x21c) / `TE_TPC_BASE` (0x220) --

 2. `BIF_TA_REQ_BASE` (0xc90) from cmd+0x274 = 0f010000 (1 MiB aligned, fine).
 3. `PDS_EXEC_BASE` (0xab8) = 0x0dc00000 (the value NO_STATE faults at).
 4. The **PB free list / page table**: `EUR_CR_DPM_TA_ALLOC_PAGE_TABLE` 0x618 and

SESSION 83, SIXTH PART — the fault window is BEHIND a correctly-loaded client PD,
and the address is inside the mapped general heap
====================================================================================
Clean boot, `kick18ccb`, module `21833840…`.  Read `BIF_DIR_LIST_BASE0` every
80 ms through one render:

    0x84da6000   <- FIRST sample: the CLIENT PD (differs from the kernel PD)
    0x85841000   <- every sample after: the kernel PD
    ...
    job page fault at 0x00401000 (write, requestor 0x2000)

Facts established, each from a reading:
* **The µkernel DOES load the client PD.**  `pd_load("do_ta")` resolves
  `pdtable[slot]` through the r14 patch site (`imae r6, r4, #4, r14; ld.a.d r4,
  r6, #0`) and writes `EUR_CR_BIF_DIR_LIST_BASE0` (`str #801` at image 0x1bf0,

  right.  The `0x85841000` that follows is the kernel's own restore (the driver's
  reset/start path), not the µkernel undoing its load.
* **`0x00401000` is INSIDE the general heap** `[0x00001000, 0x04400000)`
  (pvrsgx_core.c:283), and the frame tool's own ring 0 is allocated at
  `0x00002000` there (tool `-v`).  So the address is **mapped in the client PD**
  and **not** mapped in the kernel PD (the kernel PD gets kernel_code,
  kernel_data and sync shared into it, `pvrsgx_share_fw_heaps`, but *not*
  general).  A write to it therefore faults exactly when it happens **while the
  kernel PD is loaded** -- which is what the sample shows for all but the first
  80 ms.
* So the fault is not "a bogus pointer"; it is **"a write lands outside the TA's
  own PD window"**: either after the microkernel has finished with the client PD,
  or from a block (the EDM's bg-store path, the 3D, the TE's region writes) that
  runs with list 0 back on the kernel PD.  That reframes the search from "which
  pointer is wrong" to "which block writes after the PD is restored".

SESSION 83, SEVENTH PART — THE DECISIVE DATUM: the faulting write runs inside the
TA's own window, with the CLIENT PD loaded
====================================================================================
One driver line (pvrsgx_job.c: print DIR_LIST_BASE0 and the kernel PD in the fault

**So the write happens while the CLIENT page directory is loaded** -- the µkernel's

Which reopens a concrete, checkable question: is `0x00401000` really mapped in the
*client* PD?  It is inside the general heap `[0x00001000, 0x04400000)`, and the
tool allocates its ring 0 at `0x00002000` there -- but a heap's *range* being in
the layout does not mean a *page* is mapped: our VM allocates on demand
(`pvrsgx_gem`/gpuvm), so `0x00401000` (4 MiB + 4 KiB into the heap) may simply
never have been touched, and the block writing there is writing to an address it
computed rather than one it allocated.

The block is still unnamed (requestor bit 13 has no per-bit name in the drop), but
the window is now known exactly, and the address class is "general heap + 4 MiB +
4 KiB".  Cheapest next:
 1. **Map and touch `0x00401000`** -- have the frame tool allocate a BO at that
    exact address (`SGXGEN_MAP_401000`), one render.  If the fault disappears, the
    block is writing to a *legitimate-looking but unallocated* address, and the
    next question is which field it reads it from; if it persists, the address is
    wrong regardless.
 2. Print `BIF_MEM_REQ_STAT` and the four `*_REQ_BASE` registers (TA 0xc90, 3D
    0xcac, ZLS 0xcb0) in the same fault message: a `*_REQ_BASE` equal to
    `0x00400000` (1 MiB-aligned, since their field is `SHIFT 20`) would name the
    requestor's base as the culprit directly.
 3. Only then rebuild the µkernel around whichever field (1)/(2) names.

WHAT IT MEANS
-------------
* **The writer is aiming at a real, computed address inside the general heap.**
  Mapping `0x00400000`/`0x00401000` makes the fault *move* to `0x0001f000` -- it
  does not simply go away, and it does not stay put.  A wrong pointer would not
  move when an unrelated page is mapped; a writer that walks *forward through the
  general heap* does exactly that.  `0x00401000` is 4 MiB + 4 KiB and `0x0001f000`
  is 31 pages in, both inside `[0x00001000, 0x04400000)`.
* **The second fault is a different requestor** (`0x0002` = bit 1, vs `0x2000` =
  bit 13) with status `0xc002` = FAULT(2) | PF_N_RW(write) | FLUSH_COMPLETE.  So
  two distinct blocks write into the general heap: one at ~4 MiB (requestor bit
  13) and one at ~124 KiB (requestor bit 1).  Neither is named by the drop.
* **Both fault *with the client PD loaded*** (the driver's new message prints
  `DIR_LIST_BASE0` and the kernel PD side by side; they differ in every run).
  So the pages are genuinely **not mapped in the client PD** -- the VM maps on
  demand and the tool only ever allocated `0x2000..0x87000` there (its own `-v`
  output).  The writes are not to a bogus pointer but to a *plausible address the
  client never allocated*.
* The most likely shape, consistent with everything measured: a **DMA whose
  destination is computed from a base plus a size/stride the client supplied** --
  the same class of defect as the DMS_CTRL and 0x234 findings (a value used with
  the wrong meaning), but on the *addressing* side rather than a register field.
  Our `TA_PB`/`TA_TE`/`D3_RD` tables take `pages`, `tail_pointers_size`,
  `mt_bytes`, `MTRegionArraySize`, region sizes and strides from the client; any
  of those, used as an address or as an address offset, lands exactly here.

NEXT — cheap and decisive
-------------------------
 1. **Map a RANGE, not one page** (`SGXGEN_MAP_AT` currently holds one object):
    4 MiB of general heap, then 8 MiB.  When the fault stops moving, the writer's
    high-water mark is known, and *that number* names the field: e.g. if it stops
    after 4 MiB the block wants `0x400000 + page`; if it walks the whole heap it
    is a stride.
 2. **Print the four `*_REQ_BASE` registers (0xc90/0xcac/0xcb0) and
    `BIF_MEM_REQ_STAT` in the fault message** -- one driver line, no boot beyond
    the next.  A requestor base equal to the fault address's 1 MiB-aligned top
    names the block; a `MEM_REQ_STAT` read count climbing during the stall says
    the walk is live.
 3. Then the µkernel field is identified and the fix is one table entry.

5. NO 4 MiB LITERAL IN THE MICROKERNEL -- and the easy route was wrong

1. THE FAULT IS WHAT ENDS THE JOB — 0.07 s versus 2.05 s

So the page fault does not "replace" the stall on a slow path — it **terminates

the 2 s `job timed out` only appears once the fault is out of the way.  That is

fault has been MASKING the wall and cutting the window from 2 s to 0.07 s.  Any
future mid-hang measurement must clear the fault first, or it samples a window
twenty-eight times shorter than the one it thinks it has.

2. THE WRITE DEPOSITS NOTHING (with the instrument's own caveat stated)

The coverage range can now be read back: map_extra_range() records its CPU view,
and sgx_cover_map() hands it to the frame tool, which prints what is there after
the render.  With the range pre-filled (see the defect below), covering
0x400000+64 KiB -- the configuration where the writer SUCCEEDS -- reads:

    cover readback: 16384 dwords -- 16384 untouched, 0 zeroed, 0 foreign

i.e. every dword still holds 0xA5A5A5A5.  Per trap 430 that is NOT yet evidence
("a zero from an uncontrolled instrument is not evidence"), but it is
*directional*: the writer's access deposits no data even when it succeeds, which
is the shape of a page-table WALK (a read of PDE/PTE, or an invalidate) rather

on this stack, and none exists (session 83's four controls all read zero).

3. INSTRUMENT DEFECTS FOUND AND FIXED IN THE READBACK (each would have lied)
---------------------------------------------------------------------------
a. **The pre-fill must be flushed to DRAM before the GPU runs.**  My first
   readback pre-filled with 0xA5A5A5A5 and then read with __clear_cache.  On
   ARM glibc's __clear_cache is cacheflush(2), which CLEANS as well as
   invalidates -- so the read-time clean wrote the still-dirty pattern back over
   whatever the GPU had stored, and the first runs read "0/16384 nonzero"
   (= all zeros) when the pattern was actually intact.  Fixed by flushing the
   pattern in map_extra_range(), once, before any render; the later clean is then
   a no-op and its invalidate fetches the GPU's data.
b. **A zeroed range cannot distinguish "wrote zeros" from "never wrote".**  The
   range is now pre-filled with SGX_COVER_FILL (0xA5A5A5A5) and the readback
   counts untouched / zeroed / foreign separately, so those two are told apart.

4. RETRACTED: the 0x1000 "render done" (it was a firmware-down artefact)

tool never allocates, and the address BRN31620's dummy page would live at) changed

6. FIX_HW_BRN_31620 — CHECKED, AND IT IS NOT AN ADDRESSING BUG WE CAN SEE HERE
------------------------------------------------------------------------------
The erratum is in the SGX540 rev-120 block (`sgxerrata.h` line 965, "workaround
in services") and our driver implements none of it, so it was a real candidate:
its constants are a **4 MiB** page-table range (`BRN31620_PT_ADDRESS_RANGE_SHIFT
22`), a 64 MiB PDE cache-fill line, and a **dummy page at offset 0x1000 in EVERY
directory** (PDE 0, PTE 1; signature 0xFEEBEE01; `SGX_MMU_PTE_DUMMY_PAGE` and
`_PDE_DUMMY_PAGE` are both 0, i.e. "valid and read-only", not a magic bit).
That matches the fault's arithmetic exactly: 0x401000 is PDE 1 / PTE 1, and the
general heap's base 0x1000 -- which our tool never allocates -- is PDE 0 / PTE 1.

But the measurement refutes the addressing theory twice over:
  * mapping the general heap's first page (0x1000) does NOT move or clear the
    fault (part 4) -- if the walk needed that page valid in every directory, this
    is where it would show;
  * covering the faulting page makes the write SUCCEED with no data deposited
    (part 2), which is a walk, not a mis-addressed store.
So BRN31620 remains **unimplemented and unfalsified** rather than implicated:
record it as a candidate for the MMU writer's attention (facts file §6 already
says so), not as the cause.

  pointer and not a broken table.
* **The faulting address's structure is exact:** 0x401000 = general heap base
  (0x1000) + **4 MiB + 1 page**, and 4 MiB is *exactly one full page table*
  (1024 x 4 KiB).  So the writer lands one whole table's worth of address space
  past the heap base, then one page in.  Every candidate that could produce that
  is a *count* or *size* used where an address belongs.
* **`type 1` is the read/write bit, not a fault class:** both cores' entries set
  `bif_int_stat_fault_type = BIT(14)`, and the 540 header defines no separate
  fault-type field (`PF_N_RW` b14), so "type 1" = write.  Consistent with the
  message's own "write".

WHAT THE TOOL MAPS (for comparison)
-----------------------------------
The 256x256 frame's general-heap allocations, all in PDE 0:
     gen ring     0x00002000 +0x40000
     vdm ring     0x00042000 +0x5000
     colour BO    0x00047000 +0x40000
(nothing in PDE 1), plus the per-surface objects in kdata/tadata/3dparams.  The
colour buffer is at 0x47000, not 0x401000, so the fault is NOT the colour buffer
seen through a bad base -- it is 4 MiB further on.

WHERE THAT LEAVES THE SEARCH
----------------------------
The writer is a well-formed walk to heap_base + 4 MiB + page, in the TA's own
window (client PD loaded), sequential over 5 pages, invariant to the client.
Two shapes fit, and they are now separable:
  1. **an address computed from a 4 MiB-quantised base** (a page table's worth)
     plus a small offset -- i.e. something treating a PT *range shift* (22) as an
     address shift;
  2. **a size used as an address** where the size happens to be ~4 MiB.
Both are the trap-431/124 class (a value used with the wrong meaning) one level
down, in the addressing rather than in a register field.  The next instrument
that can split them is a µkernel-side trace of the walk (which register feeds
the BIF), or BIF_CTRL's MMU_BYPASS_* bits read mid-hang to see whether the
writing block goes through the MMU at all.

BENCH: fresh boot per configuration (devcoredump's node is consumed by the read
and this kernel has no `dismiss`; `disabled` is a one-way global kill switch --
do NOT write to it, reset it with a reboot).  Firmware kick18ccb, module
96368b07 (the SB build was reverted).  No flash, no media write.

2. THE "UNIQUE ARITHMETIC FIT" IS AN IDENTITY, NOT EVIDENCE (my own caution)
---------------------------------------------------------------------------
The tempting observation: 0x401000 = general_base (0x1000) + ((ta_data_base -
params_3d_base) >> 4), and that is the ONLY heap pair (of 90) that produces it:

    ta_data 0x0c800000 - params_3d 0x08800000 = 0x04000000 >>4 = 0x00400000
    0x00400000 + 0x1000 = 0x00401000          <- the fault, exactly

But the value that fits is the **TADATA HEAP BASE** (which happens to equal the
tail-pointer block's address, 0x0c800000), not any allocated object.  Checked
against the live allocations:

    tailptr   0x0c800000 - pb 0x08800000 >>4 = 0x00400000   MATCH (it IS the heap base)
    ta_data[1] 0x0c801000 - pb           >>4 = 0x00400100   no
    ta_data[0] 0x0c804000 - pb           >>4 = 0x00400400   no
    bg_block   0x0f026000 - pb           >>4 = 0x00682600   no

So the "fit" is the difference of two **fixed heap bases** -- an identity that
any fixed layout would satisfy -- not a value any pointer arithmetic produced.
It is a *hypothesis generator*, not a result, and must not be recorded as the
cause.  (This is the trap-403/§113 discipline applied to my own arithmetic: a
number that matches is not a mechanism.)

**The falsifiable test, if it is ever worth a boot:** the hypothesis predicts the
fault ADDRESS moves when the PB base moves, since (ta_data - pb_base) >> 4
changes with it:

    pb_base 0x08800000 -> predict 0x00401000   (today)
    pb_base 0x08900000 -> predict 0x003f1000
    pb_base 0x08c00000 -> predict 0x003c1000

pb_base is the PB allocation's address (3DPARAMS heap, first-fit from the base),
so moving it needs a deliberate driver/tool change -- not a free knob today.  If
the fault stays at 0x00401000 for a moved PB base, the identity is a coincidence
and this whole line closes.

    rd->bg_pds_word  = kobj_va(s->rd_w4[i])                        <- ABSOLUTE

2. A LATENT DEFECT: our ukernel DEREFERENCES `rd+0x114` AS A POINTER

words from `aui32SpecObject` when `SGX_FEATURE_RENDER_TARGET_ARRAYS` is clear --
which is our core's case (`sgxfeaturedefs.h` sets it only in another core's block;
grep in the SGX540 block returns 0):

    /* 3d.asm:3321-3342, the #else branch our core takes */
    MK_MEM_ACCESS_BPCACHE(ldad) r2, [R_RTData, #DOFFSET(SGXMKIF_HWRTDATA.sBGObjBaseDevAddr)];
    MK_MEM_ACCESS(ldad.f3)      r3, [r1, #DOFFSET(SGXMKIF_HWRENDERDETAILS.aui32SpecObject)-1];
    MK_MEM_ACCESS_BPCACHE(stad.f3) [r2, #0++], r3;      /* 3 floats, straight from the struct */

Our µkernel instead computes the third word through an address:

    r6 = *(rd+0x114)          /* bg_pds_word -- a DEVICE ADDRESS, 0x0f02e000 live */
    r7 = *(rd+0x108)          /* inside pad_108[2] -- the driver NEVER writes it, so 0 */

Live values confirm the field map is what we think (`rd+0x110` = `word8`

so today the dereference lands on `rd_w4`'s content and produces a sane PDS word --
**by accident, because `pad_108` is zero**.  Two consequences:

* it is not this fault (the value it yields is well-formed), so do not "fix" it as
  a suspect for the walk;
* it is nonetheless wrong on its own terms: it reads a field the driver never
  initialises (`0x108`) as an index, and it treats a device address as a pointer.
  Either write `0x108` deliberately or take the third word straight from the
  struct the way the vendor does.  Record as a code defect, one variable, for a
  session that is not mid-bisect.

SESSION 84, ELEVENTH PART — 0x400000 is a COMMON quantity in this layout, which is
why arithmetic fits are worthless here (closing the line properly)
================================================================================
Before spending a firmware build, checked how special 0x400000 actually is in this
address map — because if it is common, every "unique fit" is noise.

    heaps whose SIZE is 4 MiB:      sync (0x0d800000-0x0dc00000)
                                    kernel_code (0x0e400000-0x0e800000)
                                    kernel_data (0x0f000000-0x0f400000)
    base pairs differing by 4 MiB:  pds_pixel - sync
                                    pds_vertex - kernel_code
                                    usse_pixel - kernel_data
                                    (and ta_data - params_3d, kernel_data - pds_pixel, ...)

So 4 MiB is a **structural constant of the heap layout** on this core: three heaps
are exactly that size and several base pairs are exactly that far apart.  Any
`(a - b) >> 4` or `size << 12` expression over these heaps produces 0x400000 for
many choices, and the general heap's base (0x1000) then puts the fault at 0x401000.

**This is the durable reason to distrust arithmetic fits in this layout** —
stronger than the identity argument of the fifth part.  Nine sessions of this
fault have produced four numbers that "matched" something (0x401000, the 20 KiB,
the VDM ring's 0x5000, and `ta_data − params_3d`); three of them dissolved on
contact and the fourth is this.  The fault must be found by *watching the GPU*,
not by matching numbers.

measurement: `tailptr_bytes` is 0x100 / 0x400 / 0x1000 for 64² / 256² / 512², and

WHAT WAS BUILT (and is correct as far as it can be checked statically)
---------------------------------------------------------------------

    would say in ONE boot how far the TA path gets.

WHAT IT MEASURED — AND WHY THAT IS NOT A RESULT
-----------------------------------------------
Deployed three builds (`addr21c`, `addr618`, `stage1`/`stage2`/`stage3`/`stage5`)
and every one read **0** at words 0x3d/0x3e:

    addr21c  (trace TE_PSGREGION_BASE 0x21c)  -> 0x3d/0x3e = 0
    addr618  (trace TA_PB's 0x618)            -> 0x3d/0x3e = 0
    stage1/2/5 (milestone stamps)             -> 0x3e = 0

**And the positive control reads 0 too.**  `stage3` stamped 100 at the `kick`
entry -- an entry that demonstrably executes (it reads the CCB, the TA is kicked,
and the render faults).  Word 0x37 (`0x22222222`, the existing UK_TICKLOG marker)
proves ctlblk stores from this image land, so the image runs.  So the fault is in
**my** store path, and a zero from it is worth nothing.  Per trap 430: an
instrument whose positive control also reads 0 has not been validated.

Three hypotheses tried, each wrong or unproven:
  1. **"The store offset field is narrow, so `st.a.d r17, #62` cannot reach word
     0x3e."**  Rebased through `imae` in bytes (the UK_ENTRYLOG pattern). Still 0.
  2. **"`st.a.d base,#i` is 1-based (ISA.md:1484: base + 4*(i+1))."**  Switched to
     `#(W-1)`. Still 0 -- and this reading CONTRADICTS the working TICKLOG site,
     which writes `st.a.d r17, #0x37` and lands `0x22222222` at word 0x37 exactly.
     So either the ISA note's `(i+1)` applies to the `sa`-relative form only, or
     that note is about a different encoding.  **Unresolved, and it must be
     resolved before any ctlblk store instrument is trusted.**
  3. **"My stage clobbers live registers."**  Moved to r4 (reloaded by the entry
     paths).  Still 0.
